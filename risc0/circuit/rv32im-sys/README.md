# risc0-circuit-rv32im-sys

Generated kernels of the rv32im circuit: the C++ CPU kernels (`kernels/cxx`), CUDA/ROCm
(`kernels/cuda`), Intel (`kernels/intel`) and Metal (`kernels/metal` plus generated sources).
`build.rs` builds the ones the enabled feature needs (`cuda`, `rocm`, `intel`, `metal`; the CPU
kernels always).

## Metal kernels (`metal` feature, macOS/iOS)

Source: `docs/metal-port/PLAN.md` (section 4.2) and the item notes in `docs/metal-port/notes/`
(R1-R12, R16). Building needs the Metal toolchain (`xcrun metal`, `metallib`) and Python 3
(`RISC0_PYTHON`, else `python3`).

### What is hand-written, what is generated

| File | Kind | Made by | Checked in |
|---|---|---|---|
| `kernels/metal/{witgen.h, buffers.h, tables.h, preflight.h, cuda_compat.h, seq_exec.h, ef_fp.h, ef_fpext.h}`, `misc.metal` | hand-written MSL | - | yes |
| `kernels/metal/{defs,types,layout}.metal.inc` | translation of the zirgen `kernels/cuda/{defs.cu.inc, types.cuh.inc, layout.cu.inc}` | `kernels/cuda/cuda2metal.py incs` | **yes** (build fails if stale) |
| `$OUT_DIR/metal/accum_tu.metal` | `stepAccumA`: the `step_TopAccum` call graph of `steps.cu` | `kernels/cuda/accum_tu_gen.py --metal` | no |
| `$OUT_DIR/metal/witgen_tu.metal` | `par_stepExecW`, `fwd_stepExec`, `rev_stepExec`: the `step_Top` call graph + a hand port of `ffi.cu`'s externs | `kernels/cuda/witgen_tu_gen.py --metal` | no |
| `$OUT_DIR/metal/eval_check.metal` | baseline `eval_check` (from `eval_check.cuh`, `eval_check_0..3.cu`, `eval_check_kernel.cu`) | `kernels/cuda/cuda2metal.py eval` | no |
| `$OUT_DIR/metal/eval_check_ef.metal`, `ef_tables.rs` | evalfast `ef_eval_split` + `ef_combine`, and the host half of their poly_mix table (included by `src/lib.rs` as `metal_evalfast`) | `kernels/cuda/evalfast/regen.py --metal` (the evalfast chain up to `remat_lu.py`, then `to_metal.py`) | no |
| `$OUT_DIR/metal/rv32im_incs.metal` | `witgen.h` + the three `.inc` compiled alone, with the layout constants the host hard-codes `static_assert`ed | `build.rs` | no |

All of these compile into one `metal_kernels_rv32im.metallib` (`METAL_LIB`; entry points in
`METAL_KERNEL_NAMES`). The CUDA inputs (`steps.cu`, `ffi.cu`, the `eval_check*` files, the
evalfast inputs in `kernels/cxx` and `kernels/intel`) are the same files the CUDA build uses;
nothing Metal-specific is generated into `kernels/cuda`.

### When the generators run

`build.rs` (`build_metal_kernels`) runs every generator on each run of the build script, in the
order above, from the crate root. A generator rewrites its output only when the text changed
(a new mtime would rerun the build script on every cargo call). Total ~16 s of Python on an M5
Max (`regen.py --metal` ~9-11 s of it); the metallib compile is ~40 s cold (the TUs compile in
parallel; `accum_tu.metal` is the longest at ~27 s), and is cached by content in
`~/Library/Caches/risc0` (`metal_kernels_rv32im-<key>.metallib`), so an unchanged input set is
not compiled again even in a fresh target directory.

`RISC0_SKIP_BUILD_KERNELS` runs no generator and writes an empty metallib (and stub
`ef_tables.rs`).

### What is pinned

Every generator is a sequence of counted text rewrites; a count that differs from its pin fails
the build with a hint. A pin change means the CUDA input changed shape: regenerate with the
pins off, review the translation and compile it, re-run the bit-exactness tests of the affected
phase (`cargo test -p risc0-circuit-rv32im --features metal --lib`), then update the numbers.

| Generator | Pins | Review command (pins off) |
|---|---|---|
| `cuda2metal.py` (steps passes, used by accum/witgen) | `PINNED_STEPS` | `python3 kernels/cuda/cuda2metal.py steps -o <dir> --compile --no-pin` |
| `cuda2metal.py eval` | `PINNED_EVAL` | `python3 kernels/cuda/cuda2metal.py eval -o <dir> --compile --no-pin` |
| `accum_tu_gen.py --metal` | `PINNED_METAL` (per `--inline` mode); the accum graph may call no extern but `assert`/`log` | `python3 kernels/cuda/accum_tu_gen.py --metal -o <dir> --no-pin` |
| `witgen_tu_gen.py --metal` | `PINNED_METAL`, and the sha256 of `ffi.cu`'s extern section (`divide_rv32im .. nextStep`, hand-ported into `METAL_EXTERNS`) | `python3 kernels/cuda/witgen_tu_gen.py --metal -o <dir> --no-pin` |
| `evalfast/regen.py --metal` / `to_metal.py` | `TO_METAL_EXPECT` (regen.py) and `COUNTS` (to_metal.py), plus every evalfast pass's `EXPECT` line | `python3 kernels/cuda/evalfast/regen.py --metal <dir>` |

### Regenerating

- **The checked-in `.metal.inc` files** after a circuit regeneration (zirgen changed
  `defs.cu.inc`/`types.cuh.inc`/`layout.cu.inc`):
  `python3 kernels/cuda/cuda2metal.py incs -o kernels/metal`, then commit them. The build's
  `rv32im_incs.metal` asserts the register counts (103/1/211/90/36) and `kUserAccumSplit` (23);
  if those change, the Metal HAL buffer sizes must change too.
- **Everything else** is regenerated by the build. To look at an output, run its generator into
  any directory (commands in the pin table without `--no-pin`), or read it from
  `target/<profile>/build/risc0-circuit-rv32im-sys-*/out/metal/`.
- After changing `ffi.cu`'s extern section, re-port `METAL_EXTERNS` in `witgen_tu_gen.py` and
  update its hash.

### Checks

| Command | What it checks | Needs |
|---|---|---|
| `python3 kernels/cuda/cuda2metal.py check` | `.metal.inc` up to date; steps and eval translate with their pins | Python |
| `python3 kernels/cuda/accum_tu_gen.py --check` | `accum_tu.cu`/`steps.cu` up to date, and the `--metal` translation (both inline modes) matches `PINNED_METAL` | Python |
| `python3 kernels/cuda/evalfast/regen.py --check` | CUDA/ROCm evalfast up to date, and `to_metal.py`'s pin | Python (~20 s) |
| `python3 kernels/cuda/witgen_tu_gen.py --check` | `witgen_tu.cu` only (its Metal pins are checked by `--metal`) | Python |
| `<generator> ... -o $OUT_DIR/metal --check` (any `--metal`/`eval` command) | a build's generated file equals what the generator produces now | Python |
| `python3 kernels/cuda/cuda2metal.py --selftest` | every translator pass on snippets of the real sources, compiled with `xcrun metal`; pins and their sensitivity; refusals (~30-40 s) | Python, Metal toolchain |
| `cargo test -p risc0-circuit-rv32im-sys --features metal` | all of the above (`tests/metal_generators.rs`; the build's own commands are listed in `$OUT_DIR/metal_generators.txt`), plus `r1_layout` | Python, Metal toolchain |

### Build knobs (environment, read by `build.rs`)

| Variable | Effect |
|---|---|
| `RISC0_METAL_BUILD_TIMINGS=1` | cargo warnings with the seconds of each generator and each TU's `metal` compile (TUs compile concurrently; a kernel-cache hit is reported as such) |
| `RISC0_METAL_ACCUM_INLINE=always\|noinline` | how `accum_tu.metal`'s call graph is compiled (default `always`) |
| `RISC0_METAL_EF_WIDE=0` | evalfast with 32-bit lo/hi accumulators (`-DEF_NO_WIDE`; default 64-bit) |
| `RISC0_METAL_DEBUG_SOURCES=1` | `-frecord-sources -gline-tables-only` (GPU debugging/profiling; build_kernel) |
| `RISC0_SKIP_BUILD_KERNELS` | no generators, empty metallib |
| `RISC0_PYTHON` | the Python interpreter for the generators |

Runtime knobs (`RISC0_METAL_RV32IM_*`) are documented in
`risc0/circuit/rv32im/src/prove/hal/metal/`.
