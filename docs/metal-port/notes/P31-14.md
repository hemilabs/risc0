## Summary

- **Every receipt the 3.1 Metal prover makes verifies with the unmodified crates.io
  `risc0-zkvm 3.1.0` verifier: 28/28** (fix round 1 matrix). That covers composite, succinct and
  Groth16 for 4 cases (fibonacci, multi-segment memory-merkle, a composition through resolve, a keccak
  assumption) at the default budget, and memory-merkle, keccak and fibonacci-after-the-worker's-PSO-
  warmup at the 8 GiB and 4 GiB budgets.
- **Not every receipt type can be made at the 4 GiB budget on 3.1 (fix round 1, open issue 1).** After
  a keccak proof, or after the zk-miner worker's start-up pipeline warmup, the 3.1 Groth16 key load is
  refused by the 4 GiB working-set budget. Composite and succinct receipts are made and verify; the
  Groth16 receipt is not made. 3.0 wraps the same runs. Cause: the v0.2.0 Groth16 prover reserves
  4039 MiB (3.0: 3928 MiB), leaving 57 MiB for the process-wide Metal pipeline objects, which are
  46 MiB normally and 62 MiB once the keccak PSOs exist. Routed to P31-12 (Groth16 key footprint) and
  P31-19 (worker 4 GiB tier). The matrix carries both runs as KNOWN-FAIL.
- **Every 3.0 receipt is rejected: 30/30 as made, and 30/30 again after relabelling.** Relabelling
  rewrites every version label to the 3.1 value, so the cryptographic checks have to reject the receipt
  on their own.
- The tree's constants equal the stock 3.1 ones:
  - control root `e6feef13...`;
  - BN254 identity `de81d091...`;
  - Groth16 selector `e71e6620`;
  - rv32im seal v3, `RV32IM:v2rev3___`.
  
  A new test asserts all of them.
- **identity_p254: Metal seal == CPU seal** under the seeded-noise hook (po2 18, 129813 rows), in two
  runs (default budget and 4 GiB). The other 10 recursion proofs of the two e2e tests also match.
- The listed zkvm tests pass twice: both recursion e2e tests, `tests_metal_wrap` (8 and 4 GiB), k5, k10
  and `keccak_standalone_repeat`.
- **Cost of 3.1 in the wrap** (interleaved A/B against the frozen 3.0 tree):
  - warm identity_p254: **+163 ms (+22.7 %)**;
  - C13 ctrl commit: **+38 ms (+24 %)**;

## 1. The stock verifier: `tools/stock_verify31/`

- **Isolation.** It is a standalone crate with its own `[workspace]`. It is not a member of the risc0
  workspace, and has no path dependency and no `[patch]`.
- **Dependencies.** `risc0-zkvm = "=3.1.0"` (default features off, `std` only: no prover, no GPU code,
  no `risc0-sys`), plus `risc0-circuit-recursion =4.1.0` and `risc0-circuit-rv32im =4.1.0` for the
  constants, bincode 1.3 and hex.
- **Build check.** `build.rs` fails the build unless every `risc0-*` / `bonsai-*` package in
  `Cargo.lock` has `source = "registry+https://github.com/rust-lang/crates.io-index"`, `risc0-zkvm` is
  3.1.0, and the manifest has no path or git dependency, `[patch` or `[replace` (whitespace ignored, so
  `{path="..."}` is caught too). The committed `Cargo.lock` lists 10 risc0 packages, all from the
  registry. `run_matrix.sh` also greps the lock and builds with `--locked`.
- **Fix round 1 hardening** (review findings):
  - A missing `Cargo.lock` is now a hard error, not a warning. In practice cargo writes the lock
    before it runs build scripts, so a regenerated lock is checked too (shown with a fresh target dir:
    `STOCK_VERIFY31_RISC0_PACKAGES=10`).
  - `build.rs` also reads every cargo config file cargo may use for this build (`.cargo/config{,.toml}`
    in the crate dir and each ancestor, and in `CARGO_HOME`) and fails on a `paths = [...]` override
    or a `[patch` there. A `paths` override swaps in local sources while `Cargo.lock` still shows the
    registry, so the lock check alone could not see it.
  - Negative tests on a scratch copy (`r1/guard/`): a `.cargo/config.toml` with `paths = [<a local
    hex>]` fails with "overrides package sources"; `hex = {path="..."}` fails with "must not patch,
    replace, path- or git-depend"; the unmodified copy builds with `--locked`.
- **CLI.**
  - `verify <receipt> <image id> [--expect-journal <hex> | --expect-journal-file <path>]
    [--relabel-as-31]` runs the stock `Receipt::verify(image_id)` with the default 3.1 context. It
    first prints the kind, the seal-version word of each segment, the control ids and the parameter
    digests (Groth16 selector included).
  - `consts` prints the constants.
- **Encoding.** bincode 1.3 of `risc0_zkvm::Receipt`, the 3.1 crate's own receipt encoding (its `api`
  client/server and `Asset::Inline`).

## 2. Producing receipts: `tools/stock_verify31/produce/` and `run_matrix.sh`

### `p31-14-produce`

- **How it proves.** It is a standalone crate whose path dependencies point at the tree it lives in. It
  proves with `get_prover_server` (`--features metal`), so it uses the local Metal prover and not r0vm.
- **The chain.** It runs the e2e chain on each case:
  1. composite: `prove`;
  2. succinct: `compress`, i.e. lift / join, plus resolve for `compose`;
  3. Groth16: `compress`, i.e. identity_p254 + shrink_wrap.
- **Checks before writing.** Each receipt is verified with the tree's own verifier before it is
  written, and the producer checks that the Groth16 receipt's claim and journal equal the composite
  receipt's.
- **Segment po2.** The worker's tier for `RISC0_METAL_MAX_WORKING_SET_BYTES` (< 6 GiB 18, < 12 GiB 19),
  else 20.
- **Diagnostics (fix round 1).** It prints `[P31-14] resident after <stage>` (the device's
  allocation when a stage ends), and before the Groth16 stage it calls `release_hal_buffers` (the wrap
  does so itself) and prints the resident allocation and the headroom the key load will see.
  `P14_TRACE_ALLOC=1` prints every change of the allocation by >= 1 MiB; `P14_DIAG_IDENTITY=1` runs
  identity_p254 alone first and reports what it leaves; `P14_PREBUILD=keccak|groth16|rv32im|recursion|
  worker` builds those process-wide PSO sets at start-up (`worker`: all four on parallel threads, as
  zk-miner's `warm_up_pipelines` does).
- **Cases.**
  - `fibonacci` / `merkle`: zk-miner's benchmark guests (ProgramBinary `.bin` from
    `zk-miner/target/release-metal/riscv-guest`, copied to `scratch/w8/P31-14/guests/`), with the
    worker's `--benchmark` inputs (1000, 512).
  - `compose`: multi_test SysVerify of two proven Echo receipts.
  - `keccak`: multi_test `KeccakUnion(1)`.

### The 3.0 receipts

### `run_matrix.sh`

It does the whole thing: build, produce (each prove under `gpu-run`), and print the matrix (exit 1 on
any unexpected result). Under each budget in `BUDGETS` (8 and 4 GiB), with both producers, it proves
memory-merkle, keccak, and fibonacci after the worker's PSO warmup (`P14_PREBUILD=worker`, receipts in
`r<ver>_b<budget>_wpso`). The round-0 script proved only memory-merkle under the budgets, which is
how the keccak regression got past it.

`KNOWN_FAIL` (default `r31_b4294967296/keccak r31_b4294967296_wpso/fibonacci`) holds the runs whose
Groth16 wrap is known to be refused (open issue 1). For those the producer must fail with "Metal
working-set budget exceeded" after it has written the composite and succinct receipts, which must
still verify; the matrix prints `KNOWN-FAIL` for the missing Groth16 receipt. If a known failure starts
passing, the script reports an unexpected pass and exits 1, so the list is updated when the owner's
fix lands. Any other failed producer run or missing receipt also fails the script. `CASES`,
`VERSIONS` and `BUDGETS` split a long run; the matrix judges every receipt in `OUT`.

Round 0: receipts made twice (by hand, `receipts_run1/`; by the script, `receipts/`), same matrix.
Fix round 1: `r1/matrix/` (`run1.log` 3.1 unbudgeted, `run2.log` 3.1 budgets, `run3.log` 3.0 all),
each exit 0; `r1/matrix/logs/matrix.txt` is the full matrix.

## 6. identity_p254 on 3.1

### Seal equality (P31-11's open gate)

`RISC0_METAL_REC_SEAL_CHECK=1` re-proves every recursion proof on the CPU under the same
`with_noise_seed` seed and requires bit-identical outputs and seals. In both e2e tests, proof #6 is
identity_p254 (`po2 18 (129813 rows) seal == CPU seal (55667 words); metal 1.07s, cpu 14.94s`) and
matches. So do the 4 lifts, 2 joins and 2 resolves. Twice:
- default 16 GiB budget;
- `gpu-run --huge --budget 4294967296`.

Together with P31-15's `c11_captures_seal_match_cpu` on the 3.1 `0005_poseidon_254` capture, the Metal
x^7 p254 path is bit-exact with the stock 3.1 CPU prover. Both paths are the same by design (no
documented difference).

### Timing

**Method.**
- Interleaved A/B, separate processes, A first.
- A = `p31-14-produce wrap-timing` built from the frozen 3.0 tree (v0.1.0 key). B = the same built from
  this tree (v0.2.0 key). Identical source and build profile.
- Each process: one fibonacci succinct receipt, then 5 Groth16 wraps of it. The first wrap has no
  prewarm, so its ctrl group is "Committed". Wraps 2-5 are warm ("Restored").
- `RISC0_VERBOSE=1` for the `[recursion_prove]` / `[finalize]` phase lines.
- Default budget: 8 pairs. 8 GiB and 4 GiB: 7 pairs each.
- The 4 GiB runs use `P14_RELEASE_BETWEEN=1`. Without it a second wrap in the process does not fit 4 GiB
  in either tree (open issue 1).
- Load average 1.85-4.44 over all runs.

### Fix round 1: why the 4 GiB wrap is refused after keccak

The review reproduced it: 3.1 keccak at 4 GiB fails at the Groth16 key load with `allocating 4235118872
bytes for the Groth16 prover ... with 64946176 bytes already allocated would exceed the limit of
4294967296 bytes`; the 3.0 producer wraps the same case. Reproduced here (`r1/repro_keccak4g.log`),
then narrowed down with the producer's diagnostics (all under `gpu-run --budget`, one process each):

| run (3.1 unless noted) | resident before the wrap, this thread's provers released | allocated at the key-load check | 4 GiB result |
|---|---|---|---|
| fibonacci | 45.9 MiB | 45.9 MiB (48168960 B) | wraps (peak 4054 MiB) |
| keccak | 45.9 MiB | **61.9 MiB** (64946176 B) | **refused** |
| keccak, identity_p254 run alone first (`P14_DIAG_IDENTITY=1`) | 45.9; after identity_p254 + release 45.9 | 61.9 MiB | refused |
| fibonacci, keccak PSOs built at start (`P14_PREBUILD=keccak`) | 58.9 MiB | 58.9 MiB (61784064 B) | refused |
| keccak, Groth16 PSOs built at start (`P14_PREBUILD=groth16`) | 49.3 MiB | 49.3 MiB (51675136 B) | would fit (7.8 MiB spare) |
| fibonacci, Groth16 PSOs built at start | 49.3 MiB | 49.3 MiB | would fit |
| fibonacci, worker warmup (`P14_PREBUILD=worker`) | 61.9 MiB | 61.9 MiB (64946176 B) | **refused** |
| keccak, worker warmup | 61.9 MiB | 61.9 MiB | **refused** |
| 3.0 fibonacci / keccak, worker warmup (v0.1.0 key) | 61.9 MiB | 61.9 MiB | wraps (peak 3958 MiB) |

(The key-load figures for the "would fit" rows were read with the budget set to the key size + 1 byte,
which makes the check print what is allocated; logs `r1/e_E{1,2,3}.log`, `diag*_*.log`, `w_*4g.log`,
`w30_*4g.log`.)

- **Nothing the release can free is left over.** After `release_hal_buffers` the keccak case has the
  same 45.9 MiB resident as fibonacci, and identity_p254 leaves nothing either. The reviewer's
  hypothesis (a keccak prover or pool cached on another thread) does not hold: the keccak prover is
  dropped after its proofs (`[keccak-mem] keccak prover dropped`), the lift's recursion prover is on
  the calling thread and is released.
- **The extra 16 MiB is process-wide pipeline state.** The allocation trace (`P14_TRACE_ALLOC=1`) shows
  +16.0 MiB exactly when the keccak prover is first built (its PSOs, `keccak_kernels`, a process-wide
  `OnceLock`) and, in a keccak process, +16.0 MiB again when the Groth16 PSOs are built at the wrap,
  which a fibonacci process absorbs without growing. This looks like the device counting
  pipeline code in `currentAllocatedSize` in 16 MiB steps, so which PSO set opens a new step depends
  on the order they were built (an inference from the trace; the Metal API does not list them). These are never freed and are not meant to be (rebuilding the keccak PSOs costs
  40-190 s cold).
- **The 3.1 key leaves too little room for them.** The Groth16 prover checks its whole allocation up
  front: 4235118872 B = 4038.9 MiB on 3.1 (v0.2.0), 4118758328 B = 3928.0 MiB on 3.0 (read the same way,
  `r1/key30.log`). At 4 GiB that leaves 57.1 MiB on 3.1 and 168 MiB on 3.0 for everything else. The
  process-wide PSOs are 45.9 MiB without keccak and 58.9-61.9 MiB with it, so 3.1 has 11 MiB of room in
  the best case and none once keccak's PSOs exist.
- **This hits the zk-miner worker at the 4 GiB tier on every job, not only keccak jobs.** The frozen
  worker's `warm_up_pipelines` (`zkminer-prove-risc0/src/metal_host.rs`) builds the rv32im, recursion,
  keccak and Groth16 PSOs at start-up. Simulated with `P14_PREBUILD=worker`: 61.9 MiB resident, and a
  plain fibonacci wrap is refused at 4 GiB on 3.1 (3.0 wraps it).

**Why it is not fixed here.** The fix is in code P31-14 does not own: the Groth16 prover's 4 GiB
footprint (`groth16-sys/src/metal`, P31-12) or the worker's start-up warmup (zk-miner, P31-19). Options
for the owners, none tried here:
- The up-front check reserves more than the prover holds at once: fibonacci's wrap peaks at 4054 MiB
  with 45.9 MiB already allocated, so at most ~4008 MiB is live against 4039 MiB reserved. A check on
  the real peak (or an allocation order that frees scratch before the next buffer) would give ~31 MiB
  back, enough for 61.9 MiB.
- A smaller 4 GiB-tier layout of the v0.2.0 key (P31-12 accepted +96 MiB at 4 GiB measured without the
  keccak PSOs).
- The worker could build the Groth16 PSOs before the keccak ones at a small budget (the
  `P14_PREBUILD=groth16` rows fit), but that leaves 7.8 MiB, which is too thin to rely on.
