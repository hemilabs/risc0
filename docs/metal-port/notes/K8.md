## Binary-archive cache key coverage (finding 12)
Key = first 24 hex of `sha256(metallib bytes ‖ 0 ‖ device.name() ‖ 0 ‖ OS build ‖ 0 ‖ kernel names…)`
(`archive_key`, `archive_base`); file `<unit>-<key>-<sha256(content)[..16]>.binarchive`.
- **Changed metallib** (any kernel/translator/stage-count change, a new risc0 version): the bytes are in
  the key → new key, old file removed by the stale cleanup on the next save. Covered by
  `archive_key_inputs` (`lib` vs `lib2`).
- **Different device**: `device.name()` ("Apple M5 Max", "Apple M4", …) → covered by `archive_key_inputs`.
  Core-count variants of one chip (e.g. a 32- vs 40-core M5 Max) share the name; this is no issue:
  Metal binaries are per GPU architecture, not per core count, the cache lives in the per-machine
  `~/Library/Caches`, and an incompatible entry would only fail the `FailOnBinaryArchiveMiss` load and be
  recompiled (K5 fallback), never be used silently.
- **OS build**: `ProductBuildVersion` from `SystemVersion.plist`, else `sysctl kern.osversion`
  (`archive_key_inputs`: `25A1` vs `25A2`). A security response update changes the build string (suffix
  letter), so it is covered too. The `"unknown"` fallback was finding 11 (fixed: no archive then).
- **Kernel name set**: names in the key, 0-separated so `["a","b"]` ≠ `["ab"]` (`archive_key_inputs`).
- **Corrupt archive**: finding 1 (content checksum in the file name), `damaged_archive_falls_back`,
  `archive_bitflip_sweep`, `corrupt_archive_falls_back`.
- Not covered: a GPU driver/compiler change without an OS build change (not possible on macOS: the
  Metal compiler ships with the OS); a file Metal itself serializes wrongly (never observed).

## What was fixed and why
1. **Archive integrity (finding 1).** `archive.rs`: the archive file is now
   `<unit>-<key>-<sha256(content)[..16]>.binarchive`. `save_archive` serializes to a temp file, hashes it
   and renames it to that name (atomic, so name and content always agree for a complete write).
   `verified_archive_file` reads each candidate of the key, and only a file whose content matches its
   name is handed to Metal; any other is deleted and reported ("content does not match its checksum"),
   and the PSOs are rebuilt into a fresh archive. Old-format archives (`<unit>-<key>.binarchive`, K5) are
   deleted by the existing stale cleanup on the first save, so one rebuild after the upgrade (~25 s cold
   on an M5 Max, less with the OS shader cache warm). The module doc explains the Metal behaviour.
   Why not catch the exception: it is a C++ exception thrown inside Metal; Rust cannot unwind through it
   and the crate has no Objective-C++ shim. The checksum keeps every damaged file away from Metal.
   Residual: a file Metal itself serialized wrongly (not observed). A file replaced between our read and
   Metal's open by another process's save was observed in the round-2 verification and is handled since
   fix round 2 (finding 15, item 4 below).
2. **Test isolation (finding 2).** `hal/metal/mod.rs`: `tests` is `pub(crate)`; `prove/tests.rs`
   `basic`/`host_witness`/`fwd_rev_ab` take `gpu_test_lock()` under `metal` (a `None` stub otherwise);
   the archive tests take it too; `eval_check_shrinks_chunk_under_budget` asserts chunk 4096
   unconditionally (K5's suggestion).
3. **rerun-if-changed (finding 3).** `keccak-sys/build.rs` `build_metal_kernels`: also
   `rerun-if-changed=<abs>/kernels/cuda` (cargo scans a directory recursively). The CPU and the
   content-hashed Metal builds are unaffected when nothing changed; touching a CUDA file re-runs the
   script as touching `eval_check.cuh` already did.
4. **Concurrent archive replacement (finding 15, fix round 2).** `archive.rs`: `open_archive` is
   `open_archive_with(.., before_load)` (a test seam called between verifying a file and Metal opening
   it; production passes a no-op). If Metal fails and the verified path no longer exists, another
   process replaced it: nothing is reported or deleted, the directory is verified once more and the
   newer file loaded (a second loss falls back to an empty archive: a rebuild, never a wrong PSO). A
   load failure on a file that still exists is handled as before (reported, deleted). `save_archive`
   takes the time the process looked for an archive (`opened`); a file of the same key (same
   `<unit>-<key>-` stem with a checksum) modified at or after it is another process's concurrent save
   and is kept, so concurrent cold starts no longer delete each other's results;
   `verified_archive_file` keeps one of them on the next start. Files of other keys are still deleted
   (finding 4, K7).
