## What was fixed and why
1. **Archive integrity (finding 1).** `archive.rs`: the archive file is now
   `<unit>-<key>-<sha256(content)[..16]>.binarchive`. `save_archive` serializes to a temp file, hashes it
   and renames it to that name (atomic, so name and content always agree for a complete write).
   `verified_archive_file` reads each candidate of the key, and only a file whose content matches its
   name is handed to Metal; any other is deleted and reported ("content does not match its checksum"),
   and the PSOs are rebuilt into a fresh archive. Old-format archives (`<unit>-<key>.binarchive`, K5) are
   deleted by the existing stale cleanup on the first save, so one rebuild after the upgrade (~25 s cold
   on an M5 Max, less with the OS shader cache warm). The module doc explains the Metal behaviour.
   Why not catch the exception: it is a C++ exception thrown inside Metal; Rust cannot unwind through it
   and the crate has no Objective-C++ shim. The checksum keeps every damaged file away from Metal.
   Residual: a file Metal itself serialized wrongly, or one replaced between our read and Metal's open by
   another process's (verified) write — both not observed.
2. **Test isolation (finding 2).** `hal/metal/mod.rs`: `tests` is `pub(crate)`; `prove/tests.rs`
   `basic`/`host_witness`/`fwd_rev_ab` take `gpu_test_lock()` under `metal` (a `None` stub otherwise);
   the archive tests take it too; `eval_check_shrinks_chunk_under_budget` asserts chunk 4096
   unconditionally (K5's suggestion).
3. **rerun-if-changed (finding 3).** `keccak-sys/build.rs` `build_metal_kernels`: also
   `rerun-if-changed=<abs>/kernels/cuda` (cargo scans a directory recursively). The CPU and the
   content-hashed Metal builds are unaffected when nothing changed; touching a CUDA file re-runs the
   script as touching `eval_check.cuh` already did.

## Issues for later items
- **R17 (rv32im GPU witgen)**: the keccak generated witgen — per-arm kernels, every step function
  `static __attribute__((noinline))`, by-value buffer structs instead of virtual buffer objects, faults
  accumulated in a thread-local word — was bit-exact in 600/600 repeated calls at po2 16-18. If the
  rv32im nondeterminism turns out to be miscompilation of a large inlined kernel, K6's noinline/split
  strategy (`R0_KECCAK_WITGEN_FN`) is a tested pattern to try. The Metal crash on damaged archives
  (`archive_bitflip_probe`, `scratchpad/w4/K8/objc/probe.m`) is a second candidate for an Apple
  Feedback report.
- **C11 / Z9 / whoever hoists `archive.rs` into the zkp HAL (K5's suggestion)**: keep the content
  checksum in the file name (finding 1); without it any unit's archive can crash every process start.
- **K7**: finding 5 (hash cost ~0.12 s per process for 52 MB; a faster hash or hashing in the
  background is possible), finding 4 (LRU/age-based cleanup instead of deleting other keys).
- **zkvm owner (Z8/M4)**: `prover_impl.rs::start_metal_warmup` should also spawn
  `risc0_circuit_keccak::prove::metal_warmup` (takes no GPU lock) so non-worker hosts do not pay the
  keccak PSO build inside the first keccak proof.
- **M5**: the first start after this change rebuilds the keccak archive once (old file name format is
  deleted); include it in the cold-start baseline.
