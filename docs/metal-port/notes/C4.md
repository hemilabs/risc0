## Known gaps

- No functional kernel run in C4 beyond C1's tests (step/eval correctness: C6-C9).
- Every `--features metal` macOS build needs python3 (or `RISC0_PYTHON`) and the Metal toolchain.
  The step_exec AIR compile (~5 s) and eval_check (~6 s) run in parallel in KernelBuild.
- The smoke test's name check shells out to python3; on a machine without it, it fails (as the
  build would).

## Issues addressed to later items

- **C5 (`metal_warmup`) / M1 / K5**: creating all recursion PSOs cold costs 47-75 s here, 60 s of
  it the eval_check monolith; with only the split it would be ~8.5 s + 6.7 s for steps. Warm on a
  background thread at start, and warm only the eval variant actually selected. The cache appeared
  to miss after the executable was relinked: an `MTLBinaryArchive` (C11) would make this
  independent of the OS cache.
- **C8/C11**: both eval variants are in `METAL_LIB`; `RISC0_METAL_REC_KERNELS` only needs to pick
  the name(s). Measured cold PSO strongly favours the split (8.5 s vs 60 s).
- **C9**: run `cuda2metal_steps.py --check` and `cuda2metal_eval.py --check --split` in CI; the
  build only enforces pins/residuals, not the round trip.
- **C5**: `load_library(METAL_LIB, METAL_KERNEL_NAMES)` builds every PSO up front (F0 API); that
  would pay both eval variants (~70 s cold). Load with a name subset (e.g. exclude the unselected
  eval variant), or create eval PSOs lazily.
