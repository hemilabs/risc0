### Why the four `evalfast_matches_cpu_*` tests take ~8.8 GB at any po2
`currentAllocatedSize` peaks at only 31 MB in these tests. The footprint comes from the driver when a
deep-stack eval pipeline is first dispatched, and `currentAllocatedSize` does not count it.
`tests::eval_check_matches_cpu_po2_4` was run with each kernel selected by `RISC0_METAL_RV32IM_EVAL` (FC off):

| eval kernel dispatched | footprint, po2 4 | po2 16 | native stack (R21/R22) |
|---|---|---|---|
| `evalfast` (hoisted `ef_eval_split`, default) | 0.59 GB | 1.60 GB | 3,984 B |
| `ef_eval_split_nohoist` (`HOIST=0`) | 0.59 GB | | 4,000 B |
| `ef_eval_split_nest` (`FLAT=0`) | 2.08 GB | | 18,928 B |
| `evalfast_r15e` | 3.79 GB | 4.80 GB | ~36 KB |
| `evalfast_r12` | 4.23 GB | | |
| `baseline` (zirgen `eval_check`) | **8.71 GB** | **9.71 GB** | (not read) |

The extra memory does not grow with po2. It does grow with the kernel's stack depth. `evalfast_matches_on`
dispatches all of these kernels, the baseline among them, and pays the largest (~8.1 GB) once per process,
not their sum. Production dispatches only the 4 KB-stack kernels. This also favours `_nohoist` over `_nest` as
the guard's fallback (section 5): it does not add the +1.5 GB.

## 3. The 18 GiB mechanism, with numbers

Everything below is `prove_po2_sweep`, simple_loop, `R11_CPU=0`, 2 reps, run alone under the heavy lock.
`R11_KEEP_PROVER=1` reproduces the old behaviour: one Metal prover, and therefore one HAL and one pool, for the
whole sweep. The two numbers after each po2 are the device `currentAllocatedSize` (MiB) and the process
footprint (GiB), taken after that po2's proofs.

| po2 | old, no budget | old, 16 GiB budget (gpu-run default) | new (fresh prover per po2), 16 GiB budget |
|---|---|---|---|
| 14 | 183 / 0.91 | 183 / 0.91 | 183 / 0.88 (after the drop: 30 / 0.78) |
| 15 | 466 / 1.19 | 466 / 1.19 | 322 / 1.04 |
| 16 | 956 / 1.67 | 956 / 1.66 | 613 / 1.33 |
| 17 | 1936 / 2.62 | 1936 / 2.62 | 1192 / 1.90 |
| 18 | 3890 / 4.54 | 3890 / 4.54 | 2350 / 3.04 |
| 19 | 7799 / 8.38 | 7799 / 8.38 | 4667 / 5.32 |
| 20 | **12240 / 16.08**; Metal peak 15616 MiB | 8568 / 16.07 | 5923 / 9.90 (after the drop: 30 / 9.45) |
| process peak footprint | **16.41 GiB (17.62 GB)** | **19.37 GiB (20.80 GB)** | **10.20 GiB (10.96 GB)** |
| peak wired (system) | 15.79 GiB | 16.01 GiB | 11.82 GiB |

po2 21 alone, with a fresh prover and no budget (`R11_ALLOW_21=1`, 1 rep): the Metal peak is **18563 MiB**. The
footprint peaks at **18.64 GiB (18.98 GB)** and wired at 19.47 GiB. After the drop the footprint is still
6.74 GiB, and 3 s later it is 0.35 GiB.

The mechanism:
1. **One pool per HAL keeps every size.** The old sweep keeps one prover, so the pool holds the buffers of
   every earlier po2. They are pooled by exact size and never reused at the next po2. The held allocation
   grows 183 -> 466 -> ... -> 7799 MiB, about the sum of the per-po2 sizes. At po2 20 the device holds
   12.2 GiB, and the Metal peak is 15.6 GiB against the 9.3 GiB a po2 20 segment needs. With no budget,
   `pool_cap = limit / 2` = 14 GiB.
2. **Budget drains do not lower the footprint right away.** At the 16 GiB budget the drain holds
   `currentAllocatedSize` to 8.6 GiB, yet the footprint peak is higher (19.37 GiB) than with no budget. The
   pages of freed MTLBuffers stay charged to the process for a short while after the free. Measured with
   `R11_SETTLE_MS=3000`: after a po2 20 prover is dropped, the footprint is still 9.42 GiB at once and
   0.25 GiB 3 s later. New allocations made before that release add on top. This matters for W7-A1, which
   fixes the pool: a drain right before a big allocation does not immediately reduce wired memory.
3. **po2 21 is 18.6 GiB on its own.** Run after the old sweep's po2 20 pool (12.2 GiB held with no budget),
   one process would need more than 30 GiB on a 36 GB Mac. I did not run that combination because it would
   likely panic the machine again. The ~18.4 GiB processes in both panics match a po2 21 proof (18.6 GiB) or
   the po2 20 stage of the old sweep (16.4-19.4 GiB, depending on the budget). Three or four of them at once
   (panic logs) exhaust the 36 GB.
4. **The CPU prover's freed memory stays in the footprint (macOS malloc large cache).** With the CPU prover at
   po2 < 20 (`R11_PO2S=14..20`, fresh provers), the footprint after a dropped po2 19 CPU prover is 5.48 GiB, and
   the po2 20 Metal proof then peaks at 15.38 GiB instead of ~10. `vmmap -summary` after a po2 18 CPU proof
   shows `Malloc Large (empty)` at 2.2 GB dirty, with a 2.3 GB footprint. `malloc_zone_pressure_relief(NULL, 0)`
   released 0 bytes. `MallocLargeCache=0`, which libmalloc reads at process start, brings it to 89 MB. The tests
   that run the CPU prover now re-run themselves in a child process with it set (section 4). With that, the same
   14..20 sweep with CPU peaks at **10.08 GiB**, which is po2 20's own peak. The CPU footprint after each drop is
   0.09 GiB.
5. **The CPU prover beside a Metal pool** (`seal_matches_cpu_large`): the old code, 2 merkle segments in one
   process, peaked at **19.88 GB**. That matches R23's 19.9-21 GB. The new code peaks at 9.79 GiB (10.5 GB), the
   same for each 2-segment pair below.

## 4. The new defaults, and how to run each heavy test

The `<bin>` below is the release `--features metal` lib test binary, run from `risc0/circuit/rv32im`.
- **The gpu-run check.** Every heavy `#[ignore]` test in this item's files calls
  `tests::require_gpu_run` (or `require_gpu_run_class`) first: `prove_po2_sweep`, `seal_matches_cpu_large`,
  `pipeline_bench`, `archive_cold_start` and `witgen::tests::r15w_witgen_ab`. The check accepts the exclusive
  lock in both forms `bin/gpu-run` exports, `GPU_RUN_MODE=heavy` (default) and `huge` (`--huge`: exclusive, with
  a memory admission check of 0.60 x RAM for ~20 GB processes). It panics if the variable is unset, `light` or
  any other value, and the message names the actual mode. The ~20 GB configurations require `huge` and refuse
  plain `heavy`: the sweep with po2 21, with `R11_KEEP_PROVER=1` over several po2s up to 20, or with a CPU
  prover at po2 >= 20; `seal_matches_cpu_large` with `R11_EQ_KEEP_PROVERS=1`. `R11_NO_GPU_RUN_CHECK=1` skips the
  check. The decision is a pure function (`tests::gpu_run_check`) with a unit test, `gpu_run_check_modes`, in
  the default suite. Checked: unset, light, heavy-for-huge-class and the `R11_PO2S=21` refusal all fail with
  their messages before any GPU work.
- **`prove_po2_sweep`:**
  - `R11_PO2S` defaults to `20`. The CPU prover runs only below po2 20 unless `R11_CPU=1` (every po2) or `0`
    (never) is set.
  - po2 >= 21 needs `R11_ALLOW_21=1`.
  - The Metal prover, and therefore its HAL and pool, and the CPU prover are built fresh for each po2 and dropped
    after it. `R11_KEEP_PROVER=1` restores the single prover.
  - After each po2 the test prints `currentAllocatedSize` and the footprint, before and after the drop.
    `R11_SETTLE_MS` adds a delayed re-read.
  - When the CPU prover runs, the test re-runs itself with `MallocLargeCache=0` (`R11_KEEP_MALLOC_CACHE=1`
    skips this).
  - It prints the huge-class banner at po2 >= 20.
  - Usage: `bin/gpu-run --tag X -- <bin> prove_po2_sweep --ignored --nocapture` (`--huge` also works and is
    required for the configurations above; po2 21 alone: `R11_ALLOW_21=1 R11_PO2S=21 R11_CPU=0 bin/gpu-run
    --huge --no-budget ...`). BASELINES runs it as
    `R11_PO2S=20 R11_CPU=0 R11_REPS=4`, which is unchanged. The default run (po2 20, 2 reps): Metal peak
    9303 MiB, process footprint peak 10.19 GiB (10.94 GB), rep 1 1015 ms. At the simulated budgets
    (`--budget 4G` / `8G`) the default sweep proves nothing: its only po2 reports "budget exceeded" at the
    first allocation over the budget (3.54 GB at 4 GiB, 1.73 GB at 8 GiB; measured by the round-1 review). That is the test's existing
    report-the-failing-allocation behaviour; po2 20 does not fit those budgets.
- **`seal_matches_cpu_large`:**
  - It prints the huge-class banner and re-runs itself with `MallocLargeCache=0`.
  - For each case it first runs a fresh CPU prover and drops it, then builds a fresh Metal prover. The case's
    segment is loaded on demand and dropped after it.
  - The peak is therefore the larger of one CPU and one Metal po2 20 proof. `R11_EQ_KEEP_PROVERS=1` restores
    the old behaviour.
  - One segment per process gives the smallest footprint. A list works too: each 2-segment pair below peaked
    at 9.78-9.79 GiB.
  - Usage: `R11_EQ_PO2S= R11_SEGMENTS=a.postcard,b.postcard bin/gpu-run --huge --tag X -- <bin>
    seal_matches_cpu_large --ignored --nocapture`. `--huge` is the recommended mode (it is what `gpu-run --help`
    names for CPU-plus-Metal seal tests at po2 >= 20); plain heavy is accepted at the default settings, whose
    peak is ~9.8 GiB.
- **The banner.** It says "huge class (...): run alone with `bin/gpu-run --huge --tag <item> -- ...`" and prints
  the actual `GPU_RUN_MODE`. (The first round said `gpu-run` had no `--huge` flag. That was wrong: W7-T1 had
  added it before this item's first commit.)
- **Footprint of the self-rerunning tests.** `seal_matches_cpu_large`, and `prove_po2_sweep` when a CPU prover
  runs, do their work in a child process started with `MallocLargeCache=0`. `/usr/bin/time -l` around them sees
  only the parent: it reports about 2.3 MB ("peak memory footprint 2343440"), not the child's peak. Do not quote
  that number. Use the in-process `footprint ... (process peak ...)` lines, or the parent's line
  `child (MallocLargeCache=0) peak footprint N B`, which the parent now prints: it reads the child's
  `ri_lifetime_max_phys_footprint` while the child is a zombie (`waitid(WNOWAIT)`), then reaps it. The parent
  also fails if the child's stdout lacks `test result: ok. 1 passed;`, so a filter that matches nothing cannot
  pass vacuously (unit test `child_ran_one_test_rejects_empty_filter`).
- **Lib suite.** `seal_matches_cpu` and `witgen_sorted_amplifier` take `tests::large_test_lock()`, which is the
  existing `metal_test_lock` (one lock, so no nesting).

## 5. Guard fallback order (R23 review P2)

- `eval_regime.rs` now tries `ef_eval_split_nohoist` first, then `ef_eval_split_nest`, then
  `ef_eval_split_r15e` (`FALLBACK_KERNELS_NOHOIST_FIRST`). `_nohoist` is R22's flat kernel: the same flat shape
  as the plain kernel and about 3 % slower than it (R23 3.3). The nested chain is about 7 % slower (R22) and
  adds ~1.5 GB of footprint (section 1).
- `RISC0_METAL_RV32IM_GUARD_FALLBACK=nest` restores the old `_nest`, `_r15e` order. An unknown value is logged
  and the default is used.
- The guard logs the order it uses at info level.
- `FALLBACK_KERNELS` (the old order) is unchanged, so `eval_check.rs`'s `eval_regime_guard_kernels`, which
  indexes it, still holds.
- New unit test: `fallback_order_parsing`.

Evidence (`RISC0_METAL_RV32IM_EVAL_GUARD=force RISC0_METAL_RV32IM_EVAL_FC=0`, debug log of the module):
- `seal_matches_cpu` (14 segments, po2 13/14/17):
  - Log: "using ef_eval_split_nohoist instead of ef_eval_split (native stack 4000 B, 2351572 B of code: fast

    (ef_eval_split_nohoist)".
  - All 14 seals equal the CPU seals and verify.

## 11. Fix round 2 (review finding: heavy ignored tests overlapped in one process)

**Finding.** The gate checked each heavy `#[ignore]` test alone. Under plain `bin/gpu-run` (heavy),
`<bin> --ignored` (or `--ignored integration_tests`, or `cargo test ... -- --ignored`) passed every gate,
and the default parallel harness then ran `prove_po2_sweep` in the parent at the same time as
`seal_matches_cpu_large`'s MallocLargeCache=0 child. With the defaults that is two ~10 GiB po2 20 workloads
at once (~20 GB) under a lock this item classifies as not enough for ~20 GB. The reviewer reproduced it at
small sizes (`/Users/user/zkminer/scratch/w7/W7-R1-rev2/concurrent_ignored.log`). The child started at
t=673.81 and the sweep's Metal proofs ran from 673.88 to 674.81, interleaved with the child's lines.

**Repro test, written before the fix and kept.** `tests::ignored_heavy_tests_take_the_large_test_lock` (in
the default suite, no GPU) scans the owned test files (`integration_tests.rs`, `witgen_tests.rs`,
`pipeline_bench.rs`, `tests.rs`). It checks two things for every `#[ignore]` fn:
- the fn calls `begin_heavy_test(`;
- if it reruns itself in a child, the call comes before `rerun_without_malloc_large_cache(`.

It also checks that the five known heavy tests are found, so the test cannot pass on an empty list. On the
round-1 head it failed: "integration_tests.rs: seal_matches_cpu_large is #[ignore] but does not call
begin_heavy_test" (`fix2/scan_before.log`). After the fix it passes.

**Fix.** `tests::begin_heavy_test(test, class)` runs the gate (`require_gpu_run_class`), then takes
`large_test_lock()` and holds it for the test's whole run. It also logs how long it waited for the lock.
These tests now start with it: `prove_po2_sweep`, `seal_matches_cpu_large`, `r15w_witgen_ab`,
`pipeline_bench` and `archive_cold_start`. The last two already took `metal_test_lock`, which is the same
mutex. The old `require_gpu_run` wrapper is gone.

In `seal_matches_cpu_large`, and in the sweep when it runs the CPU prover, the lock is taken in the parent
before the child is spawned, and held until the child exits. The child is a separate process with its own
mutex, so this cannot deadlock. The child also takes its own lock and logs "waited 0 ms". Nothing called
under these tests takes `metal_test_lock` again; the only other callers are the default-suite archive tests.
Since the same lock is also taken by the large default-suite tests (`seal_matches_cpu`,
`witgen_sorted_amplifier`, ...), `--include-ignored` cannot overlap a heavy ignored test with them either.

**Evidence that the overlap is gone.** I re-ran the reviewer's command on the fixed build:
`R11_PO2S=14,15,16 R11_CPU=0 R11_REPS=3 R11_EQ_PO2S=14,15 bin/gpu-run -- <bin> --ignored integration_tests
--nocapture`. The log is `fix2/concurrent_ignored_after.log.raw`. In it, the sweep takes the lock (waited
0 ms) and runs all its po2 14/15/16 proofs. The line after its last "after dropping the prover" line is
`seal_matches_cpu_large: holding the large-test lock (waited 728 ms)`, and only after that does the parent
print "running again with MallocLargeCache=0" and spawn the child. No sweep line comes after the child
starts. Both tests pass; the child's peak footprint is 0.96 GiB.

**Not serialized by this item.** The ignored heavy tests in `eval_check.rs` (W7-Z1) and in the accum code
(its owner) do not call `begin_heavy_test`. `<bin> --ignored` can still overlap one of them with one of the
tests above. W7-Z1 and the accum owner should add `let _lock = tests::begin_heavy_test(..)` to them. They
must not take `large_test_lock` twice: it is not reentrant.
