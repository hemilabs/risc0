## 2. Constants: derived, not literals

`to_metal.py` used to hard-code `#define EF_NPC 458u` and `#define EF_NPM (EF_NPC + 107u + 62u)` in its
prelude. The static_assert after the chain caught a wrong 107/62, but nothing caught a stale EF_NPC.

Now:

| constant | source | 3.0 | 3.1 |
|---|---|---|---|
| `EF_NPC` | the chain's `#define EF_NPC <n>u` (to_cuda.py's `POLY_MIX_COUNT`), exactly one match | 458 | **484** |
| `RK_QN` | the chain's `constexpr uint32_t RK_QN = <n>;` | 107 | **109** |
| `RK_HN` | the chain's `constexpr uint32_t RK_HN = <n>;` | 62 | **49** |
| `EF_NPM` | `EF_NPC + RK_QN + RK_HN` | 627 | **642** |
| `kNumPolyMixPows` | `kernels/cuda/eval_check.cuh` (zirgen header), read on its own and not from the chain | 458 | **484** |

`to_metal.py` (`table_sizes`, `circuit_poly_mix_pows`) refuses its input, with a message that names the
mismatch, in each of these cases:

- the chain's `#define EF_NPM (EF_NPC + Qu + Hu)` disagrees with `RK_QN` / `RK_HN`;
- `EF_NPC` differs from the circuit's `kNumPolyMixPows` (`regenerate the chain for this circuit`);
- a `rk_qa` / `rk_qb` index is `>= EF_NPC`;
- an `EF_PM(i)` row is past `EF_NPM`. On 3.1 the highest row is 641, inside the 642-entry table;
- any of these appears zero times or more than once.

Changes in the output:

- **Prelude.** It now emits the derived `#define EF_NPC 484u` and `#define EF_NPM (EF_NPC + 109u + 49u)`.
  It also emits `constant constexpr uint32_t kNumPolyMixPows = 484u;` and
  `static_assert(EF_NPC == kNumPolyMixPows, ...)`.
- **Old assert kept.** The existing `static_assert(EF_NPM == EF_NPC + RK_QN + RK_HN)` against the
  chain's own `RK_QN` / `RK_HN` stays.
- **Placeholders.** Each prelude substitution is pinned to apply exactly once.
- **Build input.** `build.rs` (R12 block) now lists `kernels/cuda/eval_check.cuh` as an evalfast
  input, because to_metal.py reads it.

Diff of the generated `eval_check_ef.metal` against the plan's scratch preview
(`scratch/r31/gen/ef/`, made with the literal patched by hand): the prelude lines above, nothing else.
`ef_tables.rs` is byte-identical.

## 6. Perf record: eval_check 3.0 vs 3.1 (not an optimization claim)

**Method:**

- Binaries copied to `ab/rv_30` (frozen 3.0) and `ab/rv_31`.
- Interleaved 3.0 / 3.1, order alternating per pair (`ab.sh`, `kab.sh`).
- Per-process value: the median of reps 1-3.
- Deltas are per-pair 3.1 - 3.0.
- "Spread" is the max - min of the 3.0 process medians (A-vs-A).
- 1-min load: 1.5-1.7 (default), 4.2-7.0 (8 GiB), 3.9-5.0 (4 GiB), 2.0-7.7 (kernel).

| run | metric | 3.0 median [min, max] | 3.1 median [min, max] | per-pair delta, median [min, max] | spread |
|---|---|---|---|---|---|
| kernel, po2 20, specialized PSO (`evalfast_repeat_bit_exact`, 11 timed dispatches/process, 8 pairs) | split kernel ms | 534.2 [532.1, 539.0] | 545.0 [539.0, 556.5] | **+10.8 [0.0, +22.9] (+2.0 %)** | 7.0 |
| `prove_po2_sweep` po2 20, default budget (8 pairs) | eval_check | 540.5 [537, 550] | 547.5 [547, 554] | **+9.5 [-3, +17]** | 13 |
| | segment | 943.5 [940, 952] | 953.0 [952, 965] | +12.0 [+1, +25] | 12 |
| | data / accum commit | 210 / 109 | 210 / 109 | 0 / 0 | 0 |
| | FRI + tail | 57.5 | 59.5 | +2.0 [+1, +3] | 1 |
| | peak | 9315 MiB | 9315 MiB | 0 | |
| 8 GiB budget, po2 20 (7 pairs) | eval_check | 539.0 [538, 550] | 547.0 [544, 549] | +8.0 [-4, +10] | 12 |
| | segment / peak | 1011.0 / 8145 MiB | 1024.0 / 8129 MiB | +13.0 / -16 MiB | 17 |
| 4 GiB budget, po2 19 (7 pairs) | eval_check | 266.0 [265, 272] | 271.0 [269, 273] | +4.0 [-1, +6] | 7 |
| | segment / peak | 506.0 / 4021 MiB | 511.0 / 4080 MiB | +5.0 / +59 MiB | 9 |

**Attribution.** The kernel-level number (+10.8 ms, +2.0 %) exceeds the 3.0 spread (7.0). The
sweep's +9.5 ms is inside its spread, but has the same sign and size. The generated kernel
accounts for it:

- **Poly_mix links** in the chain bodies: 5118 -> 5211 (+93, **+1.8 %**). These are the new
  constraints of 3.1's circuit fix: +26 poly_mix powers, `NUM_POLY_MIX_POWERS` 458 -> 484. Link
  arithmetic is most of the kernel's work (R19's profile: Fp multiplies <= 15 %, trace loads ~12 %,
  slab <= 12 %, the rest is links), so +1.8 % links predicts up to ~+9.7 ms of 534.
- **Other kernel inputs are flat or smaller:**
  - closures 231 -> 231;
  - distinct trace loads 3844 -> 3841;
  - FpExt `EF_PM` terms 192 -> 179;
  - chain lines +0.35 %.
- **totalCycles / one-execution terms.** The `args[2][K]` global constraint is one read of `out`
  per row. The "approach A" LogUp restart moves 13 hoisted out/mix terms (RK_HN 62 -> 49) into 13
  more links in `rk_accblk`. That is part of the +93, and the host table shrinks by 15 entries
  net: EF_NPM 627 -> 642, of which +26 powers, +2 products, -13 hoisted.
- **Per function:** the extra links fall mostly in v2_13 (+31), v2_10 (+18), v2_15 (+15), v2_12
  (+13), `rk_accblk` (+13), v2_4/v2_11/v2_17 (+11 each). v2_3 lost 20 and v2_14 lost 9.
- **Rest of the segment:** FRI + tail +2 ms (+3 %, consistent and above the spread). That is not
  eval and was not investigated here; it is for P31-06/P31-17.

Against the program goal, 3.1 costs about +1 % of a po2 20 segment, all of it in eval_check.

**Memory.**

- Default budget: the peak is unchanged (9315 MiB). At 8 GiB it is -16 MiB.
- At 4 GiB / po2 19, 3.1's peak is +59 MiB (4080 vs 4021 MiB) in every pair, but it sits in the
  **accum commit** phase (3.1 accum commit 4080 MiB vs 3.0 3704 MiB; eval_check 3686 vs 3704). Not
  in eval: the eval table grows by 15 x 2 x 16 B = 480 B.
- BASELINES wave 7 7.3 lists 4080 MiB for the same tier, so 4021 may be this session's 3.0
  reading. Open issue for P31-17.
