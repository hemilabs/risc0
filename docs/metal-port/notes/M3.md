# M3: zkvm orchestration Metal arms

## What was done (ported from the CUDA/ROCm/Intel arms of the same files)
`risc0/zkvm/src/host/server/prove/mod.rs`
- `exclusive_gpu()` (CUDA arm, was mod.rs:489-495): new `#[cfg(all(feature = "metal", not(feature = "cuda")))]` arm returning
  `risc0_zkp::hal::metal::exclusive()`; the no-op arm is now `not(any(cuda, metal))`. Every prove session
  (`prove_session_impl`), every `with_segment_prover` call and every `prove_keccak_with` now holds the Metal GPU lock, like CUDA.
- `release_hal_buffers()` (was mod.rs:513-520): Metal arm calls `prover_impl::release_cached_provers()`.
  Reason: F0's MetalHal has no process-wide pool (each `MetalHal`'s `Runtime` owns its pool, capped at half of
  `recommendedMaxWorkingSetSize`, and frees it on drop) and there is no global "clear pool" entry point. The long-lived
  HALs are the ones held by this thread's cached segment prover and recursion provers, so dropping them returns the pool.
  All call sites run on the proving thread with the segment pipeline drained (`shrink_wrap_with`'s `pre_gpu` runs on the
  calling thread in groth16 `metal.rs`; the pre-keccak and post-wrap calls in prover_impl run after the last
  `prove_end`). `release_cached_segment_prover` uses `try_borrow_mut`, so a call while the prover is borrowed is a no-op.

`risc0/zkvm/src/host/server/prove/prover_impl.rs`
- `release_cached_segment_prover` / `release_cached_provers`: cfg widened from `any(rocm, intel)` to `any(rocm, intel, metal)`.
- `start_metal_warmup()` (new, modelled on `CUDA_WARMUP`/`spawn_cuda_warmup`, prover_impl.rs:108-140): started from
  `ProverImpl::new` once per process (`std::sync::Once`), thread `metal-warmup` calling
  `risc0_circuit_rv32im::prove::metal_warmup` (R7; respects `enabled("rv32im")`). Only rv32im has a Metal warmup today:
  recursion's Metal HAL is still the F2 CPU stub, and keccak has no warmup function (its eval_check PSOs are the ~94 s
  cold build of K3). **The warmup is never joined**, unlike CUDA's: `MetalHal::new` takes the same `exclusive()` lock the
  session holds for its whole run, so joining it from the session deadlocks. Correctness does not need a join: zkp PSOs
  are built once inside `MetalHal::new` under the lock, rv32im PSOs in a `OnceLock` whose init takes no lock, so whichever
  side comes first builds them and the other waits on the lock/OnceLock, never on a join.
- `preload_graph_background()` in `ProverImpl::new`: `cuda` -> `any(cuda, metal)` (groth16's metal arm only spawns when the
  Metal Groth16 prover is enabled).
- `_graph_preload` in `prove_session_impl`: cfg widened with `metal`. The thread does no GPU work (fast::preload is CPU), so
  the session's lock does not block it; it is detached as before.
- keccak host-witness thread (`cfg!(any(intel, rocm))`, prover_impl.rs ~1192): widened with `metal`. K1's Metal keccak HAL
  has `HOST_WITNESS = true` (CPU witgen over shared buffers), so a witness made a proof ahead overlaps with the GPU. When
  K6 ports the witgen, `prove_host_witness` returns `None` and `prove_keccak_with` falls back to proving from the inputs:
  still correct, but the thread is then wasted CPU work, so K6 (or whoever lands it) should narrow this cfg.
- Succinct segment-po2 bump (prover_impl.rs ~1485): cfg widened with `metal` so the generic `RISC0_SUCCINCT_SEGMENT_PO2`
  (and `RISC0_INTEL_SUCCINCT_SEGMENT_PO2`) override works on Metal, but **Metal never bumps on its own**. Why, against
  PLAN 9.1: the minimum target (16 GB Mac, ~4-8 GB GPU budget) must keep segments at po2 <= 18-19; even po2 20 needs
  13.7 GB today (measured below), po2 21 would be ~2x that, above the 36 GB dev machine's ~27 GB working set; and the
  bump's payoff (half the lifts/joins) is small while recursion is still the CPU prover. Segment size on Metal is the
  caller's decision (zk-miner, sized from `recommendedMaxWorkingSetSize`, M1).
- Not given Metal arms (deliberately): `release_pool_on_po2_growth` (CUDA-only; on Metal it would have to drop the segment
  prover mid-pipeline and lose the pending seal); `prestart_key`/`prestart_key_go` (no-ops in groth16's metal.rs);
  `rec_pipe` / multi-GPU / parallel-STARK paths (CUDA/ROCm only); the Intel post-session `release_idle_buffers` (see gaps).

`zkvm/src/host/server/prove/tests.rs`, `zkvm/src/host/recursion/tests.rs`
- cfg widened with `feature = "metal"`: `compress`, `fake_compress`, `verify_in_guest`, `shrink_wrap`,
  `test_recursion_host_chains_check` (errata 8.1).
- New `#[cfg(feature = "metal")] mod metal { metal_composite_succinct_round_trip }`: composite proof of the multi_test
  BusyLoop guest (`RISC0_M3_PO2`, default 18; `RISC0_M3_CYCLES`, default 2^19), verified; then `release_hal_buffers()` with
  a check that the device allocation did not grow; then `compress` composite -> succinct, verified, journal equal. A
  sampler thread (its own `MetalHalPoseidon2`, made before proving so it never needs the session's lock) polls
  `recommendedMaxWorkingSetSize - (that - currentAllocatedSize)` = `currentAllocatedSize` every 2 ms and records per-phase peaks.

## Known gaps / issues addressed to later items
- **Z6 / R8-R10 (memory)**: 3.4 GB at po2 18 and 13.7 GB at po2 20 for the composite STARK, all of it still allocated after
  the session (the cached segment prover's HAL pool). That is already at/over the minimum tier's ~4 GB active budget at
  po2 18 (PLAN 9.1) and above the 8 GB idle budget at po2 20. Someone should break down the peak per phase inside the
  segment prover (live vs pooled) and test under `RISC0_METAL_MAX_WORKING_SET_BYTES`.
- **M1 (worker)**: a session leaves the segment prover's pool resident (3.4 GB at po2 18) until the next session or a
  `release_hal_buffers` (before the keccak proofs and around the Groth16 wrap). zkvm has no public "release" entry point; if
  the worker needs the memory back between jobs on a 16 GB Mac, add one (or an Intel-style post-session release on Metal,
  with its cost measured: a rebuilt prover re-uploads hash constants and NTT tables; the PSOs are process-wide and stay).
- **K5/M1**: no keccak (or recursion) Metal warmup exists, so `start_metal_warmup` only warms rv32im. The keccak
  eval_check PSOs are ~94 s cold (K3); the first keccak proof in a process pays it under the GPU lock.
- **K6**: narrow the keccak host-witness cfg in `prover_impl.rs` once the Metal witgen lands (see above).
- **C6/C9**: `test_recursion_host_chains_check` is now compiled for Metal and fails until recursion's Metal witgen
  computes host chains (`witgen.rs` `cfg!(any(cuda, rocm))`).
- **G7**: once the Metal Groth16 prover works, run the skipped Groth16 cases above (`compress::case_3,6,7,8,9`,
  `fake_compress`, `shrink_wrap`, `verify_in_guest::case_3`). `shrink_wrap` runs 5 proofs in parallel rayon threads, each
  taking `exclusive()` around its GPU part; check it does not deadlock against rayon workers that call a HAL.
- **M4**: document the C++ guest toolchain (`rzup install cpp`) and the `AR_riscv32im_risc0_zkvm_elf` export.
- The lock caveat applies to every future Metal arm: never join a thread that creates or uses a `MetalHal` while holding
  `exclusive_gpu()`.
