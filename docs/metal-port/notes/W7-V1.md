## Changes

1. **Heavy test lock** (`prove/tests.rs::heavy_test_lock`, a copy in `recursion/tests.rs`). An exclusive
   `flock` on `$TMPDIR/risc0-zkvm-heavy-test-<pid>.lock`. Each open of the file is a separate lock owner,
   so threads of one test process exclude each other and other processes are not affected. It is a
   file rather than a static because `recursion::tests` cannot name the private `prove::tests` module.
   The two copies lock the same file. The guard is dropped at the end of the test, also on a panic.
   Every test at or above ~2.5 GB alone takes it, in its own body only. The lock is not reentrant, so
   `test_recursion_host_chains_check` now calls body functions (`lift_join_identity_p254_e2e`,
   `lift_resolve_e2e`) instead of the other test functions. The `api::tests` ones (2.5 GB) are not
   owned by this item and are not locked. Unit test `heavy_test_lock_excludes_threads`: a second thread's
   `try_lock` gets `WouldBlock` while the lock is held, and succeeds after it is dropped.
   - First cut, tests > ~4 GiB only: suite 18.92 GB. Adding > 3.5 GB: 19.10 GB. Adding > 2.5 GB: 17.68 GB.
     The one-thread floor of the suite is 15.80 GB.
2. **The three `bench_prove_*_po2_20` benches** are `#[ignore = "measurement: po2 20, run alone under
   gpu-run"]`, take the lock, and first call `require_gpu_run_heavy`. The same applies to the ignored
   `z17_first_segment_probe`, `z12_stark_phases` and `metal_wrap_after_stark`. `require_gpu_run_heavy`
   panics unless `GPU_RUN_MODE` is `heavy` or `huge` (exported by gpu-run). Checked without it: the test
   fails at once, before any proving, with "... is a heavy measurement test: run it alone under
   `gpu-run` ...; GPU_RUN_MODE is Err(NotPresent)". On a machine without gpu-run, set
   `GPU_RUN_MODE=heavy` by hand. `tests_c16::c16_groth16_release_ab` (ignored, not owned) is unchanged.
3. **keccak_union and sha_iter fit the budget.** `segment_po2_for_budget()` reads the HAL limit
   (`risc0_zkp::hal::metal::device_memory()`: the budget env, else `recommendedMaxWorkingSetSize`) and
   applies zk-miner M8's table: < 6 GiB gives po2 18, < 12 GiB gives 19, anything larger gives 20. Without
   Metal the default po2 is kept. Both tests also call `release_srs()` first, under the lock. That frees
   the Groth16 key/prover that an earlier wrap test left cached on the GPU. Every wrapping test holds
   the lock, so none is using it, and the next wrap reloads it. This took the suite from 17.68 to
   16.26 GB.
4. **tests_z17 with `RISC0_METAL_EXEC_STREAM=0`**: `z17_stream_matches_loop`, `z17_stream_succinct_twice`,
   `z17_stream_error_then_prove` and `z17_prove_inside_io_callback` return early. Each prints
   "<test>: skipped: RISC0_METAL_EXEC_STREAM=0 in the environment turns the stream off, and this test
   proves through the default mode". The other tests still run.
5. **gdb `end_to_end`** skips, printing the reason, when rzup is missing, has no default gdb version, or
   `riscv32im-gdb` is absent. Here it prints "end_to_end: skipped: rzup's gdb component is not installed".
   The check now runs before the debugger thread is spawned.
6. **Executor**: a test only (`exec::tests::segment_split_po2_14_15_16`). See the finding below; nothing
   to fix in the executor.

How to run the ignored ones (each alone, under the heavy lock):
`gpu-run -- <zkvm test bin> host::recursion::tests::bench --ignored --nocapture` (the three together
are serialized by the lock: 15.55 GB, 22 s), `... tests_z17::z17_first_segment_probe --ignored`,
`RISC0_G8_BUDGET=<bytes|none> ... tests_metal_wrap::metal_wrap_after_stark --ignored --exact`.

## Executor finding (po2 15 over-split): not a bug, a headroom choice; for the executor owner

`risc0/circuit/rv32im/src/execute/executor.rs::run` splits before an instruction once
`user + paging + RESERVED_CYCLES > 2^po2 - max_insn_cycles`. `RESERVED_CYCLES` is 4113 (lookup tables
plus 1). `max_insn_cycles` comes from `ExecutorImpl::run_with_callback`: `MAX_INSN_CYCLES_LOWER_PO2` =
2000 below po2 15 and `MAX_INSN_CYCLES` = 25000 from po2 15 on. Upstream #3098 (96e5393b5) raised it so
the largest bigint program fits in one segment. At po2 15 that leaves 32768 - 25000 - 4113 = **3655
cycles for user + paging**. That is less than one segment's paging of its working set, so every segment
stops a few dozen instructions after its pages are in.

`segment_split_po2_14_15_16` (BusyLoop 2^16; 68443 user cycles in every case):

| po2 | threshold | segments | user cycles per full segment, median [min-max] | paging per segment, median [min-max] |
|---|---|---|---|---|
| 14 | 14384 (2^14 - 2000) | 18 | 5612 [253-5613] | 4660 [4660-10803] |
| 15 | 7768 (2^15 - 25000) | **1539** | **35 [6-241]** | 3886 [3564-5294] |
| 16 | 40536 (2^16 - 25000) | 3 | 31764 [21445-31764] | 14979 [4660-14979] |

The test asserts the split rule at all three sizes: every full segment passed the threshold and stays
under 2^po2. It also asserts the cause at po2 15: `threshold - RESERVED_CYCLES <` the median paging.
A "small, clear" fix does not exist inside the owned files. Lowering the po2 15 headroom would make a
25000-cycle bigint ecall fail at po2 15 ("segment limit too small for instruction"), undoing #3098.
A proper fix would make the headroom depend on the next instruction: only a bigint/ecall needs 25000
cycles, a plain instruction needs at most its paging. That is a change to the executor's step loop
for its owner (upstream). Until then po2 15 is a size to avoid: the worker never uses it (M8: 18-20),
and Z17's test moved to po2 16. Since nothing was fixed, there is no executor A/B and no segment-count
change.

## Z17 firmer measurement (worker `--benchmark`, full suite, `--no-budget`)

zk-miner `metal` 0ca7ec9 in a scratch worktree (`scratch/w7/W7-V1/zk`, deleted afterwards), path-patched
to this branch. Its production code is identical to `zkminer/metal` b5fa9a97a. One gpu-run per run,
`RUST_LOG=info`, `/usr/bin/time -l`. Off = `RISC0_METAL_EXEC_STREAM=0`, on = default. The order inside
each pair alternated (p1 off-on, p2 on-off, p3 off-on, p4 on-off, p5 off-on). I ran a fifth pair because
p4's on run caught a load spike (1.7 -> 7.5, other agents' builds). Every run proved, wrapped and

- This session: off **169.49 [169.34-170.13]** s, on **168.81 [168.49-173.97]** s; the pair delta median
  is **+0.66 s** (3/5 off slower). Over all 7 pairs: median +0.66 s (+0.39 %), 5/7 off slower, range
  [-4.22, +1.07].
- A-vs-A spread: off runs 0.79 s (5 runs). On runs 5.48 s, or 2.60 s without the load-spiked p4. Recursion
  is identical (29.45-29.63 s, except p1-on and p4-on, which were under load).
- **Verdict: Z17 does not beat the A-vs-A spread end to end.** Over 7 pairs the +0.66 s median is below
  the on arm's 2.6 s spread and about equal to the off arm's 0.79 s. By the protocol that is "no change"
  on the full suite. The direction is consistent with the mechanism Z17 measured (-215 ms executor lead
  on sha256-chain, deterministic) and with the ~0.85 s estimate. Flipping the default is the baseline
  agent's call. Footprint: on 15.118-15.157 GB, off 15.115-15.131 GB (+~10-25 MB on, as Z17 reported).

## Correctness

- Full lib suite passed 6 times under the default harness (16 GiB; twice with the final binary),
  twice with the stream off and once without a budget. `host::server::prove` passed twice,
  `host::recursion::tests` passed, and the three ignored benches passed together.

  smaller segment po2 when the budget is small (sha_iter still checks its journal digest), and the
  skips listed above.

  `#[cfg_attr(not(feature = "metal"), allow(dead_code))]` on `require_gpu_run_heavy`, whose callers
  are Metal-only modules; that attribute is inactive in the Metal build the gates ran. `rustfmt`
  is clean on the changed files.
- No kernel changed, so no ir_scan/stress run was needed.
