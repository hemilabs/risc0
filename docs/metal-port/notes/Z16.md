## Changes

1. **zkp** (`zkp/src/hal/metal/kernels.rs`, `metal.rs`): `MetalKernels::new_zkp` builds the process-wide zkp set
   concurrently through `archive.rs` (unit `zkp`). `new_zkp_in` is the test seam (loader chosen by parameter; no
   env in tests, PLAN 8.7). Knob: `RISC0_METAL_ARCHIVE_ZKP=0` = the pre-Z16 sequential plain loader.
2. **recursion** (`recursion/src/prove/hal/metal/mod.rs`, PSO loading only): `Pipelines::new` routes the embedded
   `METAL_LIB` through the archive, one unit per kernel set (`recursion` for the base set,
   `recursion_<variant>` per eval_check variant, `set_unit`), so sets do not prune each other's archives; other
   metallibs/sets (tests) get no archive. The metallib match is by content (`METAL_LIB` is a `const`; an address
   check missed the eval set). Threads = `pso_threads()` (C11) via the new `ArchivedKernels::new_in_threads`.
   Knob: `RISC0_METAL_ARCHIVE_REC=0` = the C11 plain loader.
3. **archive.rs**: `into_parts`, `new_in_threads` (thread cap), PSO names registered with the Z9 profiler; the
   key rules are unchanged (K7/K8: metallib digest, device, OS build, kernel names; R20 adds function-constant
   values for specialized PSOs; checksum in the file name; fallback to plain PSOs on any archive error).
4. **Offline (AOT) archives** (`archive.rs` + `tools/metal_aot/build_archive.py`): opt-in
   `RISC0_METAL_AOT_DIR` = a read-only directory of `metal-tt` archives named
   `<unit>-<chunked_digest(metallib)[..24]>-<MTLDevice.architecture.name>-<checksum16>.binarchive`. The runtime
   picks only the file of its own metallib and GPU architecture, verifies the checksum before Metal reads it
   (K8: a damaged archive can abort inside Metal), and tries it first for every PSO with
   `FailOnBinaryArchiveMiss`; a miss continues with the runtime archive (hit, else compile into it). The directory
   is never written. `ArchiveReport::aot_hits`/`aot_path` report it. Unset: no behavior change. Not applied to
   R20's specialized PSOs (see open issues).
5. **Segment-po2 prewarm API** (R20 open issue 3; `rv32im::prove::metal_prewarm_segment_po2(po2, wait)`,
   additive in `eval_check.rs`): builds/loads the `ef_eval_split_fc` PSO specialized for that segment po2's
   domain. `wait=false` returns at once (background thread) and says whether it was already ready; `wait=true`
   blocks until ready. No-op for `RISC0_METAL_RV32IM_EVAL_FC=0`, rv32im Metal disabled, or a po2 outside
   `MIN_CYCLES_PO2..=MAX_CYCLES_PO2`. zk-miner M9 is to call it at worker start with the configured po2.

Go/no-go (LEADS: cpusubtype 355 for g17s verified): `metal-tt -arch applegpu_g17s -macos-version-min 27.0` on the

`z16_probe_archive_file` (fail-on-miss, `MTL_SHADER_CACHE_SIZE=0`, fresh process): **13/13 hits, 0.019 s load,

0/13 hits with a clean "Unable to find function" error, no crash (Metal treats a non-matching archive as a miss).
End to end (`RISC0_METAL_AOT_DIR` + empty runtime archive dir + cold OS cache, 2 interleaved pairs): rv32im+zkp
warmup **59.7 / 60.1 s -> 1.80 / 1.73 s** (the rest is the zkp set, which had no AOT file in that run).

Not shipped as a default: nothing in the build generates archives (K5's reasons still hold: ~1-2 min and ~35 MB
per arch per unit, and the consumer arch list g13..g17 x variants is unknown). Fallback elsewhere is by
construction (another arch's or metallib's file is never opened; a mismatching archive misses) and is covered by
`zkp_kernels_aot_archive` (wrong checksum skipped, other arch ignored, partial archive serves its kernels), but
it was not run on another Mac or OS build.

## Memory safety note (why the machine crashed twice)

Both kernel watchdog panics today (07:11, 10:05; `/Library/Logs/DiagnosticReports/panic-full-*`) show wired
memory at ~34.5 GB (2.25M 16 KB pages, 914 free) with three to four `risc0_circuit_rv32im` test processes at
14.9-18.4 GB each (crash 1: three started together under `timeout`, plus a cargo-launched one at 9.4 GB that had
started 2.5 min after Z16's earlier attempt built its rv32im test binary, probably that attempt's suite run;
crash 2: three at 18.4 GB, while Z16's process was a 56 MB PSO probe). The measured peak of one rv32im suite run
under the default harness is 16.0-16.5 GB, so any two at once on a 36 GB Mac leave nothing for the rest, and three
exhaust it. Everything in this item ran through `gpu-run` (suites under the exclusive lock, one at a time).

## Knobs

- `RISC0_METAL_ARCHIVE_ZKP=0`: zkp PSOs the pre-Z16 way (sequential, no archive).
- `RISC0_METAL_ARCHIVE_REC=0`: recursion PSOs the C11 way (threads, no archive).
- `RISC0_METAL_ARCHIVE=0`: no archive for any unit (also no offline archive).
- `RISC0_METAL_AOT_DIR=<dir>`: offline archives (unset = none).
