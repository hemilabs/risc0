# P31-10: recursion host API on 3.1 (`get_zkr`), program cache

Base `metal/P31-09` (b99d8a11f). Branch `metal/P31-10`. PORT_PLAN 1.2 row 7, section 5 row P31-10,
risk 6. Scratch and logs: `~/zkminer/scratch/w8/P31-10/` (`logs/`, `ab/`; fix round 1 in `fix1/`).

## Problem

3.1's `get_zkr` (`recursion/src/prove/zkr.rs`, `49f42eb11`) returns `Program` by value. It keeps
the xz-decoded words per process (`cached_zkr`, an `Arc<Vec<u32>>` per name), but it builds a new
`Program` on every call (`Program::from_encoded`: one Montgomery conversion per word, 12-24 MB).
Fork 3.0 had F30's `Arc<Program>` cache keyed by (name, po2). On this base the recursion crate
did not compile with `--features metal`. There were 14 errors: `ctrl_persist.rs` (the C16 prewarm
`commit(&program)` needs `&Arc<Program>`), `c11_tests`, `c13_tests`, `c16_tests` and `tests.rs`.
P31-08 and P31-09 used a local shim patch to work around them.

## Profile (before any change)

`zkr::tests::p31_10_profile_get_zkr` (ignored, release, CPU only, 15 reps per program;
`logs/profile_get_zkr_cpu.log`, two runs agree within 0.5 ms):

| program | words (bytes) | first call (xz decode) | each later call (= `from_encoded`) |
|---|---|---|---|
| `lift_rv32im_v2_20.zkr` | 3,911,817 (15.6 MB) | 52.1-52.4 ms | 1.41 ms |
| `lift_rv32im_v2_21.zkr` | 3,996,848 (16.0 MB) | 51.9-52.5 ms | 1.44 ms |
| `lift_rv32im_v2_18.zkr` | 3,353,883 (13.4 MB) | 43.7-44.0 ms | 1.21 ms |
| `join.zkr` / `resolve.zkr` | 5.97 M (23.9 MB) | 78.6-79.4 ms | 2.15 ms |
| `identity.zkr` | 2,985,699 (11.9 MB) | 38.8-39.2 ms | 1.07 ms |

So each call does hit 3.1's decode-once memo (the xz decode runs only on the first call). Every
call still runs `from_encoded`, at 1.1-2.2 ms. A second per-proof cost comes from the Metal
prover's ctrl caches, which match a program by `Arc` pointer (`claim_ctrl_caches`,
`ctrl_persist::code_for`). A new `Arc` per proof misses that pointer match, so every proof also
re-compares the program's code against the cached code (`same_code`, a parallel 16-24 MB compare).
Zkvm's `zkr.rs` wraps each call with `.into()` (`Arc::new`), so this happens on every lift, join,
resolve and identity proof.

The Metal steady-state lift is ~104 ms and the join ~126 ms on this base (C11 captures). That puts
the per-call cost above the 1 % threshold, so the cache was added. The in-process A/B below confirms
the CPU profile.

## Change

`risc0/circuit/recursion/src/prove/zkr.rs`:

- `get_zkr(name, po2) -> Result<Arc<Program>>` (fork 3.0's signature). Every call for the same
  (name, po2) returns the same `Arc`. All the existing call sites compile again unchanged: the
  test files, `ctrl_persist.rs:500` (`prewarm_p254_ctrl`), and zkvm's `get_zkr(..)?.into()` and
  `test_zkr`'s `program.into()` (`From<T> for T`). `ctrl_persist.rs`, `c10_tests`, `z10_tests`,
  `c16_tests` and `tests.rs` needed no edits. This also fixes the non-owned `c11_tests` and
  `c13_tests` errors without touching them.
- `program_cache` (as of fix round 1, see below): a `Mutex<HashMap<name, Vec<Entry>>>`, the
  programs built for each zkr name, at most `PO2_CAP = 2` po2s per name (LRU among them). Names
  are never evicted, so a zkr is xz-decoded at most once per process, as in stock 3.1. A second
  po2 of a cached name is a copy of its code with the new `po2` (same length check as
  `from_encoded`), not a decode. Programs are built outside the lock.
- Memory: with the cache on, the per-name word memo (`cached_zkr`) is not filled. The cache
  takes its place with the same bound: one copy of each zkr the process has used (every zkvm call
  passes `RECURSION_PO2`, so one program per name; a second po2 per name happens only in tests).
  Stock 3.1 keeps the raw words of every used zkr in its memo, and the prover also holds the
  `Program`s it built. With the cache, the prover holds the cached `Arc`s, so there is no second
  copy. Worst case, all 32 zkrs: ~470 MB in either. A prover uses 4-13 (its lift po2s, join,
  resolve, identity, union): 60-200 MB. Measured process peaks are equal to or below stock
  everywhere (tables below; -136 MB on the mixed-po2 job stream).
- **Revert knob:** `RISC0_METAL_REC_ZKR_CACHE=0` (or `off` / `false`). With the knob off, the
  stock 3.1 path runs (word memo, a new `Program` per call), wrapped in a new `Arc`. That is
  exactly what zkvm's `.into()` did on the unmodified base. The variable is read once per
  process. The cache lives in `zkr.rs`, so it applies to every backend; the circuit has no Metal
  code, and programs are immutable behind the `Arc`.

New tests (`zkr::tests`, CPU and Metal builds):
- `p31_10_cache_shares_and_matches_stock`: one `Arc` per (name, po2). The cached program equals
  stock `from_encoded(extract_zkr(..))`. A second po2 has the same code. With the knob off, every
  call returns a new `Arc` with equal content.
- `p31_10_no_xz_decode_after_many_programs` (fix round 1): 10 lift zkrs cycled twice; the second
  round must not run the xz decode (per-name decode counter) and must return the same `Arc`s.
- `p31_10_po2_variants_bounded_without_decode` (fix round 1): one name at po2 22, 20, 21, 22, 20,
  21, 19; at most `PO2_CAP` programs for the name, no second decode, every program equal to stock
  `from_encoded(.., po2)`.
- All three take `tests::override_lock` around the process-wide override
  (`program_cache::set_test_override`, PLAN 8.7): the crate's `global_state_test_lock` under
  `--features metal`, a local lock in the CPU build.

Bench harnesses (ignored):
- `zkr::tests::p31_10_profile_get_zkr`: the profile above. `RISC0_METAL_REC_ZKR_CACHE` picks the
  arm.
- `hal/metal/tests.rs::p31_10_bench_zkr_cache`: in-process lift/join replay of the C11 captures.
  With the knob on, every proof gets the same `Arc` (the cache). With `0`, every proof builds a new
  `Arc<Program>` from the words inside the timed region (stock 3.1). The harness prints `P3110CAP`
  and `P3110BENCH` lines (round sum plus lift and join medians).

## Fix round 1: eviction thrash (review finding)

**Finding.** The first version kept at most `CAP = 8` programs with an LRU over (name, po2) and
did not fill the word memo. Once a process used more than 8 programs, every reuse of an evicted
one re-ran the 40-85 ms xz decode, where stock 3.1 (knob 0) pays ~1.2 ms. That happens in
practice: zkvm asks for `lift_rv32im_v2_{po2}` per segment po2, and the final segment's po2
varies per job, on top of join, resolve, identity, union and povw.

**Reproduced before the fix.**
- `p31_10_no_xz_decode_after_many_programs` failed on c160a39a0: per-name decode count 1 -> 2 for
  all 10 lifts in round 2.
- The reviewer's CPU harness (`fix1/thrash`, `get_zkr` round-robin over 9 lifts, then 16 jobs of
  hot set + one rotating rare lift; `fix1/thrash/before.log`): cache on, rounds 1-2 cost 41.3 ms
  per call (all decodes) and 14 of 16 rare lifts cost 31.8-48.1 ms. Knob 0: 1.19 ms and 0.9-1.4 ms.

**Fix.** Names are never evicted (the design above): the bound is one program per used zkr,
exactly stock's word-memo bound, so no miss after first use ever decodes. The LRU now only picks
among one name's po2s (`PO2_CAP = 2`), and that eviction always keeps one, from which another po2
is a code copy. Option (a) of the review (move evicted words back to the memo) was not taken:
it still pays a decode-sized conversion (~1.4 ms) per eviction and a bound that the old CAP gave
nothing for, since stock's memo is unbounded per name anyway.

**After the fix** (`fix1/thrash/after.log`, same binary, cache on vs knob 0, two runs each, load
2.5): rounds 1-2 cost 0.00 ms per call with the cache (knob 0: 1.17-1.23 ms); all 16 rare lifts
0.0 ms (knob 0: 0.9-1.4 ms). 10 lifts + join/resolve/identity in one process: peak footprint
383.75 MB on vs 383.76 MB with knob 0, i.e. no more memory than stock.

## Tried and rejected

- Keeping the stock `Program` return and caching inside `zkr.rs` only: this cannot share anything,
  because each call must hand out a new owned `Program` (24 MB clone ≈ the `from_encoded` cost). It
  also leaves the C16 / C11 / C13 call sites that need `&Arc<Program>` broken.

## Open issues

- Fix round 1 removed the cross-name bound (CAP 8). The memory bound is now stock 3.1's own: one
  copy per used zkr (all 32: ~470 MB). Programs a prover's ctrl cache still holds share the
  cached `Arc`, so they are not a second copy.
- The fix-round-1 A/B used comb at gpu-run's 16 GiB default for the mixed stream and 4 / 8 GiB
  for the steady lift/join; the full-machine budget (`--no-budget`) was not re-measured (the
  first round's "default" was also 16 GiB).

- The capture A/B replays 3.0 programs (the C11 captures). The zkvm-path A/B uses the real 3.1
  lift/join programs and agrees with it (lift -1.3 to -2.0 ms, join -2.1 to -2.6 ms).
- The knob name says METAL, but the cache applies to every backend (the code is in `zkr.rs`).
- The `get_zkr` signature differs from stock 3.1 (`Arc<Program>`, as in fork 3.0). zkvm source
  is unchanged, because `.into()` accepts both. An external caller that needs an owned `Program`
  must use `(*get_zkr(..)?).clone()`.
