## Summary
- **Cause (phase 1, ~90 % confidence, see below):** an Apple GPU back-end compiler or hardware
  defect, not our code. A private (thread) array that was default-constructed through a
  constructor and is then written element by element in a non-unrolled loop whose body calls a
  noinline function loses the store of the last iteration. The element reads back its constructor
  value. In witgen this is `exec_ToBits_5__W` (DynPo2 of the Mul0/Div0 shift cycles). Bit 4 of the
  shift amount reads 0, so `checkU16` (col 30) becomes 1/2 = `0x3c000001`, the s0/s1/byte columns
  shift, and the u16 lookup faults (`0x2`).
- **Workaround (this branch):** `witgen_tu_gen.py` makes `cuda2metal.py` unroll every `map()` and
  `reduce()` of the witgen call graph into straight-line blocks. Each element's value goes into its
  own scalar, and the map's array is brace-initialized from those scalars. No array is
  default-constructed and then written in a loop. The generator refuses any loop in the translated
  call graph, so a later steps.cu that brings a new loop shape fails the build instead of shipping
  the defect. The CUDA output (`witgen_tu.cu`) is byte-identical, and the other generated TUs
  (steps.metal, accum_tu.metal in its default always-inline mode, eval) keep the loop lowering.
- **Fix round 1:** the witgen TU also no longer compiles the shared `fpext.h`. The generator
  writes `witgen_fpext.h` next to `witgen_tu.metal`: the shared header's text with its 4-element
  loops unrolled and `pow(FpExt)` removed. `witgen.h` and `ef_fpext.h` include it in place of
  `fpext.h` when the TU defines `RV32IM_FPEXT_HEADER`. `witgen.h`'s `storeExt`/`loadExt` are
  straight-line, and its `map`/`reduce` loop templates are left out of the witgen TU. The two
  loops in the hand-ported externs are gone. A new test preprocesses the TU as compiled
  (`xcrun metal -E`, the build's include path) and fails on any loop outside the Metal SDK that
  is not in a reviewed list (`witgen_tu_gen.py --scan-loops`, `SCAN_LOOP_ALLOW`).
- **Fix round 2:** -O0 and -Oz still lost elems[3] of `PoseidonState.zcheck` (col 67) with no loop
  left in the source. Narrowed at -O0 by marking subsets of `witgen_fpext.h` always_inline: only
  the FpExt friend operators matter (`operator*(FpExt lhs, Fp rhs) { lhs *= rhs; return lhs; }`
  and relatives). The generated copy now marks every function of `witgen_fpext.h`
  `__attribute__((always_inline))` (honoured at every -O level) and builds the value constructors
  in place. A new test compiles the TU as built to LLVM IR at -O0 and -Oz and fails if any FpExt
  member, operator or `inv(FpExt)` is defined out of line (`witgen_tu_gen.py --scan-ir`).
- **Gate: met (round 2)** for the shipped build (-O2, noinline) and for every perturbation tried:
  -O0, -O1, -Os, -Oz, compiler-decided inlining (`WITGEN_TU_FNATTR=`) at -O2, -Oz and -O0. Each
  comparison has a same-session baseline that still fails. The figures are below.
- **GPU witgen is the default on Metal again.** `RISC0_METAL_RV32IM_CPU_PHASES=witgen` is the kill
  switch. `RISC0_METAL_RV32IM_GPU_PHASES=witgen` is still accepted and changes nothing. The
  "NOT bit-exact" warning is gone and the GPU bit-exactness tests are no longer ignored. A new
  regression test (`witgen_sorted_amplifier`) runs the sorted amplifier on an in-crate trace.
- **-Os and -O1 (fix round 1):** the round-0 fix failed there at a second site
  (`PoseidonState.zcheck`, col 67). The cause is the shared `fpext.h` element loops once Fp's
  operators are called out of line. With the witgen-only `fpext.h`: -Os sorted 0/360 over the 5
  gate segments against 35/360 for the round-0 shape, -O1 sorted 0/210 against 16/210. -O0 (and,
  found by the round-1 critic, -Oz) still failed at the same site; fixed in round 2.
- R16's open issues for R17 are fixed: the getDiffCount clamp, the in-memory `--check` of
  `witgen_tu_gen.py`, and one meaning per fault bit.

## Mechanism (what the evidence supports)
Measured:
- The failing value is always the last element written in the loop (ToBits<5>[4]; element 7 of
  an 8-element reproducer). It reads back the value the constructor stored.
- The LLVM IR / AIR is correct (alloca, stores after the call, loads after the loop), so the
  defect is below AIR.
- The rate depends on how much same-kind work runs concurrently, with a non-zero floor for one
  thread. Peeling the last iteration out of the loop (store after the loop) makes it far worse:
  331672 bad rows in 8 sorted calls. Unrolling the whole map into scalars removes it.
- With -Os and -O0 front ends, the same class of failure appears in another value:
  `PoseidonState.zcheck` (an `FpExt` at cols 64-67) in Poseidon0 minor 2 rows. Only col 67 differs
  (element 3, the last). An instrumented build showed that no `STORE` or `NondetReg` writes col 67
  directly, so it is the 4th element of `STORE_EXT`. `fpext.h`'s
  `for (i < 4) elems[i] *= rhs` loops (FpExt * Fp) call `Fp::mul` out of line at -Os. That
  is the trigger shape again. A witgen-TU-only copy of `fpext.h` with those loops unrolled gives -Os
  0/40 plain + 0/30 sorted, against 5/40 for the same-session -Os build. At -O0 even the
  straight-line version fails (7/20 against 9/20): at -O0 every local is in private memory.
- Fix round 1 (critic): the round-0 fix also failed at -O1 at the same site (13/100 sorted). With
  the shipped witgen-only `fpext.h` (below) -Os and -O1 are clean (gate table). At -O0 it still
  fails, 8/40 sorted, col 67 only. Building the three thread-space `FpExt` value constructors in
  place (member initializer instead of default construction plus element stores) did not change
  that (6/40, same session), so it was not kept in round 1 (round 2 keeps it as hygiene; the
  fix there is always_inline, see below).
- Fix round 2 (critic: -Oz fails 35/150 sorted with the round-1 copy; -O0 as before). All
  measured at -O0 with the sorted amplifier on the primary segment, each batch with the round-1
  build in the same batch (`R17/fix/r2/summary.txt`, runs `a1`-`a4`):
  - The wrong col-67 value is the right one times a field constant that is the same for rows with
    the same inputs (row 5: cpu 0x444fc4f2, metal 0x21ee5e5c; row 18: the same factor). So a
    multiplication of element 3 is lost, not a constructor value read back.
  - Without always_inline, the -O0 and -Oz IR has FpExt's operators, constructors and the
    array-constructor loops of `Fp elems[4]` (`FpExt()`), `r0::array<Fp, N>` and the
    `*Struct` default constructors as separate functions; at -O2 most are inlined
    (`tools/irloops.py`). The source loop scan does not see these IR-level constructor loops.
  - Removing every IR loop (a witgen-only trivial `Fp()` plus in-place FpExt constructors: 0 back
    edges in the -O0 IR) does **not** fix it: 4/20 (round 1: 3/20). In-place constructors alone:
    7/20. So at this site the loop is not the trigger.
  - always_inline on every `witgen_fpext.h` function: 0/25 + 0/30 at -O0, 0/25 at -Oz (round 1
    6/25, 4/30; -Oz 2/25). Subsets: compound-assignment members only 6/30 (fails); all but those
    0/30 + 0/30; constructors only 5/30 (fails); the hidden-friend operators only 0/30 (round 1
    3/30). always_inline without the in-place constructors: 0/30 at -O0 and at -Oz.
  - So the trigger is an out-of-line call to a friend operator such as
    `operator*(FpExt lhs, Fp rhs) { lhs *= rhs; return lhs; }`: a by-value private aggregate
    written element by element and returned. Inferred: the last element's store is lost, the same
    defect as the map loops, without a loop. A loop-free source is therefore necessary but not
    sufficient; the round-2 guard checks the compiled IR instead.
Inferred (not provable without an AGX ISA disassembler): a missing wait / ordering hazard between
a private-memory store and a later load of the same address after a call, in the Apple G17 (M5)
back end or hardware.

## The workaround in the generator
- `cuda2metal.py`: `translate(..., map_lowering='loop'|'unroll')` (lambda pass). `'unroll'` emits one
  `{ ... }` block per element in element order, so the calls' side effects keep their order. Each
  element's result goes into `c2m_rK_j`, and the array is built as `T x = {{c2m_rK_0, ...}}`. A
  reduce threads `c2m_accK_0..N` through the blocks. N comes from the array typedef. Counts:
  `lambda.map.unroll`, `lambda.reduce.unroll`. There are two new selftest cases.
- `witgen_tu_gen.py`:
  - unroll is the default.
  - `--map-lowering loop` emits the old shape, only to build a failing baseline.
  - The pins include the `.unroll` counts.
  - `gen_metal()` raises `TranslateError` when the translated graph has any `for`/`while`/`do`,
    and `--no-pin` does not waive this.
  - `--check` (CUDA mode, CI) now runs `gen_metal()` in memory with the pins.
  - The script is importable (`main_cuda`, `__main__`).
- Cost: witgen_tu.metal grows from 19.3k to 25.6k lines. The witgen TU compiles in about 8.5 s
  outside cargo (the old TU was not timed side by side). The median call time of
  `witgen_segment_file` par on the primary segment is 59 ms (min 54), against 57 ms (min 57) for
  the baseline.
- Fix round 1, `witgen_fpext.h` (`witgen_tu_gen.py gen_fpext`, run by `--metal`; build.rs passes
  `--fpext-src $OUT_DIR/witgen_fpext_src.h`, the exact text risc0-build-kernel stages into `_sys_`
  from `METAL_INCS`; `--check` uses the source tree's `build_kernel/kernels/metal/fpext.h`):
  - every `for (uint32_t i = 0; i < 4; i++) { ... }` is replaced by its body for i = 0..3 (11
    loops: zeroize, `+=` x3, `-=` x3, `*=(Fp)` x3, `==`), and `pow(FpExt, size_t)` (a while loop
    that stores a whole FpExt after an FpExt multiply; unused by witgen) is removed, so a future
    use fails to compile. Pinned in `PINNED_FPEXT`. A loop left over fails even with `--no-pin`.
  - The copy keeps `#pragma once` and defines `RV32IM_WITGEN_FPEXT`. `witgen_tu.metal` defines
    `RV32IM_FPEXT_HEADER "witgen_fpext.h"` before `witgen.h` and `#error`s if
    `RV32IM_WITGEN_FPEXT` is not defined afterwards. If the shared header were also included,
    `FpExt` would be defined twice and the TU would not compile.
  - `witgen.h` and `ef_fpext.h` include `RV32IM_FPEXT_HEADER` when it is defined, else `fpext.h`
    as before. The shared `fpext.h` and every other kernel are unchanged.
- Fix round 1, rv32im-sys headers and externs:
  - `witgen.h`: `storeExt`/`loadExt` are straight-line (same loads and stores, same order; this
    applies to every TU that includes witgen.h, i.e. also accum_tu and rv32im_incs: the suite's
    accum and seal tests pass). The `map`/`reduce` templates are inside
    `#ifndef RV32IM_NO_MAP_TEMPLATES`, which witgen_tu.metal defines.
  - `METAL_EXTERNS`: `externW_getMemoryTxn`'s zero fill and `externW_bigIntExtern`'s 16-byte copy
    are brace-initialized instead of a default-constructed array filled in a loop.
- Fix round 1, `--scan-loops` (test `witgen_tu_preprocessed_loops_reviewed` in
  `rv32im-sys/tests/metal_generators.rs`): `xcrun metal -E` of the build's `witgen_tu.metal` with
  the build's include path; every `for`/`while`/`do` in text from a non-SDK file (line markers)
  must be in `SCAN_LOOP_ALLOW`. Today: fp.h `pow` (scalar Fp), the four `atomicCAS` retry loops
  of cuda2metal.h (device/threadgroup atomics), ef_fp.h `inv_chain` (`#pragma unroll`, scalar
  Fp), seq_exec.h's two position loops (fwd/rev_stepExec; one step per position, writes go to
  device memory). The test also checks that witgen_fpext.h and not `_sys_/fpext.h` is included,
  that an extra header loop is rejected, and that gen_fpext rejects a loop it cannot unroll and a
  pin change.
- Fix round 1, `accum_tu_gen.py --inline noinline` (the non-default fallback): its 6 maps called
  the noinline `back_*` functions in a loop, the trigger shape, so that mode now uses the unrolled
  lowering (pin `lambda.map.unroll: 6`) and refuses a loop in its graph. The default
  always-inline output is byte-identical (md5 46e6eafd...). The noinline metallib passes
  `accum` tests with `R9_ACCUM_REPEAT=3` (5 passed).
- `witgen_tu_gen.py` rejects unknown arguments (before, `--help` rewrote witgen_tu.cu).
- Fix round 2, `witgen_fpext.h` (gen_fpext, pinned `ctor.brace: 4`, `fn.always_inline: 50`):
  - every line that declares a function (`[static|friend|explicit ]constexpr ...`) gets
    `__attribute__((always_inline))`. Clang's always-inliner runs at every -O level, so no FpExt
    operation is ever an out-of-line call in the witgen TU, whatever the optimiser decides.
    Not waivable: a `constexpr` line without the attribute (a declaration shape gen_fpext does
    not recognise) fails even with `--no-pin`.
  - The thread-space constructors `FpExt()`, `FpExt(uint32_t)`, `FpExt(Fp)`, `FpExt(Fp, Fp, Fp,
    Fp)` initialise `elems` in the member initializer (no default construction of `Fp elems[4]`,
    i.e. no IR array-constructor loop, then element stores). Not the fix by itself (above), kept
    because it removes the original shape at no cost.
  - `--fpext-calls outline` leaves both out: only to build a same-session baseline.
  - `--scan-ir FILE.ll` and test `witgen_tu_fpext_always_inline_in_ir`: `xcrun metal -S
    -emit-llvm` of the built `witgen_tu.metal` at -O0 and at -Oz; any defined function whose
    mangled name is an FpExt member (`_ZN5FpExt...`), an operator with an FpExt operand or
    `inv(FpExt)` fails. Positive control in the test: the `--fpext-calls outline` copy at -O0 is
    flagged (`_Zml5FpExtS_`, ...). The test also checks that gen_fpext refuses an unmarked
    `constexpr` line. Today, the built TU has no out-of-line FpExt operation at -O0, -O1, -O2,
    -Os, -Oz, or with compiler-decided inlining. At -O2 the round-1 copy still had
    `operator*(FpExt, FpExt)` out of line.
  - Cost: none measured. `witgen_segment_file` par, primary, 2 x 30 calls each, run alone: median
    56 / 56 ms (min 53-54) against 56 / 57 ms for the round-1 copy. The witgen TU IR at -O2 has
    204 functions (round 1: 205).
- Not used: a trivial `Fp()` (it fails with compiler-decided inlining: here 8/8 sorted calls,
  65693 rows). `#pragma unroll` (phase 1: worse). The last-iteration peel (worse).

## R16 issues addressed to R17
- **getDiffCount bounds (R16 finding 1):** `PreflightTrace.cyclesLen` (preflight.h, Metal only;
  set by witgenStep, 0 in accum, `p.rows` in r1_check). `externW_getDiffCount` clamps and sets the
  new `RV32IM_FAULT_DIFF_COUNT_INDEX` (0x80), yielding 0. Test `witgen_diff_count_fault`: a cycle
  column at 2^24 gives "getDiffCount cycle out of range".
- **`--check` translates in memory:** see above. New test
  `witgen_check_detects_pin_mismatch_and_loops`, and `generator_ci_checks` asserts the new line.
- **Fault bit 0x20 (R16 finding 9):** all kernel-specific bits are now in `cuda_compat.h` with one
  meaning each: `CYCLE_INDEX` 0x20 (witgen), `ACCUM_PERM` 0x40 (was 0x20; `accum.rs` updated),
  `DIFF_COUNT_INDEX` 0x80. The generators' `#ifndef` defines are removed. `describe_fault` derives
  the "unknown bits" mask from its table.

  are removed. A `#[cfg(test)]` launch-order hook (`test_perm`) binds `usePerm` for the
  parallel launches. Production always runs `start + i`.

  - `LaunchOrder` (plain / identity / sorted; a thread-local, or `RISC0_METAL_WITGEN_PERM` for

  - `witgen_sorted_amplifier`: a po2 20 shift/mul/div loop (`shift_loop`), 4 sorted calls,

  - `witgen_default_path` replaces `witgen_default_is_cpu`.
  - `witgen_matches_cpu`, `_riscv`, `_large` and `witgen_single_buffer_matches_cpu` are no longer
    ignored.
  - `RISC0_METAL_WITGEN_DUMP_ROW=1` dumps the first bad row (in/cpu/metal).
- `mod.rs`, `integration_tests.rs`: docs, and the phase label comes from `cpu_witgen()`.

## Re-verifying after a macOS or Metal toolchain update
Scratch scripts: `R17/fix/r2/mk.sh` (variant metallibs; also writes the TU's LLVM IR and
counts its loops) and `R17/fix/r2/repro.sh` (counts bad calls; set `TBIN` to a pinned copy of the test binary: other builds in the same target dir change
which `risc0_circuit_rv32im-*` file is newest).
1. `source ~/zkminer/env.sh`, then build the rv32im tests:
   `cargo test -p risc0-circuit-rv32im --features metal --lib --no-run`, and copy the binary.
2. `cargo test -p risc0-circuit-rv32im-sys --features metal`: the pins, `--check`, the loop
   scan of the preprocessed witgen TU (`witgen_tu_preprocessed_loops_reviewed`) and the IR scan
   (`witgen_tu_fpext_always_inline_in_ir`). The loop scan is necessary, not sufficient: round 2
   failed at -O0/-Oz with no source loop.
3. Regression test: `<bin> witgen_sorted_amplifier --nocapture`, with
   `RISC0_METAL_WITGEN_AMP_REPS=20`. It must pass.
4. Same-session baselines that still fail:
   - `mk.sh base_O2 loop shared` (the original shape), `mk.sh r0_Os unroll shared -Os` (the
     fpext.h loops) and `FPX_CALLS=outline mk.sh r1_O0 unroll own -O0` (the out-of-line FpExt
     operators; same with -Oz); by hand: `python3 kernels/cuda/witgen_tu_gen.py --metal -o <dir>
     --map-lowering loop`, delete the `RV32IM_FPEXT_HEADER` define and the `#error` block, compile
     with the build's include path (`-I $OUT_DIR/_sys_ -I kernels/metal -I <dir>`) and link with
     the build's other `.air` files;
   - step 3 with `RISC0_METAL_RV32IM_METALLIB=<base_O2 lib>` should fail. If it no longer fails,
     Apple may have fixed the defect: run `minrepro/feedback/build.sh` to check.
5. Real segments, fix vs baseline: `RISC0_METAL_WITGEN_SEGMENT=<postcard>
   RISC0_METAL_WITGEN_REPS=200 RISC0_METAL_WITGEN_MODES=par <bin> witgen_segment_file
   --nocapture`, and the same with `RISC0_METAL_WITGEN_PERM=sorted`. Segments:
   `R8/fix1/segs_torture20/seg0.postcard`, `R11/fix2/segs_{torture,sha,merkle}/*.postcard`,
   `w4/R12-adv/segs_ecdsa/seg170_po218.postcard`.
6. Perturbations (sorted, primary and sha, 30+ calls each, paired with `r1_*`/`r0_*`/`base_*`
   at the same level): `mk.sh fix_<L> unroll own -<L>` for L in O0, O1, Os, Oz, and
   `mk.sh fix_auto unroll own -O2 -DWITGEN_TU_FNATTR=` (also at -Oz and -O0). All must be 0. The
   -O0/-Oz baselines fail at only 5-20 % of calls, so use 100+ calls there.
   A new failure at any level means the back end changed: localise it before shipping (the
   per-row cpu/metal values in the log; `RISC0_METAL_WITGEN_DUMP_ROW=1`), and compare the
   failing level's IR (`mk.sh` writes `witgen_tu.ll`) with -O2's.

## Open issues
1. **P1 (assurance, other kernels): the shared `fpext.h` element loops.** The
   `for (i < 4) elems[i] op= x` loops (`operator*=(Fp)`, `+=`, `-=`, zeroize; build_kernel
   `kernels/metal/fpext.h`) have the defect's shape when Fp's operators are not inlined: in every
   function at -Os/-O1/-O0, and possibly at -O2 where the inliner declines. Witgen no longer
   compiles them (round 1). Measured there: they caused the -Os/-O1 zcheck failures (35/360 and
   16/210 sorted with them, 0/360 and 0/210 without). Not measured: zkp, recursion, keccak, the
   eval kernels and accum_tu, which still use them. Proposal for the owner of the shared headers:
   unroll them in `fpext.h` itself (no semantic change; `gen_fpext` shows the exact text), then
   rerun those crates' Metal suites. Round 2 adds a second shape these kernels still compile:
   FpExt's hidden-friend operators (`lhs *= rhs; return lhs;`) when called out of line, which the
   shared header does not prevent (at -O2 `operator*(FpExt, FpExt)` stays out of line in the
   witgen TU without always_inline). The same `always_inline` marking and the `--scan-ir` check
   would apply. The other generators' outputs (recursion steps/eval, keccak
   witgen arms and eval stages) were not audited for loops that call noinline functions; the
   `--scan-loops` approach could be reused there.
2. Closed in round 2: -O0 (and -Oz) failed at the zcheck site; fixed by the always_inline FpExt
   copy (gate above). Not pinned to -O2: every level tried passes, so no level is refused.
   Inferred: the shipped build is correct because no call shape that loses a store remains in
   it, as far as the evidence reaches (the source loop scan, the IR scan, and the amplified
   gate at six code-generation settings). A toolchain update could expose a shape that none of
   these checks covers; rerun the recipe above after one. The same holds for the remaining
   out-of-line by-value aggregates (`storeExt(FpExt)`, `eqz(FpExt)`, `exec_*ExtReg_W(FpExt)`,
   `inv_0(FpExt)`), which take an FpExt but do not modify and return it; no failure was measured
   at them.
3. P2: remaining relatives of the shape in witgen, not loops and with no failure measured: private
   aggregates default-constructed and then assigned after a noinline call in a block (the
   unrolled `c2m_rK_j` temporaries, 18 `NondetRegStruct` mux results, `NondetRegStruct16Array` in
   BigIntStep, the Poseidon `Val24Array` reduce accumulators). Emitting them as declarations with
   initializers would remove the last default construction; not done because nothing points at
   them and -O0 did not change with the FpExt equivalent.
4. P2: `cargo clippy -p risc0-circuit-rv32im --features metal --tests` stops at the
   pre-existing clippy errors in rv32im-sys `build.rs` (R16 finding 14, not R17's).
5. P2: the in-crate regression test `witgen_sorted_amplifier` catches the map-loop shape but not
   the zcheck site (its trace has no Poseidon rows with a non-zero zcheck that hit it: r1_O0 passes
   20/20). The IR test guards that site instead.
6. P2 (pre-existing, not R17): above `RISC0_METAL_MAX_WORKING_SET_BYTES` the zkp allocator panics
   instead of returning an error; `prove_po2_sweep` catches the panic. Round 1 called these
   "clean budget errors".
7. The Apple feedback package is ready in `minrepro/feedback/`. Filing it is the user's decision;
   nothing was sent.
