## Problem

risc0 3.1's `recursion-sys/kernels/cuda/step_exec.cu` is zirgen's monolith (41,663 lines, no
`__noinline__`). The 3.0 fork (F30 `68b3eacbb`) checked in a 19-arm `__noinline__` split (53,092
lines) made by `split_step_exec.py`, `split_macro_ops.py` and `split_micro_ops.py`; release-3.1 deleted
those scripts (`32e072f62`). C2's `cuda2metal_steps.py` and its pins (and C6/C14, R17's recursion
section) assume the split, so on the merged tree it failed `arg_param 5/119`, `ctx_param 1/39`,
`qual.noinline 0/38`, `assert 4380/4373`, `device_auto_ref 1770/1768`.

No profile or A/B: this item restores the 3.0 kernel structure on the 3.1 circuit and changes no
code path's speed by itself. The kernel text it produces is the same form C2 shipped (19 arms, same
dispatch); only the 3.1 circuit's content differs (below).

## Generator: `recursion-sys/kernels/cuda/split_step_exec_metal.py`

One script (stdlib only, ~0.05 s per split) that does the three fork passes in sequence, in memory:

1. `step_exec` -> dispatcher + 7 arm functions (`micro_ops`, `macro_ops`, `poseidon2_{load,full,
   partial,store}`, `checked_bytes`; selector columns 1..7). Each arm function repeats the constants
   block, then the arm body, then that arm's blocks from zirgen's tail section.
2. `step_exec_macro_ops` -> dispatcher (write_addr prologue, dispatch, macro tail) + 9 sub-arms
   (`wom_init`, `wom_fini`, `bit_and_elem`, `bit_op_shorts`, `sha_{init,fini,load,mix}`,
   `set_global`; columns 9..17).
3. `step_exec_micro_ops` -> dispatcher + `micro_inst0..2` (opcode columns 8/12/16; inst1/2 re-read
   write_addr).

The cut points and every emitted line are the fork scripts' own; only the detection is new.

**Auto-detection** (the fork scripts hard-coded `x8811`, `x1726`, ..., which zirgen renumbered by +12
in 3.1):

- arms: lines at brace depth 1 of the function body matching
  `auto xN = arg0[C * steps + ((cycle - 0) & mask)];` followed within 5 lines by `if (xN != 0) {`.
  The arm's name comes from zirgen's `loc(..)` comment above the read (`select(OneHot)/<name>(Reg)` at
  the top level, `opcode(OneHot)/<name>(Reg)` inside macro_ops). A guarded read without such a comment
  is allowed only after the last arm (macro_ops' tail has one: `arg0[8]` under `component.cpp`).
- constants block: the contiguous `Fp xN(v);` run from `Fp x0(`, numbered 0..K (K = 311 on both 3.0
  and 3.1).
- micro: the `inst[k](recursion::MicroInst)/opcode(Reg)` reads, the `arg0[0 * steps` write_addr read
  next to inst 0, and the `write_addr + one` / `write_addr + two` transitions, where `one`/`two` are
  the constants with value 1 and 2 (x310/x309).

**Fails loudly** (`SplitError`, exit 1, which panics build.rs): detected (name, column) lists differ
from the expected 7 / 9 arms, arms overlap, micro opcode reads differ from [(0, 8), (1, 12), (2, 16)],
constant 1 or 2 missing or duplicated, constants not numbered 0..K, the write_addr read outside
inst0, an input that already contains `__noinline__`, a result without exactly 38 noinline
declarations + definitions, a micro write_addr line that is not a plain current-cycle `arg0[0]`
read (fix round 2: before, a `(cycle - 1)` read there raised a Python `AttributeError` instead of
`SplitError`), **any line the split would drop** (coverage check, below), or **any non-pure line the
split would emit more than once per cycle** (duplication check, below).

**Coverage check (fix round 1).** The first version only checked that the expected arms exist; it
silently dropped any statement zirgen might emit outside the places it copies (between arms, after
the constants, unguarded in the tail, in a tail block guarded by a non-selector, before
`step_exec`'s closing brace, between macro sub-arms, before micro inst[0]), and the
`cuda2metal_steps.py` pins still passed because they count the split output (review finding;
reproduced: `scratch/w8/P31-07/fix1/repro.py` + `repro.log`, all 8 placements returned without
error and the probe was absent from the output). Each of the three passes now accounts for every
line of the function body it cuts (`Coverage`): a line is either copied into the output (`take`) or
is one of the shapes the split regenerates or deliberately drops, checked by exact text (`drop`):

- the preamble `uint32_t mask = steps - 1;` / `Fp extern_args[96];` / `Fp extern_outs[32];`
  (re-emitted in every function);
- per arm: its `loc(..select(OneHot)/<arm>(Reg))` (or `opcode(OneHot)/<sub-arm>`) comment, the
  selector read `auto xN = arg0[C * steps + ..]`, `assert(xN != Fp::invalid());`,
  `if (xN != 0) {` and the arm's closing `}` (same indent);
- per tail block: its body-level `  if (<arm selector> != 0) {` and closing `  }` (tail blocks are
  now matched only at body level by exact text; before, a substring match anywhere in the tail);
- blank lines.

Any other uncovered non-blank line raises `SplitError` naming up to 5 lines. (Line numbers in a
macro_ops / micro_ops error refer to the intermediate text after the previous pass.) Lines outside
the function being cut are copied verbatim by construction. On UP30 and 3.1 the check passes with the
outputs unchanged (UP30 -> F30 sha256 and the 3.1 sha256 are the same as before the fix).

**Duplication check (fix round 2).** Coverage alone stops statements from vanishing, not from being
copied. `split_macro` emits macro_ops' prologue (the lines between the constants and the first
opcode sub-arm: today only the write_addr read `auto x1361 = arg0[0 * steps ..]` and its assert, plus
the wom_init loc comment) in the dispatcher **and** in each of the 9 sub-arm functions the dispatcher
calls, so it runs twice per macro cycle (F30's design). Any side-effecting statement zirgen put there
(an extern call such as `readIOPBody` / `womRead` / `plonkWrite_wom`, a witness write) would run twice
and the generator still exited 0 (review round 2; reproduced with the reviewer's
`scratch/w8/P31-07-rev2/host/repro_prologue.sh`, which inserts `extern_args[0] = x1361;
extern_readIOPBody(..)` there: the round-1 generator exits 0 with 4 vs 13 `readIOPBody` and the host
differential harness reports 275/2000 mismatching cycles, exactly the macro_ops cycles; copy and
log in `scratch/w8/P31-07/fix2/{repro_prologue.sh,repro.log}`: round-1 generator rc 0, new generator
rc 1 with `step_exec_macro_ops: 2 line(s) would run more than once per cycle`).

The fix is general rather than specific to the prologue: `Coverage.take(lo, hi, copies=n)` records
how many times each source line is emitted (overlapping takes add up) and `finish` raises
`SplitError` for every line emitted more than once that is not side-effect free (`PURE_RES`):

- blank lines and `//` comments;
- constants `Fp xN(v);`;
- code-column reads `auto xN = arg0[C * steps + ((cycle - 0) & mask)];` (arg0 is never written by
  step_exec; witness/data reads such as `arg2[..]` are refused, since a copy executed elsewhere could
  observe a different value);
- `assert(xN != Fp::invalid());` (re-checking a value is idempotent);
- pure SSA arithmetic `auto xN = xA op xB;` with op in `+ - *`.

Anything else (an `extern_*` call, `extern_args[..] =`, `auto& reg =`, a brace, an `if`) fails. The
emitted-more-than-once sets are: the top constants block (7 arm functions), the macro constants
(9 sub-arms + the dispatcher when it has a tail), the macro prologue (dispatcher + 9), the micro
constants (3 instances + the dispatcher when it has a tail) and a comment line shared by two adjacent
micro instructions (inst1/inst2 start one line back when it is a comment). The micro write_addr
re-read in inst1/inst2 is generated text, a pure `arg0[0]` read whose source line is now checked
to have that exact shape. Top-level tail blocks and the macro and micro tails are emitted exactly
once. On UP30 and 3.1 the check passes with both output hashes unchanged.

Two semantic properties the split inherits from F30 (not regressions, stated for the record):
- the dispatchers test `arg0[col * steps + ..] != 0` without the monolith's
  `assert(xN != Fp::invalid())` on the 19 selector reads, so an invalid selector cell dispatches
  instead of asserting;
- tail blocks run right after their arm's body instead of in zirgen's tail order (macro, load,
  store, micro, macro, load, store, checked). That is equivalent only under the OneHot invariant of
  the selector columns (at most one of columns 1..7, and of 9..17 inside macro_ops, is nonzero per
  cycle), which the circuit enforces for valid code columns.

Detected on 3.1: `micro_ops=x312 macro_ops=x1360 poseidon2_load=x8823 poseidon2_full=x9228
poseidon2_partial=x10045 poseidon2_store=x11732 checked_bytes=x11862`; macro `x1362 x1363 x1364 x1738
x2061 x2527 x3427 x5764 x8666`; micro opcode reads `x313 x663 x1012`, write_addr `x314`, transitions
`+x310/+x309`. These are exactly the PORT_PLAN renumbering.

**Wiring.** `build.rs` (Metal block) runs the generator on `kernels/cuda/step_exec.cu` into
`$OUT_DIR/split/step_exec.cu` (written only when its text changes; `rerun-if-changed` on the script),
then runs `cuda2metal_steps.py ... --step-exec-src $OUT_DIR/split/step_exec.cu`. Nothing is written
into `kernels/cuda`. Without `--step-exec-src` (e.g. `cuda2metal_steps.py --check`, which the
recursion crate's `translator_steps_check` runs), the translator imports the generator and splits in
memory; `--check`'s round trip then compares with the split text. Both paths use the same function,
and the build's `$OUT_DIR/split/step_exec.cu` and `$OUT_DIR/metal/step_exec.metal` are byte-identical
to the standalone runs (`cmp`).

## Byte-exact regression (`--selftest`)

`split_step_exec_metal.py --selftest`:

1. decompresses `kernels/cuda/testdata/step_exec_up30.cu.xz` (UP30 `9fc79b9ef`'s `step_exec.cu`, blob
   `e0857d03`, sha256 `0377b13c...`), checks its sha256, splits it and requires sha256
   `964665e6a6cf5c6c...` = F30's committed split (`git show 68b3eacbb:.../step_exec.cu`, blob
   `f3117ffa`, 53,092 lines). **Passes**: the generator reproduces F30's split byte for byte;
2. applies 5 structural mutations to the UP30 input (a top arm renamed, a macro arm moved to another
   column, a micro instruction missing, the constant 1 missing, an already split input) and requires
   a `SplitError` for each. **Passes**;
3. (fix round 1) applies 8 drop mutations to both UP30 and the current 3.1 input, the review's
   placements located structurally (`drop_mutations`): an extern call between the micro_ops and
   macro_ops arms, between the constants and the first arm, unguarded in the tail, in a tail block
   guarded by `x5` (not a selector), before `step_exec`'s closing brace; a guarded witness write
   (`auto& reg = arg2[5 * steps + cycle]; assert(..); reg = x0;`) between the macro sub-arms, before
   micro inst[0], and unguarded in the tail. Each must raise `SplitError`. **Passes** (16/16). The
   old generator (HEAD 39f13484d) accepts all 8 and drops the statement
   (`scratch/w8/P31-07/fix1/repro.log`);
   (fix round 2) adds 4 duplication mutations at the end of macro_ops' prologue (before the
   wom_init loc), on both inputs: `extern_args[0] = x0; extern_readIOPBody(..)`, an unguarded witness
   write, a witness write guarded by `if (x0 != 0)`, and a witness read `auto x99999 = arg2[5 * ..]`.
   Each must raise `SplitError`. **Passes** (8/8; 24/24 placements in total). A sixth structural
   mutation (micro write_addr read at `cycle - 1`) must raise `SplitError`, not a traceback. **Passes**;
4. positive control: the same call inserted inside the poseidon2_full arm, inside the sha_mix macro
   sub-arm and inside a tail block is kept exactly once in the output (both inputs), and a pure line
   (`auto x99999 = x0 + x0;`) in the macro prologue is accepted and emitted 10 times (both inputs).
   **Passes**;
5. splits the current `step_exec.cu` and requires sha256 `ea7ae4820cc1cdfe...` (53,141 lines,
   `CUR_SPLIT_SHA256`), byte-identical to the PORT_PLAN scratch run of the renumbered fork scripts
   (`scratch/r31/split/se31_split.cu`). Before fix round 1 this hash was only printed; a zirgen
   re-emission now fails the selftest until the split and the steps pins are reviewed together.

The whole selftest takes about 1.6 s. `lzma` is imported only inside the selftest, so a Python built
without xz support can still run the build-time split.

`recursion-sys/tests/p31_07_step_exec_split.rs` runs `--selftest` and `cuda2metal_steps.py --check
--only step_exec` (pure Python, no feature, no GPU).

**Fixture choice: compressed input + embedded output hash.** The selftest must not depend on git
history: the crate is also built from shallow clones, tarballs and worktrees, where
`git show 9fc79b9ef:` / `68b3eacbb:` may be missing. Committing both files would cost 4.5 MB
(2.2 + 2.4 MB) of generated C++. The UP30 input xz-compresses to 61 KB; the expected output only needs
its sha256 (on a mismatch the error names the F30 blob to diff against with `git show`). The input's
own sha256 is checked too, so a corrupted fixture cannot pass silently.

## Monolith probe (optional; time-boxed, partial)

Translated the 3.1 monolith directly (`cuda2metal_steps.py --only step_exec --no-pin
--step-exec-src kernels/cuda/step_exec.cu`; it translates and compiles). Front-end compile
(`xcrun metal -std=metal3.2 -O2 -c`, same flags and includes as the build), 7 interleaved pairs,
load average 9.2 -> 5.3 (`scratch/w8/P31-07/fix1/fe_time.log`): split median 3.71 s (3.68-3.72),
monolith median 4.39 s (4.34-4.47). The round-0 note said "split 10.2 s vs monolith 5 s"; that
10.2 s does not reproduce and is withdrawn (the reviewer measured 3.77 vs 4.46 s medians
over 7 pairs, matching this rerun): the split's front end is slightly faster. Offline native code (`tools/metal_audit/agx_size.py`, `metal-tt` for this GPU), kernel
`parStepExec`, interleaved 4 pairs, load average 7-18:

| | native text | stack (incl. callees) | own frame | offline back-end time (4 runs) |
|---|---|---|---|---|
| split (19 noinline arms) | 841,002 B | 3,984 B | 112 B | 3.9, 2.8, 2.8, 3.3 s |
| monolith | 1,612,604 B | 3,680 B | 3,680 B | 18.2, 18.4, 21.7, 19.2 s |

The review re-ran this over 7 interleaved pairs (load 4.8-10.5) with the same sizes and stack and
back-end medians of 2.9 s (split) vs 18.7 s (monolith). The monolith has ~1.9x the native code and a ~6x longer offline compile (a proxy for cold PSO), with
about the same stack. Not run: cold PSO on the device and lift witgen time (the recursion crate does
not compile yet, above). Conclusion: no reason to switch; the split stays. No knob added for the
monolith, since the pins and C6/C14 assume the split; if someone revisits it, the translation command
above is the starting point and it needs an interleaved witgen A/B.

## Budgets and knobs

No runtime memory or code-path change: the step kernels have the 3.0 structure. No env knob: the
split is the only supported translator input (the pins enforce it), and there is no optimization to
revert. The generator itself is build-time only.

## Open issues

- The duplication check allows only the PURE_RES shapes in multiply-emitted lines; if zirgen ever
  emits another pure shape there (e.g. a division or a `(cycle - k)` read in the macro prologue), the
  build fails loudly and PURE_RES must be extended after review.
- The split relies on the OneHot invariant for the tail reordering and does not assert selector
  validity in its dispatchers (both as in F30; see the generator section).

- GPU witgen CPU-eq, `test_recursion_circuit`, `c10_tests` and the recursion R17 stress run in P31-08
  (blocked here by the eval pins and the recursion crate's 3.1 compile errors).
- `rec_fast_assert.cuh` (ROCm) mentions the step_exec assert count (4373); it is HIP-only and outside
  this item.
