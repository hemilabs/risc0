## What was ported, from where

Parallel mode (`StepMode::Parallel`), mirroring `recursion-sys/kernels/cuda/ffi.cu`
`HostExecContext` (constructor ~1066-1150, `applyHostChains` ~1150-1197, `doStepExec` ~1198-1235,
`verifyWom` ~1236-1300) and `risc0_circuit_recursion_cuda_witgen_chains` (1593-1617):

1. Encode into the open batch: `fault_word()` (zeroing blit), `blit_fill(womRows, 0xff)` and
   `blit_fill(womIndex, 0)` (CUDA `cudaMemset`s). `sync()`.
2. Host (shared memory): memcpy `wom`, `cycles`, `iops` into HAL scratch (`ScratchBuffers::cycles`
   and `WitgenScratch`, grown with C5's `grow`, 25 % headroom). The kernels advance
   `cycles[c].iopIdx`, so the caller's trace stays pristine (needed by the prewitgen and host-chain
   checks, which re-run the witgen on the same trace). With host chains: validate them (heads and
   cycles < numCycles, sizes, data width; error before any write), then mark heads
   `isParSafe = 2`, copy `womIndex[c]` and the 9 WOM rows per chain row, and scatter the data rows
   column-major with one rayon task per column (CUDA `markHostChains` / `scatterHostChains`,
   ffi.cu:687-702; plan 4.3 says CPU scatter in round 1).
3. Dispatch `parStepExec` (`Grid::Threads(numCycles)`, C1/C2 binding order 0..9), then
   `check_fault(Witgen)` (sync + read the fault word).
4. Host: `sort_wom_rows` over the shared `womRows` / `womIndex`: a port of `cxx/ffi.cpp`
   `sortWomFast` (counting sort on the address over the written slots `[c*9, c*9 + count[c])`,
   runs of equal addresses that are not all bit-identical finished by the full `operator<`,
   fallback to a full `par_sort_unstable_by_key` when an address is >= nv), then the
   exclusive scan. Comparisons use **canonical** values (`BabyBearElem::new_raw(w).as_u32()`), as
   CUDA's `asUInt32()` tuple and the CPU `operator<` (canonical addr + `Fp::operator<`) do; the
   device rows hold raw Montgomery words. Rows `[0, nv)` get the sorted rows, written slots past nv
   are reset to the invalid pattern, so the buffer equals what `std::sort` of all rows gives
   (invalid rows sort last on the CPU). Equal keys are bit-identical rows, so the unstable sort is
   exact. `RISC0_RECURSION_FAST_SORT=0` and `RISC0_RECURSION_FAST_SORT_CHECK` are honoured as in
   the CPU witgen. A count > 9 is an error (the kernel already faults on it).
5. Dispatch `injectWomBacks` then `parStepVerifyWom` in one batch with a fresh fault word, then
   `check_fault(Witgen)`.

Sequential modes: `SeqForward` / `SeqReverse` run C5's CPU path (copy of cycles, then
`risc0_circuit_recursion_cpu_witgen` on host views after a sync). Host chains apply only to
Parallel, as in CUDA. `fwdStepExec`/`revStepExec`/`fwdStepVerifyWom` are not ported (plan 4.3).

`upload_host_witness` (errata 8.4): size check (error on mismatch), `sync()`, then `view_mut`
memcpy into `data` / `global` (Intel's `copy_from_host` equivalent; no host shadow on unified
memory).

`RISC0_METAL_REC_WITGEN_CHECK=1` (new validation hook, off by default): snapshot `data`/`global`
before the Metal witgen, run the CPU Parallel witgen on the snapshot (with a copy of the cycles),
bail at the first differing element; prints `[recursion_metal_witgen_check] #n ...`.

C6 tests (`witgen/c6_tests.rs`), all on `test_recursion_circuit.zkr` (211 cycles) at po2 16 / 18:
- `witgen_parallel_matches_cpu_po2_{16,18}`: Metal vs `CpuCircuitHal` witness (raw words of
  `data` and `global`, first mismatch reported by column/row): plain; second call (scratch reuse);
  with the production host chains (min length 16: 1 chain); with every chain of >= 2 cycles on the
  host (2 heads / 150 rows, built with `risc0_circuit_recursion_cpu_chains`); caller's
  `trace.cycles` unchanged.
- `witgen_seq_modes_match_cpu`: SeqForward and SeqReverse equal the CPU, served by the CPU path
  (counter), and equal the Parallel witness.
- `witgen_fault_on_corrupt_trace`: (1) an `iopIdx` past the IOP table -> `Err` "recursion Metal
  Witgen: kernel fault 0x00000001"; (2) one WOM table element changed (`wom[1] += 1`) -> `Err`
  (fault); (3) a host chain cycle out of range -> `Err`; afterwards a good trace still matches.
- `prewitgen_and_shadow_check_hooks`: a prover run with a CPU host witness in the preflight, once
  with `RISC0_RECURSION_PREWITGEN_CHECK=1` and once with only `RISC0_RECURSION_SHADOW_CHECK=1`:
  the check regenerates through the Metal witgen ("host witness == HAL witness" printed), then
  `upload_host_witness` uploads it; output and globals equal the CPU prover's. A host witness with
  one corrupted data element fails with "prewitgen witness mismatch in data". Without the check
  the host witness is uploaded as is (no Metal witgen call) and the proof equals the CPU one.
- `upload_host_witness_rejects_wrong_sizes`.
- `prove_with_host_chains_check`: `set_host_chains_check(true)` around full Metal proofs at po2 16
  and 18: one check each, no mismatch.
- `wom_sort_matches_full_sort`: random rows (dense and sparse addresses, mostly consistent values,
  some conflicting), 1..70000 cycles, vs a stable full sort + scan; count > 9 refused.

Mutation check: not run separately. The equivalence tests would fail if the sort ignored the
value tie-break only on traces with conflicting values (covered by `wom_sort_matches_full_sort`,
not by real traces, which are consistent).

## Known gaps / not verified

- **identity_p254 + host chains check (not C6 code, blocks C9's un-ignore):** under `metal`,
  `host_chains_backend()` is true, so `WitnessGenerator::new` also computes host chains for the
  **CPU** prover used for `poseidon_254`; with `set_host_chains_check(true)` it then re-runs the
  witgen. `CpuCircuitHal::generate_witness` (hal/cpu.rs) passes the caller's trace to the CPU
  witgen, which advances `cycles[].iopIdx` in place (extern.cpp), so the re-run reads wrong IOP
  indices and fails with "eqz failed at: zirgen/circuit/recursion/wom.cpp:78". Verified: the
  same test passes alone without the check flag. Fix options (owner C9/C10, files not C6's): copy
  the cycles in `CpuCircuitHal::generate_witness` (as the Metal HAL and `host_witgen` do), or skip
  host chains / the check when the circuit HAL ignores chains.
- `test_recursion_host_chains_check` stays ignored on metal (zkvm tests file, C9); with C6 it
  passes for every Metal lift/join step and fails only on the CPU p254 step above.
- Real-size equivalence relies on the `RISC0_METAL_REC_WITGEN_CHECK` hook in the zkvm e2e
  (in-crate tests only have a 211-cycle program).
- The C1 `markHostChains`/`scatterHostChains` kernels are unused (CPU scatter per plan).
- GPU timings above come from a shared GPU.
