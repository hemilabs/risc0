## Summary
- **The split kernel is bound by its poly_mix table loads.** Each thread makes ~5300 loads from
  the table, all lanes reading the same address. The trace loads and the ALU work cost less.
- **Change (default on):** the table is bound as `const device` instead of `constant`. The
  NBETA-folded rows (pmn) are computed from the pm row (`-11 x` by additions) instead of loaded,
  which halves the table loads. The results are bit-exact (below).
- **Result (interleaved A/B, shared and loaded machine):** `ef_eval_split` takes about 27 % less
  time at po2 20 (medians 2052 / 1959 ms against 2806 ms; minimums 1525 against 2300 ms), about
  31 % less at po2 21 (5490 against 7968 ms), and about 24 % less at po2 19 under a 4 GiB budget.
  On a quiet machine this should save ~0.5 s of a ~2.6-3.0 s po2 20 segment. The quiet-machine
  baseline run settles the absolute numbers.
- **Runtime revert switch:** `RISC0_METAL_RV32IM_EVAL=evalfast_r12` runs R12's form
  (`ef_eval_split_r12`: the same generated TU compiled with `-DEF_R12_FORM`). Its PSO is built
  on first use. Build-time `-DEF_TAB_CONSTANT` / `-DEF_PMN_LOAD` select each half on its own for
  experiments.
- **The baseline `eval_check` PSO is now lazy** (R12 open issue, ~60 s cold). It is no longer in
  `METAL_KERNEL_NAMES` / `EXPECTED_KERNELS`; the host builds it the first time
  `RISC0_METAL_RV32IM_EVAL=baseline` selects it.
- **Rejected (numbers below):** `EF_THREADS` 64 (no change) and 256 / 1024 (slower); EF_WIDE off
  (~5x slower); the slab in threadgroup memory (hot words) or device memory; inlining the chain
  functions or the helpers (no gain, cold PSO up to 259 s); `metal::mulhi` instead of the 64-bit
  products (no change); the table in threadgroup memory; simdgroup-shuffle broadcast of table rows.
- **Correctness:** CPU == evalfast == evalfast_r12 == baseline, bit for bit, at po2 4/10/16/20.
  Seals equal on all six R11 po2 20 segments. `run_stress` rv32im_eval 0/30 with the defect
  control 10/10 wrong. `ir_scan` tier A = B = S = 0 at -O2 for both TUs.

## Profile before (WIP agent's measurements, re-checked where marked)
Tool: `ef_variant_bench` (`eval_check.rs` ef_tests, `#[ignore]`). One random po2 20 input. Each
dispatch is committed and waited for on its own, and the wall time of encode + GPU + wait is
taken per dispatch. Variants run interleaved (A B C ... per round), and every run is compared
bit for bit with the embedded kernel's first run. A Metal GPU-counter profile was not available
(no Xcode / Instruments), so the split was found by removing one part at a time. Logs are in
`logs/prof1.log`, `ldprobe.log`, `syn.log`, `pmn1.log` and `n11a.log`.

| Probe (po2 20, split ms, median [min]) | Value | Meaning |
|---|---|---|
| R12 kernel (`ef_eval_split`, 2 phases) | 2126 [2088] | load ~3-6 |
| `ef_combine` | 4.9 [4.0] | negligible |
| main chain only (`only0`) / LogUp only (`only1`) | 1684 / 462 | the main chain dominates |
| no trace loads (`noload`, results wrong) | 1844 | trace loads ~0.28 s |
| no table loads (`nopm`, results wrong) | 944 | **table loads ~1.2 s** |
| PSO: maxTotalThreadsPerThreadgroup / threadExecutionWidth / static TG mem | 128 (attribute) / 32 / 0 | with the attribute at 1024 the PSO still reports 1024, so register pressure does not limit occupancy to below 1024 |
| synthetic, 8x256 64-bit madw / 32-bit mulhi+carry / 32-bit mul (`syn0/1/2`) | 11.6 / 23.3 / 6.1 ms | on M5 the 64-bit `ulong` product is 2x **faster** than the mulhi form (unlike D0's microbench) |

Per thread, the chain makes 5357 table-helper calls (each loads one 16-byte row, and the FpExt
helpers also load the 16-byte pmn row) and 5974 trace loads. All lanes of a SIMD group read the
same table address. Register and stack usage are not exposed by Metal's PSO reflection, and
`metal-objdump` has no AGX disassembler, so they were not obtained.

- The A-vs-A spread (new against new2) is 5-15 % of the median. The new-vs-r12 difference is
  24-38 % of the median and 25-36 % of the minimum, beyond that spread in every run. `old` and
  `r12` agree within noise, so the r12 TU (anonymous-namespace prelude plus macros) reproduces
  R12's kernel.
- `ef_combine` is 1-25 ms in every variant; it is not worth tuning.
- Inferred, not measured with counters: `constant` loads with a runtime index are slower on this
  GPU than `const device` loads for this access pattern. Computing pmn halves the number of
  16-byte table loads per FpExt link, at a cost of ~10 integer adds.
- The bit-exactness argument for `ef_m11`: `-(8x + 2x + x)` with Fp's reducing add and sub gives
  the canonical value of `(P - 11) x mod P`. The map is linear, so this holds for Montgomery-form
  raw words as well. The host's `e * (P - 11)` is the same canonical value. The tests compare
  the outputs bit for bit (below).

### 2. Lazy PSOs for the non-default eval kernels (kept)
- `eval_check` (baseline) and `ef_eval_split_r12` are no longer built when the library loads.
  `eval_check.rs` `lazy_pipeline` builds a PSO from the loaded library on first use and caches
  it for the process; a failed build is returned, not cached.
- Cold PSOs (`MTL_SHADER_CACHE_SIZE=0`, load ~47): `ef_eval_split` (new) 44.0 s,
  `ef_eval_split_r12` 57.4 s, `ef_combine` 0.02 s. R12 measured 27 s for its kernel at lower
  load, so these are load-inflated. In the same session the new kernel is the faster of the two
  to build. Warm: 6-8 ms.
- The first-load cost of the default path drops by the baseline's ~60 s cold PSO.

  That is not measured (no such machine here).

## Dispositions of open issues addressed to R15 / this item
- **R12 "R15 (perf): EF_THREADS 64/256; mksm2-style threadgroup slab; inlining; slab in device
  memory":** all measured, none wins (table above). The bottleneck is the table loads, and the
  table change gives ~27 %.
- **R12 "R14/M1/K5: build the baseline eval_check lazily":** done (section 2). The
  `ArchivedKernels` hoist is not done; it is not needed now that the default path has one
  ~30-45 s cold PSO.
- **R12 "EF_WIDE stays the default":** confirmed (~5x).
- **R16 finding 10 (build-time Python, "open → R14/R15"):** not addressed by R15e;
  `regen.py --metal` still takes ~9.5 s. Left open for R14 or a later R15 sub-track.
- R4 (accum TG sweep), R5 (witgen inlining), R9 (window), R8/R11 (witgen single buffer) are
  other R15 sub-tracks, not R15e.

## Open issues for later items
- **P2, baseline / M5:** re-measure evalfast against evalfast_r12 on a quiet machine, and on an
  8-10-core part if available. All numbers here were taken at load 7-47.
- **P2, R17 follow-up:** at -O0 and -Oz both evalfast TUs have tier A/B/S findings, the same
  before and after this change (by-value FpExt helper and operator calls, e.g. `rk_cl0` returning
  `RkW`, `poly_fp`'s FpExt temporaries). Only -O2 is shipped, and it is clean and stress-clean.
  If evalfast is ever built at another level, harden it as R17b did accum_tu (always_inline
  FpExt operations).
- **P3:** the remaining table cost is ~0.65 s (probe: 950 ms with computed instead of loaded
  values, against ~1.6 s). Ideas not tried: two rows per thread to share each table load
  (generator change in the chain passes), and `metal::uniform<T>` hints.
- **P3:** with `MTL_SHADER_CACHE_SIZE=0` the new `ef_eval_split` cold PSO took 44 s under load
  (R12: 27 s at lower load). A K5-style binary archive would cut first-run latency on the minimum
  target.
