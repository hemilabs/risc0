## Summary
- **Change (default on): every poly_mix table row is read as half of one 32-byte `ulong4` load of its
  aligned row pair, instead of one 16-byte `uint4` load.** The words are the same, so the results are
  bit-exact. On the M5 Max the `ef_eval_split` kernel takes 58 % less time:
  - kernel A/B at po2 18, 11 rounds, quiet: 403.8 → 169.9 ms, 11/11 rounds;
  - eval_check phase in a po2 20 proof, 7 interleaved process pairs: **1606 → 699 ms** (median), 7/7;
  - segment median 2371 → 1646 ms, and 2315 → 1354 ms in a second 7-pair run (−0.8 to −1.1 s per
    pair; both runs shared the GPU with other agents' work).
- **Same win at po2 21 and at the simulated budgets.** Peak memory is unchanged.
  - po2 21: eval_check 4325 → 1831 ms, 6/7 pairs.
  - po2 19 under 8 GiB: 854 → 490 ms.
  - po2 18 under 4 GiB: 408 → 176 ms.
- **Revert knob:** `RISC0_METAL_RV32IM_EVAL=evalfast_r15e` runs R15e's form (`ef_eval_split_r15e`: the
  same generated TU compiled with `-DEF_R15E_FORM`, a lazy PSO). Build-time `-DEF_ROW_U4` keeps the
  uint4 loads in any TU.
- **Why it works is not known.** No AGX disassembler is available, so the machine code could not be
  read. The evidence points to a compile-wide regime switch in Apple's back end, not to cheaper loads:
  - 16-byte loads of two adjacent rows (`uint4` x2, or a 32-byte struct of two `uint4`) are no faster;
  - a `ulong2` (16-byte) row load is no faster;
  - straight-line ("hardened") table helpers on top of the `ulong4` loads fall back to the slow time.
  
  Section 3 has the numbers. The default build is in the fast regime at every po2 and budget measured,
  and in the cargo-built metallib.
- **Correctness:** all of the following hold with the new default:
  - CPU == evalfast == evalfast_r15e == evalfast_r12 == baseline, bit for bit, at po2 4, 10, 16 and 20;
  - seals equal on all six R11 po2 20 segments;
  - repeat runs: 0/30 differ at po2 20 (R17 `run_stress`), 0/6 at po2 21, 0/200 at po2 16;
  - the defect control fails 10/10 (the defect is present in this session);
  - `ir_scan` tier A = B = C = S = 0 for the three evalfast TUs;
  - the suite passes 2x in parallel and at 4 and 8 GiB;
  - the Metal validation layer is clean.
- **Finding for R17 (P1):** one variant that is *not* shipped gives wrong results deterministically:
  - the variant also reads the NBETA-folded row with a second `ulong4` pair load;
  - straight-line helpers make the same variant correct;
  - so the Apple back end miscompiles a code shape adjacent to the shipped one (section 4);
  - the default-on CPU bit-exact unit tests would catch a regression of this kind.
- **Rejected (numbers in section 5):**
  - all three Montgomery multiplication forms: Z9's `hi(t) - mulhi(m, P)`, the 32-bit `mulhi` form, and the
    cheap-mul ablation, which bounds the gain at 15 %;
  - k = 0 links as additions;
  - same-k link merging: its premise is false, there are no repeated rows inside one accumulator chain;
  - LogUp as a separate kernel;
  - `EF_THREADS` 32 / 64 / 256;
  - a `constant` table;
  - loading the NBETA rows;
  - by-value helper signatures, a context copy, unrolled helper loops, and witgen's inline fp/fpext
    copies;
  - the 32-bit (`EF_NO_WIDE`) accumulators.

## 2. Change: 32-byte row-pair loads (kept, default)
`to_metal.py` adds `EF_ROW(p, i)`.
- Default: `ef_row_pair(p, i)` loads `reinterpret_cast<EF_TAB ulong4*>(p)[i >> 1]` and returns the
  `.xy` or `.zw` half as a `uint4`, using `as_type<uint2>`.
- At the chain's call sites `i` is a compile-time constant. In the outlined helpers it is uniform.
- `ef_pm_at`, `rk_cl_acc` and `rk_link_k(FpExt)` read rows through it. This is the pinned `pm_rows`
  substitution, which stays at 2.
- With `-DEF_ROW_U4`, `EF_ROW` is the plain `p[i]`.
- `-DEF_R15E_FORM` implies `EF_ROW_U4` and names the split kernel `ef_eval_split_r15e`, with no
  `ef_combine`. `-DEF_R12_FORM` implies `EF_ROW_U4` as well, so R12's form is unchanged.
- The table must be 32-byte aligned. The host binds it at offset 0 of a pool buffer, which is
  page-aligned, and checks the address (`eval_check_ef_with`).

## 3. What the regime looks like (why "not known")
- Width does not explain it. A `ulong2` row load (16 B) is as slow as `uint4`. Two `uint4` loads of the
  pair, or a 32-byte struct of two `uint4`, are just as slow. Only the `ulong4` (32 B) load is fast, and
  a `ulong4` pair-of-pairs (`quad64`) is the same speed.
- Profile of the new default by ablation (`r18prof`, `r18prof2`, po2 18, 9 rounds, A = 167.3 ms):

  | Ablation | Δ vs A | Meaning |
  |---|---|---|
  | rows computed from k | +60 ms | Slower than the loads now. |
  | no trace loads | −21 ms | 12.5 % |
  | cheap Fp mul | −25 ms | 15 % |
  | no slab (dead stores removed with it) | −19.5 ms | ≤ 12 % |
  | `EF_NO_WIDE` | +616 ms | 4.5x slower |

  The kernel is now mostly ALU: links and Fp arithmetic.
- **Hardened helpers lose the win.** `hard.py` rewrites `rk_cl_acc`, `rk_cl0` and `rk_link_k(FpExt)` as
  straight-line code: no private `X[4][4]` matrix, no loops, and aggregates built by brace-init. The
  results stay bit-exact, but the kernel takes 411.7 ms against 162.5 ms (`hard2`, 11/11 slower). That
  is the R15e-form speed again.
- Splitting off the main chain (LogUp groups exit) also compiles into the slow regime: 255.6 ms against
  162.8 ms combined (`p32prof`).
- The PSO reports `maxTotalThreadsPerThreadgroup` 1024 for every variant compiled with the 1024
  attribute, fast or slow (`a1024`). Occupancy limits visible through the API do not explain the
  regimes.
- The rv32im binary archive of this build is 23.42 MB against 23.84 MB for the R15e build. The new
  `ef_eval_split` binary is ~0.4 MB smaller, so the fast regime is less code.
- Inferred, not provable without an AGX disassembler: a back-end decision such as spilling, the
  register budget or how loads are scheduled flips with small source changes. The 16-byte uniform loads
  land on the costly side.

**Consequence:** the 58 % depends on Apple's compiler.
- It holds on the cargo-built metallib, at po2 18-21, and at both budgets.
- A future toolchain could change it. The knob and the A/B tooling are there for that.
- Any change to the evalfast generator must be re-measured. A harmless-looking rewrite can lose it
  (the hardened helpers did).

## 4. A miscompile next to the shipped shape (for R17 / Apple Feedback)
Variant `r18_pmnld.metal` (scratch `src/`) changes one thing in the shipped TU. It reads the
NBETA-folded row from the table half `[EF_NPM, 2 EF_NPM)` with the same pair load
(`EF_PMN_ROW = EF_ROW(ctx.pm, EF_NPM + k)`) instead of computing it (`ef_nbeta`).

| Variant | Result |
|---|---|
| `pmnld`: b and n both from `ulong4` pair loads | **wrong**, every run (2/2, 1/1, 11/11), thousands of elements |
| `pmnA1`: b = `uint4`, n = pair load | correct |
| `pmnA2`: b = pair load, n = `uint4` | correct |
| `pmnu4` (`-DEF_PMN_LOAD`): b = pair, n = `ctx.pmn[k]` uint4 | correct |
| `pmnld_hard`: `pmnld` with straight-line helpers (`hard.py`) | **correct** |
| debug kernel: `ef_row_pair(tab, r) == tab[r]` for every row r < 2 EF_NPM (runtime r) | all equal |

- The LLVM IR of `pmnld` is correct: two `<4 x i64>` loads with the right indices, parity branches and
  phis.
- The source has no UB.
- So Apple's back end miscompiles this shape: two 32-byte loads feeding a private `X[4][4]` matrix that
  is read in a loop, inside an outlined helper.
- It is deterministic in our runs, unlike R17's rate-dependent defect.
- `ir_scan` does not flag it: no call in a loop, no by-value aggregate parameter written after a call.

R17 / D0 should add this to the Apple Feedback material. The reproducer is the shipped TU with the
one-line `EF_PMN_ROW` change above.

What protects the default:
- `evalfast_matches_cpu_po2_4/10/16` run in the default `cargo test` (not ignored) and compare every
  element with the CPU, so a generator change that lands on such a shape fails the suite;
- the seal-equality gate.
