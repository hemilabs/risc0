## #13 executor stream (implemented, default on; `RISC0_METAL_EXEC_STREAM=0` reverts)

`prover_impl/exec_stream.rs`, entered from `prove_with_ctx` (Metal builds without cuda/rocm):

- The executor still runs on the calling thread (`run_with_callback`), so every user callback in the
  `ExecutorEnv` stays on the thread that built it.
- The executor's own segment thread preflights each segment (overlapping the previous segment's
  `prove_begin`, as the loop's preflight thread did) and hands it over a rendezvous channel to a
  scoped proving thread, which runs the rest of the loop unchanged: `prove_begin` (returns the
  previous seal), the previous receipt's decode + verify on its own thread, and after the executor
  returns, `prove_end` and the parallel last-two verification (as `RISC0_TAIL_VERIFY`).
- The proving thread takes the GPU lock around each `prove_begin` only (fix round 1; it first held
  it for the whole stream, which deadlocked, see "Fix round 1"); the calling thread takes it for the
  last `prove_end` and the tail. A calling thread that already holds the lock takes the old path. The tail of `prove_session_impl` (journal/assumption merge, keccak proofs, composite,
  recursion, Groth16) was extracted unchanged into `prove_session_tail`, which both paths call, so the
  receipts are built by the same code.
- The calling thread's cached segment prover is lent to the proving thread and put back in the
  thread-local cache afterwards (`SendProver`, an `unsafe impl Send` with its audit in the code: the
  Metal prover holds only `RefCell`s/`Arc`s it owns, Metal objects, no thread-local state; one user at
  a time, ordered by spawn and join). So `release_hal_buffers` / Z12's release before recursion /
  the worker's `ReleaseOnDrop` still find it on the thread that proved. If the proving thread panics
  the prover is dropped, not reused; on any error the pending finalize is drained first (as
  `DrainSegmentProverOnExit`).
- `Stream::step`/`finish` mirror the loop's per-segment body and tail by hand (a cross-reference
  comment sits in `exec_stream.rs`). Loop behaviour the stream leaves out, none of which applies to a
  streamed Metal session: `session.hooks` (prove_with_ctx's own Session has none),
  `release_pool_on_po2_growth` (CUDA only), `RISC0_TAIL_VERIFY=0` (the stream always verifies the
  last two in parallel), `early_seal`/`rec_pipe` (CUDA/ROCm only).
- Old path kept for: the knob, a calling thread holding the GPU lock, a non-Metal rv32im prover, a coprocessor callback (its keccak proofs
  would run on the GPU during execution, beside the segment prover), assumptions, trace callbacks or a
  profiler, a segment path, a PoVW job. A guest that requests keccak proofs **without** a coprocessor
  cannot be detected before executing; it streams its segments and its keccak proofs run after them
  exactly as before (deviation from the brief's "keep the old path for keccak sessions": the only
  keccak sessions that can be kept on it up front are the coprocessor ones, and they are).
- Segments are no longer written to disk and read back (the old path wrote every segment of a
  session to a temp dir).

## Fix round 1 (review: two deadlocks)

Both found by the reviewer's adversarial tests; both hung forever on the stream, the old path
worked.

1. **Prove inside an io callback.** The proving thread held the (per-thread reentrant) GPU lock for
   the whole execution. A user callback on the calling thread that used the GPU (an `io_callback`
   that proves) waited for that lock, while the proving thread waited on the rendezvous channel
   that the blocked executor feeds. Fix: the proving thread takes the lock around each
   `prove_begin` only, never while waiting for a segment. The HAL takes the same lock around each
   of its own calls, so a GPU user that slips in between two segments only interleaves with the
   stream, as a second session thread already could (the review's 3-thread test). A nested proof
   in a callback builds its own segment prover (the calling thread's is lent to the stream), so two
   pools are resident for that corner case; the old path proved the nested session before any
   segment and reused one prover.
2. **Caller already holds `risc0_zkp::hal::metal::exclusive()`.** The proving thread can never take
   a lock the caller owns while the caller waits in the executor (per-step locking does not help
   here). Fix: `eligible()` takes the old path when
   `risc0_zkp::hal::metal::singleton().is_owned_by_current_thread()` (parking_lot; no zkp change).

Regression tests (in `tests_z17`, each in a thread with a 120 s timeout so a hang fails instead of
stalling the suite): `z17_prove_inside_io_callback` (outer session streams, the io callback proves
a 2-segment po2-16 session and verifies it), `z17_caller_holds_gpu_lock` (proves under the lock,
must take the old path). Negative control: with `exec_stream.rs` reverted to 23e8c8367 both FAIL
("no result in 120 s (deadlock?)", `w6/Z17-fix1/negctl_old.log`); with the fix both pass.

Also: `z17_stream_error_then_prove` used `segment_limit_po2(15)`, where the executor (pre-existing,
not Z17, reported by the review) splits a BusyLoop into ~44 user cycles per segment (thousands of
segments); it now uses po2 16 (BusyLoop 2^19, session limit 2^18).

Cost of per-step locking, interleaved A/B (A = 23e8c8367, B = fix; in-process
`z17_first_segment_probe`, po2 20, 4 segments/session, mean of the 2 warm sessions per run, 8 pairs
A B under the heavy lock, load 1.5-2.5): A 3.407 s [3.395-3.422], B 3.415 s [3.393-3.443], B-A
+0.011 s median [-0.028, +0.047]; A-vs-A (consecutive A runs) [-0.010, +0.014]. No change.

The lock gap at the end of the stream (proving thread joins, the calling thread re-takes the lock
for the last `prove_end`) is now the same as the gap between any two segments; taking the lock on
the calling thread before joining is not possible (the proving thread needs it for its last
`prove_begin`).

## Test memory (the "are your tests causing OOM?" question)

**Cause (fix round 2):** `CACHED_SEGMENT_PROVER` (prover_impl.rs, a thread-local) was wrapped in
`ManuallyDrop` (upstream, for CUDA context teardown), so on Metal a segment prover and its
`MetalHal` pool (up to half of `recommendedMaxWorkingSetSize`, ~9.4 GiB at po2 20) were never freed
when their thread exited. libtest runs every test on a fresh thread and almost no test calls
`release_hal_buffers`, so each proving test leaked its pool until process exit: the peak grew with
the number of tests, not the thread count. Z17's own tests added to it (`within()` starts one more
thread per regression test). The recursion provers' cache (`PROVER_CACHE`, rv32im-free) was never
`ManuallyDrop` and already dropped at thread exit.

**Fix:** on Metal-only builds (`metal` and none of `cuda`/`rocm`/`intel`) the slot is a plain
`RefCell`, dropped at thread exit; other builds keep `ManuallyDrop` unchanged. Nothing else
changes: long-lived threads (the worker) keep their prover as before, and only an exiting thread
frees its pool. A proof on the main thread that then exits (`examples/fib -i 300000`, 3 segments)
exits cleanly (rc 0), so the TLS destructor at process exit is safe (`w6/Z17-fix2/fib.log`).

Peak process footprint (`/usr/bin/time -l`, host + unified GPU memory), `host::server::prove::`,
every run alone under the heavy lock; before = a48a19a47 (`w6/Z17-fix1/`, and the review for the

## #19 commit-pool-keep: measured, not implemented

Worker (`prof/full_verbose.log`): the first segment of every job is 1171-1192 ms of `prove_begin`
(+19-28 ms preflight) against 1012-1018 ms for the others: **+160-200 ms per job**. The worker's wrap
(and M8's release before recursion) drops the segment prover after every job, so each job rebuilds it.

In-process probe (`z17_first_segment_probe`, po2 20, 6 sessions alternating kept / released prover,
`p19/probe1.log`, load 3.5): segment 0 `prove_begin` **1043 ms with the prover kept** vs **1198-1204
ms after `release_hal_buffers`** (session wall 3.41 vs 3.58 s). So ~157 ms per job is the rebuilt
prover (fresh pool allocation and first-touch of ~9.4 GiB, the code-group cache); ~30 ms is inherent.

Not implemented here: the only variant LEADS allows on 36 GB (a budget-gated background prefault)
needs a pool-prefault entry point in the zkp/rv32im HAL (not owned by Z17), and a time to run it:
in `--benchmark` the next job starts right after the wrap releases, so a prefault would have to
overlap the wrap itself (pool 9.4 GiB beside the wrap's 5.3 GiB). Worth ~1 s per suite (6 jobs) and
~0.16 s per production job; off at 4-8 GiB. Recommended as a follow-up owned by the HAL
(`prefault_pool(po2)`) plus M9 (worker sequencing). No knob `RISC0_METAL_POOL_PREFAULT` was added,
since nothing ships.

## #16 cross-job overlap: probe, NO-GO

Not measured with a GPU timeline in this item (the GPU was shared with other agents' locked runs).
From BASELINES 5c.2: identity_p254 is 865 ms of GPU in 918 ms, shrink_wrap 625 ms of GPU in ~690 ms,
so a warm wrap has ~120 ms of GPU-idle windows. After Z17 job N+1's execution overlaps its own
segments, so the only thing left to overlap into those windows is job N+1's first segment, which needs
its segment prover (9.4 GiB at po2 20) resident beside the wrap (5.3 GiB) and concurrent GPU work in
two provers (G12 saw a wrong G2 MSM under concurrent load). Value <= ~0.1 s per job (production
throughput only; 0 in the benchmark's STARK), risk high, memory stacking rules it out below ~20 GiB.
NO-GO.

## Open issues

- `SendProver` relies on the audit in its SAFETY comment; a `Send` bound on `SegmentProver` (rv32im)
  would make it checked by the compiler.
- With the stream, another thread (or a user callback) can use the GPU between two of this session's
  segments (per-step locking, fix round 1), as the HAL's per-call lock allows; the old path holds
  the lock across its whole loop. Harmless for correctness (the review's 3-thread test); for the
  single-job worker nothing else uses the GPU then.
- A nested proof in an io callback during a stream builds a second segment prover (two pools
  resident); acceptable for that corner case.
- Fixed in round 2: the ~37 GB `host::server::prove::` peak was the `ManuallyDrop` segment-prover
  thread-local leaking one pool per test thread (see "Test memory"). Still open: CUDA/ROCm/Intel
  builds keep `ManuallyDrop` (their teardown reasons; not testable here), so they still leak one
  segment prover per exited thread; `keccak_union` alone peaks at 13.2 GB (keccak path, not Z17).
- Pre-existing executor oddity (review): at `segment_limit_po2(15)` a BusyLoop is split into ~44 user
  cycles per segment (1<<16 cycles: 1538 segments, 50.4M total cycles); po2 14 and 16 are normal.
  For the executor owner.
