# P31-16: R17 / R17b / R18 gates on every regenerated 3.1 TU

Branch `metal/P31-16` (worktree `deps/risc0-3.1-wt-P31-16`), from `metal/P31-14` `e934aa6e4` (the merged
3.1 tree with P31-T1's tooling). Scratch and logs: `/Users/user/zkminer/scratch/w8/P31-16/` (`stress_*/` one
directory per locked run, `ir*_scan.{txt,json}` the scans, `r18/` the R18 variants, `base_loop/` and
`base_r1/` the same-session baselines, `logs/` the R18 GPU runs; the large `.ll`, `.air` and `.metallib`
files were deleted after the runs, and the scripts rebuild them).

This item changes no kernel, no generator, no prover path and no default. It adds gates to
`tools/metal_audit/` only, so there is no speed A/B and no revert knob beyond the gates' own
environment variables. Machine: M5 Max (32-core GPU), macOS 27.2, Metal toolchain 27B47. Every GPU
run went through `gpu-run` heavy, alone; load average 1.8-7.8 (other agents' CPU work).

## Summary

- **All R17 / R17b gates pass on 3.1.** At -O2 (the shipped level), every one of the 175 TUs has
  tier A = 0 and tier S = 0. The new tier P (R18's shape) is also 0. The tier B and tier Z findings
  are the same functions as on 3.0, so no new finding needs an explanation.
- **3.0 vs 3.1 IR scan: identical finding sets** at -O2, -O1, -Os and -Oz. This was compared by
  (unit, TU, tier, function), not only by count. At -O0 (keccak and zkp only) the one difference is
  14 extra tier-Z instances in zkp's `p254_fold_ref` / `p254_rows_ref`. These are reference test
  kernels, and the extra instances come from 3.1's x^7 Poseidon254 S-box; tier Z is informational.
- **witgen generator scans:**
  - `--scan-loops`, `--scan-ir` (six settings, plus `ir_scan --fail-tiers ABS`) and
    `--scan-metallib` all pass: 12/12 rv32im-sys generator tests.
- **R17 stress:**
  - witgen par: **0/1000** (5 segments x 200).
  - witgen sorted: **0/150**.
  - sorted amplifier plus sorted primary/sha at -O2, -O0, -Oz, -Os, -O1 and compiler-decided
    inlining (at -O2, -Oz and -O0): **0/90 at each of the 8 settings**.
  - Same-session baseline (`--map-lowering loop`): **30/30, 30/30, 30/30 bad**, so the defect is
    present and detectable.
  - `r17_accum_segment_stress`: 0/30 on 5 segments x 3 variants.
- **All other families pass:** rv32im eval, recursion (all 5 eval_check forms), keccak eval and
  witgen, zkp (71 lines, including tier Z), groth16, and groth16 tier Z. All 0/n.
- **R18 shape on the new eval TU:**
  - The shipped `eval_check_ef*` forms have one pair load per helper (`n` is computed from `b`).
    Tier P = 0.
  - New tier P flags R18's `r18_pmnld` (380 sites). It is a gate in `run_stress.sh` with a positive
    control.
  - **Finding (not blocking, P1):** on 3.1 / this toolchain, the one-pair-load variants that R18
    measured correct are now wrong too (A1 and A2, all elements, in some chain forms), while an
    address-identical variant passes. The shipped shape is still correct. Section 4 has the details
    and the repro.
- **No generator fix was needed.** All 3.1 TUs pass.

## 4. R18 shape on the new eval TU

Shape (R18 section 4): two 32-byte `ulong4` pair loads feed a private `X[4][4]` that an outlined
helper (`rk_cl_acc`, `rk_link_k`) reads in a loop. On 3.1, the generated `eval_check_ef.metal` keeps
R18's default `EF_PMN_ROW(ctx, b, k) = ef_nbeta(b)`. Each helper has one pair load (`b`), and `n` is
computed from `b`.
- Static: the IR of all 8 evalfast forms (and of everything else) has tier P = 0. The new tier P
  flags `r18_pmnld` (b and n from pair loads, made from the 3.1 TU with a one-line `sed`) in 380
  places: every chain function that inlines the helpers, and `rk_link_k`.
- GPU (`evalfast_matches_cpu_po2_10/16`, which check all 9 forms against the CPU), variant metallibs
  loaded with `RISC0_METAL_RV32IM_METALLIB` (`logs/r18_*.log`, `r18/*_dir/`):

| variant (all 6 ef forms rebuilt) | b | n | result |
|---|---|---|---|
| shipped | pair | `ef_nbeta(b)` | all forms == CPU |
| `pmnld` (R18: wrong every run) | pair | pair at `pm + EF_NPM + k` | flat, fc, nested == CPU; **nested specialized (fc_nest) 16384/16384 and 1048576/1048576 differ** |
| `pmnA1` (R18: correct) | uint4 `pm[k]` | pair at `pm + EF_NPM + k` | **nested: 16384/16384 differ** |
| `pmnA2` (R18: correct) | pair | uint4 `pm[EF_NPM + k]` | nested forms OK; **flat (default) 16384/16384 differ**; same with binary archives off |
| `pmnu4` (`-DEF_PMN_LOAD`) | pair | uint4 `ctx.pmn[k]` (the same address as A2) | all forms == CPU |

  The first `pmnld` run, with only `eval_check_ef.metal` replaced (the forms' wrappers `#include` the
  original), passed. That shows the quoted-include pitfall, which `build_rv32im_variant.sh` now
  documents (`INCS_<TU>`).
- Reading: A2 and pmnu4 load the same words from the same address (`ctx.pmn = tab + EF_NPM`). One is
  wrong in every element and the other is right. So the table and the host are fine, and the
  compiled code differs. -O0 and -O1 builds of the eval TUs cannot be loaded ("Compute function
  exceeds available stack space"), so the compiler level could not be bisected. The cause is
  inferred (not shown) to be the same back-end family as R18's: table rows from more than one
  vector load feeding the private `X[4][4]`. Only R18's exact two-pair-load form was known before.
  These variants are not shipped, so this does not block. Tier P is deliberately wider than R18's
  shape. It flags any helper where two or more >= 16-byte vector loads, at least one >= 32 bytes,
  feed one private aggregate: it flags pmnld, A1, A2 and pmnu4 (160-380 sites each), and the
  shipped forms are 0.
- Repro: `r18/pmnA2_dir/` (the six ef sources) + `mklib.sh pmnA2 eval_check_ef=...` (or
  `build_rv32im_variant.sh` with `SRC_<form>=` per form), then
  `RISC0_METAL_RV32IM_METALLIB=<lib> <rv32im test bin> evalfast_matches_cpu_po2_10`.

## 5. Tool changes (`tools/metal_audit/`)

- `ir_scan.py`:
  - new **tier P** (R18's pair-load matrix shape; definition in the docstring). It is the last
    column of the table and the totals line (`... Z=n P=n`), so the 3.0 parsers (`$4..$8`, `Z=`)
    keep working;
  - kernel names come from `!air.kernel`;
  - `--jobs N` / `IR_SCAN_JOBS` scan files in parallel processes. The output is identical to a
    serial scan (the same 64 findings at -O2). The -O2 scan of 175 TUs drops from ~4 to ~1.5
    minutes at 6 jobs.
- `run_stress.sh`:
  - `rv32im_gen`: the rv32im-sys generator tests (scan-loops / scan-ir / scan-metallib);
  - `rv32im_witgen`: witgen_segment_file par (`R17_AUDIT_WITGEN_REPS`, default 200) and sorted
    (`R17_AUDIT_WITGEN_SORTED_REPS`, default 30) on every `R17_AUDIT_SEGMENTS` segment, summarised
    as `R17AUDIT rv32im witgen ...: k/n calls bad`;
  - `rv32im_amp`: the amplifier and sorted segments at `R17_AUDIT_AMP_LEVELS` (default the 8
    settings above). Each variant is built by `build_rv32im_variant.sh`, and the step fails if a
    variant does not build or no amplifier line is printed;
  - `rv32im_eval_forms`;
  - `recursion_<k>` (`R17_AUDIT_REC_KERNELS`, default `lz lz32 split monolith`);
  - `ir`:
    - tiers ASZP are reported, and A, S and P are gated (`R17_AUDIT_FAIL_TIERS`, default `ASP`);
    - `R17_AUDIT_IR_LEVELS` adds -O levels, where only `R17_AUDIT_FAIL_TIERS_X` (default `P`)
      gates, since only -O2 is shipped;
    - `IR_SCAN_JOBS` (default 4);
    - a tier-P positive control (`r18_pmnld` built from the build's `eval_check_ef.metal`) must be
      flagged, and its `sed` must apply, otherwise the step fails.
- `build_rv32im_variant.sh`:
  - takes every generated `OUT_DIR/metal/*.metal`. On 3.1 there are 13 TUs, and the fixed list of
    6 made metallibs that fail to load;
  - adds `INCS_<TU>` (include dirs searched first: a generator variant's `witgen_fpext.h` /
    `witgen_fp.h` are included from `witgen.h`, so without it the build's copies win silently);
  - fails on any TU compile error instead of linking a stale `.air`.
- Full run: run the steps in several heavy `gpu-run` locks (each step is listed in section 3 with
  its duration). `rv32im_witgen` with 5 segments x 200 took 10 minutes, so split it by segment.

## 6. Correctness, budgets, isolation

- No generator fix, so no CPU-equality rerun is owed. All the stress lines compare with the CPU (or
  arkworks / the baseline kernel) and between reps.
- No production code changed, so nothing was measured at the 4 / 8 GiB budgets. The largest run's
  footprint is from the existing tests (evalfast po2 20 peak 5.48 GB).
- The GPU stress steps are ignored tests or env-enabled tests that run with `--test-threads 1`
  under the heavy lock. No test file changed.

## 7. Open issues

1. **P1 (R18 / Apple feedback):** section 4. Variants with one pair load plus one `uint4` load into
   the `X[4][4]` matrix, which R18 found correct, are wrong in every element on 3.1 / macOS 27.2 in
   some chain forms, while an address-identical variant is correct. The shipped form is correct and
   tier P guards it. The owner of the evalfast generator (R18 / R22 / R23 forms) should add this to
   the Apple Feedback material. Not done here: checking the same variants on the 3.0 tree (it would
   need a test build in the frozen checkout).
2. **P2:** latent tier A / S sites at -O1 / -Os / -Oz outside witgen (recursion `step_exec*`,
   `step_verify_*`; rv32im `ef_eval_split*`, `rv32im_v2_11`; zkp eval / mdiv / ntt_x / fri). They
   are identical on 3.0. Only -O2 is built, and the rv32im-sys test covers witgen at six settings.
   If a build ever changes its -O level, these need the R17b treatment.
3. **P2:** R17's round-1 baseline (`--fpext-calls outline`) at -O0 / -Oz no longer fails (0/90 each)
   with the current generator, so the -O0 / -Oz gate here has no failing same-session baseline of
   its own. The defect itself is present (control 10/10; `--map-lowering loop` 30/30).
4. **P3:** a whole-tree -O0 scan is impractical (about 3 GB of IR; one file takes more than 10
   minutes in Python). `R17_AUDIT_IR_LEVELS=O0` works but needs splitting or more jobs, and about
   3 GB of memory per large file.
5. Tier Z is still unvalidated (P31-T1). The new -O0 instances in `p254_*_ref` are in reference
   kernels.
