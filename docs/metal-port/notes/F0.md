# F0: MetalHal runtime rewrite

## What was done
`risc0/zkp/src/hal/metal.rs` was rewritten and split into submodules:
- `metal.rs`: the public API of plan 2.7. It has `enabled()`/`device_name()` (F2's, unchanged, same paths), `singleton()`/`exclusive()`, `MetalHash` (now with `hash_fold_tree`), `MetalHashSha256`/`MetalHashPoseidon2`, `MetalHal` (`new`, `load_library`/`try_load_library`, `pipeline`, `dispatch`, `launch`, `blit_fill`, `alloc_private`, `alloc_buffer<T>`/`copy_from_slice<T>`, `flush`, `sync`/`try_sync`, `with_encoder`, `set_batch_limit`, `set_debug`, `dispatch_by_name`, deprecated `dispatch_with_resources`), and the `Hal` impl.
- `metal/runtime.rs`: `KernelArg::{Null, Buffer{buffer, offset}, Integer, Bytes}`, `Grid::{Threads, Threads2D, Groups}`, the batch, the pool, debug tracking and command-buffer error reporting.
- `metal/kernels.rs`: `MetalKernels { pub library, pipelines }` with `pipeline(name)` (panics if missing), `get`, `names`.
- `metal/buffer.rs`: `BufferImpl<T>` (`Arc<RawBuffer>` + element offset/size) with `as_buf`, `as_arg`, `as_arg_with_offset`, `as_ptr`, `as_mut_ptr`, `as_device_ptr` (u64), `gpu_address_at`.
- `metal/tests.rs`: the 18 original tests plus 16 new ones (13 by round 1, 3 more in round 2).
- `zkp/src/hal/mod.rs`: the `report_nonzero_remainders` cfg now includes `metal`, with `allow(dead_code)` when neither cuda nor rocm is on, because the Metal HAL does not call it until Z1. I did not touch F2's `pub mod metal` cfg line.
- I removed the `metal_prefix_products` code path. `prefix_products` stays the CPU loop, like CUDA.

### Behaviour (plan 2.6 / 2.7 / 2.9)
- **PSO cache.** `MetalHal::new` builds a PSO for every name in `KERNEL_NAMES` in a process-wide `OnceLock`, so this happens once per process rather than once per HAL. Before this change, a PSO was built on every dispatch. `load_library` checks `function_names()` and fails with every missing name listed. PSO creation errors (for example static threadgroup memory > 32 KB, per D0) are errors too.
- **Lazy batches.** One command buffer per batch, with one serial compute encoder. A blit switches to a blit encoder; the next dispatch opens a new compute encoder in the same command buffer.
  - `dispatch`, `launch` and `blit_fill` only encode.
  - `flush` ends encoding and commits. `sync` commits and waits on every in-flight command buffer.
  - A batch is committed after `DEFAULT_BATCH_DISPATCHES = 2048` dispatches. D0 measured no limit up to 262144, so 2048 is a latency choice, as plan 2.6 says. `RISC0_METAL_BATCH_DISPATCHES` and `set_batch_limit` override it.
  - `hash_rows`, `hash_fold`, `hash_fold_tree`, `batch_expand_into_evaluate_ntt`, `batch_interpolate_ntt`, `batch_bit_reverse` and `zk_shift` end with `flush()` (fix round 1 added the last two, matching CUDA cuda.rs:1298-1303 and 1479-1483). These are the CUDA `gpu.sync()` points; 2.6 says the batch closes there, and a commit is enough because host reads wait.
  - Repeated `setComputePipelineState`/`setBuffer` with the same values are skipped within an encoder, which avoids validation-layer warnings.
- **Host access.** `view`, `view_mut`, `get_at` and `to_vec` flush and wait whenever there is unsynced work. `to_vec` and `get_at` respect the slice offset and size; before this change `to_vec` returned the whole allocation.
- **Pool.** The pool is per HAL, keyed by byte size, and buffers are `StorageModeShared` and tracked. A buffer dropped while a batch is open or uncompleted stays in `pending`, tagged with that batch's sequence number. It becomes reusable only after that batch completes. Small buffers (< 64 KB) are always pooled. Larger ones are pooled up to `recommendedMaxWorkingSetSize / 2`. `set_bypass_pool` is honoured. `trim_device_memory` drains the pool.
- **Errors.** If a command buffer's status is `Error` after a wait or poll, the `error.localizedDescription` is read through `msg_send!`; `try_sync` returns it and `sync` and host reads panic with it.
  - If `newBufferWithLength:options:` returns nil, the pool is drained and the allocation retried once; if it fails again, `alloc_shared`/`alloc_private` return an error with the name and size, and the HAL entry points panic with it.
  - Fix round 2: the nil check now happens on the raw pointer returned by `msg_send!` (`Runtime::new_buffer_raw`), before it is wrapped in `metal::Buffer`. metal-rs 0.29's `Device::new_buffer` returns a `#[repr(transparent)] NonNull`-backed `Buffer`, so a nil there is already UB and the reviewer showed the round-1 `as_ptr().is_null()` check compiled to constant false in release, which made the drain-and-retry path dead code.
  - These are programming errors and panic: a buffer > `max_buffer_length`, threadgroup memory (static + dynamic, each rounded to 16) > `max_threadgroup_memory_length`, `Bytes` > 4096 or empty, a threadgroup larger than the PSO max, or a missing kernel.
- **Debug.** With `RISC0_METAL_DEBUG=1` (or `set_debug(true)`), every bound buffer is recorded per batch. `as_ptr`/`as_mut_ptr` panic, and host reads re-check after their sync, if the buffer is in a batch that has not been observed complete. A warning is logged if `MTL_DEBUG_LAYER` is not set.
- **Locking.** `exclusive()` (process-wide reentrant) is taken per call: in `new`, around every encode, commit, wait and allocation poll. It is never stored. Lock order is always `exclusive` → per-HAL state mutex. The pool mutex is never held while taking the state mutex. `Drop` of a buffer takes only the pool mutex and atomics.
- **`as_bytes`.** `as_bytes<T: bytemuck::NoUninit>` uses `bytemuck::cast_slice`, so it is sound for every caller (fix round 1; the first version took any `T: Copy` and could expose padding bytes). `BabyBearElem` derives `NoUninit` and `BabyBearExtElem` has an `unsafe impl NoUninit`, so all call sites are unchanged. Downstream `Params` structs passed through `KernelArg::Bytes` must be `#[repr(C)]` with explicit padding fields and `#[derive(bytemuck::NoUninit)]`.
- **Small constants.** `fri_fold`, `mix_poly_coeffs`, the NTT `rou` tables and the interpolate `norm` factor go through `KernelArg::Bytes` instead of a fresh buffer per call.
- **Sizes.** `gpu_total_memory` is `recommendedMaxWorkingSetSize`. `gpu_free_memory` is that minus `currentAllocatedSize`.

### Deliberate interpretations
- `copy_from_*` does **not** sync. It always writes into memory that no GPU work can be using: either a new allocation, or a pool buffer whose last batch completed (deferred returns). Plan 2.6 lists `copy_from*` among the syncing accessors; this is safe without the sync and keeps per-call constants from stalling the batch.
- `dispatch_with_resources` now takes `&K where K: PipelineSource + ?Sized`. `PipelineSource` is implemented for `ComputePipelineState`, `ComputePipelineStateRef`, `ComputePipelineDescriptor` and `ComputePipelineDescriptorRef`, so old-style calls passing `&desc` / `&pso` of the owned types compile without `&*` (fix round 1; tested). A descriptor builds a PSO per call. The callback runs under the per-HAL state lock and must not call back into the HAL (documented on the method). It encodes the callback and the dispatch, then syncs. It is `#[deprecated]`.
- **sha_rows workaround.** `sha.metal` declares `count`/`col_size` as writable `device uint32_t&`. The validation layer rejects `set_bytes` bound to a writable argument ("Read-only bytes are being bound at index 2/3 ..."). Until the kernel owner (zkp-hal unit) makes them `const device`/`constant`, `MetalHashSha256::hash_rows` passes them in a small buffer. `poseidon2_fold`'s unused `output_size` argument (`device uint32_t&`, poseidon2.metal:154, index 4) is left unbound, as before; binding it gave an "unused binding" warning. This is correct only while the kernel never reads it; the zkp-hal unit should make it `constant` (and then bind it) together with the sha.metal fix. Remove the sha_rows params buffer at the same time.

## Fix round 2
- `new_buffer_raw` checks the raw `*mut MTLBuffer` from `msg_send!` for nil, then `Buffer::from_ptr` takes the +1 reference (see Errors above). Used by both `alloc_shared` and `alloc_private`.
- `cfg(test)` fault-injection hooks on `Runtime`, per runtime so parallel tests do not interfere: `inject_alloc_failures(n)` (the next n raw allocations return nil) and `inject_batch_error()` (the next committed batch is reported as `MTLCommandBufferStatus::Error` with the message "injected test error" once it completes). Neither exists in non-test builds.
- New tests:
  - `alloc_failure_drains_pool_and_retries`: two pooled buffers, one injected failure → pool drained (`pool_stats() == (0, 0)`) and the retry succeeds; two injected failures → the error names the buffer ("doomed") and byte count; the same for `alloc_private`; compute afterwards is correct.
  - `command_buffer_error_try_sync`: `try_sync` returns the error once, the next `try_sync` is Ok, and the HAL computes correctly afterwards.
  - `command_buffer_error_sync_panics`: a host read (`to_vec`) through `sync` panics with "Metal command buffer failed: injected test error".
- Comment on `Bound` that its address-keyed dedup relies on retained-reference command buffers.

## Assumed / not verified / gaps
- The error paths are exercised through the test hooks, not through a real nil from Metal or a real GPU fault: I found no reliable way to make the allocator return nil below `max_buffer_length` or to make a kernel fault. `command_buffer_error` (reading `error.localizedDescription`) is therefore still not run against a real error object.
- Hazard ordering across command buffers on one queue for tracked shared buffers is relied on. The limit-7 and limit-3/4 tests exercise it and pass, but it is not separately probed.
- The `metal_prefix_products = []` feature line remains in `zkp/Cargo.toml` (owned by F2/Cargo.toml); no code references it now.
- `eltwise_zeroize_elem`, `scatter`, `eltwise_copy_elem_slice` and `prefix_products` are still host loops through `view_mut`, which syncs. Wiring the zeroize kernel and the scatter ports is Z-items work.
- `with_encoder` bindings are not tracked by the debug check, and the callback must not call back into the HAL, because the state mutex is held.
- **Cross-HAL buffers are unsupported.** A buffer may only be used through the HAL that allocated it (documented in the module docs). Host reads sync and pool returns wait only on the allocating HAL's runtime; a review harness showed a stale read when HAL B dispatched into HAL A's buffer. No debug assertion catches this yet.
- **`exclusive()` and rayon.** `exclusive()` is reentrant only on the owning thread. A HAL call from a rayon worker while another thread holds `exclusive()` and waits on that worker deadlocks (reviewer measured a hang). No current path does this; documented on `exclusive()`. M3 and groth16, which hold `exclusive()` over a whole prove, must not call the HAL from rayon workers.
- `try_sync`/`sync` hold `exclusive()` across `wait_until_completed`, so HALs on different threads serialise behind each other's waits (throughput only).
- `set_threadgroup_memory_length` persists between dispatches in one compute encoder; callers using dynamic threadgroup memory should always pass `tg_bytes` explicitly.
- The debug host-access check uses `try_lock` and is skipped under contention (false negatives possible).
- The zkp PSO cache is a process-wide `OnceLock` for the first HAL's device: fine on single-GPU Macs, wrong with several devices.
- Per-HAL pools: a buffer outliving its HAL keeps the HAL's runtime (queue and pool) alive through an `Arc`. This is intended.
