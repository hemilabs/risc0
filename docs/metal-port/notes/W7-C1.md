## 1. S5: the p254 prewarm gate race

**Bug.** `prewarm_p254_ctrl` checked its 512 MiB headroom gate and C13's cap, then took
`risc0_zkp::hal::metal::exclusive()`. A Prove holds that lock for its whole call (`risc0_zkvm`'s
`exclusive_gpu`). So a prewarm started on M9's background thread during a Prove could pass the gate
and block on the lock. The Prove then filled the budget, and once the lock was free the prewarm
committed identity_p254's ctrl (~217 MB) beside the Prove's pool.

**Fix** (`ctrl_persist.rs`). `prewarm_p254_ctrl_with(po2, headroom, early_only, commit)` runs the same
gate (`prewarm_gate`: already kept, headroom, cap) twice: once before the lock (cheap; no lock wait
when there is clearly no room) and once while holding it. Under the lock no other thread of the
process encodes or allocates through a HAL, so the second check holds until the commit ends.
- Outcomes are `Skipped("no headroom before the GPU lock: ..")` / `Skipped("no headroom under the
  GPU lock: ..")`, `Skipped(".. cap under the GPU lock")` and `AlreadyKept`.
- The headroom source is a trait, `Headroom`: production uses `MetalDeviceHeadroom`
  (`device_memory()`), the unit test a fake.
- `RISC0_METAL_P254_PREWARM_GATE=early` restores the old order (one check, before the lock).
- `prepare()` staging buffers are the one allocation made without the lock. Each is admitted
  only if it leaves 512 MiB under the limit (section 3), so it stays inside this gate's margin.

**Tests.**
- `c16_tests::w7c1_prewarm_rechecks_gate_under_lock` (unit, no GPU work, in the default suite). A
  fake headroom source flips between the two checks:
  - roomy then full: `Skipped("no headroom under the GPU lock")`, no commit, 2 reads;
  - the limit shrinks to 2 GiB, so the group no longer fits the 64 MiB cap: skipped "cap under the
    GPU lock";
  - full before the lock: skipped at once, 1 read;
  - roomy both times: commits;
  - `early` order: 1 read, and it commits through the flip.
- `c16_tests::w7c1_prewarm_race_at_budget` (ignored, heavy, `RISC0_METAL_MAX_WORKING_SET_BYTES=4294967296`).
  Thread A takes `exclusive()` and waits until B has passed the pre-lock check (a test hook counter).
  It then allocates a raw device buffer to within 400 MiB of the budget and lets go, keeping the
  buffer until B returns.
  - Default order (`race/race_4g_final.log`): A filled to 3696 MiB; B returned
    `Skipped("no headroom under the GPU lock: 3696 MiB allocated + 512 MiB > 4096 MiB working-set
    limit")`; nothing failed. With the memory back, the prewarm returned `Kept` (289 ms).
  - The bug, with `W7C1_RACE_EARLY=1` (old order):
    - at a 400 MiB margin the old order commits beside A (`Kept`, peak ~3.9 of 4.0 GiB);
    - at M9's 150 MiB margin (`W7C1_RACE_MARGIN_MIB=150`, `race/race_4g_m150.log`) it **panics**:
      `Metal working-set budget exceeded: allocating 67108864 bytes for nodes with 4288675840 bytes
      already allocated ... limit of 4294967296`;
    - in the same run the default order skipped cleanly.
  - Fix round 1 (`r1/gates/race4g.log`): while A holds the budget at 3696 MiB, thread A also checks
    that a new staging buffer is refused on the real device count (`MetalStaged::new` returns
    `None` within the 512 MiB margin). It passed, with the same Skipped outcome and then `Kept`
    (267 ms).

**Decision: staging is now the default** (`staging.rs`). It beat A-vs-A at all three budgets in both
benches. Changes made with the flip:
- **Budget.** Staging buffers are device allocations, so the device's `currentAllocatedSize`
  includes them, and that is what the HAL's default (`device`-scope) budget is checked against.
  `take_buffer` now allocates a new buffer only if it leaves `STAGE_MARGIN_BYTES` (512 MiB, the
  p254 prewarm's margin; fix round 1, it was 0) under `device_memory()`'s working-set limit.
  Otherwise it first drains the staging pool, and if it still does not fit, the proof takes the
  host path. The margin is there because `prepare()` allocates on its own thread without
  `exclusive()`, beside a Prove that may be allocating: with no margin a staging buffer could take
  the last bytes the Prove's next allocation needs (the round-1 review's S5-class finding).
  `stage_admission_keeps_margin` tests the rule. `staging_gives_way_near_the_limit` (fake device
  memory) checks that near the limit `stage_metal` leaves the preflight unstaged, that the pool is
  drained first, and that the witgen then takes the host path and still matches the CPU. No zkp file was edited. Under `RISC0_METAL_BUDGET_SCOPE=hal` they are in no HAL's
  own count (documented).
- **Wrap peak.** The pool (up to 3 buffers, ~80 MB) is drained in `release_cached_provers()`, which
  `release_hal_buffers` calls before the Groth16 wrap. With the pre-flip binary, staging raised the
  worker's wrap Metal peak by 80-84 MiB (3942 -> 4022 MiB at 4 GiB, 5377 -> 5459/5461). With the
  drain it is unchanged: final build, `ab/wfinal_*.jsonl`, 3942 / 5377 / 5377 MiB.
- **Err path** (C14 review r2). Every `Err` the witgen returns after encoding the staged inputs
  comes after a sync, because `check_fault` waits for every batch first. Only a panic could unwind
  with batches still reading the inputs. Even so, `StagedReleaseCheck` now marks the witgen done
  only at its successful end. On any other exit (an `Err` or a panic) the staged buffers are
  *retired*: when the preflight drops them, they are released, not pooled. So a later `prepare()`
  can never rewrite a buffer an aborted batch might still read. `staged_chain_faults` asserts it:
  each of the 5 faulting witgens retires exactly one buffer, and the good one retires none. The
  retire counter is per thread (fix round 1), so another test's retirements cannot shift the delta.
- `RISC0_METAL_REC_STAGE=0` (or `off` / `false`) reverts; `stage_knob_parses` tests the parser.

## 5. Recursion suite memory

`suite/`: peak footprint from `/usr/bin/time -l` on the test binary, default parallel harness, 16
GiB gpu-run budget. `fpsample.sh` samples the process with `footprint` every 0.5 s.

| build | peak footprint | IOAccelerator max (sampled) | wall |
|---|---|---|---|
| base (`zkminer/metal`), 3 runs | **6.95 / 8.60 / 6.99 GB** (C14/C15 noted 8.5-9.0) | 1.72 GB | 108-110 s |
| base, `MallocLargeCache=0` | 6.17 GB | 2.75 GB | 126 s |

| **final** (lock + large cache off in the test binary), 3 runs | **3.78 / 3.78 / 3.76 GB** | 1.39 GB | 112-116 s |

Two causes:
1. **Concurrent heavy tests.** Measured alone (`suite/pertest_*.tsv`), 45 tests exceed 250 MB, up
   to 3.8 GB each: po2 18 seal tests with a CPU prover, `accum_matches_cpu_full`, po2 18 witgens.
   They now take `heavy_test_lock()` as their first statement, before `global_state_test_lock` (one
   order everywhere). The list is in the code; the threshold was set from the per-test table.
2. **libmalloc keeps freed large blocks in the footprint.** On this macOS a freed large allocation
   stays in the process footprint, cached for a later request of the same size.
   - A probe (`scratchpad/mfree*.py`): 4 x 1 GiB malloc + memset + free leaves 5.4 GB of footprint,
     and `malloc_zone_pressure_relief` returns 0.
   - With `MallocLargeCache=0` the memory goes back at once.
   - In the suite, "Malloc Large" sat at 2.2-3.9 GB while no single running test needed that.
   - libmalloc reads the variable before any Rust code, so the test binary re-executes itself once
     with `MallocLargeCache=0`. This is a `__mod_init_func` constructor in `hal/metal/mod.rs`,
     `cfg(all(test, target_os = "macos"))`. It is skipped if the variable is already set, or with
     `RISC0_TEST_NO_REEXEC=1`. Production binaries are untouched.
   - Fix round 1: it is also skipped when the arguments contain `--ignored`, because the cache
     off cost the ignored benches ~7 ms per capture-bench round (section 3b). This is a footprint
     workaround for the default harness, not a cut in live memory.

The suite passed under the default harness three times with the final code: `suite/final1.log`
(via `cargo test`), `final2.log`, `fpafter1.log`. Each was 79 passed / 21 ignored, plus the doctest.

Fix round 1, final code: the suite passed twice more under the default harness, 81 passed / 21
ignored each, peak footprint **3.76 / 3.76 GB** (`r1/gates/suite1.log`, `suite2.log`; 127 s and
161 s wall).

**Ignored heavy tests** now call `require_heavy_gpu_run` first. That is all 19 pre-existing ignored
tests and the two new ones. Without `GPU_RUN_MODE=heavy`, the test fails with a message telling you
to run it under `bin/gpu-run` (checked under `--light`).

## 6. C16 lazy p254 variant PSOs: measured, not implemented

The four C16 PSOs (`p254_{fold,rows}_w64u`, `p254_{fold,rows}4_w64`) are in zkp's `KERNEL_NAMES`
(`zkp/src/hal/metal.rs`) and are looked up in `zkp/src/hal/metal/poseidon254.rs`. Building variants on
first use means editing both, and both are zkp files outside this item. The cost was measured
without touching zkp:
- `c16_tests::w7c1_p254_pso_cold_cost` (ignored) loads the built zkp metallib through the public
  concurrent loader (`archive::ArchivedKernels::new_in_threads`, no archive).
- `MTL_SHADER_CACHE_SIZE=0` gives a cold compile; `pso/cold.log` and `pso/pairs_alone.log` hold
  the runs (load 15-17).

| set | cold (7 interleaved pairs) | warm |
|---|---|---|
| all 72 (today) | 1609 [1595, 1628] ms | 3-4 ms |
| 70 (without `w64u`: what lazy variants would build eagerly) | 1524 [1499, 1537] ms | 3-4 ms |
| per-pair delta | **+96 ms [+71, +117]**, 7/7 | ~0 |
| `w64u` pair alone | 1367-1430 ms | 2 ms |
| lanes pair alone (default kernels: stay eager) | 145-151 ms | 2 ms |

- Lazy `w64u` would save ~0.1 s of wall time on a cold start of the zkp set. It saves nothing warm,
  where archives and OS cache hit.
- That is against BASELINES' 65-85 s first install, which rv32im's 13 PSOs dominate.
- **Not worth a cross-owner zkp change on its own.** If the zkp owner touches `KERNEL_NAMES`
  anyway, it is a ~15-line change: drop the `w64u` pair from the eager list, and build it with
  `load_library` the first time `RISC0_METAL_P254_KERNELS=w64u` asks for it.
- The knob `RISC0_METAL_P254_LAZY_VARIANTS` from the brief does not exist, because nothing was made
  lazy.

## 7. C16 lanes threshold and the core count

- The IORegistry reports `gpu-core-count = 32`.
  - `GPUConfigurationVariable` shows `num_cores = 40`, which is the die maximum (4 x 10).
  - `core_mask_list = (987, 987, 987, 975)` enables 8 + 8 + 8 + 8 = 32 cores.
  - System Information says "Total Number of Cores: 32".
  - So this Mac is the 32-core M5 Max. BASELINES' "40-core GPU" is wrong; W7-T1 fixes the text.
- `default_lanes()` = `LANES_PER_CORE` (128) x 32 = **4096**. That is exactly the threshold C16's
  sweep found best (4096 and 8192 tied, 16384 worse) and the value its
  `default_lanes_follows_core_count` test asserts.
- So the threshold math did what C16 measured. A real 40-core part would switch at 5120 (inside the
  tie range), and a 10-core part at 1280.
- Read only; no zkp change.

## 8. C15's slow round: not reproduced

`scripts/c15out.sh`, `c15out/rounds.log`: 20 fresh `c11_bench_captures` processes over the 11 C11
captures at the default budget. Each did 5 timed rounds after a warm one (100 rounds). Load and
`pmset -g therm` were logged before and after each process.

- Every process median was 1832-1838 ms, and every round 1830-1861 ms (+1.5 % worst).
- Load ran 2-18 (other agents' CPU builds in processes 11-15) with no effect.
- No thermal or performance warning was ever recorded.

C15's 5.8 s / 14.8 s rounds (one each, both arms, at load 3-6) do not recur on a GPU-quiet machine at
load up to 18. The likeliest cause was other agents' GPU work before the GPU lock existed. This is
not proven: no trace of that session survives.

## Open issues

- **Pre-existing clippy errors outside this item's files:** `prove/zkr.rs:31` (`type_complexity`) and
  `prove/witgen.rs:499,535` (`useless_vec`). `cargo clippy -p risc0-circuit-recursion` still fails on
  them.
- **Lazy `w64u` PSOs** need a zkp-owner change (section 6). The measured value is ~0.1 s cold, 0 warm.
- **Two-stream:** GO at 1.11x by LEADS2's bar. The in-process build (LEADS2 rank 3, L, high risk)
  is the next step, with its preconditions (`try_sync` lock rework, B70 / G12 history) and a 4 GiB
  memory plan.
- **Staging** adds +82 MiB to the 4 GiB recursion-phase Metal peak. Under the `hal` budget scope
  the buffers are in no HAL's count. A real 16 GB Mac and other core counts were not measured.
- **Staging pool after a succinct-only session** (round-1 review, read from the code). The pool is
  process-wide, holds at most 3 buffers (<= ~135 MB at po2 18), and only `release_cached_provers`
  (zkvm `release_hal_buffers`, the Groth16 wrap path) and `take_buffer`'s own fit check drain it.
  The HAL's budget check (`drain_all_pools`, zkp) cannot see it. So a process that proves succinct
  receipts without a wrap carries up to ~135 MB into its next session's segment phase, as it
  already carries the cached recursion provers' ctrl groups, which `drain_all_pools` cannot see
  either. The worker always wraps, so its segment peaks are unchanged (section 3). A non-wrapping
  long-lived caller should call `risc0_circuit_recursion::prove::release_cached_provers()` (or
  zkvm `release_hal_buffers`) between sessions. A drain at the end of `composite_to_succinct` would
  be a zkvm change, which this item does not own. Not measured at a 4 GiB budget with a
  succinct-only workload.
- **The libmalloc large-cache effect** applies to every long-lived process on this macOS, not only
  tests. The worker's "freed GPU pages not yet returned" in M9 is a different (GPU) effect, but its
  host footprint may hold freed large blocks the same way. Worth a look by the zk-miner footprint
  owners (M6/M9 ceilings read phys_footprint).
- **The M9 worker** should now get `Skipped("no headroom under the GPU lock")` instead of a failed
  allocation when its background prewarm races a Prove. That was not re-run through zk-miner here
  (the M9 branch is not merged); the unit and 4 GiB integration tests cover the risc0 side.
