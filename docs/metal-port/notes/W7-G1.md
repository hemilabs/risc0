## Result

- **The witness graph's real share is ~1.34 GB of host footprint, but freeing it does not lower the footprint
  on macOS by itself.** libmalloc's large-allocation cache keeps freed blocks dirty (in the footprint), and
  rebuilding the graph after a release leaves another ~580 MiB behind per cycle (the parser's node array grows
  by doubling reallocations). Release is therefore only enabled when the process runs with the cache off
  (`MallocLargeCache=0`, set by the launcher: zk-miner). There it is large:
  - **process peak footprint at 8 GiB: 7.14 -> 5.97 GB (-1.17 GiB, 8/8); at 4 GiB: 5.12 -> 3.90 GB
    (-1.22 GiB, 8/8).** Full suite at 8 GiB: 10.75 -> 8.82 GB (-1.8 GiB).
  - With release on, `par_transient` becomes the default below 20 GiB (gated on headroom). At 8 GiB the
    **wrap drops 1.68 -> 1.565 s (-120 ms, 8/8; shrink_wrap 770 -> 657 ms)** at no peak cost. At 4 GiB the gate
    builds `fast`.
  - Cost: STARK +43..+75 ms (+0.4-0.5 %, 7/8 to 8/8; mostly the cache-off allocator), identity_p254
    +4..+11 ms. At 4 GiB the wrap is +23 ms (+1.4 %).
- **Default (any Mac whose launcher does not set `MallocLargeCache=0`, and every Mac at >= 20 GiB): unchanged.**
  B0-vs-A and B-vs-A are inside A-vs-A at 4 GiB, 8 GiB and the default budget, for time and footprint.
- **Benchmark speed (full worker `--benchmark`, default budget): unchanged** (8 pairs, `def/`).
- Cache GC: the superseded version-1 compact file (324 MB) is deleted when version 2 loads. Unit test plus a
  real end-to-end check.
- **Fix round 1** (see "Fix round 1"): the pressure-drain hook `release_graph()` is now a no-op unless the
  drop lowers the footprint (spawned with `MallocLargeCache=0`, or `RISC0_G16_GRAPH_RELEASE=1`); the drop
  counter the tests use counts only cached graphs (PLAN 8.7); overlapped wraps no longer discard each
  other's graph; the `par_transient` check is taken from the graph in hand. Re-run A/Bs: RC (fix round) vs R3
  (round 0) inside noise, BC (default environment) inside A-vs-A, peaks -1.20 / -1.22 GiB at 8 / 4 GiB.
- **Fix round 2** (see "Fix round 2"): a wrap now counts as using the graph for its whole run, from the top
  of `gpu_prove` (`WrapGuard`), and so does the graph a prestart built for the wrap that follows it (a
  reservation). The pressure hook therefore cannot drop the graph in `pre_gpu`, the key load or the
  GPU-lock wait. Before the fix that forced a 0.5-0.9 s synchronous rebuild, which a kept test reproduced.
  Only the last wrap out releases the graph. Re-run A/Bs: RD (round 2) vs RC (round 1) is no change;
  peaks are -1.19 / -1.21 GiB at 8 / 4 GiB; the 8 GiB wrap is -0.105 s (0/8 > 0).
- The witness count pass "bimodality" is not a bug: the time is set by the `wtr` switch (1.2 ms with it,
  6.7-6.8 ms without, 3.0 ms `base`), stable per variant. G14's segment-reduce gap is not bucket gaps (ruled
  out by simulation on the real witness); its cause is still open.

## (2) The releasable graph

- `metal_witness.rs`: the `OnceLock` is now a `Mutex<Option<Arc<Graph>>>` plus a build mutex.
  - A caller that arrives during a build waits for it; it never builds a second copy.
  - A failed build is remembered, as before.
  - A wrap holds an `Arc`, so a release never frees a graph that is in use.
- `fast.rs`' `PROGRAM` (the `ref` evaluator and the Docker fast path) gets the same treatment.
- **Digest memo** (`fast::read_graph`): the SHA-256 (~0.2 s of the parse leg, run beside it) is skipped
  when this process already checked the same file. Identity = `fstat` of the opened file: dev, inode, size,
  mtime, ctime. A rebuild then takes 499-530 ms (`fast`) or 680 ms (`par_transient`), against 704-754 / 902-912
  ms for a first build. Knob: `RISC0_G16_GRAPH_REVERIFY=1`.
- **Policy** `RISC0_G16_GRAPH_RELEASE=0|1|auto` (default `auto`). `auto` releases only when both hold:
  - the working-set limit (`risc0_groth16_sys::effective_working_set_limit`, the HAL's limit) is below
    20 GiB;
  - `MallocLargeCache` is exactly `0` in the environment (fix round 1: other spellings such as `0x0` are
    not trusted). libmalloc reads it only at process start, so it must be in the **spawn** environment; a
    `set_var` after start is seen by this check but not by libmalloc, and would release with the cache
    on (+~580 MiB per wrap). There is no runtime probe of libmalloc's state.

  With the cache on, a release would grow the footprint by ~0.58 GB per proof (measured above, and in the
  full-suite forced-release arm F below). When release is on:
  - `preload_graph()` / `preload_graph_background()` (the worker's start and the zkvm's proof start) become
    no-ops, so the graph is not in the STARK phase.
  - `prestart_prover()` (the zkvm calls it before identity_p254) builds it on a background thread, beside
    identity_p254 (0.9 s against a 0.5-0.9 s build).
  - Each wrap drops the graph right after its witness, on a helper thread, so the drop is off the critical
    path and happens before the GPU prove.
  - Fix round 1 (overlapped or pipelined wraps): a wrap empties the cache only if it still holds the graph
    this wrap used (`release_slot`, `Arc::ptr_eq`), and the end-of-wrap guard releases only when the wrap
    failed before its witness (`ReleaseGraphAfterWrap::done`). Before, the guard emptied the cache
    unconditionally at the end of `gpu_prove`, discarding a graph that the next wrap's prestart had built
    meanwhile (review: "built it synchronously in 742 ms" twice). Covered in `graph_release_and_rebuild`.
    Fix round 2 replaces this with "last wrap out, and no live prestart reservation" (`WrapGuard`,
    `reserve_for_wrap`).
  - Fix round 1: a failed **rebuild** (after a release; e.g. a transient I/O error or the component being
    replaced) is no longer latched for the process: that wrap uses the reference evaluator and the next
    one tries again. A failed first build is still remembered, as before.
  - The wrap never depends on a background build having run. If the graph is not built, the wrap builds it
    synchronously; if a build is in progress, it waits for it. Either case is logged ("not ready at the wrap:
    ..."). In the final-build check, one of 3 wraps waited 10.7 ms (`par_transient`). Of 56 release-on runs
    with `fast` or a gated build, one waited 206 ms (`fin8` round 1, load ~20).
- **Hook for W7-A1's pressure drain**: `risc0_groth16::prove::release_graph() -> u64`.
  - It drops the graph only when no wrap holds it and no build is running.
  - It only tries the build lock (never waits) and never takes `exclusive()`. It returns the drop in
    `phys_footprint`.
  - **Fix round 1: it is a no-op (drops nothing, returns 0) unless the drop can lower the footprint**:
    the process was spawned with `MallocLargeCache=0` (any budget), or `RISC0_G16_GRAPH_RELEASE=1`;
    `RISC0_G16_GRAPH_RELEASE=0` turns it off (`parse_idle_release`). The review showed that before, with the
    large cache on (the macOS default), each drain + wrap cycle grew the footprint by ~580 MiB (4044 -> 4625
    -> 5205 -> 5785 -> 6365 MiB, "freed 0 MiB" every time). Kept as `w7g1_hook_cycle` (ignored, heavy):
    after the fix, default environment at 8 GiB: 6075.3 / 6075.4 / 6075.4 / 6075.4 / 6075.4 MiB before each
    hook call, freed 0 (graph kept); `MallocLargeCache=0`: 2420 then 2660.4-2660.5 MiB flat
    (`fix1/hook_*.log`). Unit tests: `idle_release_selection`,
    `release_hook_keeps_the_graph_with_the_large_cache_on` (failed before the fix: 1 drop counted).
  - Not registered here (W7-A1 owns `register_idle_releaser`; this item does not edit zkp). Registering it
    is a one-liner for the registry owner; in a cache-on process it is harmless now.

## (3) `par_transient`: gate and default

- **Gate** (G15 section 5). `par_fits(limit, allocated, pressure_normal)` is true when both hold:
  - `limit - allocated >= 768 MiB` (its measured transient) + 512 MiB margin;
  - `kern.memorystatus_vm_pressure_level` is normal.

  It is applied twice:
  - at build time, against the prover's planned bytes (a gated-off build compiles `fast`, and the wrap
    then takes `fast`'s overlapped path);
  - at the wrap, against the device's current allocation. A `par_transient` graph without headroom
    evaluates with a `fast` program compiled from its nodes (logged).

  Knob: `RISC0_G16_PAR_GATE=0`.
- Fix round 1: the wrap's check is decided from the graph the wrap holds (`Graph::is_par_transient`), not
  from the process cache, which another wrap may have released or rebuilt. In `fast`'s overlapped path
  (witness beside the key load), a graph that turns out to be `par_transient` (a build still running when
  the path was chosen, under a changed pressure level) is now gated against what is allocated **plus the
  key's planned bytes**, instead of 0, so its 580 MB array cannot sit beside the key load unchecked.
- **A/B** (`pt8/`, `pt4/`, 8 rounds each, W7-G1 build; P = `RISC0_G16_METAL_WITNESS=par_transient` with the
  cache on, i.e. G15's opt-in; RP = the same with release on):

  | | wrap | shrink_wrap | peak | segments-phase peak |
  |---|---|---|---|---|
  | 8 GiB, P - A (load 2.2-21) | **-0.120 s (0/8)** | -125.7 ms | **+0.201 GiB (8/8)** | +0.234 |
  | 8 GiB, RP - A | **-0.110 s (1/8)** | -118.1 ms | **-1.170 GiB** | -1.295 |
  | 8 GiB, R(fast) - A | +0.013 | +2.8 | -1.179 | -1.142 |
  | 4 GiB, RP - A (gate: `fast`, but the first version kept the serial witness) | +0.158 s | +148 ms | -1.219 | -1.200 |

  The 4 GiB row exposed a bug in the first version: the gated build was `fast`, but the wrap still took the
  `par_transient` serial path (witness before the key load), costing +148 ms. Fixed: `is_par_transient` now
  follows the built graph, or the build gate when none is built. The final 4 GiB R arm is +9.3 ms
  shrink_wrap, against RF +6.6.
- **Decision.** With the graph released, the `par_transient` program and its 580 MB array exist only from
  the wrap's prestart to its witness. Its STARK-phase cost (G15: +0.2-0.4 GB) is gone, and its wrap-phase
  array lands where the released graph used to be. It wins -110..-120 ms of wrap beyond A-vs-A (A2 - A1 wrap
  +0.005 s), and the peaks stay well under the budget (8 GiB: 5.98 GiB; 4 GiB: 3.90 GiB, gated to `fast`).
  So **`par_transient` is the default below 20 GiB when the graph is released**. With the cache on (no
  release) it stays opt-in: P raises the peak by +0.20 GiB (8/8), which this item may not do.
  `RISC0_G16_METAL_WITNESS=fast` restores `fast`.

## (4) Compact cache cleanup

- Fix round 1: a version-1 process (`RISC0_G16_METAL_COEFF_ORDER=natural`) that writes its cache and then
  fails to read it back (for example a version-2 process's GC deleted the file in between) now uses the
  coefficients it just built (`BuiltUncached`) instead of failing the load. Test
  `readback_failure_uses_the_built_coefficients` (deletes the file between write and readback, then checks
  the compact output against the full coefficients).

- `CompactCoeffs::load` (version 2, the default) deletes the version-1 file of the same original after the
  version-2 cache has loaded (from disk or freshly built). The key of each older version is recomputed
  (`source_key_v`: the version is hashed into the key, so the file names differ).
- Newer versions are never deleted, so the `RISC0_G16_METAL_COEFF_ORDER=natural` revert (version 1) keeps
  version 2, and neither are other originals' files.
- Knob: `RISC0_G16_METAL_COEFF_CACHE_GC=0`.
- Installed provers: `~/.zkminer/provers/` holds the wave-6 worker (version 2) and `zkminer-prove-risc0-metal.w5c-bak`
  (wave 5c, pre-G15, version 1 only). The backup is not the installed prover. If it is run, it rebuilds its
  version-1 file once (1-3 s), and the next default load removes it again. So nothing in use loses its cache
  permanently.
- Unit test `superseded_cache_versions_are_removed`: version 1 current keeps version 2; version 2 current
  removes this original's version 1 only.
- End to end (`logs/gc_*`, private `RISC0_G16_CACHE_DIR`): a natural-order wrap built `..4249ef7a..`, then the
  default wrap logged "removed 1 superseded compact coefficient cache file(s)" and only `..6c0faa3e..`
  remained.
- Side note: the existing `cache_entry_points_succeed` test calls `invalidate_caches()`, which deletes every
  compact cache file in the shared `~/.cache/risc0-groth16`. That is pre-existing; my suite runs used a private
  `RISC0_G16_CACHE_DIR` after the first one did this at 13:53.

## (5) Investigations (time-boxed)

- **Witness count pass "bimodality"** (~30 min). `g9_bench` on the real witness, profile mode, quiet exclusive
  GPU (`logs/inv1_*`):
  - `all` gives 1.2-1.3 ms in 16 + 12 reps, and 21 real wraps (random blinding and fuzz) are all 1.2 ms;
  - `all,-wtr` gives 6.7-6.8 ms in 12/12;
  - `base` gives 3.0 ms in 12/12.

  The two modes are the `wtr` switch, deterministic per variant. G15's "independent of `wtr`" does not
  reproduce; its runs were heavily contended and interleaved variants in one process. The default (`wtr` on)
  is the fast mode, so there is nothing to fix. A plausible mechanism, not verified: with `wtr` each thread
  writes its 8 transposed words before its atomics, which spreads the arrivals on the hot bucket (window 0,
  digit 1).
- **G14's segment-reduce gap** (~35 min). Confirmed (`logs/inv2_a.log`, 10 reps):
  - B2 `segment_reduce` is 36.4-37.1 ms with `nofuzz` (the default) against 27.6-28.4 with the fuzz;
  - each G1 MSM is 8.2-9.6 against 6.3-6.6.

  Ruled out:
  - bucket gaps: `msm_segment_reduce` runs `msm_mul_var(running, g)` for gaps g > 1. A simulator of the Booth
    c = 16 digits over the real witness (`inv2/g`) finds every bucket of every window nonempty in both modes
    (~1.3M large scalars per window), so there are 0 gaps > 1 and no extra point operations;
  - G15's structure counts (segments, transitions, final-multiplier bits).

  Left: value-dependent arithmetic (e.g. the hot window-0 bucket's piece sums, or the equal/infinity special
  cases of `Xyzz::add`). The next step would be a counter of `add` special-case hits per mode. Not a clear
  bug. No change.

## Fix round 1 (review findings)

Two blocking findings, each reproduced by a kept test that failed on the round-0 code
(`fix1/repro_before.log`, the round-0 test binary with the new tests) and passes now
(`fix1/repro_after*.log`):

1. **Test isolation (PLAN 8.7)**: the drop counter `graph_release_and_rebuild` asserts on counted every
   `Graph` drop, including the throw-away evaluators of `witness_evaluators_bit_equal`, which runs in
   parallel without the lock. `uncached_graphs_do_not_count_as_cached_drops` failed (`left: 2, right: 1`).
   Fix at the root: only graphs built for the process cache (`Graph::cached`) are counted, so no other test
   can move the counter; the tests asserting on it hold `gpu_test_lock()`.
2. **The pressure-drain hook grew the footprint with the large cache on**:
   `release_hook_keeps_the_graph_with_the_large_cache_on` failed ("the hook dropped the graph with the large
   cache on", 1 drop). Fix: `release_idle` / `release_graph` are no-ops unless `idle_release_allowed()` (see
   (2)); the heavy `w7g1_hook_cycle` loop is flat after the fix.

Non-blocking findings also fixed: overlapped-wrap release (`release_slot`, guard `done`), the `par_transient`

## Fix round 2 (review finding: a drain during a wrap)

**Finding.** The pressure-drain hook could drop the graph while a wrap was running. `gpu_prove` took the
graph only for its path decision (`is_par()` / `is_par_transient()`, which dropped the handle at once) and
again at the witness. In between, `pre_gpu`, the key load and the GPU-lock wait ran with the cached `Arc`'s
strong count at 1, so `release_idle_now` saw it as idle. The wrap then rebuilt the graph synchronously:
0.7-0.9 s, and on the in-place path under `hal::metal::exclusive()` with the key resident. This is exactly
where W7-A1's drain would fire.

**Reproduced first** by the kept test `drain_during_a_wrap_keeps_its_graph`: three wraps, each calling the
hook's mechanism (`release_idle_now`) from `pre_gpu`, then `check_proof`. It asserts the drain frees nothing
and `builds()` does not change during the wrap. On the round-1 code it failed in cycle 0 ("built it
synchronously in 518.1 ms", builds 1 -> 2; `fix2/repro_before.log`). It passes now, in the default
environment and with `MallocLargeCache=0` at 8 GiB (`fix2/repro_after*.log`). The cache-off run has a wrap of
602-624 ms with no synchronous build, against the review's 1348-1453 ms.

**Fix at the root: a wrap is "in use" for all of it, not only while it holds a handle.**
- `metal_witness::WrapGuard`: a counter of wraps in progress. `gpu_prove` begins one as its first statement
  (inside `ReleaseGraphAfterWrap`, dropped after the release) and ends it when it returns. The counter
  changes only under the `SLOT` lock, and `release_idle_now` checks it under the same lock. So a drain and a
  wrap start are ordered: either the drain sees the wrap, or the drop happened before the wrap started.
- The in-place path holds its graph from the path decision to the witness (`par_graph()` returns the
  `Arc`; `is_par()` is gone), so there is no second lookup.
- **Prestart reservation (intended trade-off).** `prestart` (called before identity_p254) calls
  `reserve_for_wrap()`. The next `WrapGuard` takes the reservation, and one that no wrap takes lapses after
  `RISC0_G16_GRAPH_RESERVE_MS` (default 30 s; `0` = no reservations). While a reservation is live, the drain
  leaves the graph alone. A drain during identity_p254 would not lower the wrap's peak, because the witness
  needs the graph anyway. It would only move the 0.7-0.9 s rebuild onto the wrap's critical path. A reservation
  that leaks (identity_p254 failed and no wrap followed) costs at most 30 s of a resident graph.
- **After-witness release (the overlapped-wrap open issue, also fixed).** `release_slot(held, own)` empties
  the cache only when no wrap besides the caller is in progress and no reservation is live. The last wrap out
  releases. A wrap that failed before its witness (no handle) can no longer discard a graph that a concurrent
  wrap or the next job's prestart needs. This closes the round-1 reviewer's non-blocking point about
  `ReleaseGraphAfterWrap::drop` -> `release_slot(None)`.
- Unit test `wraps_in_progress_and_reservations_keep_the_graph` covers these cases:
  - a drain with a wrap in its `pre_gpu`;
  - two wraps in progress, where the first one's release does nothing with or without its handle;
  - a live reservation against a drain and a failed wrap's release;
  - a drain after the reservation is taken and the wrap has finished, which drops the graph.

  The `cache_entry_points_succeed` test calls `prestart_prover()` with no wrap. It clears its reservation
  (`clear_reservations`, test-only) so that it cannot hold the graph against later idle-release tests in the
  same process (PLAN 8.7).

Non-blocking findings also fixed:
- `fast.rs` latches only a failed *first* build (`PROGRAM_BUILT`), as `metal_witness` does. A failed rebuild
  after a release fails that call, and the next call tries again.
- Doc numbers: a rebuild with the digest known is 0.68-0.94 s measured (digest + parse 240-265 ms), not
  "~0.5 s". `prove::release_graph`'s doc now says this and describes the in-use rule.

## Recommendations for W7-M11 (18 GB tier, po2 20) and zk-miner

- **Spawn the Metal worker with `MallocLargeCache=0` on small Macs** (working-set limit below 20 GiB). This is
  what turns the risc0 release on:
  - process peak -1.17 GiB at 8 GiB and -1.22 GiB at 4 GiB per `BENCH_ONLY` job, -1.8 GiB over the full suite;
  - wrap -120 ms at 8 GiB (`par_transient`);
  - cost: STARK +0.4-0.5 % at those budgets;
  - leave it unset at >= 20 GiB, where nothing is released.

  M9's recycle growth net then sees a flat idle footprint (568 MiB host after the wrap, against 2.3 GB).
- Footprint model for the 18 GB tier, per phase:
  - phase peak ~= Metal phase peak + host;
  - host = ~0.15-0.26 GB in the STARK phases with release + cache off, against 1.4-2.0 GB now;
  - wrap phase: Metal 5.4 GiB (8 GiB budget) plus the graph build (0.9 GB `fast`, ~1.05 GB `par_transient`),
    which sits beside identity_p254, not the STARK.

  A po2 20 STARK (Metal ~9.4 GiB) plus ~0.3 GB host is ~9.7-10 GB of footprint instead of ~11.2 GB.
  Measure on the real tier.
- Without the env var, do not force `RISC0_G16_GRAPH_RELEASE=1`: it raises the footprint by ~0.58 GB per proof.
- **Set `MallocLargeCache=0` in the spawn environment** (`Command::env`), never with `set_var` inside the
  worker: libmalloc reads it only at process start, and the risc0 check cannot tell the difference.
- Pipelined jobs: since fix round 2, the graph is released only by the last wrap out and never while a job's
  prestart reservation is live. Overlapped or pipelined wraps therefore share one build. While two jobs'
  wraps overlap, the graph (~0.9-1.05 GB) stays resident across both, so count it once per overlapped
  window, not per job. Call `prestart_prover` before each job's identity_p254, as the zkvm does.
- The zk-miner "graph ready 0.00 s after the preload" log line is misleading with release on (preload is a
  no-op then); fix it on the zk-miner side.
- `par_transient` adds ~+0.29 GiB to the wrap-phase peak against release + `fast` at 8 GiB (R -1.115 vs RF
  -1.400); harmless at 8 GiB, where the process peak is in the STARK phases, but count it in the 18 GB model.
- Budgets between 8 and 20 GiB (24 GB Macs) were not measured; only the headroom gate protects them.

## Open issues

- **libmalloc large cache.** The whole saving depends on `MallocLargeCache=0`, a launcher setting.
  - A risc0-side alternative would be an allocation pattern that never frees through malloc: a reserved
    node array, or an mmap-backed graph. That needs `circom_witnesscalc` (`VecNodes` has no `with_capacity`;
    `MMapNodes` exists) and `witness_fast` / `witness_par` (not owned here) to take another node storage.
  - That would also cut the ~0.43 GB of build intermediates that A holds today.
- The cache-off allocator costs ~+40-60 ms of STARK at small budgets (fresh zero-filled pages for large host
  allocations). The host allocations responsible were not identified. A pool for the largest per-segment host
  buffers would recover it.
- `par_transient`'s build (0.9 s first, 0.68 s rebuild) is as long as identity_p254 (0.9 s). One of 3
  final-check wraps waited 10.7 ms, and one loaded `fast` run waited 206 ms. Caching the compiled schedule (G13
  open issue) would remove it.
- identity_p254 is +4..+11 ms beside the graph build (CPU and page-fault interference). A lower-QoS build
  thread was not tried, because it risks making the wrap wait.
- W7-A1's registry should register `risc0_groth16::prove::release_graph` (owner: the registry / zkp side).
  - Since fix round 1 it does nothing in a process with the large cache on.
  - Since fix round 2 it also does nothing while a wrap is in progress (from the top of `gpu_prove`) or a
    prestart reservation is live, so it cannot force a synchronous rebuild.
  - It frees memory only when the graph is idle in a process spawned with `MallocLargeCache=0` (or
    `RISC0_G16_GRAPH_RELEASE=1`).
  - With release on, the wrap has usually freed the graph already, so the hook mostly returns 0 (see the
    hook-cycle runs).
- The prestart reservation is a fixed-time lapse (30 s). A job whose identity_p254 takes longer than that
  under heavy swap is again exposed to a drain-then-rebuild. That case was not measured.
- `par_graph()` can still build the graph synchronously before `pre_gpu` when the prestart build is not
  ready. This predates the item, and the logs show the waits are 1-98 ms under load. A slow build delays
  `pre_gpu`'s release of the STARK pools by that much.
- The headline peak saving combines the release and the allocator setting: of -1.20 / -1.21 GiB (8 / 4
  GiB), ~0.33 GiB comes from `MallocLargeCache=0` alone (arm L); the code's share is ~-0.85 / -0.88 GiB.
- The compact cache GC deletes version 1 whenever version 2 loads; it does not inspect installed binaries
  (only `~/.zkminer/provers/*.w5c-bak` uses version 1, checked by hand). Alternating v1 and v2 processes
  rebuild and delete 324 MB repeatedly.
- The digest memo slightly weakens the integrity check on rebuilds (knob `RISC0_G16_GRAPH_REVERIFY=1`).
- The 8 GiB A/Bs were never fully quiet: the round-1 run peaked at load ~20, the round-2 run at load 16.5
  (median 5.2). The round-2 run reproduced the `par_transient` default's -105 ms wrap at 0/8 > 0.
- `g14_witness_like_scalars` failed once in 3 full sys-suite runs (a G2 MSM mismatch, all r - 1, n 2^17,
  config without G9 tunings) and passed 8/8 alone. No MSM code changed in this item. It looks like an
  intermittent defect under the parallel harness (R17-like). It should be stress-run by the MSM owner.
- The zkvm `shrink_wrap` test cannot run at a 4 GiB budget (5 parallel wraps); pre-existing.
- G14's segment-reduce gap: see (5); not resolved.
