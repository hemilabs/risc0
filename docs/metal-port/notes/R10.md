Branch `metal/R10`, based on `zkminer/metal` (`a695b814b`). Plan sections followed: 2.0 (one queue,
`eval_check_dep` no-op), 2.1 (poly_mix as `const device FpExt*`), 2.6 (phase ends with a sync), 2.9,
4.2 (R10 row, host glue "eval_check = CPU tables -> one command buffer -> wait"), 9.1 (memory, budgets).

`require(Phase)`, `EXPECTED_KERNELS` row `(EvalCheck, ["eval_check"])` already present).

## What was ported
`MetalCircuitHal::eval_check_metal` mirrors `hal/cuda.rs::eval_check` (lines 208-265) and the host
part of CUDA `risc0_circuit_rv32im_cuda_eval_check` (`eval_check_kernel.cu`):
- `rou = ROU_FWD[po2 + log2(INV_RATE)]`, `domain = steps * INV_RATE`;
- poly_mix powers on the CPU: `map_pow(poly_mix, POLY_MIX_POWERS)`, with
  `const _: () = assert!(NUM_POLY_MIX_POWERS == 458)` (as cuda.rs) and a runtime length assert. They go
  into `ScratchBuffers::poly_mix` (grown via R7's `grow`, reused across segments) with `view_mut`,
  which flushes and waits if a batch is open, so a buffer still read by an earlier dispatch is never
  overwritten. CUDA copies them into `__constant__` memory; 7328 B exceeds the 4 KB `set_bytes`
  limit, so here it is a buffer binding (R6 ABI index 9);
- one dispatch, R6 ABI: `0 check, 1 ctrl (REGISTER_GROUP_CODE), 2 data, 3 accum, 4 mix, 5 out,
  6 rou (KernelArg::Bytes of the raw Val), 7 po2, 8 domain (KernelArg::Integer), 9 poly_mix`;
  `Grid::Groups { ceil(domain/256), 256 }` (CUDA `EVAL_CHECK_THREADS`);
- `self.hal.try_sync()` at the end of the phase; a command-buffer error is returned. Also checks
  `check.size() == 4 * domain` and `domain <= u32::MAX`, and calls `ctx.require(Phase::EvalCheck)`.
- `CircuitHal::eval_check` dispatches to it, and panics with the error plus the hint
  `set RISC0_METAL_RV32IM_CPU_PHASES=eval` (the trait returns `()`; CUDA's `ffi_wrap` panics too).
- `eval_check_dep`: default no-op (one queue). `accumulate`: unchanged empty no-op (PLAN 8.4).
- Debug log at the end of the phase: `eval_check (Metal) done: currentAllocatedSize N B, process peak N B`.

**CPU fallback**: R7's delegation is kept as `eval_check_cpu` and is selected per call by
`RISC0_METAL_RV32IM_CPU_PHASES` naming `eval` (comma list, case-insensitive, whitespace ignored;
`phase_listed()` and `CPU_PHASES_ENV` are `pub(crate)` in `eval_check.rs`). Note for R8/R9 and the
merge agent: the parser lives in eval_check.rs so mod.rs stays untouched. If R8/R9 also add one,
R11 may move a single helper into mod.rs.

## Tests (hal/metal/tests.rs)
- `eval_check_matches_cpu_po2_{4,10,16}`: random canonical inputs (`Val::random`, uniform in [0, P)).
  Code, data and accum groups use the TAPSET widths; mix and out use the circuit sizes; poly_mix is random.
  `CpuCircuitHal::eval_check` is the reference. Each test compares three paths:
  - `eval_check_metal`, which must be bit-exact over all `4*domain` elements (the mismatch count is reported);
  - `eval_check_cpu` over the same Metal buffers;
  - at po2 <= 10, the `CircuitHal::eval_check` entry point, with a check that the `PHASE_CALLS` counter grew.
  Each test prints the time and `currentAllocatedSize` per run.
- `eval_check_reuses_poly_mix_buffer`: po2 5, 4, 6 in sequence with fresh poly_mix values, bit-exact
  each time, and the same poly_mix buffer is reused.
- `cpu_phases_list_parsing`.
- The existing `segment_prover_uses_metal_hal` now proves and verifies a real po2 13 segment with the
  GPU eval_check. The debug log shows `eval_check (Metal): steps 8192, domain 32768, po2 13`.

## Measurements (indicative; shared GPU, PSOs warm in the OS shader cache)
| po2 | domain | Metal eval_check (alloc poly_mix + dispatch + wait) | CPU HAL (rayon) | `currentAllocatedSize` at the end of the phase (process) | Phase buffers |
|---|---|---|---|---|---|
| 4 | 64 | 140-148 ms | 0.8-9 ms | 14.5 MB | inputs 81 KB + check 1 KB + poly_mix 7.3 KB |
| 10 | 4096 | 134-147 ms | 22-129 ms | 19.6 MB | inputs 5.2 MB + check 64 KB + poly_mix |
| 13 (real segment) | 32768 | n/m | n/m | 84.3 MB (whole prover so far) | |
| 16 | 262144 | 478-501 ms | 2.0-2.4 s | 349 MB | inputs 330 MB + check 4.2 MB + poly_mix |

- The phase allocates only the 7328-byte poly_mix buffer (pooled and reused). Its peak is therefore the
  inputs + check that the prover already holds. `peak_allocated_size` equals `allocated_size` in every run.
- The roughly 140 ms floor at small po2 is per-HAL first-use overhead (a new HAL per test). R6 measured
  9-12 ms per dispatch on a warm queue. Not investigated.
- **Budgets:** no tested shape exceeds 4 GB or 8 GB (the max is 349 MB at po2 16), so no budget error was
  triggered. If the poly_mix allocation exceeds the budget, Z6's
  `Metal working-set budget exceeded ...` panic is raised from `alloc_buffer` inside `grow`. The input
  buffers are owned by the prover, not by this phase.
- Cold PSO: the `eval_check` PSO is built at the first rv32im circuit HAL construction (it is in
  `METAL_KERNEL_NAMES`). R6 measured 54 s cold. In these runs it was already cached.
