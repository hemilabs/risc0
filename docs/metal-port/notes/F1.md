# F1 — compat headers + build_kernel (Metal)

Branch `metal/F1`. Plan rows/sections followed: section 3 row F1, 2.1–2.3, 2.8, errata 8.5
(`threadgroup Fp x[8]` rejected by today's fp.h) and 8.6 (`.air` placement, `METAL_INCS`), and
CRITIQUE gap 11 (`__ballot_sync` cast) and gap 13 (absolute sources).

## What was done

### `build_kernel/kernels/metal/fp.h`, `fpext.h`
- `constexpr` constructors qualified `threadgroup`, `device` and `constant` next to every existing
  constructor (default, `uint32_t`, the private raw one; for FpExt: default, `uint32_t`, `Fp`,
  four `Fp`s). MSL only constructs an object in a non-thread address space through a constructor
  qualified with that address space; this is what makes `threadgroup Fp x[8]`,
  `threadgroup FpExt y[4]` and program-scope `constant Fp`/`FpExt`/`constant Fp tab[N]` legal.
  - FpExt's `threadgroup`/`constant` constructors build `elems` in the member initializer from raw
    words (`{x.asRaw(), true}` → Fp's private raw constructor; hence `friend struct FpExt;` in
    Fp). A `constant` object can't be assigned to in the body, and a thread `Fp` prvalue can't
    copy-construct an `Fp` in another address space.
  - FpExt's `device` constructors assign in the body: metal 32023.922 rejects the array member
    initializer for a `device` object ("no viable constructor copying array element").
- All binary, unary-minus and comparison operators are now **by-value hidden friends**
  (`friend constexpr Fp operator*(Fp, Fp)` …), so any operand may be thread, threadgroup, device
  or constant: it is copied into a thread value. The old member operators (thread and
  `device const` variants) were removed, because a member and a by-value free overload with the
  same parameter types are ambiguous for thread operands; every expression that compiled before
  still compiles with the same result (`Fp op uint` still converts the right operand; as a free
  function `uint op Fp` now also works). The old free `operator*(Fp, FpExt)` became a hidden
  friend of FpExt.
- Compound assignment stays a member (it mutates `*this`): existing overloads kept, plus
  `threadgroup` overloads of `+= -= *=` for Fp and FpExt (and `device` overloads of `-=`/`*=`,
  only `+=` had one). Accessors (`asUInt32`, `asRaw`, `zeroize`, `constPart`) are unchanged: copy a
  non-thread object to a thread local first (plan 2.1 convention).
- `operator=(uint32_t)` is unchanged; nothing was added that resolves `x = 0`. Measured status of
  `Fp x = 0;` / `x = 0;` / `device_ref = 0;` is identical before and after this change: under the
  compiler's default std (metal 4.1, `__METAL_VERSION__ 410`) `x = 0` on a thread Fp is
  **ambiguous (error)**, the other two compile; under `-std=metal3.2`/`metal3.1`/`metal4.0` all
  three compile (compiler behaviour, not the header). The convention stays `Fp(0)`.

### `cuda2metal.h` (new, plan 2.3)
`__device__/__host__/__forceinline__` → `inline` (with `-Wduplicate-decl-specifier` silenced for
`__device__ inline`), `__noinline__` → `__attribute__((noinline))`, `__restrict__` → empty;
`__syncthreads()`; `__syncthreads_device()`; `__syncwarp([mask])` → `simdgroup_barrier`;
`__shfl_{down,up,xor}_sync`, `__shfl_sync` and the non-sync forms as templates over
`simd_shuffle_*` (plus 64-bit overloads of the `_sync` forms that shuffle two halves; no `width`
overload, so a sub-warp width fails to compile); `__ballot_sync(m, p)` →
`(uint)(simd_vote::vote_t)simd_ballot(p)` (errata cast); `__popc/__popcll/__clz/__clzll/__brev`,
`__ffs` (= `ctz+1`, and 0 for 0 as in CUDA); `__umulhi/__umul64hi` → `mulhi`; `__ldg/__ldcg(p)` →
`*(p)`; `atomicAdd/atomicOr/atomicCAS` for `uint`/`int` on device and threadgroup memory, taking
either atomic or plain pointers, relaxed (CAS loops on MSL's weak CAS so it is strong like CUDA's);
`WARP_SZ`/`warpSize` = 32; `asm(...)`, `__asm__(...)`, `__builtin_assume` → nothing;
`__builtin_elementwise_min` → `min`; `opq(x)` → identity; `<metal_assert>` included first, then
`#undef assert` / `assert(x) ((void)0)`; `R0_FAULT(flag, cond)` (sets a thread-local `uint` flag,
e.g. `ctx.bad`, when `cond` is false) + `r0_fault_flush(device atomic_uint*, flag)` (one relaxed
OR per thread at kernel end, plan 2.0/2.9); `printf(...)` → no-op; `r0::array<T, N>` (aggregate,
`operator[]` for every address space, `size()`, `data()`) exposed as `cuda::std::array`.

### `sppark_compat.h` (new, plan 2.2)
`bb31_t`/`fr_t` → `Fp`; `bb31_4_t`/`fr4_t`/`md4_t` → `FpExt`; `index_t` → `uint`. A typedef can't
add members, so sppark's members are free functions: `zero(x)` (thread/threadgroup/device refs),
`csel(a, b, sel_a)`, `reciprocal(x)` (= `inv`), and free `operator^(Fp|FpExt, unsigned)` (= `pow`).
Porting rule: `x.zero()` → `zero(x)`, `T::csel(a,b,s)` → `csel(a,b,s)`, `x.reciprocal()` →
`reciprocal(x)`, `x ^ p` unchanged.

### `build_kernel/src/lib.rs`
- `METAL_INCS` (now `pub`) gains `cuda2metal.h`, `sppark_compat.h`.
- `KernelBuild::metal_flags()`: `-std=metal3.2` unless a `-std=` flag was given, `-O2` unless an
  `-O` flag was given, then the `.flag()`s; plus `-frecord-sources -gline-tables-only` under
  `RISC0_METAL_DEBUG_SOURCES=1` (plan 2.8; `rerun-if-env-changed` emitted). Passed to every
  `metal` invocation.
- `KernelBuild::metal_cache_key(sdk, toolchain)`: SHA-256 over effective flags, SDK, toolchain id
  (first line of `metal --version` + SDK name/version), the `METAL_INCS` contents, and, labelled by
  path and length-prefixed, every source, every file under each include dir (recursive, via
  `kernel_source_files`) and every dep (file, or recursively a directory — no more panic on a
  directory dep). `OUT_DIR` in paths/flags is replaced by a placeholder.
- `compile_metal` now uses the crate's free `cached_compile` (atomic temp + rename, day-old pruning)
  in the same `risc0_cache()` dir, keyed as above; the old private method and `Hasher` are gone.
  Per-file `cargo:rerun-if-changed` for every input (`metal_input_files()`). `<OUT_DIR>/_sys_`
  headers are rewritten only when their contents differ.
- `.air` files go to `<OUT_DIR>/<output>/<rel>.air` where `rel` = source path stripped of
  `OUT_DIR`, else of `CARGO_MANIFEST_DIR`, else of its root (`..` → `_up_`)
  (`pub fn metal_air_rel_path`). Before, they went to a temp dir under the cache, and an absolute
  source's `.air` landed beside the source (errata 8.6).
- `pub fn find_metal_toolchain() -> MetalToolchain { sdk, metal, metallib, version }`: honours
  `METAL_TC` (`$METAL_TC/usr/bin/metal`, panics if missing), else `xcrun --sdk <sdk> --find metal`,
  else `metal` on PATH; `metallib` beside it, else via xcrun/PATH; panics with a hint to
  `source /Users/user/zkminer/env.sh` (or set `METAL_TC`). Tools are run as
  `xcrun --sdk <sdk> <absolute tool path>`: running `metal` directly (no SDKROOT) records
  `air64_v27-apple-macosx15.0.0` instead of `air64_v29-apple-macosx27.2.0`, i.e. a different
  output from today's `xcrun --sdk macosx metal`; via xcrun the `.air` is byte-identical.
- `RISC0_SKIP_BUILD_KERNELS` still writes an empty `skip-<output>.metallib` and prints
  `cargo:<output>=`.

## Assumed / not verified
- Runtime behaviour of kernels built with the new headers beyond the 18 zkp DualHal tests (no GPU
  test exercises threadgroup Fp/FpExt arrays, cuda2metal shuffles/ballot/atomics or sppark_compat
  at runtime yet; they are compile-checked only). The `atomicCAS` retry loop's strong semantics
  and the 64-bit shuffle split are by construction, not runtime-tested.
- iOS SDK paths (`iphoneos`/`iphonesimulator`) are untested (no iOS SDK here).
- The "metal not found" branch without `METAL_TC` could not be exercised: xcrun finds the
  mounted toolchain even with an empty environment.

## Known gaps / deviations
- `__syncthreads_device()` orders device **and** threadgroup memory (plan text says `mem_device`;
  the superset keeps CUDA `__syncthreads()` semantics for kernels that also use threadgroup memory
  across the barrier).
- `cuda2metal.h` goes slightly beyond the 2.3 list (`__shfl_sync`/`__shfl`, `__popcll`,
  `__clzll`, `__asm__`, 64-bit shuffles, `r0_fault_flush`); nothing in it conflicts with the zkp
  kernels.
- `R0_FAULT` takes a flag lvalue (`ctx.bad`), not a context; translators pass `ctx.bad`.
- Default std `-std=metal3.2` makes `x = 0` on a thread Fp compile (it is an error only under the
  compiler's own default metal 4.1). This is compiler behaviour; the header is unchanged in this
  respect. Reviewers who want it rejected everywhere need a header change (e.g. a deleted
  `operator=(int)`), which F1 deliberately did not make.
- No accessor overloads (`asUInt32`/`asRaw` etc.) for threadgroup/constant objects: copy first.
