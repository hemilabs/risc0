# Z12: release the segment prover before recursion; segment po2 per budget tier

LEADS #34 (pipeline-release-segpool-po2-up, merged with platform-mem-max-not-sum and
recursion-small-budget-po2). Branch `metal/Z12`, based on `zkminer/metal` f1f192832.

## Summary

- **The hypothesis was only partly right.** The recursion phase's peak *is* the sum of the segment
  prover's held memory and recursion's own (4 GiB, po2 17: 3801 MiB = ~1.9 GB held + ~1.9 GB). But
  that sum does **not** decide which segment po2 fits under a budget. Under
  `RISC0_METAL_MAX_WORKING_SET_BYTES` the allocator drains every pool before it refuses, and the
  stacked recursion peak stays under the budget anyway. **What fails first is the segment phase
  itself**: po2 19 at 4 GiB and po2 20 at 8 GiB are refused while proving a segment, with or without
  a release.
- **The real gain is in zk-miner's tier table (M8).** That table is one po2 too conservative. It was
  derived from unconstrained peaks: the recursion phase *with* the segment pool, measured at a large
  budget. Under the enforced budget, po2 18 at 4 GiB and po2 19 at 8 GiB prove, wrap and verify
  today, without this change. On memory-merkle they cut the STARK by about 60 % and about 43 %
  (table below).
- **The code change** (`RISC0_METAL_RELEASE_SEG_BEFORE_REC`, budget-driven by default) drops this
  thread's cached segment prover before lift/join when what is allocated, plus recursion's ~2 GiB,
  exceeds the working-set limit.
  - Forced (`=1`), it takes the recursion phase down to recursion's own ~1.7-1.9 GB, i.e. the true
    peak becomes max(segments, recursion) instead of the sum. Measured: 4 GiB po2 18 recursion peak
    3321 -> 1719 MiB and process lifetime footprint 8.04 -> 7.10 GB; po2 17 3801 -> 1918 MiB and
    footprint 8.6-9.1 -> 6.58 GB; 8 GiB po2 19 recursion 4772 -> 3080 MiB.
  - In auto mode it does **not fire in any of the recommended tiers**, because there both fit (see
    "Auto rule").
  - It fires only when the budget really cannot hold both, which is where it avoids drain churn.
    At the default budget it never fires, so that path is unchanged by construction.

## Recommendation: segment po2 per budget tier (for M8)

| GPU working-set limit | segment po2 | basis (enforced-budget peaks, MiB) |
|---|---|---|
| < 6 GiB (4 GiB tier) | **18** (today 17) | segments 2476, recursion 3321 (1719 with release), wrap 3926; po2 19 is refused in segments |
| 6 to < 10 GiB (8 GiB tier) | **19** (today 18) | segments 4768, recursion 4772 (3080 with release), wrap 4772; po2 20 is refused in segments at 8 GiB |
| >= 10-12 GiB | **20** | segments 9404, recursion 11100 (default budget). Not measured at 10/12 GiB: the boundary is about 9.4 GB of segment peak plus margin, so M8 should verify 10 and 12 GiB before using 10 |

Caveats for M8:
- These are GPU working-set numbers. A real 16 GB Mac has no enforced budget, so the pools are not
  drained under pressure and the stacked recursion-phase peak is real memory.
  - The process footprint runs 4.5-5.5 GB above the Metal peak (BASELINES; critic-host-footprint).
  - Where host RAM is tight, M8 can set `RISC0_METAL_RELEASE_SEG_BEFORE_REC=1` in the worker. In the
    worker this costs nothing per job, because the wrap's `release_hal_buffers` drops the segment
    prover after every proof anyway. It cuts the lifetime footprint by ~1 GB at po2 18 and by ~2 GB at
    po2 17, and by nothing at po2 19, where the segment phase dominates.
  - I could not show a time cost or a time gain from `=1` under this contention. The r3 worker runs at
    4 GiB/17 were slower with `=1` (67, 73 s against 37, 45 s), but the in-process A/B was a coin flip
    (below). Re-measure on a quiet machine before making it a worker default.
- The table changes M6's `stark_peak_bytes` model. That model is the unconstrained recursion-phase peak
  (segment pool + recursion) and should stay as the "no budget" footprint figure.

## The change

- `prover_impl.rs`: `release_segment_prover_before_recursion()` runs at the start of
  `ProverImpl::composite_to_succinct`, which covers both `prove_session` with succinct/Groth16 and the
  staged `compress` that the worker benchmark uses. It also runs before `composite_to_succinct_povw`,
  which folds through the generic `Compress`.
  - Decision: `seg_release_reason(mode, (limit, allocated))`. It releases when
    `allocated + REC_PEAK_BYTES > limit`.
  - It drops only this thread's cached segment prover (`release_cached_segment_prover`), not the
    recursion provers that lift/join is about to use.
  - It does not touch the `succinct_to_groth16` release lines (C13's).
- `risc0-zkp` `hal::metal::device_memory()` (additive): returns the working-set limit, using the same
  rule as `MetalHal::working_set_limit` for an un-overridden HAL, and the device's
  `currentAllocatedSize`, without making a HAL.
- Knob `RISC0_METAL_RELEASE_SEG_BEFORE_REC`: `0` = pre-Z12 (never release), `1` = always release,
  unset = auto (budget-driven).

### Auto rule

At recursion start, held + 2 GiB against the limit:
- 4 GiB/po2 18: 1.5 + 2 = 3.5 GB, so it keeps the prover.
- 8 GiB/po2 19: 3.4 + 2 = 5.4 GB, keep.
- default/po2 20: 9.4 + 2 GB against 28 GiB, keep.

It fires only for configurations past the recommended tiers, e.g. 4 GiB with more than ~2 GB held, or
8 GiB with more than ~6 GB held, where the stacked phase would otherwise depend on pool drains. Making
auto fire at the recommended tiers would need a host-RAM-aware criterion (open issue), not this GPU
budget rule.

## A/B

- **Default budget, worker memory-merkle po2 20, knob 0 (A) vs auto (B), interleaved, 4 pairs** (d1;
  the planned 7 did not fit in the session's time under this contention).
  - Recursion phase (the only phase the change touches): A 4.21, 3.51, 6.69, 4.94 s (median 4.58);
    B 4.18, 5.97, 4.70, 5.86 s (median 5.28). The A-vs-A spread is 3.2 s.
  - Peaks identical (9404 / 11100 / 11100 MiB).
  - Whole STARK: A 19.3, 13.7, 29.8, 38.4 s; B 16.3, 384.5, 33.8, 38.8 s. The segment phase swung from
    10 to 378 s from external GPU contention.
  - Verdict: **no change**. Auto takes the no-release branch at the default budget (the harness shows
    `seg-release=0` on every B rep), so the code path is the old one plus one `MTLDevice` query per
    recursion.
- **Default budget, in-process harness po2 20, 5 segments** (`ab_def_20.log`, 8 A / 7 B reps before the
  timeout): recursion A 1.50-3.19 s (median 2.03), B 2.06-2.56 s (median 2.25). Release fired 0 times
  in B. The spread exceeds the difference: **no change**.
- **4 GiB po2 17, forced release, in-process** (`ab_4g_17.log`, `ab_4g_17b.log`, 13 pairs): the
  per-pair B-A recursion differences ranged from -26 s to +26 s, with recursion 7.8-41 s for the
  same 51 proofs. **Inconclusive** under contention. Not used to justify any default.
- **4 GiB po2 18, forced release, in-process** (`ab_4g_18.log`, 7 pairs): recursion A median 5.18 s,
  B 7.20 s, with ranges A 3.7-9.5 and B 2.8-9.8. Inside the spread: **no change** claimed.

## Correctness

- `tests_z12::z12_release_reason`: the decision, pinned at the measured held sizes per tier.
- `tests_z12::z12_release_then_reprove`:
  - A forced release inside `prove(succinct)` (under the session's GPU lock: no deadlock).
  - The succinct receipt verifies.
  - The next session on the same thread rebuilds the segment prover; mode 0 does not release.
  - The same journal and claim digest come out of both sessions.
  - Thread-local mode override, so tests running beside it are unaffected.
- Every worker run above verified its Groth16 receipt (`verified`), including the forced-release runs.
- Gates, release profile, default parallel harness:
  - `risc0_zkvm` lib `host::server::prove --skip bench`: 99 passed, 3 ignored, run twice.
  - `host::recursion --skip bench`: 13 passed.
  - `tests_z12`: 2 passed, run twice.
  - `cargo test -p risc0-zkp --features metal --release --lib -- hal::metal`: 168 passed, 29 ignored.
  - The bench tests under `host::recursion` were not run: they did not finish in 10 minutes on the
    contended GPU.
- `cargo clippy --all-targets` does not get past pre-existing denials that this item did not touch:
  `type_complexity` in zkp `prove/fri.rs` and `prover.rs`, and errors in `recursion-sys/build.rs`.
  The test builds compile with `-D warnings`.
- No Metal kernel changed, so R17 ir_scan / run_stress do not apply.

  cycles) did not get past segment proving in 150 s, while po2 16 takes ~1 s. This predates Z12 (the
  knob=0 path is the old path). Not investigated; the Z12 test uses po2 16.
- Quiet-machine re-measurement of the tier table's times and of `=1`'s time effect (this session was
  contended throughout).
- The 6-10 GiB and 10-12 GiB boundaries were measured only at 4 and 8 GiB and at the default budget.
