## Summary
- **hoist (WIN, default on).** The Metal form of ROCm's `hoist_hip.py`, in `to_metal.py` (`hoist_loads()`): in
  each of the 22 chain functions the body is cut into windows of 6 statement lines. Each of the 3,844 distinct
  trace words (pointer, column, row offset) first read in window j is read into a raw `uint32` at the start of
  window j - 1, and its uses read that value. The words and the arithmetic, in the same order, are unchanged, so
  the result is bit-exact.
  - Kernel (`ef_variant_bench`, 11 interleaved rounds): the specialized kernel is -16.8 ms at po2 20 (-3.05 %)
    and -4.4 ms at po2 18 (-3.1 %), 11/11 rounds each. The plain kernel is -23.8 / -6.5 ms (-4.1 / -4.4 %),
    11/11. A-vs-A was +1.7 and +0.2 ms.
  - Phase (`prove_po2_sweep`, 7 ABBA process pairs): eval_check is -20 ms at po2 20 (562 -> 542 ms), -5 ms at
    4 GiB / po2 18 and -11 ms at 8 GiB / po2 19, 7/7 pairs each. The po2 20 segment goes 972 -> 952 ms.
  - Fix round 1, independent harness (separate R22 build as A and A2, 9 rotated rounds, section 3.4):
    -17 ms [-27, -12] at po2 20, -5 at 4 GiB / po2 18 and -10 at 8 GiB / po2 19, 9/9 rounds each. A-vs-A
    stayed within [-7, +6] ms.
  - Peak Metal memory is unchanged at every budget.
  - Revert knob: `RISC0_METAL_RV32IM_EVAL_HOIST=0`, which runs R22's flat kernels. Their IR is identical to R22's.
- **pmlag (NO-GO).** The Metal form of `pmlag_hip.py` makes each link's poly_mix row load depend on the
  accumulator W links back, through an opaque zero. It was slower in every round: +22.4 ms (W 4) and +33.5 ms
  (W 8) at po2 20, 0/11 faster each. Not in the tree.
- **ef_combine function-constant specialization (NO-GO).** The proxy hard-codes the domain at compile time,

## 2. Method
- **Kernel.** `ef_variant_bench` runs all arms in one process. Odd rounds run in reverse order, every run is
  compared bit-for-bit with the embedded kernel's output, and there are 11 rounds (the 11/11 rule).
  - The arms are metallibs built from the generated TU by the scratch passes: `build_eval_variant.sh` with the
    build's flags, linking the plain-form and `-DEF_FC_FORM` `.air` files into one metallib, so each variant
    has `ef_combine` too.
  - New bench options in `eval_check.rs`, test code only:
    - `R15E_PSO_ONLY=1` stops after building the PSOs. It allocates no buffers, so it runs under the light
      lock (about 0.55 GB RSS).
    - `R15E_FC_ARCHIVE=<dir>` archives each arm's specialized PSO.
  - Together these keep the 12-20 s per-arm compiles out of the heavy GPU lock. Each timed po2 20 session then
    takes 66-81 s.
- **Phase.** `ab/ab.sh` runs `prove_po2_sweep` processes:
  - `R11_PO2S=<po2> R11_CPU=0 R11_REPS=4 RISC0_METAL_RV32IM_EVAL_FC=wait`, taking the median of reps 1-3.
  - A = `RISC0_METAL_RV32IM_EVAL_HOIST=0` and B = default, same binary, ABBA order.
  - Each pair runs under one heavy lock.

### 3.2 Production form
`to_metal.py`:
- `hoist_loads()` runs after `flatten()`. It pins `COUNTS['hoist_fns'] = 22` and `COUNTS['hoist_loads'] = 3844`.
  Declarations never go inside R22's `#ifdef EF_NEST_FORM` call-site blocks, and a trace load in such a block
  or outside a chain body is a generator error.
- The body text uses two macros:
  - `EF_HL(n, p, k, j)` is the hoisted `const uint32_t n = ...[k * rk_s + ((rk_c - j) & rk_m)];`.
  - `EF_HV(n, p, k, j)` is `Fp::fromRaw(n)`.
- `-DEF_NO_HOIST` expands `EF_HL` to nothing and `EF_HV` to R22's `EF_LD(...)`, token for token.
- `EF_NEST_FORM` implies `EF_NO_HOIST`, and the R12 and R15e forms nest, so the nested, r12 and r15e kernels are
  unchanged.
- Kernel names:
  - `ef_eval_split` / `ef_eval_split_fc`: hoisted, the defaults.
  - `ef_eval_split_nohoist` / `ef_eval_split_fc_nohoist`: R22's flat kernels.
  - `_nest`, `_r15e`, `_r12`: as before.
- `ef_combine` stays in the main TU only.

`rv32im-sys/build.rs` (a small additive hook outside this item's files):
- Two more wrapper TUs, `eval_check_ef_nohoist.metal` and `eval_check_ef_fc_nohoist.metal`, as R22 did for the
  nested forms.
- The metallib grows 37.0 -> 46.3 MB. The two extra TUs compile in parallel with the others.
- The startup PSO set is unchanged (13 PSOs). The R22 build guard checks the hoisted kernels: plain and fc
  3,984 B, `slow=false`.

`eval_check.rs` (dispatch):
- `ChainForm { Hoist, Flat, Nest }` replaces R22's `flat: bool`:
  - `chain_form()` reads `RISC0_METAL_RV32IM_EVAL_FLAT` (`0` gives Nest) and then
    `RISC0_METAL_RV32IM_EVAL_HOIST` (`0` gives Flat).
  - The specialized PSO map is keyed by (domain, form).
- The archive units:
  - `rv32im_fc<domain>` for Hoist, the same name as before. The metallib digest changed, so the key changes
    too.
  - `rv32im_fcnh<domain>` for Flat.
  - `rv32im_fcnest<domain>` for Nest.
- The plain fallback while the fc PSO builds is `ef_eval_split` for Hoist, and the lazy `_nohoist` / `_nest`
  kernels otherwise.
- The regime guard's fallback is used for the Hoist form only, as before for the flat form.
- Tests:
  - `Which::EvalfastNoHoist` / `EvalfastFcNoHoist` in `evalfast_matches_*` and `evalfast_seeds_match_baseline`.
  - The `_nohoist` kernels are added to `non_default_eval_psos_are_lazy` and to `eval_regime_guard_kernels`
    (both must be in the fast regime).
  - `eval_fc_parsing` covers the form mapping and `parse_hoist`.

Revert check: the -O2 IR of `eval_check_ef_fc_nohoist.metal` equals R22's `-DEF_FC_FORM` TU apart from the
file name, and `eval_check_ef_nohoist.metal` equals R22's plain TU apart from `ef_combine` and attribute
numbers. `irdiff.sh` reports 3 lines of difference: the removed function's remnant. `_nest` equals R22's

## 4. Sub-track pmlag (LEADS #14, `pmlag_hip.py`): NO-GO
On RDNA the lag stops the scheduler from hoisting s_load batches that then spill to VGPR lanes, an AMD SGPR
problem. The Metal prototype (`pp/pmlag_metal.py`) works as follows:
- The link W positions on reads its row through `ctx.pm + (dep & ef_z)`, where dep is a word of that earlier
  link's result.
- `ef_z` is the table word `pm[EF_NPM].w`. It is 0 for every table (the pmn half's 4th word), read once per
  function, so the compiler cannot fold it.
- The pass lagged 5,034 links and 157 closures at W 4, and 4,950 links at W 8.
- The compile-time row-pair select (R18) is kept: the index stays constant and only the base moves.

Results: +22.4 ms (W 4) and +33.5 ms (W 8) at po2 20, 0/11 rounds faster each, still in the fast stack regime
(4.9 KB). The extra AND, the address add and the serialization cost more than any gain from scheduling. Apple's
uniform loads show no spill problem to fix. A larger W only moved further from the baseline, so no sweep. The
lead's `mksub` was not tried: ROCm does not run it either, and R15e showed more calls are slower here.

and `v/cmb18` rewrite `ef_combine`'s 4 `domain` uses to `EF_CMB_DOM`. They ran as an arm in the production

It is bandwidth-bound: about 200 MB per po2 20 dispatch. Its whole time is about 0.13 % of eval_check. Not

- Each specialization also costs a per-po2 cold compile and an archive unit. Left as an open issue for whoever
