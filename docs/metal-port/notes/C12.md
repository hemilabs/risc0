## 2. lazy REDC vs plain, and lazy Fp: eval_check kernels (kept: `lz`)

### Harness

The scratch crate `evh/` loads one or more metallibs and runs the six split parts on random
canonical inputs: ctrl 23, data 128, accum 12 columns; po2 18, so domain 2^20.
- It compares each variant word for word with the others and with the CPU
  `risc0_circuit_recursion_cpu_eval_check`.
- It then times the variants interleaved: the whole call in one command buffer, and each part in
  its own command buffer.
- The variant sources come from C3's translator run on generator outputs in `gen/`:
  - `out_lazy`: the shipped split, with RecLz (lazy REDC of the poly_mix chains).
  - `out_plain`: `eval_check_split.py` with the ec_lazyredc pass skipped, i.e. plain Fp/FpExt
    Montgomery arithmetic.
  - `out_lz1`, `out_lz2`: the shipped split plus ec_lazyfp.py's HIP-only `lz1`/`lz2` forms applied
    to every part. These are lazy Fp sums of products: a raw 64-bit accumulator, folded only when
    needed, and one REDC where a canonical value is used.
  - `out_mix`: the best form per part.

- **The plain form is rejected:** it is 66 % slower.

- At po2 16 (`evh_po16.log`, 11 reps), the call went 15.55 -> 12.68 ms (-18 %).
- Threadgroup width 64/128/256 for lz2 gave 47.80-47.83 ms, so there is no change.

### Implementation

- **`cuda2metal_eval.py --split-lz`** writes `eval_check_split_lz.metal`, with kernels
  `ec_lz_part_0..5`. The steps:
  1. Take the translated split.
  2. Insert the Metal ports of ec_lazyfp.py's `rlf_*` helpers as a generated block
     (`Fp::asRaw`/`Fp::fromRaw` replace sppark's raw `*a`/`Fp(r)`).
  3. Run `ec_lazyfp.variant(part, 'lz2')` on each `poly_fp_partN`. The HIP generator is imported
     read-only.
  4. Rename the kernels.
- The new output is pinned (`lz.parts` 6, `lz.kernels` 6, `lz.lz2_prod` 4855, `lz.lz2_fin` 2557,
  tallies) and runs through the residual scan.
- Negative checks:
  - Changing the form to lz1 in-process is refused with a pin mismatch.
  - `--split-lz` without `--split` is refused.
- The bit-exactness argument is the generator's: REDC is linear mod P, its output is canonical,
  and every input is canonical. That is the same assumption the RecLz split already relies on.
- **`recursion-sys/build.rs`** runs the eval translator with `--split --split-lz` and adds the
  output to the metallib. `ec_lazyfp.py` is a rerun-if-changed input. The build cost is about
  +2.6 s of AIR compile, and the metallib grows by about 1 MB. A PSO is only built for the
  selected variant.
- **`recursion-sys/src/lib.rs`**: `METAL_KERNEL_NAMES` gains `ec_lz_part_0..5`.
- **`hal/metal/mod.rs`**:
  - `EvalKernels::SplitLz` is the default.
  - `RISC0_METAL_REC_KERNELS` accepts `lz` / `split-lz` (default), `split` (C11's RecLz split)
    and `monolith`.
  - `EvalKernels::ALL` is new, and `is_eval_kernel` covers all three variants.
- **`eval_check.rs`**: docs, plus the C8 variant test now checks all three variants against the
  CPU (po2 4/10/16/18), with one cached PSO set per non-selected variant.
- At po2 18 (`variants_match_cpu_po2_18`), encode+sync took:
  - monolith 128 ms;
  - split 59.1 ms;
  - lz 48.4 ms.

## 3. Metal WOM sort / parallel CPU sort (rejected)

PLAN gate: "GPU sort only if measured bottleneck". The sort plus scan is 3.0-3.4 ms per lift and
6.2 ms per join, 2-4 % of a proof (section 1), so it does not dominate. **No Metal sort.**

A cheaper attempt was tried as well: a parallel counting sort on rayon.
- Design: atomic per-address histogram and cursors. Runs of equal canonical address that are not
  all identical were finished with the full key, as in the sequential port, so the result is the
  unique `std::sort` order.
- It was bit-exact: the C6 sort test with both paths, and 11/11 capture seals under
  `RISC0_RECURSION_FAST_SORT_CHECK=1`.
- It was **slower**: witgen.sort went 3.0 -> 4.9 ms per lift and 6.2 -> 9.9 ms per join.
- Instrumented on a join: histogram 3.5 ms, scatter 4.9 ms. Contention on the atomic counters
  (popular WOM addresses, false sharing) costs more than the parallelism saves.
- A per-thread histogram would need K x nv counters (tens of MB) for at most ~3 ms.
- The code was removed.

## 4. Private storage for GPU-only buffers (rejected, no change)

- Candidates: the only recursion scratch that is GPU-only is the accum `tmp` (work_cycles FpExt,
  4 MB at po2 18) and the prefix totals. The witgen WOM buffers are read by the CPU sort, and the
  trace groups belong to zkp.
- Experiment: both were moved into one cached `StorageModePrivate` buffer (`alloc_private`).
- Correctness: 11/11 capture seals == CPU.
- A/B (`ab_private.log`, same binary, knob off/on, 7 pairs, load 2.2-12.8): 2345.9 vs 2348.3 ms,
  B faster in 3/7.
- Verdict: **no change.** This is expected on unified memory, where private storage changes
  nothing for compute buffers of this size.
- The experiment was removed.

## 5. `HOST_CHAIN_MIN_LEN` retune (knob added, default unchanged at 16)

`RISC0_REC_HOST_CHAIN_MIN_LEN=<n>` (n >= 2, read once; `prove/witgen.rs`) overrides the 16.

**Sweep** (`chain_L*.log`, serialized profile, 2 reps, minima per proof). The full proof time
includes the in-prover host-chain computation:

|---|---|---|---|
| 4 | 142.0 | 170.2-170.9 | 16.7-17.5 (7.2-7.5 / 1.2-1.9) |
| 8 | 142.4 | 171.9-172.1 | 16.3-17.8 |
| **16** | 137.0 | 161.4-162.2 | 13.7-14.0 (1.5 / 4.2) |
| 24 | 135.7 | 161.7-162.5 | 13.8-13.9 |
| 32 | 137.2 | 160.2-160.9 | 13.3-14.2 (0.8 / 5.2) |
| 48 | 136.6 | 159.7-160.5 | 14.2 |
| 64 | 136.9 | 160.4 | 14.8 (0.5 / 6.1) |
| 128 | 138.1 | 159.6-160.8 | 14.8-14.9 |
| none (1e8) | 164.5 | 180.3 | |

- Short chains on the host lose: the host scatter grows faster than the GPU exec shrinks.

**A/B 16 vs 32** (`ab_chain32.log`, same binary, 7 pairs, load 0.9-1.7):
- Round: 2348.8 -> 2337.1 ms (-0.5 %, 7/7). The A/A spread was 0.25 %.
- Lifts were within noise, joins -1.5 % (162.6 -> 160.4).
- **But the gain is in the host-chain computation inside the timed proof** (the capture path, no
  prepared preflight). Inside the GPU witgen, L = 32 trades -0.7 ms of host scatter for +1 ms of
  exec: a wash.
- The zkvm worker prepares the chains on a background thread (C11, zkvm `prepare`), where that
  CPU time is off the GPU path.

So the default stays 16, which is also what CUDA and ROCm share in this file. The baseline agent
can A/B `RISC0_REC_HOST_CHAIN_MIN_LEN=32` on the full worker pipeline.
