# P31-04: R6 baseline/oracle eval translator on 3.1's eval_check.cuh (2026-11-15)

Branch `metal/P31-04` (worktree `deps/risc0-3.1-wt-P31-04`), based on `metal/P31-02` `315ee5759`.
Plan: `scratch/r31/PORT_PLAN.md` 1.1 row 3, section 5 row P31-04, section 8 row 3. Scratch and logs:
`scratch/w8/P31-04/`. Chain: P31-02 -> **P31-04** -> P31-03 -> P31-05 -> P31-06.

This item changes only the translator (`rv32im-sys/kernels/cuda/cuda2metal.py`, eval mode and the
selftest). The CUDA sources are not edited. No GPU command was run. The rv32im Metal build still
stops at P31-03's `to_metal.py` pins, so the GPU checks of the R6/R10 baseline are deferred to
P31-06 (see "Deferred").

## Profile / starting point

- `cuda2metal.py eval` on the P31-02 tree: `qual.noinline: pinned 20, got 0`. With `--no-pin`, the
  output (`base31/eval_check.metal`) fails `xcrun metal -fsyntax-only` with one error,
  `52:1: error: expected unqualified-id`. That line is the dangling `extern` that is left when the
  poly_mix pass rewrites `extern __constant__ FpExt poly_mix[kNumPolyMixPows];` from
  `__constant__` on (`syn_base31.log`).
- `cuda2metal.py --selftest` on the P31-02 tree crashed before it reached the eval cases. Two of its
  snippet anchors no longer match the 3.1 sources:
  - `eval_check_ef.cu`'s poly_fp now starts with `FpExt x204 = FpExt(0);` (3.0 had x203). This
    raised a `ValueError`.
  - steps.cu now spells it `INVOKE_EXTERN(ctx,nextPagingIdx)`, without the space. The steps pin
    mutation therefore no longer applied, and only the assert half of it fired.

  Both anchors are in the file this item owns, so they are fixed here (see change 4).
- There is no runtime to profile: R6 is the oracle kernel, and its runtime is out of scope until
  P31-06. The only cost this item can move is the kernel's compile time, measured below.

## Header-form change (3.0 fork -> 3.1 upstream)

| | 3.0 fork `eval_check.cuh` | 3.1 `eval_check.cuh` (44 lines) |
|---|---|---|
| chain prototypes | `extern __device__ __noinline__ FpExt rv32im_v2_N(` over several lines, all 20 marked | `extern __device__ FpExt rv32im_v2_N(...);` on one line, **none** marked |
| poly_mix | `__constant__ FpExt poly_mix[kNumPolyMixPows];` | `extern __constant__ FpExt poly_mix[kNumPolyMixPows];` |
| kNumPolyMixPows | 458 | 484 |

The header belongs to upstream and hemilabs, so it is not edited. Fork commit `5c3d8389f` deleted
`eval_check_noinline_test.cuh`. The definitions in `eval_check_0..3.cu` were never marked in either
version.

## Changes (all in `cuda2metal.py`)

1. **Chain check and noinline injection (`eval_chain_noinline`, run by `eval_input` before the
   passes).**
   - It parses every `extern __device__ [__noinline__] FpExt rv32im_v2_N(` prototype in
     `eval_check.cuh`. The regex accepts any whitespace, so the one-line 3.1 form and the
     multi-line 3.0 form both parse.
   - It parses every `__device__ [__noinline__] FpExt rv32im_v2_N(` *definition* in
     `eval_check_0..3.cu`. A match counts as a definition only when `{` follows the parameter list.
   - It requires a 1:1 pairing, and it refuses each of these with a `TranslateError` that names
     the function:
     - a definition without a prototype (`no prototype for rv32im_v2_7 (defined in
       eval_check_2.cu)`);
     - a prototype without a definition;
     - a duplicate;
     - a chain that is not `rv32im_v2_0..N-1`;
     - a header that has more `rv32im_v2_N(` names than parsed prototypes (`the header form
       changed`). This catches a future third form instead of silently injecting nothing.
   - For each definition whose prototype and definition both lack the marker, it inserts
     `__noinline__` after `__device__` in the CUDA text of that definition. The `qual` pass then
     turns it into `__attribute__((noinline))` and counts it as `qual.noinline`, as before. Each
     injection is also counted as the new `eval.noinline_injected`.
   - On the 3.1 sources, all 20 attributes therefore sit on the definitions. The 3.0 output had
     them on the prototypes. Clang merges the attribute across redeclarations, and the IR check
     below confirms that the result is the same.
2. **poly_mix declaration.** `POLY_MIX_DECL_RE` is now
   `(?:\bextern\s+)?\b__constant__\s+FpExt\s+poly_mix\s*\[...\]`. The rewrite consumes the
   `extern`, so nothing dangles. The initializer refusal is unchanged.
3. **kNumPolyMixPows is derived, not a literal.**
   - `resolve_size` resolves the array size to an integer. It accepts a decimal literal, or the
     name of exactly one `constexpr <type> NAME = <int>;` in the input.
   - `eval_poly_mix_pows` requires exactly one poly_mix declaration in the combined eval input,
     with a resolvable positive size. Otherwise it raises `cannot resolve the size`.
   - The output now carries `static_assert((kNumPolyMixPows) == 484, "poly_mix: kernel buffer
     size");` in place of `> 0`, and the banner says `kNumPolyMixPows = 484 entries,
     static_asserted`.
   - The selftest's `eval_chain_v2_0` case had a literal `458`. It now copies the header's own
     `INV_RATE`/`kNumPolyMixPows`/poly_mix lines. `grep -n 458 cuda2metal.py` finds nothing
     (exit 1).
4. **Selftest.**
   - **Header-form cases.**
     - `eval_chain_v2_0_v31`: the checked-in one-line header, with 1 injected noinline.
     - `eval_chain_v2_0_v30`: the 3.0 multi-line form with `__noinline__` and a plain
       `__constant__`, with 0 injected.
     - The 3.0 form is produced by `_legacy_eval_cuh`, which rewrites the 3.1 header the way
       clang-format wrote the fork's. The frozen 3.0 checkout is outside this repo, so the
       selftest cannot read it.
     - Both cases are translated, count-checked and compiled with `xcrun metal`.
   - **Pin sensitivity** (2c, replacing "drop one `__noinline__` -> 19"). Each line below is the
     pin mismatch the test expects:
     - one 3.1 prototype marked by hand: `eval.noinline_injected: pinned 20, got 19`;
     - the whole 3.0 form: `got 0`;
     - the 3.0 form with one `__noinline__` dropped: `got 1`;
     - in all three, `qual.noinline` stays 20.
   - **Refusals:**
     - a missing prototype, 3.1 form;
     - a missing prototype, 3.0 form;
     - a duplicate prototype;
     - an unparsed prototype form (`__device__ extern ...`);
     - a prototype without a definition;
     - an unresolvable poly_mix size.
   - **Anchors fixed for 3.1.** The poly_fp snippet ends at the first `FpExt x<N> = FpExt(0);`
     (a regex). The steps sbind mutation accepts `ctx, nextPagingIdx` and `ctx,nextPagingIdx`.
5. **Pins (PINNED_EVAL).**
   - The new key is `eval.noinline_injected: 20`. It means that all 20 arms come from the
     translator.
   - `qual.noinline` is still 20, the count R6/R10 validated.
   - Every other count is unchanged from 3.0. The 3.1 sources give the same 15 counts as the 3.0
     sources did with the old translator: `aspace.device=182, aspace.thread=74, poly_mix.call=21,
     poly_mix.param=43, qual.extern_device=21, ...`.

No runtime knob was added. This is a source translation that reproduces the validated 3.0 kernel
shape on the new header. There is no alternative behaviour to fall back to, because a translator
without the injection does not compile on 3.1.

## R6 output diff, 3.0 vs 3.1 (reviewed)

`diff out30/eval_check.metal new31/eval_check.metal`: 26165 insertions and 26629 deletions over
27060 -> 26596 lines. Almost all of it is regenerated constraint bodies. The structure was compared
with a script (`struct30.txt` / `struct31.txt`):

- **Unchanged:** 21 functions in `rv32im_metal_eval` (poly_fp + rv32im_v2_0..19); every prototype
  equals its definition; the 20 chain functions are noinline and poly_fp is not; the call
  structure is the same linear chain, eval_check -> poly_fp -> v2_19 -> v2_18 -> ... -> v2_0, one
  call each; the 4 source files hold the same functions in the same order.
- **The `eval_check` kernel is byte-identical**, from `kernel void eval_check(` to the end. So
  are its buffer ABI and its `[[max_total_threads_per_threadgroup]]`. The host binding (R6/R10
  `eval_check.rs`) is unaffected, except for the poly_mix length, which goes from 458 to 484.
- **Constraint content (expected):**
  - poly_mix reads 6465 -> 6518, highest index 457 -> 483 (`< kNumPolyMixPows` = 484);
  - FpExt products about 15098 -> 15190;
  - parameter counts: v2_2 9 -> 10, v2_14 17 -> 16, v2_15 16 -> 18. These are the new trace
    arguments of the 3.1 constraints, the same shift that PORT_PLAN 1.1 notes for evalfast's
    `remat_lu.py` on v2_2;
  - every other arm keeps its arity.
- Noinline placement: on the prototypes (3.0), on the definitions (3.1). This is semantically the
  same, as the IR check above shows.

## Compile time (standalone metallib, CPU only)

Both TUs were compiled the same way: `xcrun metal -std=metal3.2 -O2 -I build_kernel/kernels/metal
-c eval_check.metal` then `xcrun metallib`. The runs alternated 3.0 / 3.1, 3 pairs, on an M5 Max
with 1-min load 5.0-5.4 (`compile_times.txt`):

| | air (s) | metallib (s) | total (s), median [min, max] |
|---|---|---|---|
| 3.0 output | 10.05, 9.95, 8.84 | 0.81, 0.78, 0.73 | **10.73** [9.58, 10.86] |
| 3.1 output | 9.25, 9.08, 8.77 | 0.82, 0.68, 0.69 | **9.76** [9.46, 10.07] |

The difference (-0.97 s) is smaller than the 3.0-vs-3.0 spread (1.28 s), so the result is **no
change**. Metallib sizes: 5,761,152 B (3.0) and 5,809,744 B (3.1). The cold PSO time, R6's 54 s
figure, is a GPU pipeline compile, so it was not measured here (see "Deferred").

## Open issues

- The output's `static_assert(kNumPolyMixPows == 484)` checks the translator against the header
  inside the TU. It does not check the host. The kernel has no bound on `poly_mix`, so the host's
  `NUM_POLY_MIX_POWERS` must also be 484 (P31-03 changes `eval_check.rs`). P31-06's GPU
  CPU-equality is the end-to-end check.
- The injected noinline now sits on the definitions, not the prototypes. If a later item compiles
  the chain functions in a separate TU from the prototype-only header, the attribute must travel
  with the definitions. Today there is one TU, so this does not apply.
