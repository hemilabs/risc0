# Z3: Poseidon2 pv/pvs kernels on Metal

Branch `metal/Z3`, based on `zkminer/metal` at `93978a8e8` (F0 merged). Plan rows: 4.1, kernel row
"pv::fold_k/rows_k/fold_tail_k, pvs w/q", and item Z3. I followed sections 2, 5 and 8.

## What was ported, and from where
All paths are under `risc0/sys/kernels/zkp/cuda/supra/`.

- **`sys/kernels/zkp/metal/pv.metal`** (new). One translation unit with global-scope entry points.
  Templates are instantiated with `[[host_name]]`, and `[[max_total_threads_per_threadgroup(128)]]`
  stands in for `__launch_bounds__(128[, 6])`.
  - **Constant tables.** `PV_RCF`/`PV_RCP`/`PV_DH` come from `pv_consts.h`. `PVS_RCF/PW/CR/CRM/DH/DHM/E0`
    come from `pv_small_consts.h`. I copied them mechanically with `sed` (`__device__ [__constant__]` →
    `constant`). `PV_DHE` and `PV_C56` come from pv.cuh:99-105. All are program-scope `constant`
    tables (plan 2.1, "CPU-built tables" in errata 8.3).
  - **`pv::` thread-per-permutation code: the HIP C++ branch of pv.cuh.**
    - `sredc`/`sredc_even`/`smul`/`canon`/`ssbox`: pv.cuh:67-97.
    - `red1`/`addm`/`m4`/`m_ext`: pv.cuh:112-176.
    - HIP `full_round`: pv.cuh:178-196.
    - HIP `ssum24` + `partial_rounds`: pv.cuh:202-241. The `v_perm_b32`/`v_pk_add_u16` packing is
      replaced by the plain sum it computes, `tb = Σ (e_i >> 24)`.
    - HIP `permute`, with the single 8-round loop: pv.cuh:265-283.
  - **Kernels.**
    - `fold_k` → `pv_fold_k`: pv.cuh:287.
    - HIP `fold_tail_k` → `pv_fold_tail_k`: pv.cuh:312. `__syncthreads` becomes
      `threadgroup_barrier(mem_device)`.
    - Generic `rows_k` → `pv_rows_k`: pv.cuh:467 and the `#else` branch. I did not port the RDNA
      buffer-resource path. The column pointer is advanced per column instead of computing
      `(i + j) * dim_x`, so matrices of more than 2^32 elements need no 64-bit index multiply.
  - **`pvs::w` / `pvs::q`: pv_small.cuh:37-304.** The math is unchanged. Shuffles are
    `simd_shuffle`/`simd_shuffle_xor`. Lane and SIMD-group indices come from
    `thread_index_in_simdgroup`/`simdgroup_index_in_threadgroup` rather than `threadIdx & 31`.
    - PTX `mred` and `cmul` use pv.cuh's HIP C++ `mred` (64-bit, wraps like the PTX carry chain).
    - `pvs::q`'s 64-bit partial-round sum is shuffled as two 32-bit words with a carry.
  - **Not ported:** `rows0_k`, `fold_q4_k` and `fold_tail_q4_k` (plan non-goals and errata 8.3).
- **`_m32` instantiations of every kernel.** These compute the same int64 values from 32-bit
  `mul` + `mulhi`. In `t - m*p`, the low words cancel exactly, so `sredc = hi(t) - mulhi(m, p)`. The
  PTX carry chain becomes `hi + mulhi(m, p) + (lo != 0)`.
  - I added them because D0's mul-bench predicted that 64-bit multiplies would be 4-5x slower.
  - Measured, they are **slower** than the int64 form (below), probably because the compiler turns
    `long(int) * int` into a single 32×32→64 multiply.
  - The default is therefore the literal HIP int64 code. `_m32` is A/B only (`RISC0_METAL_POSEIDON2=m32`).
- **`zkp/src/hal/metal/poseidon2.rs`** (new): the new `MetalHashPoseidon2`, which ports the host logic.
  - It follows api.cu `sppark_poseidon2_{fold,fold_tree,rows}` (lines 186, 232, 285) and
    pv_small.cuh `pvs::{fold,rows}` (lines 317-340): `pvs_w` if `n <= W_MAX`, else `pvs_q` if
    `n <= Q_MAX`, else `pv`.
  - Launch shapes follow CUDA/HIP:
    - `pv`: `ceil(n / bs) × bs` with `bs = min(n, 128)`, as `Grid::Groups`.
    - `pvs`: whole 128-thread groups.
    - The tail kernel: `1 × n0`.
  - `hash_fold_tree` encodes every layer into one batch, and the Hal method flushes once.
    `RISC0_METAL_PV_TAIL_MAX` (≤ 128) enables HIP's single-dispatch tail; it is off by default, as
    measured below.
  - `Poseidon2Config` (`kernels: Pv | PvM32 | Classic`, `small`, the four crossovers and `tail_max`)
    is read from the environment once per HAL and can be changed with `set_config`:
    - `RISC0_METAL_POSEIDON2=pv|m32|classic`
    - `RISC0_METAL_LEGACY=1` selects classic
    - `RISC0_METAL_PV_SMALL=0`
    - `RISC0_METAL_PVS_{W,Q}_MAX_{FOLD,ROWS}`
    - `RISC0_METAL_PV_TAIL[_MAX]`
  - The `pvs` kernels are disabled if any of their PSOs reports `thread_execution_width != 32`. The
    `pvs` rows kernels use 32-bit offsets, so they are used only when `rows * cols < 2^32`.
- **The classic oracle (kept until Z7).** The F0 `poseidon2.metal` code path stays in `metal.rs`,
  renamed `MetalHashPoseidon2Legacy`, with `pub type MetalHalPoseidon2Legacy`.
  `MetalHashPoseidon2` can also run those kernels itself (`Poseidon2Kernels::Classic`). I did not
  edit `poseidon2.metal` (Z1 owns it).
- **Shared-list edits (append-only):**
  - `sys/build.rs`: `"pv.metal"` added to the zkp list.
  - `zkp/src/hal/metal.rs`:
    - 14 names appended to `KERNEL_NAMES`.
    - `#[path = "metal/poseidon2.rs"] mod pv_poseidon2;`. The name `poseidon2` is taken by the
      existing `core::hash::poseidon2` import in that file.
    - One `pub use` line.
    - `#[cfg(test)] mod tests_z3;`.
    - The three-line rename of the old struct to `...Legacy`, plus its type alias.

## Assumed / gaps
- **SIMD layout and convergence.**
  - `thread_index_in_simdgroup` and the SIMD-group partition of a 1-D 128-thread group are assumed
    to be the contiguous 32-lane split. The kernels derive `h`/`g` from the SIMD-group index, so
    they stay correct even if that does not hold.
  - The pvs kernels need every lane of a SIMD group to be active at each shuffle. They follow
    CUDA: whole-group early exit in `w`, and `act` masking in `q`. Plan 7 lists "pvs not audited";
    shuffle sources are always in range (< 32) here.
- **Timings** come from wall clock around `sync()`, not GPU timestamps. The pv/pvs crossovers were
  measured once on a shared GPU. Z9 should re-measure with no other GPU work.
- **`_m32` vs int64.** I did not look at the generated code to explain why `_m32` is slower.
  Possibly a better 32-bit formulation exists (Z9).
- **Classic path vs Z1.** If Z1 changes `poseidon2.metal`'s bindings, the classic path in
  `poseidon2.rs` (`Poseidon2Kernels::Classic`) binds args 0..3 like F0's code, and
  `MetalHashPoseidon2Legacy` in `metal.rs` is Z1's to update. The merge agent should check both.
- **Grid dimensions.** `hash_rows` with more than 2^32 rows and folds of more than 2^32 outputs
  panic (`u32` grid parameters, as in CUDA).
