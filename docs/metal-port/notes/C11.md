Branch `metal/C11` (worktree `/Users/user/zkminer/deps/risc0-wt-C11`), based on `metal/Z10`
(`58d6c3e76`, p254 on Metal). Plan rows: 4.3 row C11, 2.0 (eval_check split vs monolith), 9.1,
8.7. Notes read: C1-C10, Z10, K5/K8 (archive), R17. Logs and scripts:
`/private/tmp/claude-501/-Users-user-zkminer/a30bccea-eec8-43d4-ac51-c5ccb6e4b957/scratchpad/w5/C11/`
(the A/B driver is `scripts/ab.py`).

**Result:** two changes are kept, and each one has a revert knob.
- **The eval_check default is now split.** Real lift/join/resolve proofs at po2 18 are about 31 %
  faster: 7/7 interleaved pairs, and also at the 4 GiB and 8 GiB budgets.
- **The recursion PSOs are built on parallel threads.** A cold recursion warmup (OS shader cache
  off) went from 40-41 s to 13-14 s. About 10 s of what remains is the zkp HAL's own sequential PSO
  build.

The other sub-tracks were measured, or reasoned about where they are too small to measure on this
shared GPU, and were not adopted. Every seal is bit-exact against the CPU.

## Measurement tooling (new, off by default)

| Knob / test | What it does |
|---|---|
| `RISC0_METAL_REC_PROFILE=1` (`hal/metal/profile.rs`) | The circuit HAL syncs at every phase boundary and prints `[rec_metal_profile] witgen.{fill,host,exec,sort,verify} witgen pre_accum accum pre_eval eval_check` in ms. `pre_accum` covers data noise/zeroize + ctrl/data commit + mix. `pre_eval` covers accum noise/zeroize + accum commit. The rest of a proof (check commit + FRI) is the wall time minus these. The syncs serialize work, so use it for attribution, never for A/B. |
| `RISC0_METAL_REC_CAPTURE=<dir>` (`hal/metal/capture.rs`) | Every Metal recursion proof writes its program, input and prepared preflight trace to `<dir>/NNNN_<hashfn>_po2P_rowsR.rcap` (raw words, same machine only; never in production). |
| `c11_tests::c11_bench_captures` (ignored) | Replays the captures (`C11_CAPTURES`, `C11_ONLY`, `C11_REPS`) after a warm pass. Host chains are prepared off the timed path, as zkvm `prepare()` does. Prints `C11CAP` per capture and `C11BENCH` per round sum. |
| `c11_bench_proofs`, `c11_pso_times`, `c11_eval_tg_sweep` (ignored) | Test-zkr proof timing, cold/warm PSO times per kernel set, and the eval_check threadgroup sweep (each width checked against the CPU). |

## 2. Kept: eval_check split by default (`RISC0_METAL_REC_KERNELS`)

Interleaved A/B, A = monolith (the unmodified default), B = split. 7 pairs, one process per run.
Each run is a warm pass plus 3 rounds over the 11 captures. Log `ab_split.log`, load 6.8-19.5.

| | median of round sums | min | max |
|---|---|---|---|
| A monolith | 3725 ms | 3355 | 4977 |
| B split | **2583 ms** | 2521 | 3652 |

- B was faster in **7/7** pairs.
- Per capture (median [min, max]):
  - lift: 274 [227, 523] -> 166 [157, 251];
  - join: 296 [249, 492] -> 189 [177, 312];
  - resolve-path lift: 243 [222, 313] -> 150 [148, 211];
  - identity_p254: 1004 -> 931.

A-vs-A spread (`ab_aa.log`, split vs split, 5 pairs, under heavier load from other agents): medians
7062 vs 5374 ms. The between-run noise in this session is therefore large. The split's per-capture
minima (147-178 ms) never overlap the monolith's (221-255 ms), so the claim stands.

Budgets (4 pairs each, much heavier GPU contention, so only the direction is meaningful):

| budget | A monolith median | B split median | B faster |
|---|---|---|---|
| 4 GiB | 13593 ms | 11118 ms | 3/4 |
| 8 GiB | 7300 ms | 3390 ms | 4/4 |

- Memory: the split and the monolith bind the same buffers. The split has no extra scratch, so peak
  memory is unchanged at both budgets (C10's table: 1.44 GB per po2 18 proof).
- Cold PSO (`pso_times.log`, `MTL_SHADER_CACHE_SIZE=0`, K5's method): monolith **36.4 s**, split
  6.6-8.0 s sequential. This agrees with C3/C4.
- Revert: `RISC0_METAL_REC_KERNELS=monolith`. Unknown values now warn and use split.

## 3. Kept: parallel PSO build (`RISC0_METAL_REC_PSO_THREADS`)

`Pipelines` (`hal/metal/mod.rs`) replaces zkp's sequential `MetalKernels` inside the recursion HAL:
- It loads the metallib once.
- Each PSO is built on a worker thread with its own autorelease pool, following K5's pattern.
- The thread count is `available_parallelism()`. No core count is hard-coded.
- The eval_check PSOs moved to their own process static (`EVAL_KERNELS`), so `warmup()` builds the
  base set and the eval set at the same time.

Cold PSO times, OS shader cache off (`pso_times2.log`, 3 runs each):

| set | sequential (`=1`, pre-C11) | parallel |
|---|---|---|
| base (11 kernels) | 5.0-5.5 s | **2.94-2.98 s** |
| split eval_check (6) | 6.7-6.8 s | **2.20-2.26 s** |
| whole `warmup()` incl. zkp HAL PSOs | 39.8-41.4 s (monolith) / 16.7-17.7 s (split) | **13.2-13.8 s** (split) |

- Warm (OS cache hit) is 0.00-0.01 s either way.
- On 8-10-core base chips the compile runs on fewer CPU cores, so the absolute cold times will be
  longer. The parallel build scales with `available_parallelism`.
- Revert: `RISC0_METAL_REC_PSO_THREADS=1`.

## 4. Measured and not adopted

- **Threadgroup sweep** (`eval_tg_builtin.log`, `eval_tg_attr.log`, `step_tg.log`). New knobs
  `RISC0_METAL_REC_EVAL_TG` / `RISC0_METAL_REC_STEP_TG` (default 0 = `Grid::Threads`, min(256, PSO
  max)). The width is clamped to the PSO max and rounded to whole SIMD groups.
  - Split eval_check launch widths 32-1024 at po2 18: every minimum was 60.1-63.2 ms. Medians were
    60-106 ms, which is noise from other agents. The 1024 width with a 1024-attribute build was the
    only consistently worse case (min 67.6 ms).
  - Rebuilding `ec_part_*` with `[[max_total_threads_per_threadgroup(N)]]` N = 64/128/256/1024
    (hand-compiled scratch metallibs, `evaltg/`) gave the same minima (59.9-62.0 ms). So register
    allocation by attribute does not help these kernels.
  - Step kernels (exec / verify WOM / compute+verify accum) at 0/32/64/128: their profile values
    (exec 5-15 ms, accum 14-30 ms) moved randomly between two repeats.
  - Verdict: **no change**. The default is unchanged and every width was bit-exact against the CPU.
- **Row passes + ZCHECK** (`RISC0_METAL_REC_ROW_PASSES=1`, `has_row_passes`/`init_rows`/
  `fill_tail`/`zeroize_rows` on C1's `recInitRows`/`recFillTail`/`recZeroizeRows`):
  - Correct: `c11_row_passes_match_generic` passes (live 0..1024 including non-quad counts). Seal
    tests at po2 16/18 pass with them on. `RISC0_HIP_REC_ZCHECK=1` passed on all 11 captures and
    36 times across the C5/C6/seal tests.
  - A/B (`ab_rowpasses.log`, 7 pairs, load 2.4-13.8): round-sum minima 2480.9 vs 2479.1 ms. Medians
    were 6356 vs 6046 ms, but the A spread was 2481-10983. B was faster in 4/7 pairs. Verdict:
    **no change** (the saving is a GPU fill/zeroize of about 1 ms).
  - The code is kept, **off** by default, as an opt-in knob for C12's re-measurement on a quiet
    machine.
- **Batching witgen/accum/eval into fewer command buffers**: not changed.
  - The witgen's two waits are inherent: the CPU WOM sort sits between exec and verify.
  - The accum is already one batch with one wait for its fault word.
  - eval_check only flushes.
  - The fill blit + sync at witgen entry costs 0.2-1 ms. With every phase boundary already at
    0.2-1 ms of sync, the remaining bubbles are under 1 % of a 180 ms proof, which is below what
    this machine can resolve today.
- **CPU sort/scan/scatter** (measured, not changed):
  - CPU WOM sort+scan: 3.2-3.6 ms per lift, 6.6-6.9 ms per join (single-threaded counting sort,
    3-4 % of a proof).
  - Host copies + chain scatter: 0.7-2 ms.
  - A GPU or parallel sort is C12's item ("Metal WOM sort if CPU sort dominates"). It does not
    dominate.
- **CPU-cached permutations + Perm kernels**: not attempted. The step kernels (exec + verify +
  accum) total about 15 ms per join against 60 ms of eval_check. A HIP-style cycle permutation
  needs new key/gather kernels and translator changes for at most a few ms.
- **simd_prefix scan for the accum prefix products**: not attempted.
  - The scan is a product of FpExt elements. `simd_prefix_*` only covers scalar sums/products,
    so a shuffle-based field scan would be needed.
  - The whole accum phase is 4-13 ms, and the scan is a fraction of that.
- **MTLBinaryArchive**: not added to recursion. K5's `archive.rs` is 1300 lines with K8's crash
  fixes, so it should be hoisted once into the zkp HAL, not copied per unit.
  - After this item, the recursion cold build is about 3 s (parallel split + base).
  - An archive would save those ~3 s only when the OS shader cache is invalidated.
  - Left to the zkp owner (below).
- **Lift/join pipelining in `composite_to_succinct` (GPU idle gaps)**: **not measured**.
  - The zkvm side is not C11's file, and the GPU was shared throughout, so idle gaps between
    proofs could not be told apart from other agents' work.
  - In the e2e logs the prover's own preflight (11-23 ms per proof) runs on the GPU thread when no
    prepared preflight is passed (the e2e tests' path). The worker pipeline prepares it on a
    background thread.
