### Working-set budget (plan 9.1)
- `RISC0_METAL_MAX_WORKING_SET_BYTES` accepts bytes or a binary suffix (`4G`, `4GiB`, `512M`, `512MB`, `1k`); malformed values are logged and ignored. `MetalHal::set_working_set_limit(Option<u64>)` overrides it per HAL (tests use this; setting env vars in parallel tests is racy).
- Limit = min(budget, `recommendedMaxWorkingSetSize`). `gpu_total_memory` = limit; `gpu_free_memory` = limit - `currentAllocatedSize`; pool cap = limit / 2.
- Enforcement only with an explicit budget: a new allocation (pool hits are not new allocations) that would take the device's `currentAllocatedSize` above the limit drains the pool, re-checks, then fails with `Metal working-set budget exceeded: allocating N bytes for <name> with M bytes already allocated would exceed the limit of L bytes (RISC0_METAL_MAX_WORKING_SET_BYTES=..., recommendedMaxWorkingSetSize=...)`. `alloc_shared`/`alloc_private` return it as an error; Hal entry points panic with it (F0's existing panic in `RawBuffer::new`).
- Without the variable nothing is enforced (Metal may legitimately exceed the recommended size); only the reported numbers come from the runtime.
- Side effect worth knowing: under a budget below 20 GB the prover's `low_mem` path (po2 21) activates on Metal, as it would on a small CUDA card.
- `currentAllocatedSize` is device-wide for the process, so the budget covers all HALs in the process (not other processes).

### Peak memory
`MetalHal::peak_allocated_size()` / `reset_peak_allocated_size()`: process-wide max of `currentAllocatedSize`, sampled after every new allocation (allocation is the only point it can rise). The bench reports it per method.

### Threadgroup-length dedupe (Z2 open issue)
`Bound` tracks `setThreadgroupMemoryLength` per index per encoder and skips unchanged values (reset with the encoder and after `pre` callbacks / `with_encoder`, as the buffer bindings are).

### DualHal and pooled buffers (test hook)
`DualHal` compares whole buffers after each call, including cells a method never writes. In a full prove the Merkle `nodes` buffer's head (`nodes[0]`, upper layers before they are folded) is never written: the CPU HAL allocates it zeroed, the Metal pool hands back old contents. The poseidon2 DualHal round trip failed on exactly this (not a Metal bug). `Runtime::set_zero_pooled(true)` (`cfg(test)` only) zeroes pooled buffers on reuse; the round-trip tests use it. Production behaviour is unchanged.

## Assumed / not verified / gaps
- Budget enforcement relies on `currentAllocatedSize`, which counts this process's allocations on the device (pooled buffers, PSOs/libraries included) but not other processes or the CPU-side memory of the CPU prover. On a real 16 GB machine the OS limit is the real constraint; the budget is a simulation.
- The budget is checked before each new buffer; a single allocation larger than the remaining budget fails even if the caller would have freed something right after (that is the intended "early" error).
- The DualHal round trip needs the `cfg(test)` zero-on-reuse hook (see above). Any future testutil that runs whole-prover flows through DualHal on Metal should enable it.
- The toy circuit's eval_check runs on the host (the round trip tests the zkp HAL, not a circuit kernel). The verifier side of the toy circuit is hand-written; its agreement with the prover is shown by the CPU seal verifying.
- No mutation check of the new tests was done beyond: (a) the poseidon2 DualHal mismatch they caught, and (b) the corrupted-seal rejection.
- Bench numbers are wall clock on a shared GPU; `1-thread dispatch + sync` ranges 0.14-3.3 ms between runs, which shows the noise. GPU timestamps (Z9) would separate GPU time from host overhead.
- `RISC0_METAL_BENCH_*` knobs are bench-only.
