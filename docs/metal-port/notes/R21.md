## Verdict: NO-GO for the code-size split

The 2.4 MB `ef_eval_split` is **not** instruction-fetch bound in a way a split could exploit.

1. **Direct test on the real kernel (decisive).** N identical copies of the evalfast chain, with
   row block `rb` running copy `rb % N`. Each thread runs the same code path as today, with the same
   work and the same stack, and the results are bit-exact. Only the code footprint on the GPU grows.
   Quiet sessions:

   | footprint | po2 16 | po2 18 | po2 20 |
   |---|---|---|---|
   | 4.65 MB (2 copies) | +4.3 % | +4.1 % | +5.4 % |
   | 9.3 MB (4 copies) | +11.4 % | +12.9 % | +13.7 % |

   The A-vs-A spread is under 0.5 %. Every quiet round was slower than A (9/9 at po2 16, 7/7 at
   po2 20), except one contended round at po2 18.

   Doubling the footprint costs about 5 %, and each further doubling costs more. Read backwards,
   halving the footprint gains under 5 %, and splitting into arbitrarily small parts gains about
   7-10 % at most. The lead estimated 15-35 %.
2. **AOT sizes of all 84 R18/R19 variants (71 timed at po2 18) do not follow code size.** A
   per-thread **stack** size in the native metadata does. This item identified that field and
   calibrated it against kernels whose stack is known. The variants form two clusters, with nothing
   in between:
   - **fast:** stack 18.2-20.8 KB, about 160 ms at po2 18;
   - **slow:** stack 32-40 KB, about 404 ms. This cluster includes R15e's form and the hardened
     helpers.

   Within the fast cluster's whole-kernel variants, time does not track code size: Pearson -0.09,
   n = 35, over 2.31-2.55 MB. The slow cluster gives +0.15, n = 19. Including the ablations that
   also remove or add ALU work (cheapmul, nopm) raises the fast-cluster figure to +0.61 / +0.77,
   so this step alone is weak evidence. Some variants with less code are slower:
   - `inl`: 2.19 MB, 184 ms;
   - `bar128`: 2.20 MB;
   - `logfirst`: 2.35 MB, 168 ms.

   R18's main/LogUp split compiled main alone to a 33 KB stack. Its parts took 254 + 44 ms, against
   163 ms for the combined kernel.
3. **The synthetic sweep finds no cliff at MB scale.** How much code size matters depends on the
   regime, so the synthetic cannot settle the question alone; that is why test 1 was run. Code
   footprint went from 16-24 KB up to 4 MB at the same work per row:
   - eval-like multiply-add mix: +5-14 %;
   - 16 KB per-thread stack traffic touched every row: flat within 9 %;
   - add/xor-only mix (contended): up to 1.4x;
   - 1 KB stack: up to 2.1x.

   The real kernel behaves like the low-sensitivity cases (test 1).

Expected end-to-end effect of a 2-4-way split:
- the ceiling is 2-5 % of the kernel, about 1-2.5 % of the STARK;
- each cut costs a write and a re-read of the cut-crossing state: up to 26 FpExt, 416 B per row,
  about 1.7 GB per cut at po2 20;
- each part rolls the stack-regime dice, a ±2.4x swing, as R18's split did;
- the expected net is 0 or negative.

Step 3 of the plan (the split prototype under the gate) therefore was **not built**.

**What to do instead (follow-up items, not done here):**
- **Regime guard (LEADS #47, cheap):** `tools/metal_audit/agx_size.py` reads `ef_eval_split`'s
  stack offline in about 30 s.
  - The fast regime is 18.9 KB; the R15e form is 36.4 KB.
  - A check that fails when the shipped kernel's stack exceeds about 24 KB would catch an R18-type
    regime flip after a generator or toolchain change before anyone measures it.
  - It needs only the CLT Metal toolchain this repository already uses.
- **Stack-sensitivity probe:** the regime is the 2.4x lever, and stack (not code) predicts it.
  - Measure d(ms)/d(stack KB) of the real kernel by adding a dummy private array that each chain
    function touches.
  - If it is steep near 19 KB, R19's P2 (a generator re-partition that shortens the 21-deep live
    tail-call nest) becomes the eval item to fund.
  - This item did not measure that slope.

## 2. Tooling (committed; nothing on a production path)
| File | What |
|---|---|
| `tools/metal_audit/agx_size.py` | Native code size and metadata of a metallib's compute functions, offline (details below). |
| `tools/metal_audit/codesize_probe/gen.py` | The synthetic fetch probe TU (details below). |
| `tools/metal_audit/codesize_probe/bench.swift` | GPU-timestamp bench for `gen.py` kernels. Each round runs every kernel; odd rounds run in reverse. Prints min/p25/median/max, ns/row, the per-round ratio to the first kernel, and raw rounds. |
| `tools/metal_audit/codesize_probe/run_sweep.sh`, `agg.py`, `wait_idle.py` | Idle-gated sessions and pooling (`agg.py --idle-only`). |
| `tools/metal_audit/codesize_probe/dup_eval.py` | The real-kernel footprint probe (details below). |
| `tools/metal_audit/codesize_probe/build_eval_variant.sh` | Compiles an evalfast TU variant with the build's flags and include path. |

`agx_size.py`:
- `metal-tt -arch applegpu_g17s -macos-version-min 27.0` translates a one-pipeline script into a
  binary archive. The archive's `__compute` section is a nested applegpu Mach-O object, and the tool
  reads that object's `__text` size.
- It also reads metadata from the object's FlatBuffers blob. These fields were identified
  empirically, with no schema available:
  - **`stack`** (root, field 0, field 14): per-thread private stack bytes including the deepest
    callee chain. Kernels with a dynamically indexed `uint[N]` report 4N + 16 for N = 256 to 8192.
    The o1/os eval variants, whose PSO creation fails with "Compute function exceeds available stack
    space" (R19), report 320 KB and 412 KB.
  - **`frame`** (field 41): the kernel's own frame. It equals `stack` when nothing is called out of
    line.
  - **`regs?`** (field 1): **not** the register count. It stays at 44 for 2 to 32 live
    accumulators, grows with the number of distinct out-of-line callees (44, 76, 136, 256), and is
    capped at 256. Unknown.
- Modes: `--keep` keeps the archive and the object, `--parse` reads kept objects, `--all` sizes every
  kernel, `--timeout` limits each function.
- The AGX back end's translation time is superlinear in function size: one 1 MB function took 240 s,
  and 4 MB did not finish in 10 min.

`gen.py`:
- Every kernel does the same arithmetic per row: `--total` blocks. Each block is an eval-like
  multiply-add link per accumulator with a fold every second block, or `--mix cheap` (add/xor/shift
  only).
- The blocks sit in noinline chunk functions, as in `ef_eval_split`. A kernel of size class B owns
  B distinct blocks and loops `total / B` times, with a trip count read at run time.
- `--fns F` fixes the number of distinct callees.
- `--slab W [--slab-dyn]` adds one private-slab store and one load per block. `--slab-dyn` makes
  every kernel touch the whole slab per row.

`dup_eval.py`:
- It copies the generated TU's `namespace rv32im_metal_ef` N times, and the split kernel picks copy
  `rb % N`.
- `t` is copy-initialised from a `?:` of calls. The first version assigned `t` in an if/else chain,
  which `ir_scan` reported as R17 tier A: a default-constructed FpExt stored after a call. That
  version gave bit-exact results in every run, but it was replaced, and its numbers below are marked
  `dup`.

Notes on the sweep:
- **Occupancy limits** set through threadgroup memory (`sw_tg32768_1`, `sw_tg16384_1`): with
  32 KB, 4 MB costs +25 % at the min and a ratio of 1.45; with 16 KB, +9 % and 1.19. The run was
  contended.
- **A confound that was found and removed:** the first slab sweeps used fixed slab indices
  (`q_slab_a`, `q_fns4_a`). They showed a 3x step between 21 KB and 39 KB of code, then a plateau.
  But a kernel with few distinct blocks also touches few slab words. With `--slab-dyn` (the same
  slab working set in every kernel) the step disappears (`q_swd_a`, flat within 9 %).
- **Summary:** whether code size matters depends on what else limits the kernel, and there is no
  MB-scale cliff.
  - In ALU-bound kernels it costs +5-20 %.
  - Under heavy private-memory traffic it costs nothing.
  - It costs most (2.1x by 1.2 MB) when the stack is small and the code streams.
  - The synthetic cannot say which of these cases `ef_eval_split` is, which is why the real-kernel
    test (section 5) was run.

## 5. The real-kernel footprint test (in place of step 3)
Steps 1-2 did not support the hypothesis, so the split prototype was not built (plan step 3 is
conditional). The footprint probe answers the same question directly, without a generator change.

- Variants:
  - `dupb1`: one copy, through the `?:` selection; same native code as A, 2,399,592 B, stack
    18,928 B;
  - `dupb2`: 4,652,476 B, stack 18,944 B;
  - `dupb4`: 9,301,830 B, stack 19,200 B.
- The stack stays in the fast regime, so the regime is controlled.
- Every run of every session was bit-exact with the built-in kernel (`ef_variant_bench` asserts it).

| session (scratch `ev/logs/`) | A ms | 1 copy | 2 copies | 4 copies | A2-A |
|---|---|---|---|---|---|
| `dupM16_3`, po2 16, 9 rounds, quiet | 42.2 [41.7, 42.4] | +0.1 [-0.5, +0.6] | **+1.8 [+0.9, +2.2], 0/9 faster (+4.3 %)** | **+4.8 [+4.7, +5.3], 0/9 (+11.4 %)** | -0.2 |
| `dupbQ18_1`, po2 18, 9 rounds, quiet (one contended round) | 161.8 [160.1, 272.0] | | +6.6 (+4.1 %), medians 169.7 vs 161.8 | +20.8 (+12.9 %), 183.6 | -0.6 |
| `dupbQ20_2`, po2 20, 7 rounds, idle start | 647.8 [645.1, 657.8] | | **+34.7 [+31.1, +219.8], 0/7 (+5.4 %)** | **+88.8 [+77.6, +301.9], 0/7 (+13.7 %)** | -0.5 |
| `dupbQ16_1`, po2 16, mostly quiet | 45.4 [43.6, ...] | +0.6 | +3.2 | +5.5 | +3.4 (spread too large: supporting only) |
| `dupL16`, 6 contended sessions, min of mins | 41.3 | 40.9 | 43.2 | 46.7 | 41.9 |

Other po2 16-20 sessions were contended (A-A spreads of 5-90 ms) and are not used for claims
(`dup_p18_a/b`, `dup_p16_a`, `dupN18_*`, `dupbQ20_1`, `dupbQ18_2`).

Reading:
- The kernel's cost rises with its GPU-wide code footprint: about 5 % per doubling at 2.4 MB, and
  about 8 % for the next doubling.
- A split moves the footprint the other way. Extrapolating the measured curve (slope falling about
  0.6x per halving):
  - 2 parts: about -2-3 %;
  - 4 parts: about -4 %;
  - the limit over all part sizes: about -7-10 %.
- The 1 KB-slab synthetic regime would have shown tens of percent at 2x. The real kernel does not
  behave like that.

Caveat: the copies raise the footprint without changing each thread's path. A split also changes the
compile of every part, and that is exactly where the stack-regime risk sits (R18's split: +83 %).

## 6. Rejected / not done (with numbers)
| Item | Why |
|---|---|
| 2-4-way split prototype of the real kernel (step 3) | Gated on steps 1-2 supporting the hypothesis; they do not. The footprint test bounds the gain at about 2-4 % of the kernel for 2-4 parts, before cut-state traffic and regime risk. |
| Synthetic as one big function | Translation superlinear (1 MB: 240 s; 4 MB: over 10 min). Replaced by noinline chunks, like the real kernel. |
| Fixed-index slab sweeps (`q_slab_a`, `q_fns4_a`) as evidence of a 32 KB i-cache cliff | Confounded by the slab working set (§3); the `--slab-dyn` rerun shows no step. |
| "regs?" metadata as a register or occupancy metric | Refuted by calibration (constant 44 for 2-32 live accumulators). |
| Bytes-of-code-per-second headroom argument | The 1 KB-slab sweep is 2.1x slower at only 3.7e12 B/s of code, below the eval's 1.5e13 B/s, so the cost is fetch latency under load, not a bandwidth ceiling. Not used for the verdict. |

  with `agx_size.py`. Today the regime flip is caught only by measuring time.
  - The translator takes about 30 s and needs only the CLT Metal toolchain.

  sensitivity may differ on 8-10 and 16-20-core parts, which have different cache sizes per core.
  Re-run `dupb2` / `dupb4` there before reusing the verdict.
