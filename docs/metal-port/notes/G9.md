## Result

The prover's GPU time on the rzup key (witness 5,635,930, domain 2^23) dropped from **2.43 s to
1.37-1.47 s (-41 to -44 %)** on a quiet machine. Every stage changed bit for bit identically to
the G7/G8 prover. The same witness with fixed r and s gives equal pre-blinding values (A', B1', B2',
C', H) and equal proofs. The wrap (`shrink_wrap` with the key cached) dropped from ~3.0-3.2 s to
~1.9 s in the best runs.

| stage (quiet, one command buffer per stage) | before (G7/G8) | after (G9) |
|---|---|---|
| zero + witness_into_poly + c = a b | 65-73 ms | 65-70 ms |
| NTT (3 x to_coset + h + w += f) | 131 ms | **84-88 ms** |
| sort_h / sort_w | 38-42 / 25-27 ms | 37 / 24-26 ms |
| MSM H (2^23 G1) | 354 ms | **184-200 ms** |
| MSM A, B1, C (G1, 5.6M) | 248-249 ms each | **132-147 ms each** |
| MSM B2 (G2, 5.6M) | 1049-1057 ms | **549-600 ms** |
| GPU sum | 2418-2438 ms | 1424-1470 ms |

"Before" is profile0/profile1 of the first session (3 reps, quiet). "After" is the quiet pairs
of this session's `booth_ab.log` and the first session's `booth2.log`.

## Profile before (measure first)

The first session's `profile0.log` and `profile1.log` (G7/G8 code, `RISC0_G16_METAL_PROFILE=1`,
plus `RISC0_G16_METAL_PROFILE_MSM=1`, which splits every MSM into its dispatches):
- MSM B2 1053 ms (43 %): buckets 611 + 374 ms in two window groups (the 256 MiB piece cap
  holds 10 G2 windows), segment_reduce 34 + 25 ms, window_reduce 2.5 ms.
- G1 MSMs 249 ms each (A, B1, C) and 354 ms (H): 95 % in `msm_buckets`, ~10 ms in
  segment_reduce, < 2 ms in window_reduce.
- NTT 131 ms; zero + witness_into_poly + c = a b 65-73 ms (G7's ~220 ms was measured under load);
  sorts 63-69 ms in all.
- Host: upload 3-13 ms, combine + blinding ~1 ms. The rest of the wrap is the CPU witness (fast.rs,

So the bucket accumulation (point additions) was ~85 % of the GPU time. Field multiplication
throughput was the first target.

## Changes kept (each with a revert switch)

`ProveOptions::tune` / `Tuning` (prover.rs). `RISC0_G16_METAL_G9=0` turns everything off (the
G7/G8 kernels and layout). `RISC0_G16_METAL_G9_OFF=wide_mul,wide_ntt,booth` turns off single
switches. `g9_bench` (ignored test) takes `Tuning::parse` specs such as `base`, `all` or `-booth`.

1. **`wide_mul`: MSM point kernels over `bn254_fast.h`** (`msm_*_g1w`, `msm_*_g2w`).
   - `FpF` uses gnark's no-carry CIOS (`mul_nc`). The carries are 32x32->64-bit
     multiply-accumulates in `ulong`, and the product and reduction rows run in one loop.
     This is valid because the top limb of BN254 p and r is below 2^31 - 1. bn254.h's CIOS uses
     compare-based carries (G2's "Intel 32-bit mulhi formulation").
   - G2 uses `Fp2L`: Karatsuba with the (a0 + a1)(b0 + b1) and sqr's (c0 + c1) sums left
     unreduced (`mul_loose`: inputs < 2P stay correct; the bound is argued in the header).
   - Layout and values are the same as `Fp`/`Fp2`, so the buffers are unchanged.
   - Micro (`g9_fast_field_ops`, 7 interleaved reps, load 8-24): Fp mul 49.3 -> 28.4
     (mul_wide) -> **26.7 ms** (mul_nc). G1 madd 61.5 -> 39.4 ms (noisy). G2 madd 172.7 ->
     **101.9 ms**, and 81.0 ms in a quiet rep.
   - In the prover, from the in-process A/B (`inproc_ab.log`, 9 rounds of base/all/-wide_mul/
     -wide_ntt/-booth, load 17-29, mins because the medians were swamped by other agents' GPU
     work): -wide_mul 2317 ms vs all 1371 ms. **About -950 ms**, nearly all of the win.
2. **`wide_ntt`: NTT kernels over `FrF`** (`ntt_stage_w`, `ntt_fused_stages_w`,
   `ntt_mul_powers_w`). This uses the same multiplication. The NTT stage went **131.0 -> 84.1-88.4
   ms** (min of 9 in `inproc_ab2.log`: 131.0 for -wide_ntt and base, 84.1-84.3 for all and
   -booth; the quiet `booth2.log`/`booth_ab.log` reps give 84.3-88.4). That is about -45 ms
   (3 % of the GPU sum).
3. **`booth`: signed MSM digits.**
   - c = 17-bit Booth windows give digits in [-2^16, 2^16], i.e. 2^16 + 1 buckets (bucket |d|).
     The sign rides in the top bit of the sorted index (`MSM_NEG`; n < 2^31 is asserted), and
     the buckets kernel adds -P.
   - The prover declares its scalars canonical Fr (`MsmScratch::set_scalar_bits(254)`), which
     gives ceil(255 / 17) = **15 windows instead of 16**.
   - The window sums carry the sort's layout (`MsmScratch::sorted_layout`, read by
     `combine_windows`). The scratch is sized for either digit mode
     (`MsmConfig::{layout, piece_nb, max_pieces_nb, max_segs_nb}`; unsigned values unchanged).
   - Quiet pairs (`booth_ab.log` reps 0-3, `booth2.log` 5 reps): all 1424-1470 ms vs -booth
     1460-1499 ms, **-30 to -46 ms (-2 to -3 %) in every quiet pair**. Per MSM: G1 buckets
     137-143 -> 132-138 ms, H 195-203 -> 187-193 ms. B2 is roughly even (the 10 + 5 vs 10 + 6
     window groups: buckets0 +10 ms, buckets1 -20 ms).
   - The noisy pairs (load 11-14, reps 4-7) go either way, so this is a small win and only shows
     on a quiet GPU.

## Tried and rejected (or not applicable)

- **G2 lane pairs** (`bn254_fast.h` `pair::`, bench kernel `g9_bench_madd_g2p`). Two lanes hold
  one Fp2 element (c0, c1), exchange operands with `simd_shuffle_xor`, and do schoolbook 2
  muls/lane. Measured 96.0 ms [95.2..105.2] vs `Fp2L` 81.0 ms [80.9..88.1] for the same number
  of madds: **+18 %**, rejected. The shuffles plus lost Karatsuba (4 muls vs 3) cost more than
  the halved register footprint gains. The code stays for the record and is only used by the
  bench kernel.
- **G2 bucket threadgroup width** (first session's `exp_tg.log`, `max_total_threads` 32-512): 32-256
  gave the same time (605-615 + 363-371 ms); 512 was slower (846 ms). Occupancy is not limited
  by the threadgroup size. The session also has `exp_load.log` (bucket-loop load variants); its
  code was not kept and the variants are not documented, so I do not use it as evidence.
- **`sqr_wide`** (dedicated squaring, 36 products, `g9_bench_madd_g1s`): 26.9 vs 24.5 ms,
  rejected. **`add_wide`/`sub_wide`** (64-bit carry chains for +/-, `_g1a`): 23.2 vs 22.3 ms in
  madd (the Fp add micro is 6.70 vs 7.02 ms), no gain, rejected. **mul_wide** (two-loop CIOS)
  vs `mul_nc`: 28.4 vs 26.7 ms (Fp), G2 madd 93.5 vs 87.3 ms, so `mul_nc` is kept. **Fp2 without
  lazy sums** (`g2f`): within noise of `g2l` (149 vs 145, loaded). `g2l` is kept because the
  saving is free.
- **wbits sweep** (new knob `RISC0_G16_METAL_MSM_WBITS`, measurement only). 7 rounds of def /
  wbits 15 / piece 512 MiB interleaved in separate processes (`sweep.log`, load 4-14). GPU sum
  min 1378 (def) / 1373 (wbits 15) / 1350 (piece 512), medians all inside each other's spread:
  **no change**.
  - With Booth, wbits 15 means c = 16 and 16 windows, so it should lose. c >= 18 is outside
    `MsmConfig::validate` and saves no window before c = 19 (14 windows, 4x the buckets: segment
    reduce ~+30 ms per MSM vs ~-16 ms of buckets), so I did not try it.
- **B2 piece cap 512 MiB** (`RISC0_G16_METAL_MSM_PIECE_MIB=512`; B2 in one window group): min
  1350 vs 1378 ms, inside the spread, so **no change**. It would also add 256 MiB of scratch,
  which works against the 16 GB target. It is not adopted.
- **Shared vs Private MSM scratch** (`RISC0_G16_METAL_SCRATCH_SHARED=1`; first session's
  `shared.log`, 7 alternating runs): quiet first pair 1368 (Private) vs 1453 (Shared); later
  pairs were under load and overlap (2551-2994 vs 2582-2963). There was no win for Shared, so
  Private stays the default and the knob stays.
- **"ones row"** (summing the points of scalar-1 terms directly): not applicable. Every MSM
  scalar is witness + fuzz (`fr_add`, fuzz uniform below 2^253) or h, so the digit
  distribution is uniform. A special row for digit 1 would not take any load off.
  (The piece split already balances any heavy bucket.)
- **Privatized-histogram sort**: not done. A threadgroup-private histogram of 2^16 + 1 buckets
  per window (256 KiB) does not fit the 32 KiB threadgroup memory. A two-level radix sort would
  be needed for at most the 61-63 ms (4 %) the two sorts take. This moves to G10 if the sort ever
  grows.
- **`witness_par` into the shared buffer**: not in this item's files. The CPU witness is
  `groth16/src/prove/{fast,witness_par}.rs`, and `witness_par` is `cfg(feature = "cuda")` in
  `groth16/src/prove/mod.rs`. Writing it straight into the shared witness buffer would save
  only the 3-13 ms upload. The big lever is `witness_par` itself (0.66-1.4 s of CPU witness),
  which needs the groth16 crate owner (open issue below).

## Hardware dependence (PLAN 9.1)

- Nothing new depends on the core count. Grids still derive from n, c and PSO limits.
- The gain comes from the integer multiply path: `ulong` multiply-accumulates instead of
  compare-based carries. It should carry over to every Apple GPU family, but I only measured it
  on the M5 Max 40-core. The 8-10 and 16-20 core parts were not measured.
- Under the 4-8 GB budgets the prover itself is still the 5.6 GB of G7, so the 4 GB tier is
  refused (G10).

## Dispositions of open issues addressed to G9

- G2 "no 32x32->64 accumulation or dedicated squaring tried; optimization belongs to G9": done.
  `mul_nc`/`mul_wide` were adopted (-46 % per Fp mul). `sqr_wide` was measured and rejected.
- G4 "`fr_powers` strided-start variant if it shows in a profile": it does not. It is a
  per-key-load table build (GPU setup 0.04-0.3 s), not in the prove profile. No change.
- G5 "NTT v2: smaller twiddles, fuse the coset multiply, radix-4/8, 1024-Fr blocks": only the
  faster multiplication was done (-45 ms). The fusions and the twiddle shrink are open for G10
  (the NTT is now 84-88 ms; the coset fusion was estimated at ~3 ms per NTT).
- G6 "G2 occupancy / lane pairs / batch-affine; Booth; sweep c, piece, seg": lane pairs were
  measured and rejected, the threadgroup width makes no difference, Booth was adopted, and the
  c / piece-cap sweep showed no change. Batch-affine (Montgomery-trick) bucket accumulation was
  not tried and is the next large G2 lever (G10).
- G7 "MSM B2 40 %, four G1 MSMs ~1.1 s, witness_into_poly ~220 ms": B2 1053 -> ~560-600 ms, G1
  MSMs 1100 -> ~590-630 ms. witness_into_poly is 65-73 ms on a quiet machine (G7's figure was
  under load), so no change.
- G8 "the wrap's own peak is 5.6 GB; the 4 GB tier is refused": unchanged (+3 MiB). Memory
  levers are G10's (compact coefficients, zkey mmap, aliasing a/b/c with the MSM scratch).
