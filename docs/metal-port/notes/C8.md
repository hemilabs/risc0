## What was ported, from where

- Host side of `recursion-sys/kernels/cuda/ffi_supra.cu:73-117`
  (`risc0_circuit_recursion_cuda_eval_check`) and `hal/cuda.rs` `eval_check`:
  - `map_pow(poly_mix, POLY_MIX_POWERS)` (158 FpExt) is written into `ScratchBuffers::poly_mix`
    (C5's reserved slot, grown with `grow`, 25 % headroom) with `view_mut`; CUDA's
    `cudaMemcpyToSymbolAsync` into `__constant__ poly_mix`. `view_mut` syncs first if any batch is
    unsynced, so a previous eval_check still reading the scratch can never be overwritten (in the
    prover the queue is already idle at that point: poly_mix comes out of Fiat-Shamir on the host).
  - `RecEvalParams { rou: ROU_FWD[po2 + log2(INV_RATE)].as_u32_montgomery(), po2, domain, _pad: 0 }`
    (16 B, `#[repr(C)]`, size asserted; `unsafe impl bytemuck::NoUninit` because the crate does not
    enable bytemuck's derive feature) bound with `set_bytes` at buffer 7.
  - Bindings exactly C3's "Kernel ABI": 0 poly_mix, 1 check, 2 ctrl, 3 data, 4 accum, 5 mix, 6 out,
    7 params (`bind` const table in the file). `Grid::Threads(domain)` (TG = min(256, PSO max)).
  - Monolith: one `eval_check` dispatch. Split (`RISC0_METAL_REC_KERNELS=split`): `ec_part_0..5`
    back to back on the serial encoder with the same bindings (`eval_check_split.cu` `launch_parts`;
    the parts depend through `check`).
  - PSOs from C5's `eval_kernels()` (selected variant, built once per process at warmup or first
    use).
  - Phase end: `hal.flush()` (commit, no wait), so the prover's `post_eval_check` host work overlaps
    the GPU as on CUDA's stream; whoever reads `check` syncs. eval_check has no fault word (no
    asserts; reads are `& mask`-clamped, C3), so the host validates instead: `domain` a power of two
    and < 2^32, `check.size() == 4*domain`, ctrl/data/accum at least `group_size(taps) * domain`,
    mix >= MIX_SIZE, out >= OUTPUT_SIZE (panics: programming errors per 2.9).
- `CircuitHal::eval_check_dep`: explicit no-op (one queue in round 1). `accumulate` stays
  `unimplemented!()` as in cuda.rs/hip.rs.
- `cpu_eval_check(...) -> Vec` (the `hal/cpu.rs` FFI call into `kernels/cxx/poly_fp.cpp`) is the
  reference for tests and for the new debug knob **`RISC0_METAL_EVAL_CHECK_SHADOW=1`**: after the
  GPU dispatch it syncs, recomputes on the CPU over the same buffers and panics on the first
  differing word (column, cycle); on success it prints
  `RISC0_METAL_EVAL_CHECK_SHADOW: eval_check (<variant>) po2 N matches the CPU (W words)` to
  stderr. Read once per process. Cost: a sync plus ~2-3 s of CPU at po2 18.
- `encode_eval_check(variant, kernels, ...)` (crate-private) takes the variant and PSOs explicitly
  so the tests run both variants in one process.

## Measurements (M5 Max shared with other agents: indicative only)

**GPU time per eval_check** (wall time of encode + `sync()`, warm PSOs, best of 3, random inputs;
lib-test runs, debug test binary with optimized deps):

| po2 (domain) | monolith | split | CPU `poly_fp` (reference, par) |
|---|---|---|---|
| 4 (64) | 5.0 ms | 4.2 ms | 0.3-0.6 ms |
| 10 (4096) | 4.7 ms | 6.6 ms | 9-14 ms |
| 16 (262144) | 37.4 ms | 16.1-17.9 ms (42 ms in one loaded run) | 340-570 ms |
| 18 (1048576) | 178 ms | 61-79 ms (95-127 ms in loaded runs) | 1.9-3.7 s |

Split is ~2-3x faster than the monolith at po2 16-18 (matches C3's 2.2x); at po2 <= 10 the
fixed per-dispatch/sync overhead dominates. Not a decision: C11 owns the default.

**Peak GPU memory** (`currentAllocatedSize`):
- eval_check itself allocates only the poly_mix scratch (2528 B, one 32 KB pooled page): po2 4 test
  +32 KB over the base. Inputs + check of the random-input tests: po2 10 +2.7 MB, po2 16 +175 MB
  (peak 181 MB), **po2 18 +700 MB (peak 706 MB)**; identical under the 4 GB and 8 GB budgets.
- In a real proof (C5's per-phase recording, unchanged by C8): eval_check entry 322 MB at po2 16,
  1.25 GB at po2 18; proof peak 371 MB / 1.44 GB. The zkvm lift/join/resolve/identity tests pass
  under 4 GB.
- No recursion shape tested exceeds either budget (4 GB, 8 GB), so the budget error path was not
  hit by C8 (C5 showed the clean error under a 1 GiB budget).

**Cold PSO**: both variants were already in the OS shader cache on this machine (C3/C4/C5 runs):
monolith and split loads were 0.00 s. Cold numbers are C3/C4/C5's (monolith 17-60 s, split ~7 s).

## Known gaps / assumptions

- No GPU fault channel for eval_check (none in the kernel; host shape checks instead).
- `view_mut` on poly_mix forces a sync if a batch is open; in the prover none is (Fiat-Shamir just
  read the roots), so it is free there, but a future batching item (C11 "A/B/accum/eval in 4 command
  buffers") should switch to a fresh pooled buffer per call (`copy_from_slice`, deferred pool
  return) or a ring if it wants eval_check encoded without a sync.
- The GPU times are wall times including commit/wait, not `GPUStartTime/GPUEndTime`.
- 8-10-core base chips not measured; the split's advantage may differ there.
