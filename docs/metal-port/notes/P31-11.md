# P31-11: Poseidon254 S-box x^8 -> x^7 on Metal (security, risc0 3.1)

Branch `metal/P31-11` (worktree `deps/risc0-3.1-wt-P31-11`), based on `zkminer/metal-3.1` `fb7997cd8`.
Plan: `scratch/r31/PORT_PLAN.md` 1.3, section 1 table (Poseidon254 row), section 2 lesson 7,
section 5 row P31-11. Notes read: Z10, C16, R17, P31-01, BASELINES "Wave 7".
Logs: `scratch/w8/P31-11/` (`ab/`, `gates/`, `stress*/`, `ir/`, `var/`, `py/`).

## Summary

- risc0 3.1 (upstream `62e9e18a9`, `210a6b5d9`) changed the Poseidon254 S-box from x^8 to x^7. x^8 is
  not a permutation of BN254 Fr (gcd(8, r - 1) = 8); x^7 is (gcd(7, r - 1) = 1). Round constants,
  matrices and round counts did not change. The Metal kernel `sys/kernels/zkp/metal/poseidon254.metal`
  still computed x^8 after the P31-01 merge. Every Metal p254 digest then differed from the 3.1 CPU:
  the unmodified merge build fails `fold_matches_cpu` and `rows_matches_cpu` at the first element
  (`scratch/w8/P31-11/negctl_A.log`).
- Both S-box implementations now compute x^7:
  - `ref` (bn254.h `Fr`);
  - the `w64` template, which serves `*_w64` (compact, default), `*_w64c`, `*_w64u` and the 4-lane
    `p254_{fold4,rows4}_w64`.
- The header comment is updated. There is **no knob back to x^8** (security fix).
- Bit-exact against the stock 3.1 CPU `poseidon_254` in every variant and lane form. 3.1's test
  vectors pass through the Metal kernels, and a negative control checks that no x^8 digest or 3.0
  vector comes out.
- Cost: the default p254 kernels take **+26.5 %** (sum of the identity_p254 hash shapes:
  756.8 -> 957.1 ms). The first straightforward x^7 cost +33 %. Choosing the compact form (below)
  removed about a fifth of the extra time.

## 1. The change

### `ref` (bn254.h `Fr`, fully reduced)

```
x2 = x.sqr(); x4 = x2.sqr(); x6 = x4 * x2; return x6 * x;
```

Bounds: bn254.h's `Fr` keeps every input and output below r, so the two new products need nothing
beyond bn254.h's own CIOS (inputs < r).

### `w64` (`template <bool SOS, bool LOOP> sbox`)

- `LOOP = false` (`*_w64u`): `x2 = sqr(x); x4 = sqr(x2); x6 = mul(x4, x2); x7 = mul(x6, x)`.
- `LOOP = true` (the default compact `*_w64`, `*_w64c` and both 4-lane kernels): the addition chain
  x -> x^2 -> x^3 -> x^6 -> x^7, as two passes of `y = mul_loop(sqr(y), x)` in a non-unrolled loop.
  - That is the same 2 squarings + 2 products, with one copy of the squaring code and one of the
    multiplication.
  - `mul_loop` is `mul` with its 8-word CIOS loop not unrolled (section 4 says why).
  - Each pass has no conditional and no operand select.
  - R17: everything is `always_inline` (no calls), and the state is scalars plus `F` values assigned
    whole. The loop writes no private array element by element. `ir_scan.py` reports
    A = B = C = S = 0 (section 3).

### Bounds argument (written into the kernel comment)

- Values: r < 2^254, R = 2^256, so 4r < R and 3r + 1 < R. `python3` check: 4r^2/R + r = 1.756 r.
- `sbox` precondition: x < 2r. Every caller passes an `addk` / `add` / `csub2r` output, all in [0, 2r):
  - full rounds: `addk(s, RC)`;
  - partial rounds: `s0 = csub2r(dot3k(...))`, plus `addk` for the first;
  - 4-lane: `addk` and `csub2r(dot3k)`.
- `sqr_sos(a)`, a < 2r: a^2 < 4r^2. The 8 reduction rows add < R * r, then divide by R:
  < 4r^2/R + r < 1.76 r < 2r. The top word is 0 (Z10).
- `mul(a, b)` / `mul_loop(a, b)` with a < 2r and b < 2r:
  - the running CIOS T stays below a + r + 1 < 3r + 1 < 2^256 between word steps, so it fits t0..t8,
    with t9 as the carry;
  - the result is < a*b/R + r < 4r^2/R + r < 1.76 r < 2r. That needs a*b < R*r, and 4r^2 < R*r holds
    because 4r < R.
- The new products and their operands:
  - unrolled: x6 = mul(x4, x2) with x4, x2 < 1.76 r (square outputs); x7 = mul(x6, x) with x6 < 1.76 r
    and x < 2r;
  - LOOP: x3 = mul(x2, x) and x7 = mul(x6, x), with x2, x6 < 1.76 r (square outputs) and x < 2r.
- So every operand of every step is < 2r and x^7 < 1.76 r < 2r. That is the same output range as
  the old x^8, so the callers' next `addk` / `dot3k` / `mulk` (all take < 2r) need no extra `csub`.
  The canonical digest is unchanged by the redundant representation (`from_mont` + final `csub(r)`).

### Tests (`zkp/src/hal/metal/tests_z10.rs`)

New test `p31_x7_test_vectors_metal`. It runs 3.1's `p254_test_vectors` with every hash on Metal:
- `hash_elem_slice` through `encode_rows` (1 row);
- `hash_pair` through `encode_fold` (n = 1);
- the Fiat-Shamir rng is the CPU's.

It covers all 4 arithmetic variants (`W64`, `W64Unrolled`, `W64Cios`, `Ref`) x lanes {0, MAX}
(MAX = the 4-lane `fold4` / `rows4` kernels). It asserts:
- each digest (d1, d2, d3 and the 28-element d4) == the CPU suite's;
- d1..d3 == the x^7 reference words and **!=** the x^8 words (negative control);
- outputs == (76, 1489312893, 1416259846) (3.1) and != (5, 328085114, 726238606) (3.0).

The x^7 / x^8 digest constants come from an independent Python reference,
`scratch/w8/P31-11/py/p254_ref.py`. It follows `ref::mix` in canonical arithmetic, with constants
parsed from the kernel's Montgomery blob and the exponent selectable. It reproduces **both**
published vector sets: x^7 -> 3.1's (76, 1489312893, 1416259846), and x^8 -> 3.0's
(5, 328085114, 726238606), the frozen 3.0 checkout's `p254_test_vectors`
(`py/ref_out.txt`). So the x^8 negative-control digests are the real 3.0 digests, and the x^7 ones
are checked against the CPU inside the test as well.

All forms are bit-exact (`fold`/`rows`/vector tests). Sizes are native `__text` (`agx_size.py`) of

| V1: loop 2x `y = mul(sqr(y), x)`, `mul` unrolled | 75.6 / 46.0 KB | 1008.4 [1007.3, 1009.7] | +33.2 % |
| V2: straight `sqr, sqr, x4*x2, *x` in the compact kernels | 116.9 / 73.5 KB | 1089.2 [1087.2, 1106.4] | +43.9 % |

- As in C16, the compact kernels are bound by instruction fetch.
  - The unrolled products (V1, V2) cost more in code size than they save in loop overhead.
  - The 4-lane latency-bound layers are hurt most: fri2 tree 1.90 ms -> 3.48 (V1) vs 2.45 (V5).
- V6 is smaller still but runs more instructions (C16 saw the same for CIOS squaring).
- The unrolled `*_w64u` keeps the requested straight chain. It is a revert path for C16 and is not
  tuned.

## 5. Budgets and memory

- No buffer, launch shape or allocation changed. Only the arithmetic inside the permutation did.
- The `tests_z10` suite passes at 4 GiB and 8 GiB simulated budgets.
- Peak memory is unchanged by construction. The registers per thread (`regs?` from agx_size) are
  44 / 48, the same as before, so occupancy is unchanged.

## 6. Knobs

- None added. The x^8 S-box is a security defect, so there is deliberately no way back to it.
- The S-box form (V5) is the only x^7 Metal form that ever shipped, so there is no earlier x^7 form
  to revert to.
- The existing knobs still select the other arithmetic, all now x^7:
  - `RISC0_METAL_P254_KERNELS=w64u|w64c|ref`;
  - `RISC0_METAL_P254_LANES`;
  - `RISC0_METAL_REC_P254=cpu` (the CPU prover, x^7).
