# R7: rv32im Metal HAL skeleton

Branch `metal/R7`, based on `zkminer/metal` (`93978a8e8`, F0 merged).

## What was done
`risc0/circuit/rv32im/src/prove/hal/metal.rs` (F2's stub) was replaced by a directory module:
- `hal/metal/mod.rs`
  - `MetalCircuitHal<MH>`: holds an `Arc<MetalHal<MH>>` (as `CudaCircuitHal` holds its `Arc<CudaHal>`) and a `MetalRv32imCtx`. `MetalCircuitHalPoseidon2` alias. `segment_prover()` mirrors `hal/cuda.rs`: the factory builds `Arc<MetalHalPoseidon2>` and `Arc<MetalCircuitHalPoseidon2>` and hands them to `SegmentProverImpl`. Before that, it loads the rv32im metallib, so a broken metallib fails at `segment_prover()` and not inside the prover. It logs `rv32im segment prover: Metal HAL (<device>) ...` at debug level.
  - `MetalRv32imCtx { hal, kernels (library + PSOs), scratch: Mutex<ScratchBuffers> }`.
    - `ScratchBuffers` holds `table_u8`, `table_u16`, `pf` (cycles|txns|bigint) with its `pf_layout`, `perm`, `scratch` and `poly_mix`. Each buffer is a pooled shared `BufferImpl` from the same HAL, grown with 25 % headroom.
    - Helpers `tables()`, `upload_preflight(trace)` (memcpy after `try_sync`, sections 256-byte aligned so later items can bind them by offset), `pipeline(name)`, `require(phase)`, `library()`, `scratch()`.
  - Sizes are asserted at compile time: `size_of::<RawPreflightCycle>() == 36` and `size_of::<RawMemoryTransaction>() == 20`. The tables hold 2^8 and 2^16 `u32` cells, as CUDA `ffi.cu:298-299` allocates them.
  - **Kernel loading.** `Rv32imKernels` is loaded once per process (`OnceLock`, like F0's zkp PSO cache), through `MetalHal::try_load_library`:
    1. A first load with no names reads `function_names()`.
    2. A second load builds a PSO for every `risc0_circuit_rv32im_sys::METAL_KERNEL_NAMES` entry (these must exist, so the load fails fast), plus every `EXPECTED_KERNELS` entry that the library has.
    3. Expected names the library lacks are recorded per `Phase`. `require(phase)` errors only for that phase and names the missing kernels.
  - `EXPECTED_KERNELS` starts with the CUDA `__global__` names from PLAN 4.2, and R8/R9/R10 edit their own row:
    - Witgen: `injectCycleCols par_stepExecW fwd_stepExec rev_stepExec`
    - Accum: `stepAccumA finalizeZeroizeAccum`
    - EvalCheck: `eval_check`
  - `warmup()` creates a HAL (zkp PSOs) and a circuit HAL (rv32im PSOs).
  - `PHASE_CALLS` counts, per phase, the calls the Metal circuit HAL serves. Tests use it, and it costs one relaxed atomic add per phase call.
- `hal/metal/witgen.rs`, `accum.rs`, `eval_check.rs` contain only the delegation:
  - Each `try_sync`s the HAL, then calls the CPU circuit kernels on raw host pointers of the Metal shared buffers.
  - witgen and accum call `risc0_circuit_rv32im_cpu_witgen` and `risc0_circuit_rv32im_cpu_accum` with the same `RawExecBuffers`/`RawAccumBuffers` construction as `hal/cpu.rs:56-150`.
  - eval_check uses the rayon loop over `risc0_circuit_rv32im_cpu_poly_fp` from `hal/cpu.rs:153-212`.
  - Flags stay at the CPU values: `writes_cycle_cols`, `takes_zeroed_data` and `step_accum_zeroizes` are all false.
  - `CircuitHal::accumulate` is an empty no-op like `hal/cuda.rs`, per PLAN 8.4. `eval_check_dep` is the default no-op.
- `hal/metal/tests.rs` (new) has 6 tests, described under Verified.
- `prove/mod.rs`: added `#[cfg(feature = "metal")] pub fn metal_warmup()`, next to `cuda_warmup`/`rocm_warmup`. It respects `enabled("rv32im")` and logs failures. F2's `segment_prover()` cfg_if metal arm already had the right shape (after intel, before CPU, `enabled("rv32im")` → CPU fallback), so it is unchanged.
- `hal/mod.rs`: unchanged. Its `#[cfg(feature = "metal")] pub(crate) mod metal;` now resolves to the directory module. Gating stays on `feature = "metal"` as F2 left it (8.1; the -sys crates `compile_error!` on non-Apple targets).

## Deviations
- `ScratchBuffers` is behind a `Mutex`, not the `RefCell` that PLAN 2.6 names. With a `RefCell`, clippy's `arc_with_non_send_sync` fires on `Arc::new(MetalCircuitHal)`. With the `Mutex`, the circuit HAL is Send + Sync like `MetalHal`, and the lock is uncontended.
- Delegation uses `BufferImpl::as_ptr()` after an explicit `try_sync()`, not nested `view()` closures. That is one sync per phase, and the `RISC0_METAL_DEBUG` check still applies to `as_ptr`.
- `drop_trace` in `hal/mod.rs` was not extended to metal; plan R14 owns that.

The 6 tests in `prove::hal::metal`:
- `segment_prover_uses_metal_hal`: asserts `enabled("rv32im")`, proves `basic` via `crate::prove::segment_prover()`, verifies the seal, and asserts that each of the three `PHASE_CALLS` counters increased. This is the proof that the Metal circuit HAL was used.
- `eval_check_matches_cpu`: po2 4, random inputs; the delegating Metal eval_check equals `CpuCircuitHal`'s, as in the CUDA test.
- `missing_kernels_error_only_when_phase_required`: a fake expected name fails only `require(Accum)` and the error names it.
- `listed_kernel_missing_fails_load`
- `real_metallib_loads`: also runs `warmup()`.
- `scratch_tables_and_preflight_upload`: checks byte-level layout and buffer reuse.

## Assumed / gaps
- No rv32im Metal kernels exist yet (the metallib is still F2's `noop`). Every phase currently reports its expected kernels as missing, but no phase calls `require` until R8/R9/R10 switch their submodule from delegation to Metal.
- The preflight buffer layout (256-byte section alignment) and the `ScratchBuffers` fields are a proposal for R8/R9/R10, and nothing reads them on the GPU yet.
- The rv32im PSO cache is per process for the first HAL's device, the same single-GPU assumption as F0.
- `metal_warmup()` has no caller yet; M1/M3 wire it into the worker.
