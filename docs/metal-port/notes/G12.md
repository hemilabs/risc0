## Profile before (measure first)

`g9_bench` with `G9_PROFILE=1 RISC0_G16_METAL_PROFILE_MSM=1` (`logs/profile0.log`, 5 reps, then the quiet
`-lenperm` arms of the later runs). Per-dispatch minimum, ms:

| MSM | buckets | segment_reduce | window_reduce |
|---|---|---|---|
| B2 (G2, 15 windows in two groups of 10 + 5) | 360-375 + 197-200 | 23-25 + 19-20 | 1.7-3 |
| A, B1, C (G1) | 134-138 each | 6.6-7.5 each | 0.5 |
| H (G1, 2^23) | 190-196 | 6.4 | 0.5 |

So bucket accumulation is 92 % of B2 and 95 % of each G1 MSM. Is it ALU-bound or memory-bound?
- B2 makes 15 x 5.64M = 84.5M mixed additions in ~560 ms of buckets. That is 6.6 ns per G2 madd.
- G9's `g9_bench_madd_g2l` micro, where the points come from a small table and the loop is the same, runs
  at 5.0 ns per madd (`g12_batch_affine_probe`, 2^18 threads x 63).
- The point reads are 84.5M x 128 B = 10.8 GB per B2, about 19 GB/s, far below the memory system.

So the kernel is ALU-bound (Montgomery multiplications), and it ran at about 75 % of the madd throughput of
the same arithmetic. That gap pointed at lane imbalance, not at memory. A thread sums one piece, which is
one bucket of about 86 points (Poisson-like). A SIMD group of 32 consecutive pieces runs as long as its
largest bucket, about 86 + 2 sigma = 105 additions, which gives ~80 % lane efficiency.

## Changes kept

### 1. `lenperm`: pieces summed longest first (balanced SIMD lanes)

After the sort, four small kernels (`msm_sort.metal`: `msm_len_clear`, `msm_len_count`, `msm_len_scan`,
`msm_len_scatter`) build a per-window counting sort of the pieces by length:
- 1024 length bins, `min(len, 1023)`;
- longest bin first;
- written to `perm[w][t]`.

`msm_buckets_perm_{g1w,g2w}` is `msm_buckets` with thread t summing piece `perm[w][t]`. The pieces themselves
do not change: each is still summed by one thread in entry order, and written at its own index. So
`piece_bucket`, the segment reduction and the window sums are untouched. Only which thread sums which piece
changes, so that the 32 lanes of a SIMD group add about as many points each. The order inside a length bin
depends on atomics; the outputs do not. The list is built once per sort, so sort_w's serves A, B1, C and B2.
- Cost: the four kernels add +0.1 ms to the sorts (+0.3 ms in another run). Memory: `perm` is
  16 windows x max_pieces x 4 B = 6.3 MB, plus `lhist` 64 KB. Both are allocated with the scratch.
- In-process A/B (`logs/lp1/`, 3 processes x 4 rounds, `-lenperm` vs `all`, load 1.4-2.1):
  - GPU **-184.1 ms** [-537, +92], 1/12 slower (the outlier is a contended rep);
  - B2 -105.4 [-111.3, -87.4], 0/12;
  - G1 x3 -58.0;
  - H -20.8 [-21.9, -20.0], 0/12.
- B2 buckets now run at 409.6 ms / 84.5M = 4.85 ns per madd, which is the madd micro's throughput. The
  B2 bucket kernel is now at the arithmetic floor of its field multiplication.
- Revert: `RISC0_G16_METAL_G12_OFF=lenperm` (or `RISC0_G16_METAL_G12=0`). The switch needs `wide_mul`
  (the perm kernels exist for `_g1w`/`_g2w`); it is ignored with `RISC0_G16_METAL_G9_OFF=wide_mul`.

### 2. `lent_groups`: B2 in one window group (re-sweep of the piece cap)

G9 measured a 512 MiB piece cap (all of B2 in one group) as "no change", and it would have cost 256 MiB. In
the G10 layout the pieces buffer is lent: it is a, b, 512 MiB at the rzup key, free from MSM H's sort to the
end of the proof. The 15 G2 windows need 15 x 98305 x 256 B = 360 MiB of it. `lent_groups` sizes the
window groups by the lent buffer's whole length instead of the 256 MiB cap.
- **No memory of its own.** Without a lent buffer (`RISC0_G16_METAL_G10_OFF=alias`) the cap applies as
  before.
- Effect: B2 runs one buckets + segment_reduce pair instead of two.
- In-process A/B (`logs/lg2/`, 3 x 4 rounds, `-lent_groups` vs `all`; load 18-22, contended):
  - B2 -19.4 ms median, minima 459.1 -> 439.8;
  - segment reduce **-12.9 ms [-33.6, -10.6], 0/12 slower**.

  In the quiet final run above: B2 458.2 -> 439.9 (segment reduce 40.4 -> 28.4).
- Contract: `MsmScratch::new_with` documents that, with this switch, the caller must not use any of the
  lent buffer during the MSMs (the prover's a, b are dead then, also in `fuzz_check`).
- Revert: `RISC0_G16_METAL_G12_OFF=lent_groups`.

## R17 finding: `msm_window_reduce` was nondeterministic under load (fixed)

`r17_msm_repeat` gained the G10 open issue's config: G2, n = 1000, wbits = 1, seg = 3, which gives 129
windows. On its first 30-rep run it failed once. The investigation used `g12_tiny_g2_repeat` (ignored),
which counts wrong results and normalizes every stage's output to affine points.
- **Pre-existing.** With the G11 kernels (`g9` variant, lenperm off), G2 was wrong 10/300 and 9/300 in two
  runs while other agents loaded the GPU, and 3/300 x 3 with three concurrent processes. G1 was never
  wrong.
- **Localized to `msm_window_reduce`.**
  - With `RISC0_G16_METAL_SCRATCH_SHARED=1` the pieces and the segment partials of the wrong reps all
    agreed with the majority. Only 1-2 window sums per wrong rep differed.
  - `msm_window_reduce` alone, re-run on one MSM's partials (`r17_msm_window_reduce_repeat`), gave a
    minority window sum in 3-5 of 2000 re-runs per process under load. It gave 0 when the GPU was quiet.
- **Amplifier.** Running a prover (`g9_bench`) on the GPU at the same time works reliably. Same-session
  positive control, kernels as in G11: **58 of 18000** window_reduce re-runs wrong (3 processes x 3000,
  twice) and 2/200 full G2 MSMs wrong.
- **Cause.** The kernel is the R17 shape that `ir_scan.py` reports as tier B at msm_reduce.metal's window
  loop: a private `Xyzz` aggregate written in a loop (the strided sum and the tree) around an out-of-line
  `Xyzz::add` call. There is no race in the kernel: the tree has a barrier per level and the threadgroup is
  uniform.
- **Fix.** `msm_window_reduce_*` moved to its own TU, `msm_window.metal`, compiled under
  `#pragma clang attribute push(__attribute__((always_inline)), apply_to = function)` (the Z10 method).
  The bucket and segment kernels stay in `msm_reduce.metal`. Results under the same load:
  - fix: **0 of 18000** re-runs wrong, and 0/200 full MSMs;
  - control: 58/18000.

  With the final binary, under load: 0/9000, `r17_msm_repeat` 20/20, the tiny config 0/200.
- **Cost.**
  - Speed: none measurable. In the e2e A/B the knob-off arm K has the fix and its B2 equals A within
    +1.0 ms; window_reduce is 1.7-3 ms either way.
  - Cold compile: the serial plain PSO build goes 26.0 -> 33.3 s (`msm_window_reduce_g2w` 3.6 -> 8.4 s).
    The archive-miss path that a first run takes goes 23.1 -> 22.2 s, unchanged because
    `msm_segment_reduce_g2w` bounds it. The metallib build gains ~8 s for this TU. An archive hit is
    unchanged.
- **No revert knob.** This is a correctness fix; the old kernel is the defect.
- **Inlining all of `msm_reduce.metal` too: rejected.** It removes every B/C site of the TU, but costs
  B2 +40 ms (buckets 410.9 -> 444.1, segment 29.1 -> 34.9; 3 x 4 alternating processes, `logs/inl/`) and
  2.7x the cold PSO compile (28.4 -> 76.2 s serial; `msm_segment_reduce_g2w` 18.4 -> 58.7 s). No wrong
  piece or partial was ever seen in the bucket or segment kernels: every readout under load agreed with
  the majority.

## Tried and rejected (each with numbers)

**Lazy-reduction Fp2 multiplication (Karatsuba with two REDCs instead of three).** `bn254_g12.h` `Fp2R`:
- T0 = a0 b0, T1 = a1 b1 and T2 = (a0 + a1)(b0 + b1) as 512-bit products;
- c0 = REDC(T0 - T1 + P^2), c1 = REDC(T2 - T0 - T1);
- `mul_512`/`redc_512`, always_inline, unrolled.

It is bit-exact with `Fp2L` on random and edge values (`g12_fast_field_ops`, one-product and 64-chain
checks), but slower:
- Fp2 product chain: **32.6 ms vs 12.2 ms (2.7x slower)**;
- G2 madd: **168 vs 89 ms (1.9x)**.

The 512-bit intermediates (16 words each, several live) cost more in registers and private memory than the
saved REDC (1/6 of the multiplies). On this GPU the interleaved CIOS (`mul_nc`, 8 live words) wins.

**`hi(t) - mulhi(m, p)` first word of each REDC row (Z9's identity, `mul_nch`, `FpH`).** Bit-exact; no gain:
- Fp2 product 14.4 vs 14.6 ms (same);
- G1 madd 23.5 vs 23.5 ms;
- G2 madd 83.5 vs 80.8 ms (+3 %).

The compiler already folds the carry of the first word. (`logs/micro2.log`, 7 interleaved reps, load ~27.)

**Batch-affine bucket accumulation (Montgomery trick), G2 and G1.** Probe kernel `g12_bench_batch_affine_*`:
K slots per thread in device memory (slot-major), one Fp2 inversion (Fermat) per K additions, affine
formulas. Same number of additions as `g9_bench_madd`. Results (`logs/ba_probe*.log`):

| | G2 madd (XYZZ) | G2 batch-affine | G1 madd | G1 batch-affine |
|---|---|---|---|---|
| 2^18 slots x 63 adds (slot layout thread-major) | 82.3 ms | K = 8/16/32/64: 212/148/144/223 ms | 29.0 ms | 203/140/120/156 ms |
| 2^20 slots x 16 adds, coalesced slot-major | 179 ms (includes the 2^20 Xyzz stores) | K = 32/64/128: 117/108/136 ms | 42.0 ms | K = 32/64/128: 104/74/58 ms |

- Per addition, the best G2 batch-affine (K = 64, 5.5-6.4 ns) loses to the XYZZ madd's 5.0 ns per
  addition (2^18 x 63 run). Best G1: 3.1-3.4 ns against 1.8 ns.
- One Fp2 inversion costs 85-134 ns (`g12_bench_fp2_inv`), about 20 madds.
- Even with the inversion cost removed, the slot state traffic (each addition re-reads and writes its
  affine accumulator and prefix product) costs about as much as the multiplications saved (17 vs 28 Fp
  products per addition).
- Batch sizes large enough to amortize the inversion leave too few threads: B2 has ~1M pieces in all.
- So batch-affine is not a win on this GPU even with a 4x faster inversion. Not integrated.

**Chunk layout (`chunks`, equal-length lane work).** Pieces were made the intersections of the buckets
with fixed chunks of `piece` sorted entries (`msm_window_scan_chunks`, `msm_buckets_chunk_*`), so that
every thread adds exactly T points and writes a piece at each bucket end. It was bit-exact and passed
`msm_tune_variants`, but it is dominated by `lenperm`:
- chunk length T = piece (1x, the best of 1/2/4; `logs/sweep1/`, 3 x 5 rounds):
  - GPU -59.8 ms;
  - B2 -12.5 (buckets -35.6, segment +22.8: 50 % more pieces);
  - G1 -34.4, H -12.5;
- against `lenperm` in one process (`logs/lp1/`): chunks -57.8 ms vs lenperm -184.1 ms.

The code was removed (only the numbers are kept).

## Not done
- **Overlapping MSMs on independent command buffers.**
  - A, B1, C and B2 share the MSM scratch (`sorted`, pieces, partials). Overlapping them needs a second
    scratch of ~536 MiB, which breaks the 4 GiB tier.
  - With the length order the bucket dispatches have short tails: the longest pieces start first.
- **Fewer sort passes / Booth digit reuse.** The two sorts are 60 ms (5 % of the GPU sum). Their cost is
  the scattered 4-byte writes of `msm_scatter`, which a threadgroup-local pre-sort would address. Not
  attempted.
- **Fp2 Karatsuba / lazy reduction**: done as a probe and rejected (above).

## Hardware dependence (PLAN 9.1)
- Nothing depends on core count. The length order is by piece length, and the window grouping by buffer
  length.
- The lane-balance gain comes from SIMD groups running as long as their longest lane. The order
  needs no SIMD width and helps any width. I expect it on every Apple GPU, but measured it on the
  M5 Max 40-core only.
- The window_reduce defect was seen on this M5 Max (G17 family) under load. The fix (no call in a loop)
  is the R17 remedy and holds for any family.

## Open issues
- **Remaining tier B/C sites** in `msm_reduce.metal`: 14 B, 6 C, in the bucket and segment loops. No wrong
  result was seen there (pieces and partials always agreed under load). Inlining them costs 8 % of B2 and
  2.7x the cold compile. A cheaper restructuring (for example straight-line accumulators without a
  private aggregate around the call) is open for an R17 follow-up. `r17_msm_repeat` and the new window
  test should be run under load by the next audit (the amplifier: a prover running concurrently).
- **B2 is now at the madd floor** (4.85 ns per G2 madd). Further B2 gains need fewer Fp multiplications per
  addition. This round measured the two known routes (lazy Fp2, batch-affine) as losses on this GPU.
- **The sorts** (60 ms) are the next MSM-side item: a threadgroup-local pre-sort for `msm_scatter`.
- **Final baseline**: re-take the wrap numbers quiet after merge; add `RISC0_G16_METAL_G12=0` as a knob arm.
