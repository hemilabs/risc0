Branch `metal/W7-R2` (worktree `deps/risc0-wt-W7-R2`), based on `metal/W7-A1` `6af50cf84`. LEADS2 rank 40
(small-mac-drop-data-witness-early, with small-mac-coeffs-recompute as fallback), rank 46
(recursion-smallmac-po2-19-at-4gib), Z14's prefill cap (open issue), and the unattributed 1.23 GB of

`ab_*/`, `k8g19/`, `knobs/`, `t4/`, `t8/`, `tdef/`, `attr/`, `full8/`, `corr/`, `scripts/`). Every GPU

  through the worker. Every seal equals the CPU's (`seal_matches_cpu_large` at both budgets and at the
  default budget) and every Groth16 receipt verifies.
- **Worker memory-merkle (7 interleaved rounds each):**
  - 4 GiB: po2 18 (A1 build) -> po2 19 (this branch): STARK **13.98 -> 10.73 s (-23.2 %)**, 600K -> 733K c/s.
  - 8 GiB: po2 19 -> po2 20: STARK **10.19 -> 8.74 s (-14.3 %)**, 772K -> 840K c/s.
  - Full six-program suite at 8 GiB, once per arm: **207.3 -> 180.7 s (-12.8 %)**, 774K -> 855K c/s.
- **Default budget and the old tiers: no change** (worker STARK -0.015 s [-0.020, +0.065] against A-vs-A
  +0.020 [-0.020, +0.200]; rv32im segment +2.5 ms [-17.5, +43] against A-vs-A +4.0 [-39, +26]; po2 19 /
  8 GiB +0.5 ms and po2 18 / 4 GiB +0.5 ms, both inside A-vs-A; Metal peaks and footprint identical).
- **The binding phase is not the accum commit any more, and the margin is below the brief's 5 %.** After
  steps 1 and 2 the largest live set of a segment is at the FRI mix (all groups' coefficients, LDEs and
  trees plus the check group and the mix buffer): **96.5 % of the budget at both tiers** (7905 of 8192 MiB at

  tier fails at the check group's Merkle nodes. The brief's coeffs-recompute fallback does not lower that
  phase (see "Tried and rejected"); what would is listed under open issues.
- **Host footprint rises with the tier** (it is the bigger segment, not this branch): 4 GiB 5.18 -> 6.84 GB
  (+1.66), 8 GiB 7.10 -> 11.65 GB (+4.55) for memory-merkle, 9.72 -> 13.35 GB for the full suite at 8 GiB.
  At the default budget the footprint is unchanged (12.95 -> 12.89 GB).
- **The 1.23 GB is R22's flat eval chain**, not Z14's prefill: `RISC0_METAL_RV32IM_EVAL_FLAT=0` alone adds
  +1.230 GB [+1.218, +1.243], all wave-6 rv32im knobs off +1.241 GB; prefill, commit fusion, hoist and the
  Z15 knobs each change it by <= 0.01 GB.

## What changed (each step has a revert knob)

1. **Drop the data witness after `step_accum` at every po2 on unified-memory HALs** (`witgen/mod.rs`).
   That means Metal *and the CPU HAL*: `CpuHal::has_unified_memory` is true, so the knob also changes CPU
   proofs. The seals do not change (CPU seals still equal Metal's).
   Nothing reads it after accum (the data group has its own coefficients and LDE). On Metal the buffer goes
   to the pool, so the default budget is unchanged (it stays pooled, and Z14's prefill still takes it);
   under a budget the drain before a refused allocation can release it. Knob
   `RISC0_METAL_DROP_DATA_EARLY=0` (only at po2 >= 22, as before).
2. **Prefill set-aside cap from headroom, released on a po2 change** (`hal/metal.rs`,
   `hal/mod.rs::prefill_elem_within`; fix round 2: no edit to `metal/runtime.rs`, see below).
   - A buffer is set aside only while `held + len <= free_size - need`, where `need` is what the rest of
     the segment still allocates (rv32im passes 1024 B per cycle; measured 656 B per cycle from the live
     sets above: check poly, check group, mix buffer, FRI). Set-aside memory is the one pool memory that
     A1's LRU cap does not release (only a drain does), so it must not stand in for memory the next
     phase needs. The bound is conservative: `free_size` already excludes what is set aside (fix round 2;
     round 0 added the held bytes back, which needed a runtime hook; at the measured points it decides the
     same, see Correctness). At the default budget both buffers are still set aside (same as Z14); at 4 / 8 GiB with
     the new tiers nothing is (there is no headroom; a drain would release them anyway).
   - A change of the commit domain (po2) releases the set-asides (`note_commit_domain`), which before stayed
     idle until a drain.
   - `RISC0_METAL_PREFILL_LOG=1` logs each decision. Knob `RISC0_METAL_PREFILL_CAP=limit8`: Z14's limit/8
     cap, kept across po2 changes.
3. Re-measured: both tiers then prove (step 1 alone suffices for the accum commit; see knobs below), but
   the margin was 2 % (FRI phase) and a budget 5 % lower failed. So:
   - (a) **Commit accum in place** (`Hal::commit_coeffs_lde_in_place`, CPU default = the unfused steps;
     Metal = Z13's chunked commit with the witness as its own coefficient buffer, whose inverse NTT already
     runs in place for `batch_interpolate_ntt`; `Prover::commit_group_in_place`). Fix round 2: rv32im's
     witgen gives the accum witness up with the new `Hal::donate_to_commit` at the end of `accum()`, and
     `Prover::commit_group` commits a donated buffer in place (`Hal::take_commit_donation`; default: never).
     The rv32im call sites are unchanged. No kernel changed. Auto: only when the planned accum-commit live set
     exceeds 85 % of the working-set limit (fires at 4 GiB po2 19 and 8 GiB po2 20, not at the default
     budget or the old tiers). Knob `RISC0_METAL_ACCUM_IN_PLACE=0/1` (default auto).
   - **Drop the groups' coefficients after the FRI mix** (`prover.rs`): nothing reads them after it. Without
     this the FRI phase was the peak (~98-99 % live). Gated: only when the free working set is smaller than
     those coefficients; unconditionally it cost +8 ms at po2 19 / 8 GiB (the pool's LRU cap evicts buffers
     freed early, and the next segment's commits allocate afresh; `k8g19/`). Knob
     `RISC0_METAL_DROP_COEFFS_AFTER_MIX=0/1` (default auto).
   - (b) the coeffs-recompute fallback: not built (below).
4. Clippy: the 7 `type_complexity` errors (`prover.rs`, `fri.rs`) are fixed with a `fri::TreeOpenings` alias;
   rustfmt drift in `poly_group.rs` / `prover.rs` fixed (`cargo clippy -p risc0-zkp --features metal
   --release --lib --tests` is clean; rv32im with `--no-deps` has one pre-existing `new_without_default` in
   `execute/testutil.rs`, not owned).

## Tried and rejected

- **coeffs-recompute (LEADS2 small-mac-coeffs-recompute), not built.** Dropping the data/accum
  coefficients after their commits and rebuilding them by an inverse NTT of every 4th LDE point before
  eval_u lowers the accum-commit and eval_check phases (already at ~89 % live), not the binding one. The
  rebuild must happen after the check commit (the check group exists by then, Fiat-Shamir order) and before
  eval_u and the mix, which read every group's coefficients at once (Z15's fused mix) or in two separate
  passes. So at the rebuild the live set is again all coefficients + all LDEs + the check group: 7825 MiB at
  po2 20, the same as without the drop. Doing it per group would need two rebuilds per group (eval_u, then
  the mix after `mix` is drawn), ~4 inverse NTTs of a po2 20 segment.
- **The CUDA low-memory path at po2 <= 20** (release every group's LDE after eval_check, re-expand it per
  group for the FRI queries), forced with a local knob (`prof3/p19_4g_lowmem.log`): live peak 3657 MiB
  (89 %) at po2 19 / 4 GiB, but FRI+tail 34 -> 146 ms, **+112 ms per segment (+22 %)**. Rejected (the tier
  gains 14-23 % on the whole STARK); the knob was removed.
- **Ungated coefficient drop after the mix**: -64 MiB Metal peak and -0.065 GB footprint at the default
  budget (`tdef_pregate/`), but +8.5 ms [-6.5, +13.5] per po2 19 segment at 8 GiB (data commit +10, accum
  commit +4, FRI -6, 7/7) and +14.5 ms at po2 18 / 4 GiB; `k8g19/` (4 rounds): `DROP_COEFFS_AFTER_MIX=0`
  gives A's 475.5 ms against 484 ms, `DROP_DATA_EARLY=0` does not. Now gated to a short free working set.

## Recommendation for W7-M11 (zk-miner tier table; not implemented here)

| working-set limit | M8 today | recommended | basis |
|---|---|---|---|

Conditions:
- The live margin is 3.5 % at both new tiers (96.5 % of the budget at the FRI mix). It is deterministic
  in the po2 (all buffers are sized by the segment, not the program), but it leaves little room for
  anything else the worker allocates on the GPU during a segment. M11 should keep `min_limit_for_po2` at
  the tier budget itself (4 GiB for 19, 8 GiB for 20), not below it.
- The 8 GiB / po2 20 tier's host footprint (11.7-13.4 GB) is above what a 16 GB Mac can hold beside macOS
  comfortably; M6's footprint model must accept it, or M11 should use po2 20 at 8 GiB only on 18 GB+ Macs
  (and po2 19 on 16 GB). Real-hardware validation is deferred (no 16 GB Mac here).
- The ceiling (`ZKMINER_METAL_NO_PO2_CEILING`) had to be lifted for both measurements: M8's ceiling is
  18 at < 6 GiB and 19 below 10 GiB.

## Ownership (fix round 2): every edit is in the owned files

Rounds 0-1 edited two files outside the owned list (rv32im `prove/hal/mod.rs`: the two accum-commit call
sites; zkp `hal/metal/runtime.rs`: `note_domain -> bool`, `prefill_release`, `prefill_held`) and added
`hal/metal/tests_r2.rs`. Fix round 2 reverts all three to W7-A1 and does the same work in owned files:

- **Call sites -> commit donation.** `Hal::donate_to_commit(&witness)` / `Hal::take_commit_donation`
  (hal/mod.rs, defaults: no-op / false). rv32im witgen (`accum()`, owned) donates the accum witness when
  `accum_in_place` says so; `Prover::commit_group` (owned) checks the donation and calls
  `commit_group_in_place`. The contract is opt-in by the buffer's owner, so no other caller of
  `commit_group` changes. MetalHal keeps a handle to the last donated buffer and matches by GPU address
  and size (a held handle, so the address cannot be reused by another buffer meanwhile); a match consumes
  it. `witgen.accum` now stays `Some` (holding coefficients) until the witness generator is dropped right
  after the commit; it is the same allocation as the group's coefficients, so the live set is unchanged
  (peaks below are identical to round 0).
- **runtime.rs hooks -> MetalHal bookkeeping (metal.rs).** The po2 change is detected by MetalHal's own
  last-domain atomic (`rt.note_domain` is still called for A1's epoch). The set-asides are released by
  taking each (bytes, word) this HAL set aside (`R2State::prefill_keys`) with A1's existing
  `prefill_take`, wrapping it with `RawBuffer::from_pooled` and dropping it with `set_bypass_pool`, which
  frees it through `Runtime::freed` (same accounting as the old `forget`; in-flight fills stay safe because
  freed buffers are only discarded when idle). The key list can only over-list (a buffer since taken or
  drained): releasing such a key finds nothing, which `r2_prefill_headroom_and_po2_release` tests.
  `prefill_held` is gone: the cap is `free_size - need` (conservative, see step 2).
  Side effect: each release counts as a pool hit in A1's counters (cosmetic).
- **Tests** moved inline into `hal/metal.rs` (`mod tests_r2`), plus a new `r2_commit_donation`.

## Knobs

`RISC0_METAL_DROP_DATA_EARLY=0`, `RISC0_METAL_PREFILL_CAP=limit8`, `RISC0_METAL_ACCUM_IN_PLACE=0|1`
(default auto), `RISC0_METAL_DROP_COEFFS_AFTER_MIX=0|1` (default auto); measurement:

## Open issues

- **Margin below 5 % at both new tiers** (96.5 % live at the mix). What would lower that phase: a deferred
  re-expansion of the data group's LDE only (release it after eval_check, re-expand it from the data
  coefficients after the mix, then drop those; estimated ~+50 ms per po2 20 segment, ~+5 %, for ~90 %
  live), or Merkle trees that do not keep the bottom node layer (recompute leaf hashes for the queries).
  Neither is built.
- **po2 20 segments under an 8 GiB budget are ~8 % slower than unconstrained** (1013 against 937 ms:
  data commit +18 ms, witgen +22 ms, from drains and fresh allocations each segment). A segment-aware
  drain (release only what the refused allocation needs) would recover most of it.
- rv32im's scratch buffers (`MetalRv32imCtx`, preflight upload) are ~180 MiB at po2 20 and stay live
  across segments; not owned here.
- Real 16 GB Mac validation is deferred (no hardware): host footprint and the system-wide GPU check under
  real pressure.
- Not rerun in fix round 2 (the Metal work per segment is the same, only how the in-place decision
  reaches the prover changed): the worker tier A/Bs and the default-budget A/Bs. The tier re-check above
  shows the same phase peaks.
- The worker numbers needed a local, uncommitted `R2_WORKER_PO2` override in zk-miner's `main.rs`.
- Set-asides from the previous po2 are released at the new po2's first commit (`note_commit_domain`), not
  when the new po2's witgen allocates. At a 19 -> 20 change under 8 GiB, 628 MiB of po2-19 set-asides are
  still held while the po2-20 data witness is allocated, and that step relies on A1's pressure drain. It
  proves, and the seals match (`corr_fix1/seal_large_8g.log` includes that transition). Releasing at
  witgen start would be tighter, but it needs a hook in rv32im's witgen allocation path. Not built.
- The review measured one gain this note did not claim: po2 21 at the default 16 GiB budget. A1 refuses it
  (512 MiB of nodes), and so does this branch with all four knobs off. With R2 on (in-place accum,
  auto-selected) it proves at a 16355 of 16384 MiB peak (99.8 %). That margin is too thin to rely on. The
  measurement is the reviewer's, against an approximate A1 binary.
- `FINALIZE_BYTES_PER_CYCLE = 1024` (measured 656 B per cycle) and `ACCUM_IN_PLACE_MARGIN = 0.15` are
  untuned heuristics. They scale with cycles and with the working-set limit, and none is a RAM fraction
  (PLAN 9.1). Re-check them if the live set at finalize or at the mix changes, because a change there can
  silently flip the auto modes.
