## 2. (a) Committed ctrl groups kept across provers

### 2.1 Design

- **zkp** (`prove/poly_group.rs`, `prove/merkle.rs`; additive only):
  - `PolyGroup::to_host() -> PolyGroupHost` copies the coefficients plus every Merkle node, the
    root and the top layer.
  - `PolyGroup::host_bytes()` reports the size without copying.
  - `PolyGroup::from_host(hal, &host)` rebuilds the group: it uploads the coefficients and
    re-expands the evaluated domain from them, using what `restore_evaluated` does (bit-reverse,
    `batch_expand_into_evaluate_ntt`, bit-reverse back). It then uploads the nodes into a
    `MerkleTreeProver::from_host`, whose cached top layer means `commit` needs no read-back.
  - No hashing. The evaluated domain (96 MB for p254) is recomputed, not stored, which saves
    host memory.
  - `PolyGroupHost::same_as` is for tests.
- **recursion** (`prove/ctrl_persist.rs`, new):
  - A process-wide map keyed by (hash suite name, `CtrlKey`). Each entry holds the host group,
    the program code it was built from (an `Arc`), a `Weak` to the shared program, the commit
    time and the byte size.
  - `RecursionProverImpl::commit_ctrl` (new; used by `prove_impl` and `prewarm`) tries three
    sources in order:
    1. the device cache (as before);
    2. a persisted host group, rebuilt with `PolyGroup::from_host`;
    3. a fresh commit, which also takes a host snapshot when the policy wants it.
- **Exactness of a hit:**
  - `claim_ctrl_caches` takes the code `Arc` from a persisted entry only if it is the same
    program (`Weak` pointer equality) or `same_code` holds. Otherwise it copies the code, as
    before.
  - `lookup` then requires `Arc::ptr_eq` with that code.
  - A program whose code differs only where `CtrlKey` does not sample it gets the same key but
    no group (`c13_persisted_group_needs_same_code`).
- **Policy** (`RISC0_METAL_REC_CTRL_PERSIST`, read once):
  - default `1`: Poseidon254 groups only;
  - `all`: every suite;
  - `0`: off.
  - Bytes are capped by `cap_bytes(gpu_total_memory())`: a 32nd of the working-set budget, so
    128 MiB at 4 GiB. `RISC0_METAL_REC_CTRL_PERSIST_BYTES` overrides it. Why a 32nd: it caps
    host RAM (not the Metal working set), scales with the budget as PLAN 9.1 asks, and is the
    smallest power-of-two fraction that holds identity_p254's ~98 MiB group at the minimum
    4 GiB budget, while staying a small share of a 16 GB Mac's RAM (256 MiB at 8 GiB).
  - Over the cap, the entry of lowest priority is evicted. The priority is deterministic and
    uses no measured times: Poseidon254 groups first, then larger groups, then the key.
    `would_keep` admits a group if it fits next to the entries that rank above it (the lower
    ones would be evicted), so a large group is not starved by small ones kept earlier. Fix
    round 1 replaced the earlier commit-ms-per-byte order, which in mode `all` let shared-GPU
    timing noise pick the victim, and which refused the ~91 MB p254 group after ~34 MB of
    poseidon2 groups at a 100 MB cap (reviewer finding). The commit time is still logged.
    Fix round 2: the Poseidon254 rank compared the suite with the prover-selection string
    `"poseidon_254"`. The name commit_ctrl passes is `HashSuite::name`, which is `"poseidon254"`,
    so the bonus never applied in production (mode `all` only; the default keeps only p254
    groups). `priority()` now uses `p254_suite_name()`, as `mode_wants` does.
  - Only unified-memory GPU HALs persist (`has_unified_memory && gpu_total_memory != MAX`), so
    the CPU prover used by seal checks is unchanged.
- **zkvm**: no change to `succinct_to_groth16`. The release lines stay as they are, because
  the host copies outlive the provers they release. The only zkvm edit is a test knob: G8's
  `metal_wrap_after_stark` gains `RISC0_G8_JOBS` (several STARK + wrap jobs in one process).

The suite-based rule is deterministic, and it is what the measurements support.

## 3. (b) uint4 mix-power load in `rec_lz_add`

### 3.1 Change

- `cuda2metal_eval.py --split-lz` replaces the C12 body of `rec_lz_add` in the lazy Fp split,
  pinned as `lz.uint4_add = 1`. The old body issued four 4-byte reads of `poly_mix[k]`
  through a `uint32_t*`. The new body is one load:
  `uint4 m = *(reinterpret_cast<const device uint4*>(poly_mix) + k);`
  followed by four multiply-adds.
- Alignment: the 158 powers sit in the HAL-owned `rec_poly_mix` buffer at offset 0, and FpExt
  is 16 bytes, so every power is 16-byte aligned.
- `tally.poly_mix_read` goes 172 -> 171 (the `&poly_mix[k]` is gone).
- The same run also writes `eval_check_split_lz_u32.metal`: the exact C12 text with kernels
  renamed `ec_lz32_part_0..5`, pinned `lz32.*`.
  - The metallib lists it (`METAL_KERNEL_NAMES`; the c4 test matches `--list-kernels`).
  - The HAL has `EvalKernels::SplitLzU32`, selected by `RISC0_METAL_REC_LZ_UINT4=0` or
    `RISC0_METAL_REC_KERNELS=lz32`.
  - Cost: about +0.97 MB of metallib and one more AIR compile at build time. No PSO is built
    unless the variant is selected.
- The uint4 TU compiles much smaller: 787 KB vs 966 KB metallib for the lz file alone, built
  standalone.
