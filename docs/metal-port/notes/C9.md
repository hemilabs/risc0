## The fix that un-ignores `test_recursion_host_chains_check`

C6 reported it as a known issue (C6 note, "identity_p254 + host chains check"). Under `metal`, `host_chains_backend()` is true. So
`WitnessGenerator::new` also computes host chains for the **CPU** prover that serves
`poseidon_254`, and with `set_host_chains_check(true)` it re-runs the witgen to compare. The CPU
witgen (`kernels/cxx/extern.cpp`) advances `cycles[c].iopIdx` in place. `CpuCircuitHal` passed
the caller's trace, so the re-run read advanced IOP indices and failed with `eqz failed at:
zirgen/circuit/recursion/wom.cpp:78`. The fix: the CPU HAL now copies the cycles first, as the Metal HAL
(C5/C6) and `host_witgen` already do, so `generate_witness` is a pure function of its inputs. This
affects every build that uses the CPU recursion HAL. The cost is a ~2 MB memcpy per witgen at 260k cycles. A mutation
check verified it: with `cpu.rs` reverted, `cpu_witgen_keeps_trace` (trace changed) and
`p254_cpu_fallback_with_host_chains_check` (the exact `wom.cpp:78` error) both fail. With the fix both pass.

I chose this over making the host-chain check skip HALs that ignore chains. The check still exercises the CPU path,
and the root cause (a non-idempotent witgen on the caller's buffer) is gone for every caller.

## Seal equality vs CPU

The recursion prover has exactly two randomness sources, the ZK noise of the data tail and of the accum tail
(`prove/witgen.rs`). Fiat-Shamir does everything else. With `with_noise_seed`, a Metal proof and a
CPU proof of the same input must therefore give bit-identical seals. Two entry points use this:

- `prove_seal_checked(metal, cpu, program, input, preflight)`: proves with Metal under a random seed. It then
  proves with the CPU prover under the same seed, on a copy of the preflight (trace + output; when
  `prepare()` already consumed the input, the copy carries it). It bails on the first differing
  output or seal word.
- **`RISC0_METAL_REC_SEAL_CHECK=1`** (read once): `recursion_prover("poseidon2" | "sha-256")`
  returns a `SealCheckProver` that does this for every proof. With it, real zkvm lifts, joins and resolves are
  compared without touching zkvm code. It doubles the proof cost and makes the noise deterministic, so
  it is validation only (a `warn!` is logged when the prover is created). `poseidon_254` is already
  the CPU prover and is not wrapped.

## Tests (`hal/metal/tests.rs`, all under `--features metal`, default `test` feature)

- `translator_steps_check`, `translator_eval_check_monolith`, `translator_eval_check_split`: run
  `python3 cuda2metal_steps.py --check` and `cuda2metal_eval.py --check [--split]` from
  `recursion-sys/kernels/cuda` (`$PYTHON` overrides the interpreter). These cover the pins, the residual scan and the round trip. The C4 note
  says the build enforces only the pins. Pins seen: step_exec 51 `Fp(0)`, 4373 asserts, 1768 `device auto&`,
  38 noinline; step_verify_mem 960 asserts; compute/verify accum 486 / 329 `c1_bad`, 1 trap each.
- `metallib_smoke`: the set of `METAL_LIB` function names equals `METAL_KERNEL_NAMES` exactly (21,
  both eval variants included, no PSO built), and the four step-wrapper base PSOs load.
- `noise_seed_controls_the_seal`: this shows the check is not vacuous. Unseeded CPU seals differ. The same seed gives
  identical seals, a different seed gives different ones, and the seed is restored afterwards.
- `seal_matches_cpu_{poseidon2_po2_16, poseidon2_po2_18, sha256_po2_16}`: test zkr. A full Metal
  proof (all three circuit phase counters incremented) has the same seal as the CPU prover. The words compared are
  46979 at po2 16 and 55667 at po2 18.
- `seal_check_detects_a_difference`: a CPU side with another seed is reported as `seal differs`.
- `cpu_witgen_keeps_trace`: the regression test for the fix (trace unchanged; two CPU witgens over it
  are equal in raw words).
- `p254_cpu_fallback_with_host_chains_check`: `Prover::new(.., "poseidon_254")` →
  `prepare()` (preflight + host chains) → `run()` with `set_host_chains_check(true)`. The check runs once (1 chain).
  The output and globals equal the CPU prover's. The same is repeated for `poseidon2` (Metal HAL).

The phase-level equivalence and fault-path tests live with their phases and were not moved:
witgen `c6_tests` (Parallel ± host chains, Seq modes, corrupt trace / WOM / chain → `Err`,

split == CPU). `recursion/src/testutil.rs` was not created. The existing `testutil` module in

## Measurements (M5 Max, GPU shared with other agents: indicative only)

**Wall time per recursion proof, Metal vs CPU prover**, from the seal-check lines. Both are full `prove_shared` calls with the
preflight already prepared. The CPU prover uses all cores, on the debug-profile test binary with opt deps:

| proof (po2 18) | Metal | CPU |
|---|---|---|
| lift, 134164 rows (x4) | 0.28-0.36 s | 9.7-11.6 s |
| lift, 121426 rows (x2) | 0.31-0.37 s | 11.1-13.6 s |
| join, 259612 rows (x2) | 0.32-0.36 s | 9.9-11.8 s |
| resolve, 259668 rows (x2) | 0.32-0.40 s | 10.7-13.3 s |
| test zkr po2 16 / 18 (lib tests, 3 runs) | 0.08-0.12 s / 0.24-0.30 s | 1.5-3.9 s / 6.4-11.3 s |
| test zkr po2 16 sha-256 | 0.06 s | 0.65-2.2 s |

The Metal prover is about 30x faster than the CPU prover per lift/join. The witgen + accum phases alone are below the
CPU's by C6/C7's numbers (witgen 40-163 ms vs 100-370 ms; accum 24 ms vs 65-72 ms at 2^18).

**Peak GPU memory** (`currentAllocatedSize`): the test-zkr seal tests read 367 MB (po2 16) and
1.44 GB (po2 18) at the witgen, accum and eval_check phase entries and as the proof peak. That is identical under the
default, 4 GB and 8 GB budgets. The numbers are flat across phases because a warm-up proof had already grown
the pool, so this is the steady-state footprint of a repeated recursion proof. It matches C5's
cold per-proof peak (371 MB / 1.44 GB). **No recursion shape exceeds 4 GB or 8 GB.** The zkvm lift/join/resolve e2e
(rv32im segments + recursion in one process) passes under both budgets, so no budget error was produced.
C5's 1 GiB probe showed the clean over-budget error. The real lift/join peaks inside the zkvm process
were not isolated: `currentAllocatedSize` is process-wide and includes the rv32im composite.

## Known gaps

- `RISC0_METAL_REC_SEAL_CHECK` is read once per process. The in-crate tests call
  `prove_seal_checked` directly.
- Seal equality relies on the noise hook. A future noise source (a new random draw outside
  `noise_rng`) would make the check fail loudly, not pass silently.
- With metal, host chains are still computed (and ignored) for the CPU p254 prover: a few ms of
  host time per identity_p254. The check now passes there too.
- identity_p254 is CPU until Z10. The zkvm `compress`/`shrink_wrap` tests are not in scope (M3/G7).
- The zkvm e2e under budgets ran only the two lift/join/resolve tests, not the full 16.
- The timings come from a GPU shared with other agents. No 8-10-core base chip was measured.
