### build.rs contract for R4/R5/R6
Inside `build_metal_kernels()` there are three blocks, each initially a comment only:
`// ---- BEGIN R4 accum_tu (metal) ----` … `// ---- END R4 accum_tu (metal) ----`, the same for
`R5 witgen_tu (metal)` and `R6 eval_check (metal)`. In scope for a block:
- `gen_dir: PathBuf` = `$OUT_DIR/metal` (created; on the `-I` path and in the cache key);
- `generated: Vec<PathBuf>` — push the absolute paths of the `.metal` TUs to compile;
- `flags: Vec<String>` — extra compiler flags (apply to every source of the metallib);
- `skip: bool` — RISC0_SKIP_BUILD_KERNELS: do nothing (no python, empty metallib);
- helpers `run_metal_generator(script, &args, hint)` (python_command from the crate root,
  panics with stdout/stderr + `hint`), `write_if_changed(path, text)`, `rerun_if_changed(p)`.
A generator must not rewrite an unchanged output (KernelBuild prints `rerun-if-changed` for
every source; a fresh mtime reruns the build script on every cargo call). Each block prints
`rerun-if-changed` for its own generator inputs. Kernel names still go into `src/lib.rs`
`METAL_KERNEL_NAMES` (not R3's file).

### Translation rules (R1's note, now applied / documented)
- Layouts are program-scope `constant constexpr` (layout.metal.inc), so `BoundLayout<T>` binds
  `const constant T&`. No generated `.inc`/steps code constructs `BoundLayout(a, b)` (0 sites in
  steps.cu/steps.cuh/witgen_tu.cu/accum_tu.cu: all go through `BIND_LAYOUT`, which witgen.h maps
  to `bindLayout`); generators that hand-write one must spell `bindLayout(a, b)`.
- `MutableBufObj data(dataBuf, preDataBuf)` → `BufferObj data = makeMutableBuf(dataBuf, preDataBuf);`
  `MutableBufObj accum(accumBuf, /*zeroBack=*/k)` → `makeMutableBuf(accumBuf, nullBuffer(), k)`;
  `GlobalBufObj g(buf)` → `BufferObj g = makeGlobalBuf(buf);` and pass `&data` where CUDA passed
  `&data`. The only sites are in the kernel-wrapper templates of `witgen_tu_gen.py:101-103` and
  `accum_tu_gen.py:117-123` (R5/R4) and ffi.cu (hand ports).
- **New:** `r0::array::operator[]` (F1's cuda2metal.h) is not `constexpr`, so CUDA's
  `constexpr size_t kUserAccumSplitA = kLayout_TopAccum.columns[0].col;` (accum_tu_gen.py:106)
  does not compile as a constant expression on Metal; write
  `kLayout_TopAccum.columns.elems[0].col` (verified in `rv32im_incs.metal`).

## Assumed / not verified
- No GPU execution of translated layout code beyond compile-time evaluation (static_asserts);
  R1's selftest covers the binding machinery with hand-written layouts; R5/R8 are the runtime gate.
- The mixed operators are checked by compilation and by construction (identical formulas to CUDA);
  no dedicated GPU numeric test (they change only `elems[0]` with fp.h's `+`/`-`).
