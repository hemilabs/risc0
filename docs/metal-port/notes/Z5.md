# Z5: combos_divide on Metal (mdiv)

## What was ported, from where
- `risc0/sys/kernels/zkp/metal/mdiv.metal` (new). A transliteration of `risc0/sys/kernels/zkp/cuda/supra/mdiv.cuh`, using its default non-`MD_COAL` path with `MD_NTH = 256`:
  - `md_block_suffix_scan<NT>` → same algorithm. The FpExt shuffles are four `simd_shuffle_down/up` on the raw words.
  - `mdiv_agg0` → `mdiv_agg0<E>`.
  - `mdiv_scan<NTILES>` → `mdiv_scan<NT>`.
  - `mdiv_apply` → `mdiv_apply<E>`.
  - `mdiv_final` → `mdiv_final`.
  - Instantiations use `[[host_name]]`: `mdiv_agg0_e8/_e16`, `mdiv_apply_e8/_e16`, `mdiv_scan_{32,64,128,256,512,1024}`, `mdiv_final`.
  - `[[max_total_threads_per_threadgroup]]` comes before `kernel`. Zero is written as `FpExt()`.
  - The launch shapes match CUDA: agg0/apply are (ntiles, njobs) × 256, scan is njobs × NT, final is 1 × 32.
- `risc0/zkp/src/hal/metal/mdiv.rs` (new). It ports `mdiv_supported` → `mdiv_shape` and `mdiv_run` → `mdiv_plan` + `mdiv_encode`. It also ports the `supra_poly_divide_multi` dispatch (`supra/api.cu`), including the ROCm-style grouping of `MD_MAXJ = 8` combos per run. For other shapes there is a host fallback (`host_combos_divide`) with the same rotate semantics.
- `risc0/zkp/src/hal/metal.rs`: the `mod mdiv;` and `#[cfg(test)] mod tests_z5;` lines, 11 appended `KERNEL_NAMES` entries, and `Hal::combos_divide`. That method calls `mdiv_combos_divide` and then `report_nonzero_remainders`, as `cuda.rs:1878-1911` does.
- `risc0/sys/build.rs`: `"mdiv.metal"` appended to the zkp Metal list.
- `risc0/zkp/src/hal/metal/tests_z5.rs` (new): the tests.

### Semantics (same as CUDA)
- Each combo slice is divided by its roots in order, with sppark `div_by_x_minus_z<rotate=true>` semantics: `a[k] = S_{k+1}` and `a[n-1] = S_0`, which is the remainder.
- The remainders, one per root in `chunks` order, are reported through `report_nonzero_remainders`, which logs `tracing::error!` and does not panic.
- With zero remainders the result equals the CPU HAL, whose `poly_divide` leaves `a[n-1] = 0`.
- Combos with no roots are skipped and produce no remainders.
- The combo index is honoured. The CPU HAL ignores it: it zips `chunks` with the slices in order, which the prover's in-order chunks make equivalent.
- The batch closes at the end: the remainder read syncs, as CUDA's `cudaStreamSynchronize`.

### Decisions (open questions 2 and 3)
- **No pointers in `MdJobs`.**
  - CUDA passes `MdJob` with device pointers as a `__grid_constant__`. Here each job holds u32 **element offsets** into two buffers that are bound explicitly: buffer 0 is combos and buffer 1 is one scratch buffer (aggregates, carries, remainders). `MdJobs` (528 B, sizes `static_assert`ed in both MSL and Rust) goes through `set_bytes`.
  - Both buffers are therefore bound with `set_buffer` and hazard-tracked like any argument. No `use_resource` is needed, which removes the silent write loss D0 found. This follows plan 2.0's default ("explicit bindings + set_bytes POD structs").
  - Open question 2 (pointers via `gpu_address` in `set_bytes`) therefore does not arise for Z5. D0's answer stands: it works only with `use_resource`.
  - The host asserts that all offsets fit in u32.
- **po2 < 16 (ntiles < 32 at E = 8).**
  - `mdiv_scan_32` pads with zero tiles: tiles ≥ ntiles read as zero, and the previous remainder goes into tile `ntiles-1`. So each slice's scan is one 32-thread threadgroup, and agg0/apply are unchanged. This covers po2 11..15.
  - Below po2 11 (n < 2048), and for any non-power-of-two tile count, the host loop runs. CUDA likewise falls back to the per-root sppark path.
  - Measured: below po2 16 the CPU HAL is faster than the GPU path. The GPU wall time is about 1-3 ms and mostly fixed per-dispatch/command-buffer overhead, against 0.4-2.2 ms for the CPU. I kept the GPU path, because it is correct and the absolute difference is ≤ 2 ms. Choosing a crossover is left to Z9.
- **po2 22 (ntiles 2048 at E = 8).** Two options were implemented and both are tested bit-exact:
  - (a) A two-level scan: each `mdiv_scan` thread takes K = ntiles/1024 tiles. It does a local Horner with weight z^T, then a block scan with weight z^(T·K), then walks down its K carries. This supports po2 up to 23 (`MD_MAXK = 4`).
  - (b) E = 16: tiles of 4096, so 1024 tiles.
  - Measured, best of 3 GPU time, 6 slices, 11 roots: E16 was faster at every po2 from 20 up (numbers below). The default is therefore **E = 16 for n ≥ 2^20 and E = 8 (CUDA's) below**. `RISC0_METAL_MDIV_E=8|16` overrides this, so E = 8 at po2 22 uses (a).
  - A CPU fallback for po2 22 was rejected: the CPU HAL takes about 155 ms there.
- `RISC0_METAL_MDIV=0` forces the host loop, mirroring `RISC0_CUDA_MDIV=0`.

- New tests (`tests_z5.rs`):
  - `combos_divide_po2_{13..22}`: 7 slices, 6 in-order chunks with 1/2/3/1/2/1 roots, slice 6 untouched. The CPU HAL's `combos_divide` is compared with Metal's `Hal::combos_divide` bit-exactly over the whole buffer. Every Metal remainder is zero, and the host reference equals the CPU HAL.
  - `combos_divide_nonzero_po2_{13..22}`:
    - Chunks name slices out of order. Two chunks (4 roots) hold random, non-divisible data.
    - The oracle is `host_combos_divide`: CPU `poly_divide` followed by `a[n-1] = rem`, which are the CUDA semantics.
    - Data is checked bit-exactly, and the `report_nonzero_remainders` log lines are captured with a thread-local `tracing_subscriber` and compared: 4 lines, identical.
    - (The CPU HAL panics on nonzero remainders, so it cannot be the oracle here.)
  - `combos_divide_explicit_e`: E16 at po2 16/18, E8 at po2 20/21/22 (K = 2), and E16 at po2 22, each with zero and nonzero remainders.
  - `combos_divide_many_combos`: 11 combos, which is 2 groups of `MD_MAXJ`, and includes a chunk with 0 roots.
  - `combos_divide_host_fallback`: po2 4 and 10, plus a forced host loop at po2 16.
  - `combos_divide_after_unsynced_divide`: a divide encoded but not synced, followed by `combos_divide`. It must equal two CPU divides.
  - `mdiv_shapes`: shape, grouping and default-E checks.

## Assumed / not verified / gaps
- The `MD_COAL` path (coalesced tile load/store through threadgroup memory) is not ported. CUDA does not enable it by default. It would be a Z9 candidate, since apply dominates.
- SIMD lanes are taken as `t & 31` (consecutive 1-D thread indices form a SIMD group), as in the CUDA code and the existing ntt.metal. This was not probed separately; it is consistent with every test passing.
- The po2 < 16 GPU-vs-CPU crossover and E for po2 18-19 are left to Z9. They were measured once, on a busy machine.
- `DualHal` does not forward `combos_divide` to its second HAL. These tests therefore call both HALs directly. Z6 owns testutil if a DualHal form is wanted.
- The default E = 16 for n ≥ 2^20 departs from CUDA's MD_E = 8. Results are bit-identical because the arithmetic is exact in the field, but the thread register footprint differs. No spill check was done beyond the timing.
