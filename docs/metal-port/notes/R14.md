## Summary
- **Profile:** with R15e in, a po2 20 segment in the zkvm-style pipeline takes **~2.10-2.15 s
  when the GPU is quiet**. Almost all of it is GPU-bound phases that each end in a wait: eval_check
  ~1.55-1.60 s, data commit ~0.25 s, accum commit ~0.13 s, finalize ~0.07 s, witgen ~0.03 s,
  accum ~0.02 s. The host-only time in which the GPU has nothing queued, measured directly, is
  about **2 ms per segment**: the preflight copy ~1.6 ms, the evalfast table < 0.1 ms, the
  inline trace drop 0.0-0.1 ms, and the zkvm-style loop outside `prove_begin` ~0.03 ms per
  segment. The memory pool is reused across segments (allocation flat at 9355 MiB over 32 passes).
- **So the overlap sub-tracks have nothing to win** (≤ 0.1 % per segment), and none was kept:
  the drop_trace thread, eval_check committed without a wait (with and without a wait in
  `eval_check_dep`; a second queue would have nothing to run, because everything after eval_check
  depends on it), a parallel preflight copy, cross-segment pipelining. Blit fills were already
  done everywhere (zkp `fill_u32` blits byte-repeating values, witgen/accum use `blit_fill`).
- **Cold start (kept, default on):** keccak's `MTLBinaryArchive` code (K5) was moved into the zkp
  Metal HAL (`risc0_zkp::hal::metal::archive`). keccak re-exports it, and its archive files and
  keys are unchanged. rv32im now builds its PSOs through it, under unit `rv32im`. With the OS
  shader cache off (`MTL_SHADER_CACHE_SIZE=0`), building every rv32im PSO took 120.6 s / 230.3 s
  with the old serial loader. Through the archive it took 100.5 s / 148.5 s on the first (miss)
  run, which only indicates that the concurrent build is not slower (2 noisy runs, one at load
  42; not a measured win), and **0.16 s / 0.21 s** from the archive in later processes. The
  reviewer's interleaved 7-pair process-level A/B confirms the hit path: median 258.8 s [134.2,
  387.7] before vs 4.36 s [2.95, 9.95] after (zkp PSOs included, load 15-69). With a warm OS
  shader cache the archive costs ~0.1 s more per process start (read + checksum of 24 MB). Revert switch: `RISC0_METAL_RV32IM_ARCHIVE=0` (the pre-R14 loader).
- **R8 open issue fixed:** the scratch Mutex is locked poison-tolerantly, so a budget panic inside
  `grow` no longer makes every later phase of that circuit HAL panic.
- **Perm window sweep:** inconclusive under the machine's load (below). The default stays 14;
  the knob is the existing `RISC0_METAL_ACCUM_SORT`.
- **Correctness:** no kernel or GPU result changed. Seals equal the CPU seals on 3 po2 20 real
  segments. Every pipeline-bench seal (4 segments x 4 variants x 8 rounds) equals the first
  variant's and verifies. The rv32im suite passes (124/0 after fix 1) twice, under 4 / 8 GiB
  budgets and with the archive off. The keccak suite, including its 9 non-ignored archive tests
  (3 more are ignored probes), passes 29/0 twice.

## Profile before (measure first)
Tool: new `pipeline_bench` (ignored test, `hal/metal/pipeline_bench.rs`). It drives
`SegmentProver::prove_begin` / `prove_end` the way zkvm's `prover_impl.rs` does, with the next
segment's preflight on a background thread. It uses R11's dumped po2 20 segments (sha #0, #8,
torture #0 / #7, merkle #55) with a fixed `rand_z`, interleaves the variants per round, and
compares every seal. Phase times come from `RISC0_VERBOSE`. Host-only spans come from the new
`R14_STATS` timers in mod.rs / eval_check.rs. Each timer covers a span that starts after a
completed wait and ends at the next dispatch, so the GPU has nothing queued during it.

A GPU-side timeline (command-buffer `GPUStartTime`/`GPUEndTime`) needs a hook in the zkp
runtime's `poll`, which R14 does not own. Without Xcode, counters are not available either. So the
idle gaps are host-measured, not GPU-timestamped (open issue for Z9 below).

Quiet segment (`prof0.log`, third segment, load ~5): `witgen=29.9 data_commit=245.0 accum=14.8
accum_commit=132.0 main=421.6 ms`, `eval_check_launch=1598.2 ms` (synchronous), `finalize
total=70.3 ms` (check commit 30, eval_u 17.7, combos 10.2, fri 12.3), `prove_begin total=2090.3
ms`. main + eval_check + finalize = 2090.1 ms, so there is no unaccounted time outside these
phases.

Noise: other agents' GPU jobs (G10, R15w, K7, C11) ran throughout, at load 3-49. A segment
measured 2.1 s on a quiet GPU and 3-5.5 s under contention. Contended segments showed data commit
at 500-1200 ms instead of 245 ms. To check whether the CPU preflight thread causes that, preflight
in the background (`bg`) was compared with all preflights done before the pass (`up`), 7 rounds
(`prof2.log`). In the one round with a quiet GPU the two are equal (bg 2144, up 2154, bg2 2134
ms/seg). The slow rounds hit bg and up alike, so the slowdown comes from the other GPU jobs, not
from the preflight thread.

## Sub-tracks (interleaved A/B, `ab1.log`: 4 segments, 4 variants, 1 warm-up + 7 rounds, load 2.2-9.9)
A = the unmodified behaviour (serial preflight copy, eval_check waits at its end). Per segment ms.
| Variant | pass median [min, max] | quiet round 3 | quiet round 4 | measured span |
|---|---|---|---|---|
| A | 2406 [2099, 5466] | 2099 | 2105 | preflight copy 1.6 ms/seg (6.5 ms per 4-segment pass) |
| par (rayon preflight copy) | 2271 [2106, 3091] | 2106 | 2208 | copy 1.1-1.7 ms/seg; 7-20 ms/seg in contended rounds, the same as A |
| async (eval_check commits, no wait) | 2587 [2101, 4329] | 2101 | 2208 | — |
| wait (commits, `eval_check_dep` waits) | 2930 [2103, 5314] | 2103 | 2151 | the ~1.6 s wait moved into eval_check_dep, as intended |

- The medians are dominated by other jobs' GPU load: A-vs-variant differences flip sign between
  rounds, and max/min ratios are 1.5-2.6x. In the quiet rounds all four are within 1 % (2099-2106
  ms/seg in round 3). The largest saving any of them can deliver is the host span it removes,
  measured directly: ≤ 0.5 ms per segment for the copy, and for the async eval_check the wake-up
  plus encode latency between eval_check and the check iNTT (the next zkp NTT/commit waits again
  anyway). **Verdict: no change; rejected, code removed.**
- **drop_trace thread** (R7 open issue): the inline drop of the preflight trace, which is all the
  thread could take off the critical path, measured 0.0 ms in 20 of 24 segments, 0.1 ms in 3 and
  0.8 ms in 1 (`post_eval_check` in `prof0/1.log`; macOS frees the big Vecs cheaply, unlike the
  10-20 ms CUDA measured). Rejected, hal/mod.rs unchanged.
- **Second command queue / eval_check overlap (PLAN 2.0, question 5):** answered **no**. eval_check
  occupies the whole GPU (65536 threadgroups at po2 20). Everything after it in the segment depends
  on the check polynomial. The next segment's GPU work cannot start before zkvm calls the next
  `prove_begin`, and at that point eval_check has already been waited for. So a second queue has
  nothing to overlap. `eval_check_dep` stays the no-op.
- **Pipelining consecutive segments:** the GPU-idle time between segments is the preflight copy
  (~1.6 ms) plus the loop overhead (~0.03 ms/seg; "outside prove_begin" 0.1 ms per 4-segment
  pass). The preflight of the next segment already overlaps on a CPU thread (zkvm). Not worth a
  loop restructure that would also hold two segments' buffers at once (PLAN 9.1 memory). No zkvm
  change.
- **Per-segment allocation / pool reuse:** `currentAllocatedSize` stays at 9355 MiB after every
  pass (32 passes), so the exact-size pool reuses every buffer from segment to segment at a fixed
  po2. Nothing to do. The pool keeping both sizes after a smaller tail segment (R11) is a
  release-policy question for M-items (zkvm already has `release_pool_on_po2_growth`).
- **Blit fills:** nothing left to convert. zkp `fill_u32` (and with it `alloc_elem_init` /
  `alloc_extelem_zeroed`) already uses `blit_fill` for byte-repeating words, and every rv32im fill
  value is byte-repeating (INVALID = 0xffffffff, 0). rv32im witgen/accum already blit-fill their
  tables and fault words. The `eltwise_zeroize_fp` kernels on `global`/`code` are zeroize passes,
  not fills, they live in `witgen/mod.rs` (not R14's), and they cost < 0.1 ms.
- **Perm window sweep** (`RISC0_METAL_ACCUM_SORT`, read once per process, so one process per
  (round, window), interleaved): only 11 runs finished before I stopped it, because the machine
  was too loaded (load 5-22). Accum phase ms per segment, 3 segments:

  | window | runs (ms) |
  |---|---|
  | 14 (default) | 57/91/60, 86/17/145, 64/75/48 |
  | 0 (off) | 79/62/44, 326/52/155 |
  | 11 | 31/16/230, 113/33/25 |
  | 12 | 216/165/55, 55/45/149 |
  | 13 | 137/60/32, 97/30/111 |

  The spread within one setting (15-325 ms) is 10x the quiet phase time (15-25 ms), so no
  setting can be claimed better. The whole phase is ~1 % of a segment. Default unchanged; this
  should be re-run on the quiet baseline machine and on an 8-10-core part (R9's open issue stays
  open).

## Change kept: binary archive for the rv32im PSOs (cold start)

  `ArchivedKernels` / `ArchiveReport` and helpers, moved verbatim from keccak (crate paths
  adjusted). Additions: `ArchivedKernels::library()` (rv32im's lazy PSOs need the library), and
  `pub` + `#[doc(hidden)]` on the test seams keccak's tests use. Behaviour is unchanged: key,

  their keys.

- Measurements (`archive_cold_start`, ignored test, `MTL_SHADER_CACHE_SIZE=0`, every PSO of
  `METAL_KERNEL_NAMES` + `EXPECTED_KERNELS`, 10 kernels):

  | run | load avg | plain loader (pre-R14) | archive, empty dir (misses) | archive, second load (hits) |
  |---|---|---|---|---|
  | cold1 (plain, miss, hit) | 7.3 → 4.9 | 120.58 s | 100.51 s (adds 144 s summed over threads, save 0.18 s) | **0.16 s**, 10/10 hits |

- Not core-count dependent. The archive key includes the device name and OS build, so a binary is
  never reused on another GPU. On 8-10-core parts the cold compile is longer, which makes the hit

## Open issues for later items
- **Z9 (zkp runtime):** a GPU timeline hook (record `GPUStartTime`/`GPUEndTime` of each completed
  command buffer in `Runtime::poll` behind an env flag) would turn R14's host-side gap accounting
  into GPU-timestamped idle gaps. R14 found ~2 ms/segment of host-visible idle. The zkp commit
  phases' internal waits (merkle root reads etc.) were not visible from rv32im code.
- **C11 / M1 (recursion, zkp):** use `risc0_zkp::hal::metal::archive::ArchivedKernels` for the
  recursion metallib (unit `recursion`) and, if the zkp PSOs' cold build is significant on base
  chips, for the zkp library too (`MetalHal::new`; not measured here).
- **Baseline (quiet machine):** re-run `pipeline_bench` A-vs-A and the window sweep
  (`RISC0_METAL_ACCUM_SORT` 0/11/12/13/14) when no other agent uses the GPU. Every number here
  was taken under load 2-49.
- **R15:** the remaining per-segment levers are GPU kernels: eval_check ~75 % of a quiet segment,
  data commit ~12 %, accum commit ~6 %. Overlap and host overheads are exhausted (~0.1 %).
- **R8 (witgen_tests.rs owner):** `witgen_snapshot_over_budget_is_an_error` is flaky under the
  default parallel harness: it sets a device-wide working-set limit relative to
  `allocated_size()`, which other tests change concurrently. Once in 3 runs at
  `RISC0_METAL_MAX_WORKING_SET_BYTES=4294967296` the snapshot fitted and the kernel faulted
  (0x4, memory transaction index out of range on its synthetic trace) instead of the budget
  error (`fix1/budget_4294967296.log`). It should take a shared test lock (e.g. R14's
  `tests::metal_test_lock`) and/or not depend on the process-wide allocation.
- **Merge / R15:** rename or `cfg`-gate `R14_STATS` (an item-specific name in production code).
- **Baseline (16 GB base chip):** the cold archive build compiles on `available_parallelism`
  threads at once; the compiler service's peak memory during it was not measured. Concurrent
  cold processes each keep their own archive file until the next load prunes them, and worktrees
  with different metallibs evict each other's `rv32im-*` archives in the default directory
  (development churn only).
- **Budgets on real segments:** po2 19 at 4 GiB and po2 20 at 8 GiB panic in
  `seal_matches_cpu_large` (identical bytes with the archive off; R14 changes no allocation).
  Memory policy stays with the M-items.
