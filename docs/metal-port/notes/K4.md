## What was done
- `circuit/keccak/src/prove/hal/metal/eval_check.rs` (new): the runtime of K3's staged kernels.
  Ported from the Intel launcher `keccak-sys/kernels/intel/kernels.h` (`risc0_circuit_keccak_intel_eval_check`
  lines ~117-170, `launch_eval_stage` ~82-100) with the inputs of `hal/cuda.rs` `eval_check` (165-221).
  - Chunked launcher: the domain goes through all `S` stages a chunk of `C` cycles at a time (`C` =
    32768 by default, `RISC0_KECCAK_METAL_EVAL_CHUNK` overrides, `MetalCircuitHal::set_eval_chunk` for
    tests/K7). Each stage is one `hal.dispatch(pso, args, Grid::Threads(count))` (`count = min(C,
    remaining)`, `EvalParams {count, first, domain, stride, quot[4]}` via `set_bytes`); the batch's serial
    encoder orders the stages and the next chunk's reuse of scratch/carry. 16 chunks × 58 stages = 928
    dispatches at po2 17 (the HAL commits a batch every 2048). The phase ends with `try_sync` (error →
    panic with the command-buffer error; `CircuitHal::eval_check` returns `()`).
  - Scratch (`EVAL_SCRATCH_ELEMS` = 8237 words a cycle) and carry (20 words a cycle) are
    `StorageModePrivate` (`hal.alloc_private`), stride = chunk, allocated once per eval_check
    (shared by all chunks and stages of the call) and **freed when eval_check returns** (fix round 1,
    see below; round 0 cached them in the circuit HAL across calls). `set_keep_eval_scratch(true)`
    restores the cross-call cache (tests/K7): then a call regrows only if it needs a larger stride (a
    smaller domain/chunk reuses the larger buffers: `count <= stride`). Stride is `min(chunk,
    domain)`, capped at `maxBufferLength / (8237·4)`, so small proofs take small scratch (po2 12:
    516 MiB, po2 ≥ 13: 1032 MiB). `release_eval_scratch()` frees, `eval_scratch_bytes()` reports.
  - Budget-aware chunk: if `allocated_size + scratch` exceeds `MetalHal::working_set_limit()`
    (`RISC0_METAL_MAX_WORKING_SET_BYTES` or `recommendedMaxWorkingSetSize`), it trims the pool and
    halves the chunk down to 1024 (warns); if even that does not fit, `alloc_private` panics with the
    HAL's budget message. No core count or RAM fraction is assumed.
  - `quot[cycle & 3]`: `vanishing_quotients(po2)` computes the four `1/((3·rou^k)^(2^po2) − 1)` on the
    host (as Intel; asserts rou's order) and passes them as raw Montgomery words
    (`BabyBearElem::as_u32_montgomery`), which the last stage reads with `Fp::fromRaw`.
  - Bindings: each stage binds only the buffers its code may touch (`EVAL_STAGE_BINDINGS`, fix round
    1), the others nil.
  - `poly_mix`: `map_pow(poly_mix, POLY_MIX_POWERS)` (2175 FpExt, 34.8 KB) copied into a pooled shared
    buffer bound at `EVAL_BUF_POLY_MIX` (asserted equal to `EVAL_NUM_POLY_MIX_POWS`).
  - Asserts (K3's list): `(EVAL_MAX_COLUMN + 1) * domain <= 2^32` (po2 ≤ 19), `stride <=
    EVAL_MAX_STRIDE`, `EVAL_SCRATCH_ELEMS * stride` and `EVAL_CARRY_WORDS * stride <= 2^32`,
    `count <= stride`, `steps == 2^po2`, `INV_RATE` matches, and — because the kernels read without
    bounds checks — `check.size() == 4·domain`, ctrl/data/accum ≥ `TAPSET.group_size(g)·domain`,
    mix/out ≥ `MIX_SIZE`/`OUTPUT_SIZE`; plus "no stages" (skip build).
- `hal/metal/mod.rs`: `mod eval_check;`, an `eval: EvalCheckState` field, and `eval_check` now calls
  `eval_check_metal` (K2's CPU `poly_fp` bridge removed; the `#[cfg(test)]` `METAL_EVAL_CHECKS` count
  and `mark_phase(EvalCheck/Finalize)` calls kept). Unused imports removed; docs updated.
- `keccak-sys/src/lib.rs`: `pub mod metal_eval { include!(env!("KECCAK_METAL_EVAL_RS")); }`;
  `METAL_KERNEL_NAMES` is now `["scatter_preflight"]` followed by `metal_eval::EVAL_STAGE_NAMES`, built at
  compile time by a `const fn concat_names` (hand-written names stay in `METAL_HAND_KERNEL_NAMES`; K6
  appends its names there). One library load builds all PSOs.
- **Deviation (files outside the owned list)**: `RISC0_SKIP_BUILD_KERNELS` cannot be handled in
  `lib.rs` alone (`include!` needs the env var at compile time and build.rs did not set it under skip).
  `keccak-sys/build_metal_eval.rs` gained `write_skip_consts(out_dir)` (a stub
  `keccak_metal_eval.rs`: 0 stages, sizes 1, same bindings) and `keccak-sys/build.rs`
  `build_metal_kernels` calls it in a new 2-line `else` branch of its existing skip check. Merge note:
  K6 also edits build.rs (different lines).

## Fix round 1 (review findings)
1. **PSOs per proof** (blocking). `MetalCircuitHal::new` built all 59 keccak PSOs every time, and the
   zkvm makes a new keccak prover (so a new circuit HAL) per proof. Now `hal/metal/mod.rs`
   `keccak_kernels(device) -> &'static MetalKernels` builds them once per process in a `OnceLock`
   (same pattern as zkp's `zkp_kernels`, `zkp/src/hal/metal.rs:214`), and the HAL stores
   `kernels: &'static MetalKernels`. Test `kernels_are_process_wide`: two circuit HALs share the same
   `MetalKernels` and the same PSO for each of `METAL_KERNEL_NAMES`, and the second construction takes
   < 500 ms (it builds no PSO).
2. **Cached scratch broke reused provers under 4 GiB** (blocking). Option (a) of the review: eval_check
   now frees its scratch/carry when it returns (after `try_sync`), so nothing is left behind for the
   next proof's commit phase. The cross-call cache is still available as an opt-in
   (`set_keep_eval_scratch(true)`, used by the multi-chunk/budget tests and the profile). Sticky chunk
   and a `KeccakProver` hook were not needed. Cost of allocating per call, measured with
   `eval_check_stage_profile` (best of 3 batched runs, `K4_PROFILE_KEEP=0/1`): po2 14 0.155 s vs
   0.131 s cached, po2 17 1.119 s vs 1.076 s cached, so about 25-45 ms per proof (indicative, load ~20).
   The zkvm makes a prover per proof anyway, so in production the cache never survived a proof.
   Also: the chunk is capped at `maxBufferLength / (EVAL_SCRATCH_ELEMS·4)` (review note), and the
   halving loop is now a pure `fit_chunk(want, allocated, limit)` with an exact unit test
   (`fit_chunk_halves_to_the_budget`). `eval_check_shrinks_chunk_under_budget` was racy under parallel
   tests: the budget counts the whole process's Metal memory, and another test freed memory mid-run
   (seen once in the 8 GiB run: chunk stayed 32768). It now asserts exactly 4096 only with
   `RUST_TEST_THREADS=1`, and otherwise a power of two in 1024..=32768. Bit-exactness is always checked.
   Regression test `metal_prover_reuse_under_budget` (`#[ignore]`, run alone): one prover, po2
   `K4_SEQ_PO2S` (default 14,17) under `K4_SEQ_BUDGET` (default 4 GiB), each proof verified, and
   no scratch left after each one. `K4_SEQ_KEEP=1` turns the old cache back on, and the test then
   reproduces the review's panic.
3. **Unused bindings** (blocking). `build_metal_eval.rs` now works out, per stage, which bindings
   its code may touch and emits `EVAL_STAGE_BINDINGS: [u32; S]` (bit `i` = `EVAL_BUF_*` index `i`;
   the skip stub emits `[u32; 0]`). The rules are: params and scratch always; check on the last
   stage; carry unless the stage is last and loads nothing; an input (ctrl/out/data/mix/accum) when
   a member function's `const Fp*` parameter traced to it (K3's `roots`) appears as an identifier on
   a line other than the tail call; poly_mix when `poly_mix` appears. This is a superset of what the
   kernel reads, never a subset. The launcher binds only those buffers and leaves the rest nil. With
   58 stages: stage 0 `0x3cc` (out, data, poly_mix, scratch, carry, params), the last `0x3c9`, the
   others `0x3c8` or `0x388`. No stage reads ctrl, mix or accum, which matches the three warnings the
   review saw. Test `eval_stage_bindings` checks the invariants. The bit-exact tests show the masks
   omit nothing a kernel reads (a nil buffer read would fault or give wrong results).
   The round-0 validation claim was wrong, because cargo's output capture hid the NSLog lines (see the
   corrected table above).
   Files outside the owned list: `keccak-sys/build_metal_eval.rs` (K3's) gets `Stage::bindings`,
   `BUFS`, `buf_bit`, `mentions`, the mask computation in `translate` and the new const in
   `rust_consts`/`write_skip_consts`. The generated `.metal` text is unchanged, so the metallib and
   its shader-cache entries are unchanged too.

## Assumed / not verified / gaps
- Stage counts other than 58 are build-time (`RISC0_KECCAK_METAL_EVAL_STAGES`); each was run in a
  separate target dir; the committed default stays 58.
- PSO/GPU times are indicative (load 22-120 from other agents). The first 16-stage profile run was
  killed after ~20 min (the watcher that launched it expired), so the reported 16-stage cold total may
  include some stages already cached by that run.
- Not measured: CPU eval_check time at po2 17 for a speedup ratio (K7); TG size 128 vs 256; chunk sweep.
- `eval_check_matches_cpu_po2_17` needs ~7 GB host RAM (CPU + Metal copies): ignored by default.
- `metal_peak_memory` samples every 100 µs plus phase marks (K2's method).
- (Round 0) Scratch was cached for the circuit HAL's lifetime; since round 1 it is freed after every
  eval_check, so a long-lived prover holds no eval_check memory between jobs.
