### to_metal.py (branch point HIP_LAST, as the ROCm kernel; plan open question 11)
Input: the chain after remat_lu.py (25830 lines). Output: `eval_check_ef.metal` (25495 lines) and
`ef_tables.rs` (346 lines). Every rewrite count is pinned (`COUNTS`), and the summary line is pinned in
regen.py (`TO_METAL_EXPECT`): "106 signatures and 20 calls take EfCtx instead of 117 pointer arguments,
5 pointer locals, 5357 table-helper calls, 62 hoisted terms and 107 products on the host".
- **No asm, C++ `#else` paths:** the `EF_SLAB_ASM` block is replaced by `thread` slab macros; `ef_madw`
  keeps only `c + uint64_t(a) * uint64_t(b)` (`EF_MADW_ASM` dropped). No mksm2.py / mksub.py (they run after HIP_LAST).
- **EfCtx:** `struct EfCtx { const device Fp* accum, data, out, mix; constant uint4* pm, pmn; thread Fp* slab; }`.
  Chain functions (`rv32im_v2_N`, `rk_accblk`, `poly_fp`) take `uint32_t cycle, uint32_t steps, thread const EfCtx& ctx`
  instead of `size_t cycle, size_t steps, FpExt* poly_mix` and their pointer parameters. The pointer
  identities come from args_hip.py's `_analyze` (imported, not duplicated). A pointer without a proven
  identity fails the generator. Each function re-declares its former pointer parameters as locals from
  ctx, so the generated bodies are unchanged. `poly_fp`'s `args[k]` become ctx members.
- The helpers that read CUDA's `__constant__` tables (`rk_cl_acc`, `rk_cl0`, `rk_link_k`, `rk_link_nf_k`) take
  ctx; `EF_PM(i)` reads `ctx.pm`. Helper reference parameters become `thread`. Program-scope constants
  become `constant constexpr`. `namespace risc0::circuit::rv32im_v2` becomes `rv32im_metal_ef`.
- **Thread slab:** `uint32_t lslab[RK_NWORDS = 324]` in the kernel (1296 B/thread).
- **EF_WIDE switch:** defined by default (CUDA's choice); `-DEF_NO_WIDE` selects the 32-bit lo/hi forms.
- The final checks refuse any leftover `__device__`, `__constant__`, asm, `size_t`, `args[`, `Fp**`, or a
  pointer declaration without an address space.
- The generated chains use fp.h/fpext.h's operators. HIP's add/sub/mul forms (which the HIP kernel was
  validated with) and Metal fp.h's agree on the lazy [0, 2P) values lazyfp.py emits; the bit-exact tests confirm it.

### Kernels and host (ABI in the generated file and in `eval_check_evalfast`'s doc)
- `ef_eval_split`: `0 check, 1 data, 2 accum, 3 mix, 4 out, 5 tab (constant uint4*), 6 scratch, 7 domain`;
  `ceil(domain/128)*2` threadgroups of 128 (`EF_THREADS`); even groups run the main chain into `check`,
  odd groups the LogUp chain into `scratch` (as CUDA's split).
- `ef_combine`: `0 check, 1 scratch, 2 tab, 3 domain`; `check = (check + scratch) * q[cycle & 3]`.
- **CPU table builder (`ef_table`)** replaces CUDA's one-thread `ef_prep` / `ef_prep_n`. One shared buffer
  of `2*627+1` FpExt holds: pm (458 powers, 107 products `pm[RK_QA]*pm[RK_QB]`, and 62 `rk_hoist` terms
  from out/mix), then pmn (`(pm.1, pm.2, pm.3)*(P-11), 0`), then the 4 quotients. `rk_hoist` is generated
  as straight-line Rust over `risc0_core` BabyBear with the same statements in the same order. The table
  uses R7's `ScratchBuffers::poly_mix` (grown to 1255 entries; the baseline uses its first 458). The
  LogUp partials use `ScratchBuffers::scratch` (4*domain words; 64 MiB at po2 20). Both dispatches go in
  one batch; the phase ends with `try_sync`.
- The host reads `out`/`mix` with `view()`, which flushes and waits if a batch is open. The baseline's
  `view_mut` of poly_mix already did the same.

## Dispositions of open issues addressed to R12
- **R10 "add evalfast as a branch of eval_check_metal; reuse poly_mix buffer and CPU fallback"**: done.
  `eval_check_metal` selects; the CPU fallback (`RISC0_METAL_RV32IM_CPU_PHASES=eval`) is unchanged.
- **R11 "eval_check is 5.9 of 6.6 s; ef_fp.h uses metal::mulhi; run repeated bit-exact runs on big inputs"**:
  evalfast does not include ef_fp.h. Its generated helpers use `uint64_t` products, compiled as written.
  Repeated runs: 20 at po2 20 (two builds) + 4 at po2 21, 0 differ. 9 real-segment po2 20 proofs equal
  CPU (torture #0 and #7 twice each). No nondeterminism was seen. R11's witgen symptom (a lane runs the
  wrong mux arm) needs divergent control flow; evalfast is straight-line code.
- **R6 "the fpp call-site rewrite emits device Fp* for every expanded pointer; give the thread slab a thread
  space or keep an EfCtx design"**: EfCtx design. cuda2metal.py is not used for evalfast.
- **R1 "Fp::mulM → ef_mulM"**: not needed. `Fp::mulM` only appears in the ROCm form (to_hip.py), which is after the branch point.
- **R6 / R7 / K5 cold start**: ef_eval_split is 27 s cold (below 30 s), so no archive. But the rv32im
  metallib now has two big PSOs (eval_check 62 s + ef_eval_split 27 s) and builds them eagerly. See issues.
- **Open question 11 (branch point)**: HIP_LAST. That gives 3x over the baseline. Whether the
  post-HIP passes help on Apple (smem words → threadgroup memory, mksub splits) is R15's question.

## Issues for later items
- **R15 (perf, P2):** evalfast is only ~3x the baseline at po2 20 (CUDA got far more). Try in this order:
  - `EF_THREADS` 64/256 (`-DEF_THREADS`; the host constant `EF_THREADS` in eval_check.rs must match);
  - mksm2.py-style threadgroup-memory slab words (≤ 32 KB);
  - inlining the chain functions (inline_hip.py precedent);
  - the slab in device memory.
  EF_WIDE stays the default (the 32-bit form was ~3x slower in one loaded A/B and its cold PSO took 101 s).
- **R14 / M1 / K5 (cold start, P2):** METAL_KERNEL_NAMES makes the first circuit HAL build both
  eval_check PSOs, ~90 s cold in total on the M5 Max. Now that evalfast is the default, `eval_check`
  (baseline) could be built lazily, only when `RISC0_METAL_RV32IM_EVAL=baseline`. That needs mod.rs's
  loader (not R12's file). K5's `ArchivedKernels` (keccak `hal/metal/archive.rs`) should be hoisted into
  the zkp Metal HAL so rv32im can use it. R12 did not duplicate it.
- **R16:** `regen.py --metal` adds ~9 s to a cold rv32im-sys build. `--check` of the Metal outputs is
  available for CI.
- **R17:** none from R12; the witgen kernels are untouched. Adding the evalfast TU changes the
  metallib's linkonce helper set (R11 point 4), so R17's experiments should use a metallib that includes it.
- **M5 baseline:** record the eval_check phase with evalfast on a quiet machine. All numbers here were taken under load.
