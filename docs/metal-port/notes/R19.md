**What the profile says now:**
- The main chain is a nest of 21 tail calls: `poly_fp` → `rv32im_v2_19` → ... → `rv32im_v2_3`. The LogUp
  chain is `rk_accblk` → `rv32im_v2_2` → `_1` → `_0`. Each callee runs while every caller's frame is
  live. That explains the stack limit at -O1 / -Os.
- Flattening the nest without the R17 shapes is not possible:
  - the values that flow between the functions are up to 26 FpExt;
  - returning them as an aggregate, or through the private slab after a call, is the R17 hazard
    ("private store, later load after a call").
  
  It was therefore not built.
- R18's ablation profile still applies: Fp multiplies ≤ 15 %, trace loads ~12 %, slab ≤ 12 %, the rest
  is link arithmetic, which is already the minimum (4 64-bit multiply-adds per Fp link, folded every
  second link).
- Estimated from the link count (not measured): at po2 20 the split kernel issues about 1.8e11 32-bit
  integer multiplies in 653 ms (4.19M rows x ~5350 links x 4 lanes x lo/hi). That is several times
  below what the 40-core GPU should sustain even at a quarter-rate multiply, so the kernel is probably
  not ALU-throughput-bound. It is also not bound by
  the accumulator dependency chain (dual), by barrier-free lockstep (barriers), or by the launch shape.
- With no AGX disassembler the remaining limiter cannot be named. Candidates are occupancy (registers
  and stack) and instruction issue. R18 section 3's compiler-regime caveat applies to all of these
  variants.

## 4. The lazy-bound finding (correctness tooling)
- **What failed.** The `dual` and `dual12` variants gave wrong elements on some inputs:
  - 8-288 wrong elements per po2 18 input, on 4 of 6 seeds (`dk1`-`dk6`, `sd1`-`sd6`);
  - in the first runs it looked load-dependent, because the bench's inputs came from an unseeded
    `rand::rng()`: `dual1` showed 0/9 wrong, then `dual2` / `dualchk1` 9/9 and 5/5;
  - two differently compiled variants gave identical wrong values on the same input, which pointed at
    the arithmetic rather than the hardware.
- **Root cause (verified).**
  - The generator places lazily reduced Fp coefficients (lazyfp.py: values in [0, 2P)) only in folding
    links whose base has hi < P.
  - `dual.py` re-paired the nf/k (no-fold/fold) pattern per sub-chain, so a lazy coefficient could follow
    a no-fold link. The 64-bit accumulator's high word then exceeds 2^32 (P + 0.94P + 0.94P > 2^32).
  - `ALLK=1` (fold every link) is bit-exact on every failing seed (1, 2, 4, 6) and in 9/9 runs of
    `final1`.
  - It is **not** an R17-type defect.
  - `ir_scan.py --fail-tiers ABS` on the dual IR is clean (A = B = C = S = 0), as expected for an
    arithmetic bug.
- **Detection rate by input** (dual vs A, one input each):

  | input | detected |
  |---|---|
  | uniform, po2 18 | 4 of 6 seeds |
  | uniform, po2 16 | 1 of 5 seeds |
  | uniform, po2 10 | 1 of 16 seeds |
  | `High` (uniform in [P/2, P)), po2 16 | 0 of 5 seeds |
  | `Extreme` (mostly P-1 / P-2, some 0 / 1), po2 18 | 0 of 2 seeds |

  The failure needs particular combinations of trace values and poly_mix table rows. Edge values do not
  provoke it.
- **What this item adds.**
  - **Seeded inputs** (reproducible mismatches): `Inputs::seeded(po2, seed, Dist)`, and `R15E_INPUT` /
    `R15E_SEED` in the bench.
  - **`evalfast_seeds_match_baseline`** (`#[ignore]`): evalfast against the baseline kernel on 8 seeded
    uniform po2 18 inputs (~80 s). At the rate above (4 of 6 seeds), it would catch a bug of
    this kind with probability roughly 1 - (1/3)^8 (an estimate from six seeds). Run it after any change to the evalfast generator or helpers. The
    shipped default passes: 8/8 seeds, 0 elements differ.
  - **`evalfast_matches_cpu_extreme_po2_12`** (default-on, 0.7 s): edge values against the CPU at two
    seeds. It does not catch the dual bug, and its doc comment says so. It covers the 0 / 1 / P-1
    corners the uniform tests rarely hit.

## Open issues
- **P1, zkp owner (data commit 217 ms + accum commit 113 ms = 31 % of a po2 20 segment):** no cheap knob
  win. What is left needs code:
  - `pv_rows_k_z9` (~21 % of GPU time; Z9's reduction already won 1.16x);
  - the commit NTTs (~24 %);
  - the `blit_fill` fills (3.6 %): check whether the buffers the NTT expand overwrites need a fill at
    all.
- **P2, evalfast generator (this kernel family):**
  - the 21-deep nested tail-call chain keeps every frame live (the stack limit at -O1 / -Os);
  - a driver that calls the chain functions in sequence would need their live-outs (up to 26 FpExt)
    returned through private memory or aggregates, which are the R17-hazard shapes;
  - so it needs a generator-level design (for example re-partitioning so each function's live-out is one
    FpExt) and the R17 gate.
  
  Everything cheaper was measured here (section 3) and lost.
- **P2:** consider a static interval check of the lazy bounds in `close.py` / `lazyfp.py` / `linkext.py`
  (hi < 2^32 for every link given the producer of each coefficient). Random tests catch an over-bound
  transform only probabilistically (section 4), and `evalfast_seeds_match_baseline` is opt-in.
- **P3 (from R18, unchanged):** `rv32im-sys/src/lib.rs` should name `ef_eval_split_r15e` among the lazy
  kernels (outside this item's files).
- **P3:** all numbers are from the 40-core M5 Max. The interleaved grid (section 3: +8 % when the main and
  LogUp groups are separated) may matter differently on 8-10-core parts.
