## Changes kept

### (1) `hdense` + `htr`: MSM H's sort, one window per scatter dispatch from transposed scalars

- `MsmScratch::set_dense(true, tr)` for the next sort. The scatter is dispatched once per window
  (`MsmParams::w0/wcount`; serial dispatches on tracked buffers), so each dispatch's stores fall into one
  window's n entries. With `tr` = (buffer, offset) of 32 n free bytes, `msm_hist_count` also writes the scalars
  transposed there (word k of scalar i at k n + i), and each window's scatter reads only the one or two words
  that hold its digit instead of the whole 32-byte scalar.
- The prover passes b (abc at n): it is free from the NTT stage's `fr_mul_sub_from_mont` (h is in a) until the
  pieces of MSM H are written (lent a, b, after the sort). No new memory.
- Profile (`logs/g9_all_prof.log`, 9 rounds): scatter **36.1 [34.5..39.7] -> 7.8 [7.7..8.2] ms**; one window per
  dispatch alone (`-htr`) 20.8 [20.2..23.3]. Count pass unchanged (4.3 ms).
- Production mode: sort_h + MSM H **214.1 -> 188.1 ms (-26.0)**, ranges disjoint.
- Same results by construction (the same entries per bucket; the order inside a bucket was never
  deterministic). Knobs: `RISC0_G16_METAL_G15_OFF=hdense` (both), `RISC0_G16_METAL_G15_OFF=htr` (no copy).

### (2) `wtr`: the witness sort as a dense one with the copy in a

- Without the copy, one window per dispatch is slower for the witness (scatter 5.9 -> 10.6 ms: 44 % of the
  scalars are 0, so the per-window passes over the scalars cost more than the stores). With the copy in a (free
  once sort_h has consumed h, and after the G10 late fuzz has been added to the witness), the scatter is
  6.6 -> 3.7 ms.
- Production mode: sort_w + MSM A, B1, C 122.9 -> 119.6 ms (-3.3; minima -2.2), A-vs-A 0.4 ms.
- The witness count pass runs at 1.0-1.3 ms or at 6.5-7.5 ms, bimodally, with and without `wtr` (not caused by
  this change; not explained). Knob: `RISC0_G16_METAL_G15_OFF=wtr`.

### (3) LEADS #38: length-ordered rows in the compact cache

- Row-length statistics of the rzup key (`tools/rowlen.py`): A 17.5M coefficients in 5.68M rows, B 11.6M in 5.68M
  rows; most rows have 1-2 coefficients, a few up to 499. A SIMD group of 32 consecutive rows runs as long as its
  longest row: **11.4 % (A) and 8.1 % (B) of the lanes' steps do work** (4.8M + 4.5M group-steps); in length
  order, 100 % (0.55M + 0.36M).
- The cache file (version 2) stores the rows of each list longest first (stable sort, so rows of one length keep
  their order); each row keeps its coefficients in order and writes its own output, so a and b are bit-identical.
  No kernel change, no memory change. The validation now checks that no two rows of a list share an output
  (bitmap) instead of strictly increasing outputs.
- Process pairs (`order/summary.txt`, 7 rounds, `poly_nc` on in both): witness_poly **34.5-37.6 (natural) ->
  7.8-8.0 ms** (minima), -27 ms.
- Cost: the first run after the upgrade rebuilds the cache (1-3 s, once); the version-1 file (324 MB) stays in
  the cache directory (see open issues). Knob: `RISC0_G16_METAL_COEFF_ORDER=natural` (the version-1 cache, built
  if missing).

### (4) `poly_nc`: the compact witness_poly products through `mul_nc`

- `witness_into_poly_compact_nc` (bn254_fast.h's no-carry CIOS; the same values for canonical inputs, which the
  kernel checks: a non-canonical input sets fault 4 and the proof is refused either way).
- In the natural order it was worth -22 ms (57 -> 35 ms, the lanes waiting on long rows multiply more); after (3)
  1.7 ms (production in-process 92.9 -> 91.2 ms for witness_poly + NTT, minima -1.9; A-vs-A 0.0).
  Knob: `RISC0_G16_METAL_G15_OFF=poly_nc`.

### (5) G13 open issue: `par_transient`, the parallel witness on small Macs

G13 used `fast` (single-threaded, ~165 ms) below a 20 GiB working-set limit, because `par` keeps a 580 MB node
array resident. `par_transient` is `par` whose array is out of the footprint between wraps: after each evaluation
`madvise(MADV_FREE_REUSABLE)` hands its pages back to the kernel (they leave `phys_footprint` and are reclaimed
under memory pressure), and the next evaluation takes them back with `MADV_FREE_REUSE` (reclaimed pages come back
zero-filled; the evaluation writes every node before reading it, so contents do not matter).

- Footprint and time (`logs/par_footprint.txt`, `g15_par_footprint`, the first, least-loaded round, load 46):

  | evaluator | footprint after compile | per witness |
  |---|---|---|
  | `fast` | +286 MiB | 156-196 ms |
  | `par_transient` | +446 MiB | 46-56 ms |
  | `par` (resident) | +1000 MiB | 33-92 ms |

  Later rounds ran under heavy swap, where `phys_footprint` itself moved (pages compressed or swapped).
- **Default: unchanged (fix round 1).** The first round made `par_transient` the default below 20 GiB where the
  key can be loaded early (16-24 GB Macs, an 8 GiB budget). Review measured that it raises peak memory on the
  minimum-target budget, so it is now **opt-in only** (`RISC0_G16_METAL_WITNESS=par_transient`); the default below
  20 GiB is `fast`, as in G13, and `metal::early_key_possible` (its gate) was removed. The measurements:
  - **Wrap-phase peak, +0.74 GB at 8 GiB** (reviewer, `w6/G15-verify/ab/summary.txt`, `metal_shrink_wrap`
    processes, 3 wraps, `/usr/bin/time -l`): A (`fast`) 5.99-6.14 GB, median 6.00, n = 16; `par_transient` 6.16-7.03,
    median 6.74, n = 16; G15 with `WITNESS=fast` 5.996-5.998; resident `par` 6.743-6.745; `par_transient` 6.742-6.748.
    With the key loaded early, the witness is computed **in place** (`metal_prove_in_place`), after the key and the
    3.9 GiB GPU working set are allocated, and `MADV_FREE_REUSE` brings the 580 MB array back at exactly that point:
    `par_transient`'s wrap peak equals `par`'s. RSS trace: wrap-0 peak 4.03 GB (`fast`) vs 4.63 GB. The first
    round's "array in the footprint only after identity_p254 has released its working set" was wrong for the
    in-place path.
  - **STARK-phase peak, +0.2-0.4 GB at 8 GiB** (`BENCH_ONLY=memory-merkle` worker, `/usr/bin/time -l`, 3 rounds
    each, under load and swap; n = 3 is short of the protocol's 7): my `wab/summary_8g_memory-merkle.txt` medians
    `par_transient` 9.018 GB [8.936-9.088] vs `fast` 8.610 [8.187-8.747] vs A 8.634 [8.524-8.910] (+0.41 / +0.38 GB,
    ranges disjoint from `fast`'s); the reviewer's rotated rounds (`w6/G15-r1-adv/mm/summary.txt`, load 31-83)
    worker lifetime peak B - Bfast +223 / +172 / +279 MiB in the same round, lowest B above highest Bfast and A.
    The program (compiled on the graph-preload thread during the STARK phase, ~160 MiB more than `fast`'s, plus
    compile intermediates) lands on the segments-phase peak. The first round's "~+160 MB" and "+0.2-0.3 GB"
    understated this.
  - **Wrap time.** Component level, `BENCH_ONLY=fibonacci` at 8 GiB (`wab/logs/8g_fibonacci_*`, 8 interleaved
    rounds, load 15-70): in-place witness 61-96 ms vs `fast`'s witness tail ~164-580 ms past `pre_gpu`. My
    end-to-end shrink_wrap there showed **no difference** (1862.4 vs 1863.2 ms median, `fast` vs `par_transient`;
    contended). The reviewer's 7 rounds x 2 pairs of `metal_shrink_wrap` at 8 GiB (load 12-45) measured a warm wrap
    per-round min(B) - min(A) of -223 ms median [-311, +15], 6/7 (A2 - A1 -46 ms), in-place witness 40-110 vs
    170-280 ms; that A/B includes the GPU changes (1)-(4) as well.
  - So: ~-120 ms of witness on the 8 GiB critical path for +0.74 GB of wrap peak and +0.2-0.4 GB of STARK peak on a
    16 GB Mac. Not taken as a default; the merge/baseline agent or a later item can revisit it with a quiet
    interleaved 8 GiB run (>= 7 pairs, wrap time and both peaks).
- **What would make it default-worthy** (not done): keep `par_transient` off the in-place path (compute the witness
  and hand the array back before the GPU working set is allocated; loses the in-place overlap), and build the
  program only after the STARK pools are released, or hand back its per-node metadata between wraps as for the
  value array, gated on measured headroom (limit minus the planned STARK peak).
- `par_transient` (opt-in) without an early key computes the witness before the key load rather than beside it, so
  that its array never coexists with the key's allocations. `is_par_transient` now decides on `kind()` alone, so it

- 4 GiB: `fast`, as before. The 4 GiB memory-merkle worker footprints of the first round (B 6.38-6.43 GB vs A 5.82,
  n = 1-2, B was `fast` there by the gate) were inconclusive noise.
- Knob: `RISC0_G16_METAL_WITNESS=par_transient` opts in (also `par`, `fast`, `ref`).

## Tried and rejected (NO-GO)

- **MSM H window size, Booth digits, bucket counts, precomputed bases** (analysis plus G9/G12 sweeps):
  - H is 15 windows x 8.4M points = 126M mixed additions in 168 ms, 1.33 ns each: at the G1 madd floor (G12:
    B2 and G1 at the floor; the kernel is integer-multiply bound, ~85 % of the M5's int-multiply rate by a
    rough count).
  - c = 17 Booth already gives 15 windows (c = 16: 16 windows, +64 ms in G12). c = 18 saves no window
    (14 x 18 < 255); c = 19 saves 1/15 of the additions (~11 ms) but needs 4x the buckets: the reduction grows
    from ~2M to ~7M full additions, more than the saving. Mixed widths (13 x 18 + 1 x 21) have the same problem.
  - Precomputed bases (2^(cw) P tables) do not reduce additions; they only remove per-window reductions, which
    cost 7 ms here, for +0.5 GB per table.
  - GLV (BN254 G1 endomorphism): 2n points with 128-bit scalars need 8 windows at c = 17, 16n additions against
    15n now.
  - CUDA does nothing special for H: sppark's default (wbits 15 for 2^23 points, 17 windows), which is more
    windows than Metal's.
  - Batch-affine buckets were measured as a loss in G12.
  - So no H MSM change; the H gain came from its sort.
- **K6 SIMD-aggregated atomics / threadgroup pre-sort** (LEADS #41): the premise (atomic contention) does not
  hold for H (count pass 4.3 ms for 126M atomics; H's digits are uniform over 65,537 buckets, so SIMD lanes almost
  never share one). The cost was the scatter's store pattern, fixed by (1) and (2). Not built.
- **LEADS #43 NTT coset fusion**: the coset multiplication folded into the last pass of the DIF inverse
  (`NTT_COSET` in `ntt_fused_stages`), bit-exact (all NTT tests, both paths). Measured in process
  (`logs/g9_all_prof.log`): NTT stage 83.1 -> 82.8 ms (-0.3, inside noise). The separate `ntt_mul_powers` costs
  5 ms for the three polynomials (measured by skipping it), almost all of it the two multiplications per element
  that the fused version still does; the saved read and write of x are ~0.3 ms. **Removed** (not committed).
- **Per-MSM segment lengths** (pieces per `msm_segment_reduce` thread; G14 open issue): in profile mode (one
  command buffer per dispatch) 32 instead of 64 looked like -5 ms for B2 and -0.6 ms per G1 MSM
  (`logs/g9_seg.log`), but window_reduce grows (B2 2.1 -> 3.6 ms) and in production mode (`logs/g9_seg2.log`,
  11 rounds, two interleaved copies of each arm) B2 was 150.4-150.9 vs 151.1-151.4 ms (noise) and the G1 group
  1-2 ms **slower**. 16 and 24 were worse. **Removed.**
- **G14 open issue (segment reduce +16 ms without the fuzz)**: investigated, not resolved. A temporary test read
  the piece buckets of MSM B2 after a real-witness proof (`RISC0_G16_METAL_SCRATCH_SHARED=1`): with the fuzz /
  without it, 15,192 / 15,365 segments, 951,956 / 951,935 bucket transitions, 0 / 0 gaps, SIMD efficiency of the
  transitions 0.997 / 0.992, 227,480 / 227,914 bits of final multipliers. The work is the same; the +30 % (B2
  28.5 vs 37.7 ms) is not in the structure. Write order is not it either (`-lenperm` keeps the gap). Next
  step would be per-window timings of the reduction, or values (e.g. pieces of one point with ZZ = 1).

## Hardware dependence (PLAN 9.1)

- (1), (2) reduce DRAM write-back of scattered stores; they do not depend on core count. The gain depends on the
  cache size relative to one window's 33.5 MB of entries (measured on the M5 Max only).
- (3) helps any SIMD width (it equalises lane work).
- (5) is opt-in; the default evaluator choice is G13's (working-set limit).

| `RISC0_G16_METAL_COEFF_ORDER=natural` | the version-1 (natural row order) compact cache |
| `RISC0_G16_METAL_WITNESS=par_transient` | opt-in G15 evaluator (also `par`, `fast`, `ref`; default as G13) |
| `RISC0_G16_METAL_PROFILE_MSM=1` (with `RISC0_G16_METAL_PROFILE=1`) | now also splits the sorts (`sort_h.clear` ... `sort_w.len`) |
| `G15_WITNESS_KIND=par\|fast` (test only) | the evaluator of the `g15_par_footprint` probe (default `par_transient`) |

All of A's behaviour is restored by `RISC0_G16_METAL_G15=0 RISC0_G16_METAL_COEFF_ORDER=natural`.

## Open issues

- **End-to-end confirmation.** Only the fibonacci worker A/B (-71 ms, 8/8) resolved anything; the memory-merkle
  and budget worker A/Bs were unusable (contention, swap). A quiet baseline should take warm `shrink_wrap` at
  the default budget (expected ~-75 ms) and at 8 GiB (expected ~-75 ms of GPU; the default evaluator is unchanged).
- **Orphaned version-1 cache.** The upgrade leaves the 324 MB version-1 compact cache file on disk (only
  `invalidate_cache` removes all versions). A cleanup of other-version files of the same key could go into
  `CompactCoeffs::load`, but only after checking that no other installed prover build still uses version 1.
- **Witness count pass bimodality** (1.0-1.3 vs 6.5-7.5 ms, independent of `wtr`): unexplained. A SIMD-aggregated
  increment of the hot bucket (window 0, digit 1: 1.69M increments of one counter) is the obvious next try, worth
  at most ~6 ms when the slow mode hits.
- **G14's segment-reduce gap** (B2 37.7 vs 28.5 ms with the fuzz): same structure measured, cause unknown (see
  above).
- **What is left is at arithmetic floors**: H and the witness MSMs' buckets (madd floor), the NTT (one multiply per
  butterfly, 23 levels, compute bound: skipping the forward transforms saved 37.7 ms of 83). Further shrink_wrap
  gains need fewer Montgomery multiplications (e.g. a floating-point FMA product scheme) or fewer transforms.
- **`par_transient` is opt-in, not default** (fix round 1): +0.74 GB wrap peak and +0.2-0.4 GB STARK peak at 8 GiB
  against ~-120 ms of witness. Making it default-worthy needs the changes listed in (5) plus a quiet 8 GiB
  interleaved A/B of wrap time and both peaks. A smaller `out_idx` (a pair list instead of an 18.1M array) would
  save ~27 MB of its program.
