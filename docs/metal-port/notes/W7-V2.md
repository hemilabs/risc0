## 1. What is live at keccak start (profile before)

The K10 merge record said the 4 GiB k5 po2-17 failure ("864026624 bytes for evaluated with ~3.45 GB
already allocated") was the segment prover's pool held while keccak proves. **That diagnosis was wrong.**
Re-run on the unmodified build (`binA/k5`, 4 GiB, `K5_E2E_PO2S=17`):

    thread 'segment-stream' panicked at risc0/zkp/src/hal/metal/buffer.rs:66:33:
    Metal working-set budget exceeded: allocating 864026624 bytes for evaluated with 3453779968 bytes ...
    [poly_group(data)] count=211 size=524288 ...

- The failing allocation is on the Z17 `segment-stream` thread, in the rv32im segment proof (211 data
  columns, 2^19 rows).
- The test harness proves the keccak guest at the executor's default segment po2. At 4 GiB the worker
  uses po2 18 (M8), and po2 19 does not fit 4 GiB.
- union:3's 4/8 GiB failure in K10 has the same cause.
- Keccak never started in either case.

Logged at the keccak phase points (the `[keccak-mem]` lines are `currentAllocatedSize`: every HAL, pool,
pipeline and library). The log is device-wide: it does not attribute bytes to owners. The owners below
(segment-prover pool, PSOs/libraries, the lift's recursion prover) are inferred from the before/after
deltas of each release or drop, not measured per owner. The run is `binB/k5` at 4 GiB with segment po2 18, `prof_k5_4g.log` / `k5_4g.log`:

| job | keccak start | after `release_hal_buffers` | prover built | proofs done (prover live) | prover dropped | lifts done |
|---|---|---|---|---|---|---|
| k5 po2 14 | 1199 MiB | 29 MiB | 45 | 497 | 45 | 1517 |
| k5 po2 17 | 3040 MiB | 45 MiB | 45 | 1367 | 45 | 1530 |
| union:3 (2 sessions) | 1612 / 2098 MiB | 29 / 45 MiB | | | | |
| k5 po2 17, 8 GiB | 4499 MiB | 45 MiB | | | | |
| k5 po2 18, 8 GiB | 5779 MiB | 45 MiB | | | | |

How to read the table:
- Before the release, the segment prover's pool and scratch are live (1.2-5.8 GB).
- The existing `release_hal_buffers` at the top of the session's keccak phase drops them. That holds on the
  Z17 path too: the stream hands the prover back to the calling thread before the tail runs, so the
  calling thread's release reaches it.
- What stays is 29-45 MiB: PSOs and libraries.
- No recursion or Groth16 prewarm buffers are live at that point.
- So nothing needs releasing before keccak on the session path. The session path's failure was the
  harness's segment po2.

The leak that does exist is on the **standalone path** (`ProverServer::prove_keccak`, an in-process
coprocessor). Each call lifts its seal, and the lift leaves the recursion prover cached on the thread:
~1.5 GiB, plus ~200 MiB per further keccak zkr. The next keccak proof then runs beside it.
`keccak_standalone_repeat` with `RISC0_KECCAK_SMALL_BUDGET_RELEASE=0` (= the unmodified behaviour) at
4 GiB, 14,15,16,17 (`sa4g_seq_knob.log`):

    po2=14 peak 1501 start 5 | po2=15 peak 2873 start 1501 | po2=16 peak 3930 start 1703
    po2=17: Metal working-set budget exceeded: allocating 524288 bytes for accum with 4294770688 bytes already allocated

## 3. Design and knobs

All of the following is in `prove/keccak.rs`, with one hook in `prover_impl.rs`.

- **Headroom cap** (`headroom_capped_max_po2`, called in `ProverImpl::prove_with_ctx` before execution).
  - It caps the session's keccak max po2 (the caller's, or 17) to the largest po2 whose measured
    minimum peak fits the Metal working-set limit (`KECCAK_MIN_PEAK_MIB` = 1501/1506/2773/3968/7084
    for po2 14..18).
  - At the targeted tiers only po2 18 moves: to 17 below 7084 MiB, i.e. at 4 GiB, 6 GiB and on an
    8 GB Mac. **po2 17 is kept at 4 GiB**: it proves there (3968-4094 MiB peaks, every 4 GiB job above).
    The brief's fallback, 16 below ~5 GiB, was only for the case where 17 did not fit.
  - The guest then gets the batch-full signal at the smaller capacity. It asks for more, smaller proofs,
    and the receipts verify the same way.
  - It is skipped when the env has a coprocessor callback, because that callback may prove elsewhere and
    gets the caller's po2s. It is also skipped with the CPU keccak prover.
  - It warns when the caller set the po2 explicitly.
  - A pre-executed `prove_session` cannot be capped: the cap applies only in `prove_with_ctx`. A caller
    that runs the executor itself (and zk-miner's `KeccakAudit`, section 8) gets an uncapped execution,
    so the same `RISC0_KECCAK_PO2=18` job can still fail at 4 GiB on that path.
  - The cap is visible to the guest. With an explicit po2 18 below 7084 MiB, a guest that ignores
    `sys_keccak`'s batch-full return (as the k5 test guest does, asking for one whole po2-18 batch) now
    fails execution with "keccak batch is full, prove must be called", where before it tried po2 18
    and failed at proving. A well-behaved guest proves. The k5 test skips po2 18 when it is capped.
    This is documented on `ProverServer::prove_with_ctx`.
  - A requested po2 outside 14..=18 is left alone (fix round 1; before, the warning text indexed the
    peak table with it and could panic). The session's own range check rejects it.
  - Revert: `RISC0_KECCAK_PO2_HEADROOM_CAP=0`.
- **Release before a standalone keccak proof** (`release_before_keccak` in `prove_keccak_with`, the
  `ProverServer::prove_keccak` / coprocessor path).
  - If the allocation now plus the po2's unconstrained keccak-phase peak (`KECCAK_PEAK_MIB`) exceeds the
    limit, it drops this thread's cached segment and recursion provers (`release_cached_provers`, the
    model of `release_segment_prover_before_recursion`).
  - It never fires at the default budget. It uses the unconstrained peaks, so at 4 GiB it fires before
    every po2-17 proof, even from a 29 MiB start (releasing an empty cache costs nothing measurable).
  - It reaches only the calling thread's caches. Provers cached by other threads that are still alive
    stay. A review probe at 4 GiB (three threads calling `prove_keccak` for a full po2-17 request one
    after another, each staying alive) proved on threads 0 and 1 and panicked on thread 2 in the
    Metal HAL's budget check with ~1850 MiB of the other threads' recursion provers live. Two threads
    pass. So the 4 GiB coprocessor-path guarantee is per thread. This is not a regression: A releases
    nothing.
  - With `RISC0_KECCAK_REUSE_HAL=0` (the K10 revert), the session's per-request loop calls
    `prove_keccak_with`, so at a small budget that path now also drops the recursion cache between
    requests. This is safe, at the cost of the rebuilt recursion prover per lift.
  - Revert: `RISC0_KECCAK_SMALL_BUDGET_RELEASE=0`.
- **Rebuild on a po2 change** (`rebuild_for_po2_change` in `prove_and_lift_keccaks`).
  - It drops and rebuilds the keccak prover before a request whose po2 differs from the previous one,
    when the pool plus the next proof's peak would exceed the limit.
  - `RISC0_KECCAK_PO2_REBUILD`: `1` forces this, `0` never does it, and unset means auto.
  - Auto applies only when no `RISC0_METAL_MAX_WORKING_SET_BYTES` is set: a device that is actually
    small, where nothing drains the pools. That branch is not measurable on this Mac (see open issues).
    Auto keys on the environment variable. A budget set only through `set_working_set_limit` counts as
    "no budget", so auto would rebuild there although the allocator drains. The runtime's explicit
    budget is `pub(crate)` in risc0-zkp, which this item does not own.
  - A rebuild (dropping the old prover and its pool, then building a new one) took 2.9-9.9 ms at 4 GiB
    (24 rebuilds in `fr1/mixab4g_fr1b.log`). The earlier "~0.1 ms" was wrong.
  - Under an enforced budget the drain is cheaper. In-process interleaved A/B (`keccak_phase_peaks`,
    `W7V2_AB=8`: A B per round, first round discarded, 7 pairs), 4 GiB, committed binary
    `fr1/bin/lib`, `fr1/mixab4g_fr1b.log`, load 2.7-2.8:

    | sequence | A (`=0`) median [min-max] | B (`=1`) median [min-max] | rebuilds A / B | peak A -> B |
    |---|---|---|---|---|
    | 14,17,14,17 | 2711.6 [2703.7-2718.2] ms | 2778.3 [2771.3-2781.0] ms (+67, +2.5 %) | 0 / 2 | 3980 -> 3968 MiB |
    | 17,16,15,14 | 2405.7 [2399.7-2408.9] ms | 2432.6 [2425.1-2437.0] ms (+27, +1.1 %) | 0 / 1 | 4094 -> 3968 MiB |

  Both slowdowns exceed the A spread (9-15 ms), so forced rebuild is not a default under a budget. The
  same A/B at load 15-20 (`fr1/mixab4g_fr1.log`) was too noisy to separate the arms (spreads of
  170-280 ms) and is not used. The reviewer's process-level A/B (8 pairs, first discarded) agrees:
  +67 ms and +21 ms.
- `RISC0_KECCAK_REUSE_HAL=0` and `RISC0_KECCAK_RIGHTSIZE_PO2=0` (K10) are unchanged. The rebuild lives
  inside the reuse path, and `=0` bypasses it.

Standalone release A/B (`keccak_standalone_repeat`, 4 GiB, one invocation each; knob off = old
behaviour):

## 6. cfg and Send

- **exec_stream gate** (Z17 review). `exec_stream` and its call were gated `metal, not(cuda|rocm)`, while
  the plain-RefCell segment-prover TLS was `not(cuda|rocm|intel)`. All three gates (the module and the
  call in `prover_impl.rs`, `tests_z17` in `mod.rs`) now exclude `intel` too.
  - This is the right side to move. With `intel` beside `metal`, `segment_prover()` returns the Intel
    prover (cfg_if order cuda > rocm > intel > metal). The stream would then lend that prover to its
    thread under an audit written for the Metal one, and leak it per exited thread (ManuallyDrop slot).
  - metal+intel cannot be built at all: risc0-sys's build script rejects `metal` together with `cuda`,
    `rocm` or `intel` ("Feature 'metal' is mutually exclusive with ..."; the reviewer confirmed it with
    `cargo check --features metal,intel`). So the `intel` exclusion is dead code today. It only keeps the
    two gates from drifting apart, and the comment in `prover_impl.rs` now says so.
  - `cargo check -p risc0-zkvm --features metal` and `--features prove` are clean.
- **Send bound**: not added.
  - I tried a supertrait that is `Send` on Metal-only builds and empty elsewhere, plus a matching
    `Self: SegmentProverSend` bound on `SegmentProverImpl`'s impl.
  - It fails for both the Metal and the CPU prover: the cached code `PolyGroup` (risc0-zkp
    `prove/poly_group.rs`) has `coeffs_host` / `evaluated_host: Option<Rc<Vec<Elem>>>`. CUDA/ROCm are not
    the blocker.
  - Those fields are always `None` on Metal (host spills are off on unified memory, `unified_memory_gpu`).
    Every clone of the group lives in the prover or in the segment proof it is finishing, so the move
    stays sound.
  - I reverted the attempt, and the `SendProver` SAFETY comment in `prover_impl/exec_stream.rs` now says
    all this.
  - Making those two fields `Arc` in risc0-zkp would let the bound compile and the `unsafe impl` go.
    That is a zkp change, outside this item.

## 7. Coprocessor/API path and the documented po2

- The API path (`ApiClient::prove_keccak`) connects to a new `r0vm` server process per request (`connect`
  spawns the server), so one prover per session would need a long-lived server. That is not cheap, so it
  was not done.
- The in-process `ProverServer::prove_keccak` builds a prover per call. A rebuild measured 2.9-9.9 ms
  at 4 GiB (section 3; the 45 ms first build is the HAL and archive). The real per-call cost there was
  the leftover recursion prover, which is fixed above.
- `ProveKeccakRequest.po2` can now be smaller than the keccak max po2 (K10 rightsizing). This is
  documented on `ProverServer::prove_keccak` and `ApiClient::prove_keccak`.
- The struct's own field doc is in `host/client/env.rs`, which this item does not own. Suggested line:
  "the po2 the executor asks for: the smallest whose circuit holds the batch, at most the keccak max po2".
- The behaviour change from the K10 adversarial review is unchanged and documented here:
  `prove_and_lift_keccaks` takes `exclusive_gpu()` only around the proving phase. The lifts run under
  the session's outer lock on the session path. In a standalone call they take each HAL call's own lock,
  so another thread's GPU work can interleave between lifts. This is safe because every HAL call locks.

## 8. For W7-M10 (zk-miner)

Keccak max po2 the worker should expect per tier, at the default 17 (no `RISC0_KECCAK_PO2`):

| working-set limit | segment po2 (M8) | keccak max po2 | keccak phase peak |
|---|---|---|---|
| < 6 GiB (4 GiB tier) | 18 | **17** (fits, 3968-4094 MiB at 4 GiB) | about the limit |
| 6 to < 12 GiB | 19 | 17 | 4484 MiB |
| any, with `RISC0_KECCAK_PO2=18` | | 18 only at >= 7084 MiB, else 17 | 7084-7906 MiB |

- `KECCAK_REQUEST_CYCLES` (zk-miner `crates/zkminer-prove-risc0/src/main.rs:1061`, `1<<20 <<
  (po2-17)`) is unchanged at every tier with the default po2: requests are <= 17, and rightsized smaller
  ones are still charged 2^20, which is right because the lift and join dominate them.
- Only with `RISC0_KECCAK_PO2=18` below 7084 MiB does the prover's execution make twice the requests at
  17 (2 x 2^20 instead of 2^21: the same total charge).
- But the `KeccakAudit` executor runs with a coprocessor callback, which is not capped. Its request list,
  and the root assumption it computes, would then differ from the ones the prover's own execution makes.
  The worker should run the audit with the same cap: `keccak_max_po2(min(requested, 17))` below
  7084 MiB of working set. Or it should never set po2 18 on those tiers.

## Fix round 1 (review findings)

**Blocking: the rebuild A/B harness switched the wrong knob.** `keccak_phase_peaks` with `W7V2_AB` was
documented to alternate `RISC0_KECCAK_PO2_REBUILD=0` (A) and `=1` (B), but it set and removed
`RISC0_KECCAK_SMALL_BUDGET_RELEASE`, which `prove_and_lift_keccaks` never reads. Both arms ran the same
code. The first-round table had come from an earlier binary (`mixab4g.log`), so the committed harness
could not reproduce it.

- Reproduction, kept as tests:
  - The arms are now one table, `REBUILD_AB_ARMS` (arm, knob, value), and the knob is resolved by a pure
    `rebuild_allowed(knob, explicit_budget)`. The CPU unit test
    `policy_tests::rebuild_ab_arms_toggle_the_rebuild` checks that each arm names
    `RISC0_KECCAK_PO2_REBUILD`, that A never rebuilds and that B may rebuild under an explicit budget.
    With the old knob put back into the table, it fails ("left: RISC0_KECCAK_SMALL_BUDGET_RELEASE,
    right: RISC0_KECCAK_PO2_REBUILD"; `fr1/repro_policy_oldtoggle.log`).
  - `prove_and_lift_keccaks` counts its rebuilds (`KECCAK_PO2_REBUILDS`). `keccak_phase_peaks` prints
    `rebuilds=` per sequence, asserts 0 in arm A, and below 5 GiB asserts at least one in arm B for a
    sequence with a po2 change into or out of 17. With the old knob, 14,17,14,17 at 4 GiB fails with
    "arm B did not rebuild" (`fr1/repro_ab_oldtoggle.log`).
- Fix: the arms set `RISC0_KECCAK_PO2_REBUILD`. The A/B was re-run with the committed binary (section 3):
  +67 ms and +27 ms, peaks 3980 -> 3968 and 4094 -> 3968 MiB, so the decision stands.

Non-blocking items handled:
- `headroom_capped_max_po2` no longer indexes the peak table with an out-of-range po2.
- Rebuild cost corrected to 2.9-9.9 ms (doc comment and note).
- Section 5 now says which budget each A/B used. A `--no-budget` A/B was added.
- Documented: the owner breakdown is inferred; release is per thread and fires before every po2 17 at
  4 GiB; the `REUSE_HAL=0` behaviour; the cap is guest-visible and only in `prove_with_ctx`; auto keys
  on the env var; metal+intel cannot be built.

## Open issues

- The auto rebuild (no explicit budget, a small real device) was not measured: on this Mac the limit
  without a budget is 28 GiB. An 8 GB Mac (~5.3 GiB recommended) would run it.
- At 4 GiB po2 17 runs within 2-128 MiB of the limit; the budget's drains make it fit. On a real 4 GiB
  owner cap without enforcement (zk-miner S3), the pools are real memory. If S3 starts enforcing,
  nothing changes. If a real 4 GiB device misbehaves, lowering `KECCAK_MIN_PEAK_MIB[17]` above 4096
  MiB moves the cap to 16 (peak 2773 MiB, about +18 % keccak time per full po2-17 batch).
- CUDA/ROCm/Intel are untested here. The cap and the releases are gated to `metal`. The cfg change
  excludes `intel` from the stream (not compiled with intel here).
- `ProveKeccakRequest.po2` field doc (in `host/client/env.rs`, not owned).
- The `SegmentProver: Send` bound needs `PolyGroup`'s `Rc` -> `Arc` in risc0-zkp.
- The KeccakAudit cap in zk-miner (section 8) is for W7-M10.
- `KECCAK_PEAK_MIB` and `KECCAK_MIN_PEAK_MIB` are absolute peaks measured on this M5 Max (40 GPU cores),
  not RAM fractions. The eval-chunk sizing on a 10-core base chip, and so its po2-17 peak at 4 GiB, was
  not checked. The k5/k10 test helpers `segment_po2()` hard-code the M8 tier thresholds (6 and 12 GiB),
  duplicating zk-miner's `metal_sizing` (test-only).
- The auto rebuild keys on `RISC0_METAL_MAX_WORKING_SET_BYTES`. A budget set only through
  `set_working_set_limit` is treated as "no budget". Fixing that needs risc0-zkp to expose the runtime's
  explicit budget.
- The small-budget release is per thread. Several live threads each proving po2 17 on the coprocessor
  path at 4 GiB can still exhaust the budget, and that surfaces as a panic in the Metal HAL rather than
  an `Err` (section 3).
- Pre-existing, not from this item: the reviewer saw 1 hang in 5 runs of the `prove::tests` shard
  (`compress::case_3` holds the GPU lock while a rayon worker that stole a `shrink_wrap` job waits for
  it in `exec_stream`'s segment-stream thread). The stacks contain no W7-V2 code. That suite belongs to
  the base tree / W7-V1. It passed here in fix round 1.
- `prover_impl/exec_stream.rs` has a comment-only change (the `SendProver` SAFETY audit) outside the
  named owned files, and `cargo fmt` reordered two test-module declarations in `prove/mod.rs`. The merge
  agent should check both against W7-V1.
- The ignored tests `keccak_phase_peaks` (with `W7V2_AB`) and `keccak_standalone_repeat` set process env
  and read the process-wide peak counter without a lock (zkvm has no test lock). Run them alone, as
  their docs say.
