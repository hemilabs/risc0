## Tracks

Knobs: `RISC0_G16_METAL_G10=0` reverts to the G9 layout. `RISC0_G16_METAL_G10_OFF=compact,mmap,alias`
turns off single switches. `MemOptions` in `prover.rs` holds them; it is read at prover
construction (`MetalProver::new`; `new_with` for tests). Each switch's saving is measured with
that switch off and the others on.

### 1. zkey zero-copy mapping (`mmap`): probe, then adopted

The probe is `filemap.rs` plus `g10_mapped_srs_probe` (ignored). It found:
- `newBufferWithBytesNoCopy` accepts a `PROT_READ`/`MAP_PRIVATE` file mapping. The pointer must
  be page aligned and the length a multiple of the page size (16 KiB here, read with
  `getpagesize`).
- The zkey point sections start at 4-byte-aligned offsets (A at 1280319592, mod 64 = 40; B1 mod 64
  = 52; B2 mod 64 = 0; C mod 64 = 12; H mod 64 = 24). `FileMap` maps the whole pages that hold a
  section, and the MSM binds the points at the in-page offset (`SharedBuf::offset`, `pts()`).
  `SharedBuf::get` and `bytes()` read at any alignment. `as_slice` asserts alignment.
- `currentAllocatedSize` **counts** the mapped buffers (+2232 MiB), so the budget arithmetic is
  unchanged. The process' `phys_footprint` does **not** count them (+1.2 MiB, against +2233 MiB
  for the copy).
- Timing with a warm page cache: map with `MADV_WILLNEED` 73-78 ms, pread copy 130-134 ms. The
  first run, under load, was 1.2 s against 0.39 s. Without the advice the map takes 26-42 ms but
  the first touch pays the faults (81-106 ms).
- A GPU blit out of a no-copy buffer at unaligned offsets reads back the file bytes
  (`file_map_reads_back`).

With `mmap` on, the compact cache file's sections are also mapped no-copy (they are 16 KiB
aligned). Footprint (`footprint_variants.log`, one `metal_shrink_wrap` process each):
`-mmap` peaks at 8600 MiB against 6058 MiB with every switch on, so this switch saves **2.5 GB
of footprint**.

**Cost:** the G1 sections are not 64-byte aligned, so every 64-byte point straddles cache lines.
The G1 MSMs get slower by the minimum of interleaved reps (bench3/bench4, 9-11 reps):
- msm_a +4.6-5.0 ms;
- msm_b1 +4.4-5.0 ms;
- msm_c +4.2-4.6 ms;
- msm_h +11 ms.

B2 is unchanged (its section is 64-byte aligned). That is about +25 ms per proof (1.7 % of the
GPU time, ~0.15 % of a 16 s worker wrap). Re-aligning would need a 2.2 GB aligned copy on disk,
which was not pursued.

I kept `mmap` on by default because this item is about memory. On 16 GB Macs the 2.2 GB of points
become clean file-backed pages instead of anonymous memory that has to be compressed or swapped.
Machines that only care about speed can set `RISC0_G16_METAL_G10_OFF=mmap`.

Not verified: whether macOS actually evicts these pages under memory pressure while the buffer
exists. Producing pressure on the shared machine was not attempted.

### 2. Compact coefficients + Rust disk cache (`compact`): adopted

`compact.rs` ports CUDA's cold-path `compact_load`. Per coefficient it stores `(s, value index)`
as 8 bytes, plus a table of distinct values (16,413 on the rzup key, 0.5 MiB), each row's output
index (`rowc`) and the row starts. That is **309 MiB instead of 1375 MiB**.

`witness_into_poly_compact` (`witness_poly.metal`) sums in the same order, so a and b are
bit-identical. It has the same fault bits, and a value index out of the table counts as
`BAD_INDEX`.

Disk cache:
- Path: `<cache dir>/coeffs_compact_metal_<key>.bin`. The cache dir is the CUDA library's
  (`RISC0_G16_CACHE_DIR`, `$XDG_CACHE_HOME/risc0-groth16`, `~/.cache/risc0-groth16`).
- The backend tag `metal-compact` is in the key, the file name and the magic `R0G16MCP`. The
  layout differs from CUDA's: every section starts on a 16 KiB boundary so it can be mapped.
- The key hashes the format, 64 sampled 4 KiB blocks of the original, and its size, mtime,
  inode and device.
- Each load checks the header and counts, a payload checksum (CUDA's multiply-xor, 8 threads)
  and the kernel's invariants (`CompactCoeffs::validate`: index lists, increasing rows below the
  domain, `s < wn`, value index < table, canonical values).
- A build first validates the whole original (`validate_part`, as before), reading it through
  a host-only mmap rather than a 1.44 GB copy. It writes the file as a temporary and renames it.
- A damaged or truncated file is rebuilt. A file that only fails the size checks is kept, since
  the rebuild fails the same way.
- `RISC0_G16_METAL_COEFF_CACHE=0` turns the disk cache off (build in memory each load).
- `prove::invalidate_caches()` (`groth16/src/prove/metal.rs`) deletes the files. The zkvm calls
  it after a Groth16 seal fails verification.

Load time: the first load (build + write, 324 MB file) takes 464-669 ms; a cache hit takes
27-30 ms (`compact_build.log`). The full path was 210 ms load + 12 ms validation.

Speed: `zero+witness_poly` minimum 73.6 ms against 89.6 ms (base) in bench4, and 74.3 against 81.7
median in bench1, so about -8 to -16 ms. Footprint: `-compact` peaks at 7433 MiB, so the switch
saves **1.4 GB of footprint**.

### 3. Aliasing (`alias`): adopted

No buffer of the prover is live for the whole proof:
- **c in the MSM scratch's `sorted` buffer** (512 MiB, of which c needs 256 MiB) during the NTT
  phase. No sort of the proof has written it yet: sort_h is the first, and it comes after the NTT
  command buffer.
- **No persistent fuzz.** Once sort_h has consumed h, a and b are free. A new `fuzz` stage
  regenerates the ChaCha fuzz into them (same kernel, same all-zero state as the build-time fuzz)
  and adds it to the witness before sort_w. It costs 1.8-1.9 ms of GPU time per proof.
  `fuzz_check` does the same.
- **The MSM piece buffer is a, b** (`MsmScratch::new_with` lends a buffer; it is 240 MiB, inside
  a, b's 512 MiB). The MSMs run only after sort_h, and the late fuzz is dead once `fr_add` has
  folded it into the witness. `pieces_bytes` keeps the configured cap, so the window grouping
  (and the timing) are unchanged.

Every hazard is between tracked buffers on one queue: the same ordering the G7 prover already
relies on. Saving: **-668 MiB of device memory**. Footprint: `-alias` peaks at 6726 MiB, so the
switch saves 0.67 GB.

### 4. Lazy revert-path pipelines: adopted (G9 open issue)

`MsmKernels` now builds the G7/G8 `_g1`/`_g2` point pipelines on first use (`OnceLock`). Only
`RISC0_G16_METAL_G9_OFF=wide_mul` uses them. `RISC0_G16_METAL_EAGER_PSOS=1` restores eager
building, for a warm-up that must cover every switch. The default path no longer compiles 6
unused PSOs, which matters for the cold-start cost G7 measured in minutes. The device allocation
of a `G10=0` prover went from 5631.7 to 5627.2 MiB (the PSOs not built). A cold-cache compile
was not re-measured: that needs a fresh, differently built binary.

### Not done (measured ceiling, or not applicable)

- **Deferred collect via completion handlers.** After the wait, the host side of a proof is
  combine + fuzz removal + blinding = 1.2-4.4 ms (`host=` in the `[groth16-metal]` lines), about
  0.1-0.3 % of the proof. That is far below the A-vs-A spread (tens of ms), so overlapping it with
  the B2 MSM through `addCompletedHandler` cannot show. Not implemented.
  - The witness upload (6.6-13.4 ms) has to precede the first kernel. Removing it needs the
    witness written straight into the shared buffer (`fast.rs`/`witness_par`, owned by the
    groth16 crate's `mod.rs`; see open issues).
- **sppark 3-pass NTT.** The fused schedule already makes 3 passes per direction at lg 23 (9 + 7
  + 7 levels, `NttPlan::passes`), the same pass count as sppark's 3-pass. The NTT stage is 83 ms
  (6 % of the GPU time). Fused does not lose, so per the PLAN row it was not done.

## Budgets and hardware (PLAN 9.1)

- Minimum tier (~4 GB active budget): the wrap now fits. The smallest budget that builds the
  prover is 3930 MiB, and the wrap's own device peak is 3.9 GB.
  - On top of the wrap, the worker still needs its host memory: the CPU witness and witness graph
    are the rest of the 6.1 GB peak footprint (G8: the STARK pools are released before the
    key loads).
- 8 GB: unchanged (fits).
- Nothing depends on the core count. The page size is read at runtime. The cache file's 16 KiB
  section alignment is a multiple of both 4 KiB and 16 KiB pages.
- The mmap misalignment cost is a memory-system effect. I expect it on every Apple GPU, but only
  measured it on the M5 Max 40-core.

## Open issues for later items

- **`msm_configs` wrong G2 result, seen once.** It happened in 1 of 7 groth16-sys suite runs of the G10 binary
  (a 4 GiB budget run) for G2, n = 1000, wbits = 1, seg = 3, on the default (wide) kernels. It did not
  reproduce in 24 isolated reruns, 50 concurrent reruns (25 each on the G9 and G10 binaries) or 6 more
  full-suite runs at 4 GiB (3 per binary). G10 does not change any MSM kernel, and this test does not use the
  prover's lent piece buffer (`MsmScratch::new`). It may be an R17-class intermittent wrong
  result under load in `msm_reduce` (tier B/C shapes, see G9).
  - **R17 follow-up / G11**: add a 1-bit-window G2 config to `r17_msm_repeat`.
- **Memory, next levers**:
  - NTT twiddle shrink (two-level tables: -124 MiB);
  - `sorted` sized for 16 windows while Booth uses 15 (-32 MiB, needs the scratch sized by the
    tune);
  - lend the `sorted` buffer's spare half (256 MiB free during the NTT phase).
- **mmap eviction under pressure**: not verified that macOS drops the mapped point pages while
  the prover is cached, then faults them back for the GPU. A 16 GB machine under memory pressure
  should check it (zk-miner M-items).
- **groth16 `mod.rs` owner**: enable `witness_par` for metal, and let the witness be written
  straight into the prover's shared buffer (saves the 6.6-13.4 ms upload and a 172 MiB host
  copy).
- **zk-miner (M-items)**:
  - `RISC0_G16_CACHE_DIR` / `~/.cache/risc0-groth16` now gets a 324 MB file on the first wrap;
    the installer may want to pre-build it (`metal_preload` does).
  - Re-measure the worker's wrap footprint: G10's 6.1 GB peak against G9's 10.3 GB, in this test.
- **Final baseline**: the absolute times here come from a shared GPU. The memory figures are
  exact.
