## What was done
- `circuit/keccak-sys/build_metal_eval.rs` (replaces K1's stub; **build.rs not touched**: K1's
  `mod` line and its `metal_eval_sources(kernel_dir, gen_dir)` call site were already there).
  - Ported from build.rs `write_intel_translation_unit` + `cut_into_stages` (build.rs:492-752) and
    kernels/intel/{prelude.h,kernels.h}, which themselves follow kernels/cuda/eval_check_scratch_*.cuh.
    Input: `kernels/cuda/eval_check.cuh` + `eval_check_{0..4}.cu` (58 functions, 90,630 body lines).
  - It works on **parsed functions**, not text: signature → typed parameters (`const Fp*` is matched
    before `Fp*`, as the errata asks), body lines checked against the generator's shapes, the tail
    call found. The chain is cut on these parsed functions (i.e. before `__device__` is gone); output
    signatures are emitted fresh, without `__device__`.
  - Rewrites: `Fp x13[8237]` → `ScratchRef x13 = ectx.scratch`; `Fp* argN` → `ScratchRef argN`;
    `const Fp* argN` → `const device Fp* argN`; every function gains `EvalCtx ectx` after `size` and
    every call passes it; `poly_mix[` → `ectx.poly_mix[` (bound `device` buffer);
    `constexpr size_t X = v` → `constant constexpr uint32_t X = v` (only constants a stage uses, so no
    unused warnings; `uint32_t` keeps all indexing 32-bit). Writes stay `Fp(...)`/assignments of Fp
    values (the generator never writes `= 0`).
  - **Explicit carry emission**: at a cut, `auto xR = head(idx, size, a...); return xR;` becomes
    `carry_store(ectx, slot, a)` for each FpExt argument (slot = order among the head's FpExt params)
    and `return FpExt();`. The next stage's kernel calls `head(...)` with `carry_load(ectx, slot)` for
    FpExt params, `ectx.scratch` for scratch params, and the **traced** kernel input buffer for each
    `const Fp*` param (every `const Fp*` parameter is traced through the chain to the `poly_fp`
    parameter it always is: ctrl/out/data/mix/accum). So no pointer is ever stored in the carry
    (Intel stored 64-bit pointers there; Metal pointers in buffers would need `use_resource`).
  - Stages: `eval_stage_0..S-1`, one `.metal` file each in `$OUT_DIR/metal`, kernels at global scope,
    functions in `namespace keccak_eval`, callee-first so no prototypes. `S` =
    `RISC0_KECCAK_METAL_EVAL_STAGES` (default 58; `rerun-if-env-changed`; non-positive/non-numeric
    panics; > 58 is clamped with a cargo warning). Cutting is the Intel line-balanced rule, changed
    so it always yields exactly `min(S, 58)` stages (Intel's rule could skip cuts after short
    functions). Stale `eval_stage_*.metal` from a previous larger count are deleted (verified: after
    S=8 the gen dir held exactly 8 files).
  - Shape asserts (panic with file/function/line): any header statement other than the extern decls,
    the two known `constexpr size_t` constants and the `poly_mix` extern; any line outside a function
    besides the known boilerplate; `Fp *` spelling; parameter types other than the three; any body
    line whose shape (operands replaced by their type) isn't one of 12 known shapes; ops on undeclared
    or redeclared names; a call that isn't the tail call; more than one call per function; not exactly
    one `Fp xN[M]` and not in poly_fp; definitions ≠ declarations (names and parameter lists);
    functions outside the chain from poly_fp; argument type mismatches at each call (scratch/FpExt/input);
    poly_fp's parameter list changed.
  - Also writes `$OUT_DIR/keccak_metal_eval.rs` and sets `KECCAK_METAL_EVAL_RS` (path) and
    `KECCAK_METAL_EVAL_STAGES` (count) via `cargo:rustc-env`, for K4:
    `EVAL_STAGES`, `EVAL_STAGE_NAMES`, `EVAL_SCRATCH_ELEMS` (8237), `EVAL_CARRY_WORDS` (20),
    `EVAL_MAX_STRIDE` (2^32/8237 = 521,429), `EVAL_MAX_COLUMN` (1095), `EVAL_INV_RATE`,
    `EVAL_NUM_POLY_MIX_POWS` (2175), `EVAL_BUF_*` binding indices, `EVAL_PARAMS_SIZE` (32).
- `circuit/keccak-sys/kernels/metal/eval_check_prelude.h` (new): `EvalParams {count, first, domain,
  stride, quot[4] (raw Montgomery words)}` (static_assert 32 B); `keccak_eval::ScratchRef {device Fp*
  base; uint stride; device Fp& operator[](uint i) const}` (element i of thread t at
  `scratch[i*stride + t]`); `EvalCtx {poly_mix, scratch, carry, stride}`; `make_eval_ctx`,
  `carry_store/carry_load` (word w of thread t at `carry[w*stride + t]`), `write_check` (last stage:
  `check[domain*i + cycle] = tot.elems[i] * quot[cycle & 3]`, as intel kernels.h); the shared kernel
  signature/prologue macros (bindings 0..9 documented at the top of the header); `R0_KECCAK_EVAL_TG`
  (default 256, emitted before `kernel void`); `R0_KECCAK_EVAL_FN` = `static inline`, or
  `static __attribute__((noinline))` under `-DR0_KECCAK_EVAL_NOINLINE` (for K7; not measured).
- `circuit/keccak-sys/tests/k3_eval_translate.rs` (new; includes the translator via `#[path]`):

  carry 20 words), `rejects_changed_generator` (10 mutations, each panics: verified the panic messages

## Assumed / not verified / gaps
- **Nothing has run on the GPU** (no dispatch, no bit-exact check): that is K4 (`metal::tests::eval_check`
  at PO2 4/8/14/17 vs CPU). In particular the carry layout and quot encoding (raw Montgomery words,
  as Rust's `BabyBearElem` stores them) are unexercised.
- Index math is 32-bit, as in CUDA: K4 must check `(EVAL_MAX_COLUMN + 1) * domain <= 2^32` (true to
  po2 19 domain 2^21) and `stride <= EVAL_MAX_STRIDE`, `count <= stride`.
- K4 should `include!(env!("KECCAK_METAL_EVAL_RS"))` only when kernels are built: under
  `RISC0_SKIP_BUILD_KERNELS` build.rs does not call the translator, so neither env var is set
  (the k3 test handles this with `option_env!`).
- `METAL_KERNEL_NAMES` (src/lib.rs, not K3's file) still lists only `scatter_preflight`; K4 adds
  `EVAL_STAGE_NAMES` when it loads the stages.
- PSO timing ran while other agents used the machine (numbers indicative); only sequential PSO
  creation measured (concurrent creation and `MTLBinaryArchive` are K5/K7). `-DR0_KECCAK_EVAL_NOINLINE`
  only checked to compile (8-stage eval_stage_7: 9.0 s front end, no errors); its PSO/runtime effect is
  unmeasured (K7).
- `rejects_changed_generator` prints the expected panic messages on stderr (default panic hook).
