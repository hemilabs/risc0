## (a) What was built

**Kernel** `pv_rows_side_k_z9` (`pv.metal`): the Z9 `pv_rows<2>` row hash, unchanged, followed by
side work that touches neither its input nor its output:
- **Bit reversal.** In-place reversal of `cols` columns of 2^lg (lg >= 10). A column is viewed as a
  32 x 2^(lg-10) x 32 array; bit reversal maps tile t to tile rev(t), transposed with both 5-bit
  coordinates reversed. Each threadgroup takes tile pairs (t, rev t) in a grid-stride loop and stages
  both in threadgroup memory (2 x 32 x 33 words, padded against bank conflicts), so there are no
  private arrays in the side path (R17).
- **Fills.** Up to two uint4 fills of a word, grid-stride.

The hash is ALU-bound and the side work is bandwidth-bound, so the side work is hidden.

**Host.**
- `Hal::fuses_bit_reverse_into_hash`, `hash_rows_bit_reverse`, `commit_coeffs_lde_bit_reversed`. The
  defaults keep today's behaviour for CPU, CUDA, HIP and SHA/Poseidon254 Metal hashes.
- `Prover::commit_group` asks for the coefficients left bit-reversed, and `PolyGroup` /
  `MerkleTreeProver::new_bit_reverse` hand them to the row hash. The check group's `PolyGroup::new`
  path does the same.
- It falls back to the separate pass when the coefficients spill to the host (non-unified HALs) or
  when the row shape takes a pvs latency kernel.
- **Metal `prefill_elem`** (was the trait's no-op on Metal). It sets aside a buffer that is already
  pooled (ready, or pending; ordering comes from Metal's hazard tracking, buffers are tracked), never
  a new allocation. The next row hash that can carry the fill encodes it, and the next
  `alloc_elem_init` of that size and value takes the buffer.
- **Budget gate.** Set-aside bytes are capped at working-set limit / 8 (512 MiB at 4 GiB, which takes
  accum but not data at po2 20). A pool drain releases them.

## (b) Fused NTT pass in the absorb: not started

The brief gates (b) on "(a) and Z13 leave the NTT passes as the commit's largest cost". They do not.
After (a), the po2 20 x 211 commit is 199.5 ms. The row hash is 136.1 ms of it (68 %) and the NTT
(`commit_coeffs_lde`, Z13: 71.4 ms wall, chunked and on-chip-bound) is the rest.

Z13's numbers also limit what fusion could hide. The chunked commit NTT runs at ~470 GB/s of pass
traffic with ~6 ms of non-overlapping ALU per pass, and threadgroup-exchange passes, unlike the
streaming copies of (a), compete with the hash for the same ALU. The Swift go/no-go prototype
(fused CT pass + absorb vs each alone, >= 60 % hidden) was therefore not built.

## (c) Tree top in one dispatch: NO-GO

`tests_z3::bench_fold_tree`, 4 interleaved rounds, best µs (`treetop1.txt`, load 12):

| config | L7 | L10 | L14 | L18 | L21 |
|---|---|---|---|---|---|
| default (one dispatch per layer) | 127.7 | 184.2 | 277.3 | 910.2 | 5214.2 |
| tail128 (top 7 layers in one dispatch) | 120.7 | 185.5 | 277.3 | 914.4 | 5220.4 |
| tail16 | 123.5 | 180.2 | 273.1 | 912.2 | 5217.4 |

The single-dispatch tail is within noise at every size, as Z3 measured. Why a deeper version cannot
win:
- A 10-layer tree costs 184 µs, ~18 µs per layer, which is one Poseidon2 permutation's latency
  (17-22 µs, Z3).
- One dispatch for the top 10 layers still runs those layers back to back, each at least one
  permutation latency. The 1024-output layer would also run on a single core in one 1024-thread
  group.
- The ceiling is therefore ~0, and ~5 trees per segment x a few µs is < 0.01 %.
- Not implemented.

## Memory safety of the tests (the two machine crashes)

- **The measurement tests (`z14_commit_ab`, `z14_tg_probe`).** These now fill their buffers in place
  and share one set across shapes. Before, they built a 3.5 GB host `Vec` plus its device copy per
  shape, and the buffers freed by one shape stayed in the shared pool during the next. They also drain the pool between shapes. Peak RSS is
  0.93 GB per run; they need ~6.6 GB of GPU memory at po2 20 x 211 and must run under the heavy lock.
- **The full zkp lib suite.** Under the default parallel harness its process peaks at **28.8 GB
  RSS** (`/usr/bin/time -l`, unified memory, so it includes GPU buffers). The Z14 tests account for
  ~1.9 GB of that; the rest predates this item. Run beside another prover (e.g. one worker at
  15.7 GB) on the 36 GB machine, that is enough to exhaust RAM. Run the suite only under the
  exclusive lock, and see the open issues.
- Each rv32im `prove_po2_sweep` process at po2 20 peaks at ~9.3 GB of GPU memory and ~1.1-1.4 GiB
  of RSS. The A/Bs run one process at a time.
- **Single tests too big to share the machine** (all predate Z14):
  - `tests_z2::ntt_commit_coeffs_lde_lg_10_20` (211 columns x 2^20, on the CPU and the GPU):
    20-23+ GiB alone.
  - The rest of `tests_z2` under the parallel harness: 16-19 GiB.
  - rv32im `seal_matches_cpu_large` at its default po2 20: ~22.8 GB.

  Any of these, beside a worker (15.7 GB) or a second suite, can exhaust the 36 GB machine. The
