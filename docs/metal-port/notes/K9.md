## Summary
- **Change:** the eval_check chunk (scratch stride) is now chosen per call (`auto_chunk`):
  **32768 when the domain spans at least 8 such chunks (po2 >= 16) and the working-set budget has room
  for the larger scratch, else 16384** (K7's value). `fit_chunk` still halves below that under a tight
  budget, as before. `RISC0_KECCAK_METAL_EVAL_CHUNK=<n>` fixes the chunk as before;
  **`RISC0_KECCAK_METAL_EVAL_CHUNK=16384` reverts to K7**; `=auto` (or unset) is the new default.

- **Not changed:** the strict-stage copy stays (see "Strict copy"). No Metal kernel changed (no TU to

## Change (`eval_check.rs`)
- `auto_chunk(domain, free, cached)`: `LARGE_EVAL_CHUNK` (32768) if `domain / 8 >= 32768` and
  `scratch_bytes(32768) - scratch_bytes(cached) <= free`, else `DEFAULT_EVAL_CHUNK` (16384) capped
  at the domain. `free` is the HAL's `gpu_free_memory()` (Z6: working-set limit = explicit budget
  capped at `recommendedMaxWorkingSetSize`, minus the budget scope's allocation level, pooled buffers
  included). `cached` is a scratch kept by `set_keep_eval_scratch` (freed before the new one).
- **Why this test is "room on top of the rest of the keccak prove peak":** eval_check is the peak
  phase of a keccak proof (K7 `metal_peak_memory`; every earlier phase allocates less, and the scratch
  is freed before check commit/FRI), and the scratch is the last thing it allocates. So
  `allocated + scratch_bytes(32768) <= limit` at that moment is exactly "this proof's peak with the
  larger chunk fits the budget". The extra memory comes from the circuit's sizes
  (`(EVAL_SCRATCH_ELEMS + EVAL_CARRY_WORDS) * 4 * 16384` = 541 MB), not from constants.
- State: `chunk: Cell<Option<u32>>` (None = auto), `last_chunk` (what the last call ran with).
  New `set_eval_chunk_auto()`, `last_eval_chunk()`; `eval_chunk()` now returns `Option<u32>`
  (no users outside the module). A debug trace logs `po2, chunk (wanted)` per call.
- Tests: `matches_cpu` (po2 4/8/14 and the ignored po2 17) and `r17_eval_check_repeat` now run the
  automatic chunk, so the po2 17 CPU-exact and stress tests cover the 32768 shape the prover now
  uses (`R17_AUDIT_CHUNK` fixes one). New `auto_chunk_follows_domain_and_budget` (pure: po2 8-18,
  exact-fit boundary, cached scratch, the extra-bytes formula) and `mod.rs`
  `auto_eval_chunk_follows_budget` (po2 16 proofs: 32768 at the default limit; under a budget of that
  proof's peak minus half the extra, 16384 with no further halving, peak under the budget; both
  seals verify).

## Strict copy (K7 open issue)
Baseline confirmed the lazy kernels (strict +460 ms, 9/9). Dropping the strict copy is **not trivial**
and was left: it is emitted by `keccak-sys/build_metal_eval.rs` (outside this item's files), pinned in
`k3_eval_translate`, and has the `keccakstrict` archive unit and `RISC0_KECCAK_METAL_EVAL_MACC` knob in
the HAL; removing it changes the metallib (every machine rebuilds the keccak archive once). A keccak-sys
item can do it.

## Knobs
`RISC0_KECCAK_METAL_EVAL_CHUNK` = unset / `auto` (K9 default), or a cycle count (fixed; `16384` = K7,
`32768` = K4). Test-only: `R17_AUDIT_CHUNK`. API: `set_eval_chunk`, `set_eval_chunk_auto`,
`eval_chunk() -> Option<u32>`, `last_eval_chunk`.

## Open issues
- **Base-chip crossover (PLAN 9.1), not measured.** `LARGE_CHUNK_MIN_CHUNKS = 8` comes from the
  40-core M5 Max: the gain per dispatch avoided (~40 µs here) is likely smaller on 8-10 core GPUs
  (16384 threads already fill them many times over), while the allocation cost scales with memory
  bandwidth. On a base chip the large chunk may be neutral or slower at po2 16; re-run `ab.sh` with
  `RISC0_KECCAK_METAL_EVAL_CHUNK=16384` vs auto there.
- **The fixed ~10 ms allocation cost per call** (fresh 0.5-1 GB private scratch each eval_check) is
  what makes the large chunk lose at po2 13-14. A scratch reused across proofs (zkp pool for private
  buffers, or a prover-lifetime cache with a budget check) would remove it and could make 32768 (or
  larger) a win at every po2; the zkvm builds a new prover per keccak proof, so this needs zkp/zkvm work.
- **Concurrent HALs:** with a device-scope explicit budget, another HAL allocating after the chunk
  decision competes for the same headroom (true of every allocation; the margin left at 8 GiB po2 18
  is 281 MiB).
- po2 18 at 4 GiB still panics in zkp commit (`buffer.rs:49`, Z6 owner), unchanged.
