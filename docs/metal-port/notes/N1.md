## Verdict

**VERDICT eval: NO-GO; NTT: NO-GO**

- **The matrix units are real and fast, and the arithmetic is exact.**
  - uint8 x uint8 -> int32 `matmul2d` runs at up to 43-49 TMAC/s on the M5 Max.
  - That is 2.2-2.5x the chain link's scalar field-product rate, before staging.
  - Every result checked equals the CPU reference.
- **Criterion 1 holds only in the isolated chain microbenchmark.** That is the RDNA4 chain shape with staging
  included, in blocks of 32 links. The chain arithmetic is 4.3x faster when the c terms come from loads, and
  3.2x when they come from ALU work.
- **Criterion 2 fails.** The bit-exact real-kernel prototype is the decider: all 115 eligible chains of
  `ef_eval_split` were rewritten (4380 Fp links per row), at po2 20.
  - With the Q tiles built in the kernel, the kernel is +141 to +170 ms slower.
  - The best structural form with the Q tiles **free** (a wrong-result timing bound) is
    +0.3 / +5.7 ms. That is no gain.
  - The scalar arithmetic it replaces is worth 47-58 ms.
  - Moving the per-point terms into and out of the operand layout costs about as much as the arithmetic it
    removes.
  - Projected gain: **≤ 0 %** (needed: ≥ 3 %).
- **NTT: NO-GO.**
  - A fixed-twiddle radix-32 block as a dense byte-decomposed matmul needs 12.8x the field products of a
    radix-2 FFT.
  - It would be about 3x slower than the current ALU butterflies even with free staging (section 5).

## 1. Profile before
- Wave 5c baseline: the po2 20 segment is 1020 ms, of which eval_check is 608 ms (the R20 specialized
  `ef_eval_split_fc`).
- This item measured the plain `ef_eval_split` in `ef_variant_bench`: 641.8-649.3 ms (A, po2 20, 7 rounds per
  session), A2−A −0.8 to +1.8 ms.
- The evalfast TU (`count_chains.py`, regenerated with `regen.py --metal`, identical to the cargo OUT_DIR
  copy) has, per row:
  - 282 poly_mix chains with 5118 links: 4948 with an Fp term and 170 with an FpExt term;
  - 154 chains with ≥ 4 Fp links (4749 links), 118 with ≥ 8 (4559) and 86 with ≥ 16 (4224);
  - chain lengths up to 144 links, with a mean of about 31 for the long ones.

  An Fp link is 4 lazy 32x32->64 multiply-adds. In the byte decomposition it is 64 byte-MACs.

**Arithmetic share of the chains (real kernel, R21-style ablation, `ev_abl1.log`, `ev_tc*.log`):**

| variant (po2 20, 7 rounds, `ef_variant_bench`) | stack (agx_size) | split − A |
|---|---|---|
| every Fp link → one xor per element (`nolink`) | 18.7 KB (fast regime) | **−66.9 ms [−69.3, −64.1] (−10.4 %)**, 7/7 |
| Fp links of the chains with ≥ 8 Fp links → xor (`nlall`) | 21.0 KB | −47.2 / −51.6 / −54.6 / −57.9 ms in four sessions |
| `rv32im_v2_14` only (620 links) | 19.0 KB | −13.9 ms |
| multiply → xor, add kept (`nomul`) / product twice (`dupmul`) | 38.6 / 39.1 KB (slow regime) | invalid probes: the stack regime flips |
| `nomul3`, `duplo` (other forms) | 22.1 / 22.0 KB | +162 / +185 ms: a third, slow regime (R21's stack sensitivity again); invalid |

- The chain arithmetic is therefore **at most ~10 % of the kernel** (≈ 67 ms at po2 20).
- The kernel is load-bound (R18/R19), and the remaining 90 % is not this arithmetic.
- The ceiling of any rewrite of these chains is ~10 %.

## 2. Raw throughput (step 1)
`tput.metal` + `tput.py`, `logs/tput1.log`. Setup:
- 7 interleaved rounds; odd rounds run the list in reverse;
- GPU time from command-buffer timestamps;
- 4096 threadgroups of 128 threads;
- load 2.5-2.9;
- the min/max spread of every kernel is < 1 %.

The operands stay resident and the destination is a cooperative tensor accumulated in place. `sg1` means
`execution_simdgroup` (one tile per simdgroup); `sg4` means `execution_simdgroups<4>`.

| shape (M x N x K) | uint8 (TG operands) | int8 (TG) | uint8 (device operands) | half → float (TG / device) |
|---|---|---|---|---|
| 16x16x16 sg1 | 20.1 TMAC/s | 20.1 | 20.3 | 17.4 / 17.5 |
| 16x32x64 sg1 | 35.5 | 35.2 | **49.3** | 20.0 / 26.0 |
| 32x32x32 sg1 | **43.4** | 43.5 | 46.4 | 24.9 / 26.1 |
| 32x32x32 sg4 | 29.1 | 29.1 | 32.2 | 21.9 / 22.9 |
| 64x32x32 sg4 | 35.6 | 35.7 | 38.9 | 24.9 / 25.5 |
| 64x64x64 sg4 | 42.0 | 42.0 | 46.8 | 25.2 / 26.0 |
| 16x32x128 sg1 / 16x32x256 sg1 | 29.7 | | 48.7 | |

| scalar (8 independent chains per thread) | rate |
|---|---|
| fp32 FMA | 6.23 T/s |
| 32-bit `mul` | 3.31 T/s |
| `mulhi` | 1.65 T/s |
| 32x32->64 multiply-add | 1.52 T/s |
| **chain link** (64-bit madd + fold of the high word, `rk_link` EF_WIDE) | **1.25 T field products/s** |
| Baby Bear Montgomery product (`ef_lmul`) | 0.66 T/s |

Field products per second on the matrix units, at 16 byte-MACs each:
- 1.26-3.08 T/s;
- **1.0-2.46x the chain link** and 1.9-4.7x the Montgomery product, before any staging and before combine/REDC;
- the larger the tile, the better (16x16x16 only matches the scalar link).

**int8 is on the accelerator path:**
- int8 and uint8 give the same rate;
- int8 runs at 1.7-1.8x half;
- half → float matmul (25 TMAC/s) runs at 4x the fp32 FMA rate of the shader ALUs (6.2 T/s), so it cannot be
  running on them.

**Exactness:** `chkmm.py` dumps compared with a Python reference: 0/2048 and 0/4096 elements differ.

## 3. Chain-shape microbenchmark (step 2)
`chain.metal` + `tables.py` + `run_chain.sh`; logs `logs/chain2.log` and `logs/chain_final.log`, two
sessions with the same picture.

The workload:
- 1M points, one per thread;
- each thread runs 150 chains of 32 links;
- each link's c is `ef_lmul` of two loaded trace words, made canonical (`-DCH_NOLOAD`: an ALU hash instead);
- pm rows come from a 1255-row table, as in the real kernel.

The forms:
- **`ch_scalar`** is the eval chain (EF_WIDE `rk_link` / `rk_link_nf` alternating, then `rk_fin`).
- **`ch_mm_BL`** is the RDNA4 scheme:
  - each thread stores its c raw words (4·BL bytes, point-major) in its simdgroup's threadgroup staging;
  - one uint8 matmul2d runs per block of BL links: 16 x 32 points x 4·BL, right operand transposed, Q tiles
    from device memory;
  - D goes through threadgroup memory;
  - T_j = Σ_b D[(j,b)] << 8b is folded into the 64-bit lazy accumulator;
  - the same `rk_fin` follows.
- **`ch_none`** does only the c work, so a form's chain arithmetic is form − `ch_none`.

Every tensor form equals `ch_scalar` word for word (14/14 CHK lines, 0/4194304 differ). The second
`ch_scalar` instance (A2) is within 0.3 ms (≤ 1 %).

| (medians, ms, 9 rounds; final session) | scalar | mm BL=8 | mm BL=16 | mm4 BL=16 (`simdgroups<4>`, N=128) | mm BL=32 | none |
|---|---|---|---|---|---|---|
| c from loads | 33.53 | 30.37 | 30.91 | 32.56 | **27.65** | 25.79 |
| chain arithmetic (− none) | 7.86 | 4.70 (1.67x) | 5.04 (1.54x) | 6.69 (1.16x) | **1.86 (4.3x)** | |
| c from ALU (`noload`) | 33.09 | 23.01 | 21.07 | 22.74 | **20.62** | 14.89 |
| chain arithmetic (− none) | 18.2 | 8.13 (2.24x) | 6.08 (2.98x) | 7.76 (2.33x) | **5.73 (3.18x)** | |

- With BL = 32 the matrix path meets the ≥ 2x rule including staging in this shape. Here that means 4.3x and
  3.2x, or 1.22x / 1.60x of the whole microkernel.
- The matmul work itself (3.2e11 MACs ≈ 7 ms at 45 TMAC/s) is **mostly hidden**: the load-shape increment is
  1.9 ms. The neural accelerators run alongside the shader ALUs and memory stalls.

## 4. Real kernel: bit-exact prototype (steps 2-3, the decider)
`mm_chain.py` rewrites the generated TU's chains in the tensor form:
- chains with ≥ 8 Fp links; FpExt links stay scalar;
- 32-link blocks, 6 KB of threadgroup memory per simdgroup;
- the Q tile is built in the kernel per block from the pm rows. That is conservative: production would
  precompute Q per proof, as `ef_prep_q` does on AMD.

`real_kernel.sh` builds the variants (`-std=metal4.0 -DN1_MPP -DN1_TC`) and runs `ef_variant_bench` at po2 20.
**The tensor forms are bit-exact**: `tcm`, `tc14`, `tcall`, `tcm2`, `acc1` show 0/7 mismatching runs against
the built-in kernel in every session.

Sessions: `ev_tc1`-`ev_tc4` and `real_kernel_final`, load 2.9-4.3, A2−A within ±2 ms:

| variant | what | split − A (ms) per session |
|---|---|---|
| `nlall` | scalar arithmetic of the rewritten chains removed (bound) | −47.2, −51.6, −54.6, −57.9 |
| `tcall` | tensor, Q tile via 64-bit `%` | +559.0, +558.7 |
| `tcm` | tensor, Q tile via Montgomery (**bit-exact**) | +169.6, +170.3, +169.9, +167.5 |
| `tcnoq` | tensor, **no Q build** (timing bound) | +19.6, +23.2, +20.9, +19.6 |
| `tcnomm` | … and no matmul: staging + combine + barriers | +4.5, +9.3, +2.9 |
| `tcnobar` | … and no barriers | +7.0 |
| `tcstonly` | staging stores only | −41.0 |
| `acc1` | chain-level accumulation in the cooperative tensor (`multiply_accumulate`, one combine per chain), Q via Montgomery (**bit-exact**) | +142.4, +140.6 |
| `acc2` | `acc1` without the Q build (**best case**) | **+5.7 [+4.9, +7.7], +0.3 [−1.7, +1.9]** |

Decomposition, relative to `nlall` (all medians from the `ev_tc3` session):
- staging stores +10.6 ms;
- per-block combine (16 threadgroup loads + 64-bit adds and folds) ~+48 ms;
- barriers ~+2 ms;
- matmul + D store ~+14 ms;
- in-kernel Q build ~+147 ms.

Per-chain accumulation (`acc`) halves the combine cost. Even then the best case, with free Q, is no faster
than today, and a precomputed Q table adds a 2 KB tile load per block per simdgroup on top. The microbenchmark
did not show this staging cost because its threads hold ~10 live values. The real kernel runs at the 18.9 KB
stack / 256-register limit, where every extra live value and memory operation costs. Section 1 shows the same
sensitivity.

Presence costs, measured separately (`ev_m4.log`, bit-exact):

| variant | split − A | stack |
|---|---|---|
| TU compiled with `-std=metal4.0` | +2.8 / +2.4 ms | identical to metal3.2: 2399592 B, 18928 B |
| + MPP headers | | identical to metal3.2: 2399592 B, 18928 B |
| + 16 KB threadgroup memory | +3.4 ms | |
| + one matmul2d per simdgroup at the kernel end | −0.6 ms | |

So Metal 4 itself is not the problem; the operand staging is.

**Projected eval gain** = chain share (≤ 67 ms, 10.4 %) − (tensor cost of the same chains):
- measured: −141 to −170 ms (bit-exact forms);
- with free Q: −6 to 0 ms;
- that is **≤ 0 %, under the 3 % rule. NO-GO.**

## 5. NTT estimate (step 4, estimate only)
The commits (data 217 + accum 113 ms per po2 20 segment) are NTT + Poseidon2 rows + Merkle folds. R19's
serialized profile puts the NTT kernels at ~24 % against ~31 % for Poseidon2, so the NTT is ~145 ms of the
330 ms.

A fixed-twiddle radix-32 block as a matmul:
- It is a dense 32x32 DFT: 32 field products per point per pass, against 2.5 for five radix-2 stages
  (12.8x).
- In the byte decomposition that is 512 byte-MACs per point per pass: 11.4 ps at 45 TMAC/s.
- The ALU does 2.5 Montgomery products in 3.8 ps at 0.66 T/s.
- So the matmul is **about 3x slower before any staging**.
- Radix 8 (8 against 1.5 products per point, 5.3x) at best breaks even before staging.
- Section 4 showed that staging alone costs about as much as the arithmetic.

**NO-GO** (a recommendation for future items, not built).

## 6. Runtime availability, toolchain, archives (step 5)
- **The M5 Max** (macOS 27.2.1, `host.m`) reports `supportsFamily`:
  - Apple10 = yes;
  - Apple9 = yes (families are cumulative);
  - Metal4 = yes;
  - maxThreadgroupMemoryLength = 32 KB.
- **Metal 4 is not a proxy for the matrix units.** `MTLGPUFamilyMetal4` is a feature-set family that M1-M4
  also report, so a tensor path would have to be gated on `MTLGPUFamilyApple10` (or newer) and on measured
  benefit.
- **M1-M4 would run `matmul2d` on the shader ALUs** (inferred, not measured: we only have the M5 Max). There
  it can be no faster than the shader's own int multiply. The half → float rate above is 4x the M5's fp32
  ALU rate, which shows what the accelerators add.
- **Compiling:**
  - a TU with MPP needs `-std=metal4.0`;
  - other TUs are unaffected;
  - compiling the evalfast TU at `metal4.0` gives byte-identical native code (section 4).
- **The runtime binary-archive path (R14) handles tensor kernels.** `N1_ARCHIVE` in `host.m` adds the PSO to a
  fresh `MTLBinaryArchive`, serializes it, reloads it and builds with `FailOnBinaryArchiveMiss`. That gave a
  hit (32-35 KB per kernel) for `mm_dev_u8_16x32x64_1`, `mm_tg_u8_64x64x64_4` and `ch_mm_32`.
- **The offline translator (`metal-tt`, used by R21's `agx_size.py`) fails on every MPP kernel:**
  `applegpu-nt: error: unsupported deferred-static-alloca-size function body in ...cooperative_tensor...`.
  The R21 stack-regime guard therefore cannot read a tensor kernel's stack.
- **Cooperative tensor layout** (`layout.metal`): implementation-defined and distributed.
  - Right operand, 16x32x128 NT: each lane holds 128 bytes spread over 8 points (dims {0-3, 16-19} for lane 0)
    and 16 k values.
  - Destination: each lane holds rows {0, 8} of 8 points.
  - A point-per-thread value cannot feed the operand from registers without shuffles or threadgroup memory.
    That is the staging cost section 4 measured.

## 7. Correctness, R17, budgets
- **Bit-exact:**
  - microbenchmark tensor chains = scalar chains (all 14 CHK comparisons of the final session and all of `chain2`, 0 words differ);
  - scalar = a Python reference;
  - real-kernel prototypes `tcm`/`acc1`/`tc14`/`tcall` = the built-in kernel on every run.

  The wrong-result variants are timing ablations by design. `ef_variant_bench` therefore exits with "a variant
  differs" in those sessions.
- **R17:** `ir_scan.py` gives tier A = B = S = 0 on:
  - `tput.metal` and `chain.metal` (both builds);
  - the real-kernel tensor prototypes (`acc1`, `tcm`);
  - the base TU.

  Tier C hits in the probe TUs are MPP-internal loops; nothing ships. No production kernel changed, so
  `run_stress.sh` was not needed.
- **Budgets / peak memory:** unchanged; nothing in the prover changed. The prototypes add 24 KB of threadgroup
  memory per 128-thread threadgroup, which is on-chip, not device memory.
- **Knob:** none. `RISC0_METAL_RV32IM_EVAL_TENSOR` was not added, because nothing is kept.

## 8. Tools (`tools/metal_audit/tensor_probe/`)
- `build.sh <dir>`: builds the host and the metallibs.
- `host.m`: a Swift-free Objective-C host.
  - It runs kernels interleaved in rounds and reports GPU-timestamp medians, min and max.
  - `:chk` groups compare output buffers word for word.
  - `N1_INA` / `N1_INB` load table files.
  - `N1_DUMP` writes the output buffers.
  - `N1_ARCHIVE` runs the binary-archive check.
- `tput.metal` / `tput.py`: step 1.
- `chain.metal` / `tables.py` / `run_chain.sh`: step 2.
- `count_chains.py`: chain counts of the generated TU.
- `mm_chain.py` / `real_kernel.sh`: the real-kernel prototype and ablations (step 3; switches `--acc`,
  `N1_QMODE`, `N1_NOMM`, `N1_NOBAR`, `N1_NOCOMB`).
- `layout.metal`: dumps the cooperative tensor layout.

## 9. Open issues / what would change the verdict
- **A cheap point-per-thread → operand path.** The tensor form would win only if the per-point terms could
  reach the matmul operand without threadgroup round trips, at less than ~1 ms of the ~58 ms.
  - One candidate is a future MPP layout where a lane owns its point's K column.
  - Another is a shuffle-based fill of the right-input cooperative tensor, not tried here: 32 shuffles per lane
    per block, probably no cheaper than the staging stores.
- **Restructuring.** If eval_check were restructured so that many points' c values are produced directly in
  threadgroup memory (e.g. a column-major pass computing c for a whole tile), the staging would disappear. That
  is a different kernel design (R18/R21 regime risk), not a chain rewrite.
- **Other GPU generations.** M5 Pro/Max successors could change the balance; the probe tools rerun as they are.
- **Offline translation.** `metal-tt` cannot translate MPP kernels, so `agx_size.py` and any stack-regime
  guard are blind to them. A future tensor kernel needs a runtime-only check.
