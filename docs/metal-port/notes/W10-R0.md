from **B** (the merge). Both builds used the same `METAL_TC` (env.sh, Metal 27B47, SDK 27.2) and the

## Cross-platform audit: fork tip vs origin/release-3.1

`git diff origin/release-3.1...metal/W10-R0 --stat`: 461 files, +146477 -27272. The merge base is
5beab26b5, so this is the whole fork delta. Of these files, 366 are Metal-only by path: `*/metal/*`
directories, `*.metal`, `docs/metal-port/`, `tools/{metal_audit,metal_aot,stock_verify31,hotbench}`,
and `*metal*` test and generator files. The other 95 files are classified below. Every new Rust
module under a `metal` directory is behind `#[cfg(feature = "metal")]` (or
`all(feature = "metal", target_os = macos|ios)`). Every sys crate and `zkvm/src/lib.rs` add
`compile_error!` for `metal` with cuda/rocm/intel, and for `metal` off macOS/iOS. The sys build
scripts gate every Metal step on `metal_enabled()` = `CARGO_FEATURE_METAL && target_os in
{macos, ios}`.

### Behaviour changes for non-Metal builds (assessed, also in open issues)

1. **K10 keccak right-sizing, executor level, every platform.** In
   `zkvm/src/host/server/exec/syscall/keccak.rs` a `ProveKeccakRequest` now carries the smallest po2
   of `KECCAK_PO2_RANGE` whose circuit holds its inputs, not the session's max. CUDA/ROCm/Intel/CPU
   provers and coprocessor callbacks therefore see requests of several sizes. The lifted receipt's
   control ID is that po2's `KECCAK_CONTROL_IDS` entry, under the same `KECCAK_CONTROL_ROOT`. The
   guest-visible batch-full signal still uses the max. Revert: `RISC0_KECCAK_RIGHTSIZE_PO2=0`.
   Not exercised on CUDA/ROCm/Intel here. The non-Metal keccak provers already take `request.po2`,
   since `keccak_max_po2` was always settable in 14..=18.
2. **Recursion ZK noise (B9-SEC and P31-09), every backend** (`recursion/src/prove/witgen.rs`).
   - Default path: `noise_seed()` is `None`, so `draw_noise` draws one `BabyBearElem::random` per
     cell from `rand::rng()`. That is the same RNG (ChaCha12 ThreadRng, OS-seeded) and the same
     per-cell distribution as stock 3.1 (`f68f86020`).
   - The draws now run on a helper thread (`EarlyNoise`, one spawn per recursion proof). Its own
     `ThreadRng` is seeded from the OS on first use. Revert: `RISC0_RECURSION_NOISE_OVERLAP=0`.
   - The seeded path (`with_noise_seed32`, 256-bit seed, SHA-256 domain-separated stream keys,
     `StdRng::from_seed`) is reachable only from the Metal seal check
     (`RISC0_METAL_REC_SEAL_CHECK`, `cfg(feature="metal")`) and tests.
   - `with_noise_seed32` is `pub(crate)`, and the 64-bit `with_noise_seed` is `#[cfg(test)]`.
   - No public API changes. Same distribution as stock on CUDA/ROCm/Intel/CPU.
3. **`get_zkr` program cache, every platform** (`recursion/src/prove/zkr.rs`).
   - `risc0_circuit_recursion::prove::zkr::get_zkr` now returns `Result<Arc<Program>>` (was
     `Result<Program>`): a **public signature change**. zkvm's caller uses `.into()` and compiles
     unchanged. zk-miner main does not call it (`git grep get_zkr origin/main`: none).
   - A per-process program cache (one decode per zkr, same bound as stock's word memo) is on by
     default everywhere. Revert: `RISC0_METAL_REC_ZKR_CACHE=0`, which applies despite the name.
4. **`CpuHal` paths** (Linux/Windows CPU-only builds).
   - rv32im `DROP_DATA_EARLY` (`rv32im/src/prove/witgen/mod.rs`): `CpuHal::has_unified_memory()`
     is true, so CPU proofs drop the data witness after `step_accum` at every po2 (upstream: po2≥22
     only). Nothing reads it afterwards, so seals are unchanged. Revert:
     `RISC0_METAL_DROP_DATA_EARLY=0`.
   - The CPU recursion witgen (`recursion/src/prove/hal/cpu.rs`) runs on a copy of the trace's
     cycles (8 B/cycle), because `readIOPBody` advances `iopIdx` in place. The first witgen over a
     pristine trace produces the same witness. Only re-runs (the validation checks) differ, and they
     now see the same input.
5. **Intel Groth16 `fast.rs`** (compiled for `intel` and `metal`).
   - G13's memoized graph build is the default: one inverse per distinct constant, parallel
     translation, SHA-256 overlapped with the parse.
   - The program is a releasable `Arc` (a failed first build is still remembered).
   - The graph file's identity (`fstat`, or size+mtime off Unix) skips re-hashing an unchanged file
     on rebuilds, and only Metal releases.
   - Same program. The digest is still checked on the first build.
   - Revert: `RISC0_G16_GRAPH_MEMO=0`, `RISC0_G16_GRAPH_REVERIFY=1`.
   - The `cfg(not(unix))` `file_id` (Windows Intel) could not be compiled here.
6. `RISC0_REC_HOST_CHAIN_MIN_LEN` now overrides the CUDA/ROCm host-chain length. The default (16)
   is unchanged.

## Open issues

- The six non-Metal behaviour changes above need a decision, and ideally a Linux CUDA/ROCm/Intel CI
  run, before zk-miner main relies on the fork for those platforms. The most visible are K10's
  right-sized keccak requests (executor level, every platform) and the public `get_zkr` signature.
- Windows targets and real non-Metal compiles were not checked here.
- The worker sanity used the P31-14 producer built from the merge, not a zk-miner worker (the pin
  belongs to the zk-miner merge agent).
- R17 `ir_scan.py` / `run_stress.sh`: not run. No kernel TU changed, and the metallibs are
  byte-identical.
