## Summary
- **No P0 and no P1 in R16's files.** One P1 in a file R16 does not own (witgen's unclamped
  `getDiffCount` index) goes to R17. The P2 hygiene findings in R16's files are fixed. Two P2s are
  left open for wave 5 (build time).
- **`--check` now covers the Metal outputs.** These outputs live in OUT_DIR and are never checked in.
  The checks run without a Metal build:
  - `accum_tu_gen.py --check` also translates `--metal` in both inline modes and checks `PINNED_METAL`.
  - New `cuda2metal.py check`: the `.metal.inc` files must be up to date, and steps and eval must
    translate with their pins.
  - `regen.py --check` already checked to_metal's pin (R12).
  - The R5 witgen generator is R17's (see the issues).

  Every generator command a build ran can be re-run with `--check` against that build's outputs.
  build.rs lists the commands in `$OUT_DIR/metal_generators.txt`, exported as `RV32IM_METAL_GENERATORS`.
- **The selftest and the checks are cargo tests**, in the new `tests/metal_generators.rs`, run by
  `cargo test -p risc0-circuit-rv32im-sys --features metal`:
  - `cuda2metal_selftest`;
  - `generator_ci_checks`;
  - `build_outputs_up_to_date`;
  - `check_detects_stale_output`: every OUT_DIR output, copied and changed by one line, must be
    reported out of date.
- **Compile-time logging.** With `RISC0_METAL_BUILD_TIMINGS=1`, build.rs prints cargo warnings with
  the seconds of each generator, each TU's `metal` compile, and the metallib total. A kernel-cache hit
  is reported as a cache hit. Without the variable it prints nothing.
- **New `rv32im-sys/README.md`.** It covers what is generated and where, what is pinned, how to
  regenerate, the checks, and the build knobs.

## Fix round 1 (review of round 0)
The blocking review finding was the flaky `check_detects_stale_output` (finding 15); the non-blocking
notes led to findings 16 and 17. Changes are only in `tests/metal_generators.rs`:
- `Scratch` guard: per-process (`std::process::id()`) and per-output scratch dir under
  `CARGO_TARGET_TMPDIR`, removed in `Drop` (also while unwinding from a failed assertion).
- `stale_check_concurrent_processes`: spawns this test binary three times, filtered to
  `check_detects_stale_output --exact`, started 0 / 1.0 / 2.5 s apart (in lockstep the copies are
  byte-identical and the old shared dir did not fail), concurrently with the in-harness copy; every
  child must pass. A `R16_STALE_CHECK_CHILD` env var stops the children recursing.
- `accum_check_detects_pin_mismatch`: imports accum_tu_gen, checks `metal_pin_check()` is clean, then
  bumps one pinned count per inline mode and requires a report naming that mode, and finally requires
  `main_cuda(check=True)` (the `--check` entry point) to exit non-zero.

The per-TU figure is the time from the start of the metallib compile until that TU's `.air` was
written. KernelBuild compiles the TUs concurrently (rayon), so it equals the TU's compile time as long
as the pool has at least 6 threads. That holds on every supported Mac: base chips have 8 or more CPU
cores. These are front-end compile times, not PSO creation times (R4/R6/R12 notes). No GPU phase
changed, so there is no peak-GPU-memory figure for this item.

## Assumed / not verified

  does not run them. `cuda2metal.py check`, `accum_tu_gen.py --check` and `regen.py --check` need
  only Python and could be added to the Linux CI job. No workflow file is in R16's scope.

  cache from `$HOME` on macOS. The new cache file appeared under the scratch HOME, so it did.
