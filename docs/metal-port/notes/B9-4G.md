## Profile before

Reproduced P31-14's failure with the unmodified producer (`logs/before_wpso_4g.log`, `P14_PREBUILD=worker`,
4 GiB): `allocating 4235118872 bytes for the Groth16 prover ... with 64946176 bytes already allocated would
exceed the limit of 4294967296`. Allocation trace: 29.9 MiB after the warmup, 61.9 MiB after the composite and
succinct proofs and `release_hal_buffers` (process-wide pipeline state in 16 MiB steps, never freed).

Where the 4 GiB check stood (P31-12 `logs/final_g10_split.log`, re-measured here in `b9_4g_tw_lent_bit_exact`):
- planned 4038.9 MiB, real growth 4008.0 MiB: the check carried **30.9 MiB more** than the prover allocates. That
  is `PLAN_SLACK` = 32 MiB, sized for `RISC0_G16_METAL_ARCHIVE=0`, where every key load builds the NTT plan's own
  pipelines after the check. With the archive (default since G11) the plan builds nothing; the real excess over
  the bare buffer sum is page rounding, measured 1.1 MiB.
- Real peak with the best PSO state (45.9 MiB): 4054 MiB = 42 MiB headroom; with the keccak PSOs the check fails.

So making the check exact gives back ~31 MiB (enough for 61.9 MiB, 26 MiB of real headroom, measured below),
but not the >= 128 MiB the item asks for. That needs ~106 MiB less real allocation at 4 GiB. Breakdown of the
split layout (P31-12): points 2421, compact coefficients 343, a/b 512, witness 191, NTT tables 128, MSM scratch
~412 MiB. Candidates:
- points, coefficients, a/b, witness: live for the whole proof (or reloaded per proof: tens of ms).
- **NTT twiddle table (n/2 Fr = 128 MiB)**: used only in the NTT stage. The MSM scratch's `sorted` buffer
  (16 windows x 6,257,165 x 4 B = 381.9 MiB) holds c during that stage (G10 alias, 256 MiB) and its tail
  (125.9 MiB) is free until MSM H's sort. 2.1 MiB short of the table (P31-12's open issue noted it).

## Change 2: `MemOptions::tw_lent`, the NTT twiddles in the MSM scratch (the 4 GiB layout)

- `ntt.rs`: `NttPlan::with_lent_twiddles(.., Some((buffer, offset)))` keeps the twiddle table in a caller's
  region instead of an own 128 MiB buffer (offset bound with `set_buffer`, kernels unchanged). The region is
  rebuilt before each use: the caller fills it with the byte 0x01 (`LENT_FILL_BYTE`; every limb 0x01010101 is
  a canonical Montgomery value K) and `encode_lent_twiddles` runs one `ntt_mul_powers` pass over n/2 entries
  with two small owned tables (lo = w^k, k < 2^12; hi = K^-1 w^(k 2^12), 1024 entries; 160 KiB), so entry j
  = K * w^(j mod 4096) * K^-1 w^(4096 (j >> 12)) = w^j, canonical, bit for bit the owned table.
- `msm.rs`: `MsmScratch::new_with_sorted(.., min_sorted)`: `sorted` grows to hold c (n Fr) and the table
  (n/2 Fr): 384.0 MiB instead of 381.9.
- `prover.rs`: with `tw_lent` the scratch is built first and the plan lends `sorted` at offset n * 32 (behind c).
  Each proof's first command buffer fills the region (same blit as a, b's zero fill); the NTT stage rebuilds the
  table first. witness_poly writes only c (before it); MSM H's sort, after the NTT stage, is the first writer of
  the rest of `sorted`. No allocation during a proof (asserted).
- **Layout choice** (`choose_layout`, under `Auto`): candidates fastest first: whole; split H; whole + lent;
  split + lent. The first that leaves `AUTO_HEADROOM_BYTES` (128 MiB, twice the largest pipeline set measured)
  of the room (fix round 1: the whole layout too, see below); else the smallest. At a 4 GiB budget (room
  4034-4050 MiB) that is split + lent in every order; at 8 GiB and the default budget whole. With `tw_lent`
  not `Auto` it is P31-12's rule exactly (whole whenever it fits).
- Knobs: `RISC0_G16_METAL_TW_LENT=on|auto|off` (default `auto`), `RISC0_G16_METAL_G10_OFF=tw_lent` (= off),
  `RISC0_G16_METAL_G10=0` (G9 layout), `MemOptions::parse("tw_lent=..")`. `BuildStats::tw_lent`,
  `MetalProver::tw_lent()` report the decision. `RISC0_G16_METAL_TW_LENT=off` + `RISC0_G16_METAL_PLAN_SLACK_MIB=32`
  is the base behaviour exactly (refused after the warmup, `head/knob_off_slack32.log`). Forcing `on` forces
  only the twiddles: with split H on `auto` it takes whole + lent at 4 GiB (peak 4072 MiB, `knob_on.log`).

### Tried and rejected: rebuilding the table with `ntt_powers`

The first version rebuilt the lent table per proof with the plan's own `ntt_powers` kernel (up to 22
