## Summary
- **eval_check is ~80% of a keccak proof and is ALU-bound.** Layout, threadgroup size, register budget,
  stage count, `constant` poly_mix and chunk size did not move it; a cheaper multiply did.
- **Winner 1: lazy multiply-accumulate** (translator rewrite, `RISC0_KECCAK_METAL_EVAL_MACC=strict` reverts).
  eval_check po2 17: median **686 vs 1217 ms** (min 615 vs 1096), po2 14: 132 vs 234 ms. The whole proof
  is about 35% faster: the review's interleaved process-level A/B (10 pairs, base `zkminer/metal` build
  vs K7, see "After") gives medians po2 17 **924 vs 1411 ms**, po2 18 **1822 vs 2817 ms**. The output is
  bit-identical to the CPU and to the strict kernels.
- **Winner 2: default chunk 32768 → 16384** (`RISC0_KECCAK_METAL_EVAL_CHUNK=32768` reverts). Speed is the
  same at po2 17 and faster at po2 14 (102 vs 132 ms). Peak GPU memory is **532 MiB lower** from po2 13 up:
  po2 17 3952 MiB (was 4484, so it now fits 4 GiB without shrinking the chunk), po2 18 7374 MiB (was 7906).
- **Winner 3: archive hash** (K8 finding 5; `RISC0_METAL_ARCHIVE_HASH=sha256` reverts). A sha256 over the
  per-MiB sha256s, computed on all cores. Warm-start hashing (key + checksum) drops from 39.5 + 58.7 ms
  to 4.8 + 5.3 ms (medians of an 11-pair interleaved A/B, fix round 1).
- **Archive cleanup** (K8 finding 4; `RISC0_METAL_ARCHIVE_KEEP=1` reverts). Up to 4 keys per unit are kept,
  least recently used first out, and keys unused for 30 days are dropped. Two binaries no longer evict
  each other.
- Rejected, with numbers below: stage counts 29/16/8, the 32-bit mulhi Fp multiply, tiled scratch,
  threadgroup size 64/128, the register-budget attributes (TG 128/1024), `constant` poly_mix, and chunk
  sizes 8192 and 65536. Round 0 had kept the tiled scratch and runtime-TG knobs although they showed no
  change; fix round 1 removed them (see "Fix round 1"). Not done: witgen bucket batching (witgen is ~4% of the proof). GPU fill/zeroize
  is already on the GPU (zkp `fill_u32` / `eltwise_zeroize_fp`, setup phase 4-11 ms).

## Measurement method
- The machine was shared throughout. Other agents' GPU benchmarks (G10, R14/R15, Z10) kept "Device
  Utilization" at 92-100%, and the CPU load average was 5-93.
- In-process interleaving: test `eval_check::tests::k7_eval_ab` (ignored) runs configurations A B C … A B C
  in one process, each call as the prover makes it (scratch allocated and freed, one sync). It reports the
  median, min and max, and asserts every output equals the first configuration's (and the CPU's with
  `K7_CPU=1`).
  - Metallib variants run in the same process: `K7_LIBS=path[@keccak_metal_eval.rs]` loads other
    metallibs, built by `mklib.sh` with a source transform or flags, or by keccak-sys with another stage

  - An A/A pair (the same config twice) gives the noise. Process-level alternation was unusable: one
    sample swung from 1.1 s to 7.5 s.
- Phase times: `tests::k7_phase_breakdown` (ignored) reads timestamps from the circuit HAL's phase marks.
  It times Metal proofs at po2 17 and 18 and, with `K7_CPU=1`, the CPU prover.
- Results that depend on the 40-core GPU are flagged below. No base-chip hardware was available.

## Change 1: lazy multiply-accumulate (`keccak-sys/build_metal_eval.rs`, `eval_check_prelude.h`)
- **What the code does now.** About 13.4k lines a cycle have the form
  `FpExt xB = xA + poly_mix[N] * xC;`. Each is 4 Montgomery products and 4 modular additions.
- **The rewrite.** The translator (`lazy_plan`, `emit_function`) finds chains of such lines, where `xA` is
  used only as the next line's accumulator. It emits 4 `uint64_t` accumulators per step:
  - **Start:** `raw(xA) << 32`, which is xA·R² in Montgomery terms (R = 2^32).
  - **Each step:** add the 64-bit product `raw(pm_j) * raw(xC)`, which is p·c·R².
  - **Fold:** when the next product could pass 2^64, `lazy_fold` reduces the high word mod P. It uses
    two conditional subtractions and no multiply. The bound is tracked statically in the translator
    (u128 arithmetic).
  - **End:** `lazy_ext` Montgomery-reduces each limb once.
- **Why it is bit-exact.** The result is the same field element in canonical form, so it is bit-identical.
  Multiplies per accumulate fall from 4 Montgomery products (16 hardware multiplies) to 4 widening
  products plus a share of the final reduction.
- **Counts (58 stages):** 13435 rewritten lines in 93 chains, 6644 folds. They are pinned in
  `k3_eval_translate::pinned_counts`.
- **Strict copy and the runtime switch.** Every stage is also emitted unchanged as `eval_strict_stage_<k>`
  (`EVAL_STRICT_STAGE_NAMES`).
  - These kernels are not in `METAL_KERNEL_NAMES`, so warmup does not build them.
  - The HAL builds them on first use when `RISC0_KECCAK_METAL_EVAL_MACC=strict`
    (`keccak_strict_kernels`). They go through their own archive, unit `keccakstrict`.
  - Cost of keeping the switch: the embedded metallib grows from 17.8 MB to 23.1 MB (lazy + strict
    stages, scatter, witgen arms), and the keccak-sys build compiles 116 stage files instead of 58.
    The keccak archive (lazy stages + scatter + arms) is 34.6 MB instead of 52 MB; the strict one
    (35.6 MB) exists only once strict was used.
- **R17 checks.** Every helper is `always_inline`, straight-line and works on scalars.
  - `tools/metal_audit/ir_scan.py --fail-tiers ABS` on all 117 keccak eval/scatter TUs (lazy and strict,
    -O2, build flags): 279 functions, call loops 0, A = B = C = S = 0, exit 0.
  - `run_stress.sh` (control, keccak_eval, keccak_witgen; 30 reps): the defect control fails 10/10 (the
    defect is present in this session). keccak eval_check po2 17 (lazy): 0/30 differ from rep 0, 0/30
    differ from the CPU. Witgen po2 17 and 18: 30 + 30 identical to the CPU. Logs in `stress/`.
- **Same experiment as a source transform** (`tools/lazy_macc.py`, metallib `var/lazy`) before porting it
  into the translator: po2 14 CPU-exact, 108.7 vs 171.9 ms; po2 17 min 611 vs 1068.

## Change 3: archive hash and cleanup (`archive.rs`, K8 findings 4 and 5)
- **Hash.** `chunked_digest` is sha256 over (length ‖ sha256 of each 1 MiB chunk), with the chunks hashed
  on `available_parallelism` threads. Any changed byte changes the result (test
  `chunked_digest_sensitivity`). It feeds the key and the file-name checksum.
  - `k7_archive_hash_cost` (fix round 1: interleaved, plain sha256 and the chunked digest alternated
    11 times, which goes first alternates, after one untimed call of each; `r1_hash_ab.log`), load
    average 14.1 / 22.3 / 35.9 before and after:

    | input | plain sha256 median [min..max] | chunked median [min..max] | per-pair chunked/plain |
    |---|---|---|---|
    | key: embedded metallib (23.1 MB) | 39.5 ms [38.9..44.6] | 4.8 ms [4.8..4.9] | 0.122 |
    | checksum: keccak archive (34.6 MB) | 58.7 ms [58.2..60.4] | 5.3 ms [5.2..7.2] | 0.090 |

    So a warm start hashes for ~10 ms instead of ~98 ms. The rest of the key (sha256 over < 1 KB of
    device/OS/kernel names) is the same in both forms. Round 0's numbers (40 → 5 ms key, 93 → 14 ms over
    K5's 49 MB archive) were best-of-5 runs one variant after the other and are superseded.
  - `RISC0_METAL_ARCHIVE_HASH=sha256` restores K8's digest. A different digest means different names, so
    the first start after switching rebuilds the archive once. This commit changes the metallib anyway,
    so every machine rebuilds once in any case.
- **Cleanup.** Archives of other keys are no longer all deleted on save (`prune_other_keys`).
  - The `RISC0_METAL_ARCHIVE_KEEP - 1` most recently used ones stay (default 4 keys per unit). A load
    refreshes the file's mtime.
  - Any key unused for 30 days is deleted.
  - Same-key leftovers and dead temp files are handled as K8 left them.
  - `RISC0_METAL_ARCHIVE_KEEP=1` gives the old rule.
  - Tests: `prune_keeps_recent_keys`, and `archive_roundtrip` (now expects the other key's archive to stay).

## Fix round 1 (review findings)
- **Tile layout and runtime TG removed** (blocking finding 1). Neither won in its A/B, so both are gone:
  `EvalParams` is back to K4's 32 bytes, `make_eval_ctx` is K4's `base + t` / `stride` again, the launcher
  has no tile rounding and no `Grid::Groups` path, and `RISC0_KECCAK_METAL_EVAL_TILE` / `_TG` and
  `set_eval_tile` / `set_eval_tg` are removed. The prelude is now exactly K4's plus the lazy helpers, so
  the strict kernels are K4's code again and the default path pays nothing for a tile. The measurements
  stay in "What was tried"; re-tuning layout and TG on 8-10 and 16-20 core GPUs is an open issue.
- **Tile out-of-bounds bug** (blocking finding 4: a non-power-of-two clamped tile when the budget halved
  the chunk, writing past scratch/carry). Fixed by the removal: there is no tile any more, every layout
  is K4's `scratch[i * stride + t]` with `count <= stride` asserted. The budget-halved, non-power-of-two
  and cached-stride paths are covered bit-exact against the CPU by `eval_check_shrinks_chunk_under_budget`
  (chunk halved to 4096 under a budget, scratch kept), `eval_check_multi_chunk` (partial last chunk and a
  cached stride larger than the chunk), `eval_check_strict_and_lazy_match_cpu` (chunk 3000) and the
  4/8 GiB suites. The review's repro (tile 4096, chunk 12288 halved to 3072) has no tile knob to set any
  more; the same chunk/budget without a tile is what `eval_check_shrinks_chunk_under_budget` covers.
- **Archive hash A/B** (blocking finding 2): `k7_archive_hash_cost` is now an interleaved A/B, numbers
  in Change 3.
- **K6 issues** (blocking finding 3): dispositioned below.
- Non-blocking: `keccak_strict_kernels` no longer calls `keccak_kernels` inside a `KECCAK_LIB`
  initializer (that was a re-entrant `OnceLock` init); it calls `keccak_kernels` first and then reads
  `KECCAK_LIB`. The `archive.rs` module doc now describes the keep-4 / 30-day cleanup. The host-memory
  and whole-proof wording above is corrected. The K4 small-stage merge is dispositioned below.
