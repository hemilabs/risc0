# G1: groth16 Metal plumbing

Branch `metal/G1`, based on `zkminer/metal` (`93978a8e8`, F0 merged). Scope: PLAN.md 4.5 row G1 as
amended by errata 8.1 (F2 added the feature lines and the Docker-fallback cfg arms; G1 does not
edit any Cargo.toml).

## What was done

- **`groth16-sys/build.rs` `build_metal_kernels()`**: compiles every `kernels/metal/*.metal`
  (sorted) with `KernelBuild::new(KernelType::Metal)`, flags `-std=metal3.2 -O2` (plan 2.8), the
  whole `kernels/metal` directory as a dependency (headers such as G2's `bn254.h` are part of the
  cache key and trigger rebuilds), and `cargo:rerun-if-changed=kernels/metal` so new files are
  picked up. Output `metal_kernels_groth16`, `GROTH16_METAL_PATH` as before (F2).
  - **Deviation:** `METAL_KERNEL_NAMES` is generated by build.rs into
    `$OUT_DIR/metal_kernel_names.rs` (included by `src/lib.rs`), scanned from the sources:
    `kernel void NAME` outside a template, `[[host_name("NAME")]]` for explicit instantiations,
    template definitions skipped, comments stripped, duplicate names fail the build. Reason: G2,
    G4, G5 and G6 add `.metal` files concurrently and none of them owns `src/lib.rs`; with a
    hand-written list every kernel item would edit G1's file.
  - With no `.metal` source (the state after this item) `metallib` cannot link zero objects, so
    build.rs writes an empty `metal_kernels_groth16.metallib` and an empty name list (and still
    prints the `cargo:metal_kernels_groth16=` link metadata).
- **Deleted `kernels/metal/noop.metal`** (8.2) and its `noop` entry; added
  `kernels/metal/README.md` (keeps the directory in git; documents the build rules and the
  conventions of plan 2.1-2.4).
- **`groth16-sys/src/metal/mod.rs`** (new; `pub mod metal` in lib.rs, re-exported at the crate
  root): `metal_preload(&SetupParams)`, `metal_prove(&ProverParams, &SetupParams)`,
  `metal_release()` with the `intel_*` signatures, plus `metal_supported() -> Result<()>` and the
  error type `MetalNotImplemented`. `metal_supported`/`metal_preload`/`metal_prove` return
  `MetalNotImplemented` ("the Metal Groth16 prover is not implemented yet ...; use the Docker
  prover"); `metal_release` returns Ok (nothing is cached; a caller releasing between proofs must
  not fail).
  - **Addition beyond the intel mirror:** `metal_supported()` is a cheap capability check that
    needs no proving key, so the groth16 crate can decide before computing a witness or looking up
    the rzup component. G7 makes it return Ok (and may check for a device).
- **`groth16/src/prove/metal.rs`**: rewritten from F2's stub as a copy of `intel.rs`
  (`preload`, `prestart`, `preload_srs`, `release_srs`, `shrink_wrap` with the key loader thread
  overlapping `fast::witness`, `[groth16-metal]` timings under `RISC0_VERBOSE`), adapted:
  - `enabled()` = `risc0_zkp::hal::metal::enabled("groth16")` (RISC0_METAL / RISC0_METAL_SKIP)
    && `RISC0_GROTH16_METAL_PROVER != "docker"` && `risc0_groth16_sys::metal_supported().is_ok()`.
    The last term replaces F2's `AVAILABLE` const: every `prove/mod.rs` cfg site already branches
    on `metal::enabled()`, so today all of them take the Docker/no-op path, and they switch to the
    GPU when G7 makes `metal_supported` succeed, with no further edits.
  - Automatic Docker fallback: `shrink_wrap_with` runs the GPU path and, if any error in the chain
    is `MetalNotImplemented` (checked with `err.chain().any(|e| e.is::<..>())`, so `.context()`
    wrapping does not hide it), logs at info and calls `docker::shrink_wrap`. `metal_supported()` is
    checked first, before the component lookup and the witness. `pre_gpu` runs exactly once on
    every path.
  - `shrink_wrap_with` computes the witness on a scoped helper thread while `pre_gpu` runs on the
    caller (CUDA's shape, cuda.rs `shrink_wrap_inner`).
  - Locking: `risc0_zkp::hal::metal::exclusive()` is held over the GPU part of the wrap (join of
    the key loader, `metal_prove`, reading the proof), over `preload_srs` and over `release_srs`.
    The witness runs before the lock (as CUDA takes its singleton only for the prove), so a CPU
    witness does not block STARK proofs on other threads. The loader thread does not take the lock
    (it would deadlock against the holder waiting on it, see F0's `exclusive()` notes), and the
    `prestart` background preload does not either (as CUDA's prestart). Consequence for G7:
    `metal_preload` must not use a `MetalHal`, and its key cache needs its own mutex because
    prestart's and shrink_wrap's loaders can run concurrently.
  - `prestart_key`/`prestart_key_go` stay no-ops (CUDA-only gating); `invalidate_caches` releases
    the in-memory prover (no disk caches on Metal); `preload_srs` treats NotImplemented as Ok.
- **`groth16/src/prove/mod.rs`**: doc lines only (`shrink_wrap_with`, `prestart_prover` mention
  metal). Every 8.1 cfg site already had a metal arm from F2 (verified by reading:
  `mod component`, `mod docker` via `not(any(cuda, rocm))`, `mod fast`, `mod metal`,
  `preload_graph`, `preload_graph_background`, `prestart_prover`, `prestart_key`,
  `prestart_key_go`, `preload_srs`, `release_srs`, `invalidate_caches`, `shrink_wrap_with`,
  `shrink_wrap`); `docker.rs` `fast_enabled` (both) unchanged.

No CUDA/HIP/Intel kernel code was ported in this item (plumbing only); the Rust host flow is
`groth16/src/prove/intel.rs` (whole file) plus the `shrink_wrap_with` helper-thread shape from
`groth16/src/prove/cuda.rs:416-475`.

`falls_back_to_docker` is the Docker-fallback acceptance test: it calls `docker::shrink_wrap`
(the CPU build's path), `metal::shrink_wrap_with` directly (bypassing `enabled()`, so it exercises
the NotImplemented fallback), `prove::shrink_wrap` and `prove::shrink_wrap_with`, and asserts all
four return the same error, none panic, `pre_gpu` runs exactly once, and, Docker not being
installed on this machine (`which docker` → not found), that the error is exactly
`Please install docker first.`.

Kernel-list generation was checked with a temporary `kernels/metal/zz_probe.metal` + `zz_probe.h`
(not committed): a plain kernel with `[[max_total_threads_per_threadgroup(256)]]`, a template
definition, two `[[host_name]]` instantiations and two commented-out kernels. Generated list:
`["probe_plain", "probe_tmpl_8", "probe_tmpl_16"]`; the metallib (10678 bytes) compiled through
KernelBuild (`xcrun metal ... -std=metal3.2 -O2`), and `kernel_names_match_library` loaded it with
`new_library_with_data` and found every listed name. Editing the header alone recompiled the
library. After removing the probe the list is `&[]` and the metallib is 0 bytes again.

## Assumed / not verified

- The Docker success path was not run (no Docker here); the fallback only reuses the existing
  `docker::shrink_wrap`, so its behaviour with Docker installed is today's.
- The GPU branch of `shrink_wrap` (component lookup, witness, loader, `metal_prove`, proof JSON)
  compiles but cannot run until G7; it is a line-for-line copy of intel.rs apart from the lock and
  the helper thread.
- The name scanner does not evaluate the preprocessor: a kernel inside `#if 0` would be listed
  and `load_library` would then fail fast on it (the intended safety net).
