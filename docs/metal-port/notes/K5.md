## What was done
- **`circuit/keccak/src/prove/hal/metal/archive.rs` (new)**: `ArchivedKernels::new(device, unit, metallib, names)`
  loads the metallib once and builds every PSO through a binary archive file.
  - Location: `RISC0_METAL_ARCHIVE_DIR`, else the risc0 cache dir that `risc0-build-kernel` uses
    (`directories::ProjectDirs("com.risczero","RISC Zero","risc0")` = `~/Library/Caches/com.risczero.RISC-Zero.risc0`)
    `/metal-archives/<unit>-<key>.binarchive`. `RISC0_METAL_ARCHIVE=0` disables it.
  - Key: first 24 hex of `sha256(metallib ‖ 0 ‖ device name ‖ 0 ‖ OS build ‖ 0 ‖ kernel names…)`. OS build is
    `ProductBuildVersion` from `/System/Library/CoreServices/SystemVersion.plist` (fallback `sysctl -n kern.osversion`).
    Writing a new archive deletes the unit's other `*.binarchive` files (stale keys).
  - Per kernel: (1) create the PSO with the archive attached and `MTLPipelineOptionFailOnBinaryArchiveMiss` (hit:
    stored binary, no compile); (2) on a miss, `addComputePipelineFunctionsWithDescriptor` (compiles into the archive)
    then (1) again, so a cold kernel is compiled once; (3) if the add or the reload fails, plain
    `newComputePipelineStateWithDescriptor` and the error goes into the report. Then the archive is serialized to a
    temp file in the same directory and renamed. A corrupt/unloadable file is deleted and replaced; a failed save
    only warns. The archive can never make a load fail that would have succeeded without it.
  - PSOs are built on `available_parallelism()` threads (no hard-coded core count). Concurrent adds to one archive are
    not documented as thread-safe; each add is verified by the fail-on-miss reload (fallback otherwise). In every run
    here (incl. 71 concurrent cold adds) there were no errors.
  - metal-rs 0.29 workarounds: raw `msg_send!` for `newComputePipelineStateWithDescriptor:options:reflection:error:`
    with nil reflection (the crate's wrapper wraps the nil reflection pointer); `URL::new_with_string` wraps an
    autoreleased NSURL as owned, which crashed (SIGSEGV) on drop — `file_url` retains it once.
  - `ArchiveReport { path, loaded, hits, misses, saved, errors, elapsed, add_time, save_time }`.
  - The module is unit-agnostic: rv32im/recursion (C11, M1) can hoist it into the zkp Metal HAL.
- **`hal/metal/mod.rs`**: `keccak_kernels(device)` (process-wide `OnceLock`, K4) now holds `KeccakKernels`
  (`ArchivedKernels` + registry id, asserted) built from `kernel_names()` = `METAL_KERNEL_NAMES` (scatter + 58 stages)
  + `metal_witgen::WITGEN_KERNEL_NAMES` (12 arms): **71 PSOs from one metallib load** (K6 loaded the metallib a second
  time for the arms, ~12.6 MiB). `pub(crate) fn warmup() -> Result<ArchiveReport>` builds them on the system default
  device without creating a `MetalHal`, so it takes **no GPU lock** (safe on a background thread beside a session,
  per M3's lock caveat); a panic from a broken metallib is caught and returned as `Err`.
- **`hal/metal/witgen.rs`** (K6's file, deviation): `witgen_pipelines`/`WitgenPipelines`/`warm_witgen_pipelines`
  removed; the arm dispatch uses `self.pipeline(WITGEN_ARM_KERNELS[cycle_type])`. Consequence: the arm PSOs are now
  built eagerly with the rest (first circuit HAL or warmup), not lazily at the first GPU witness.
- **`prove/mod.rs`** (K1's file, deviation, additive): `#[cfg(feature = "metal")] pub fn metal_warmup()` mirroring
  `risc0_circuit_rv32im::prove::metal_warmup` (honours `enabled("keccak")`, logs the report or the error).
  **Not wired into zkvm** (`prover_impl.rs::start_metal_warmup` is not mine) — see issues.
- **`zkvm/tests/k5_keccak_metal_e2e.rs` (new test)**: `claim_digest_matches_known` (host recomputation of the guest's
  inputs reproduces `tests/keccak.rs`'s po2 16/17 digests) and `keccak_e2e_po2_range` (`#[ignore]`, `K5_E2E_PO2S`,
  default 14..18): guest + keccak assumption, keccak proved on the selected prover and lifted, asserts the lifted
  receipt's `control_id == KECCAK_CONTROL_IDS[po2-14]` and `receipt.verify(KECCAK_ID)`.
- No `build_kernel` change (metal-tt evaluated by hand, below).

## Fix round 1
- **Budget suite was not deterministic (blocking finding).** The working-set budget
  (`RISC0_METAL_MAX_WORKING_SET_BYTES`) and `current_allocated_size` count the whole process's Metal memory, and
  the test harness runs tests in parallel: in the verifier's first 4 GiB run, K6's `metal_prover_uses_gpu_witgen`
  overlapped the po2 17 eval_check / K4 reuse tests and failed (`allocating 35913728 bytes for data with
  4274143232 bytes already allocated would exceed the limit of 4294967296 bytes`); later parallel runs passed. So
  the round-0 "pass 25/25" row for 4 GiB depended on scheduling. Fix: a test-only `gpu_test_lock()`
  (`hal/metal/mod.rs` tests, poison-tolerant `Mutex<()>`) that every test creating a Metal HAL takes first (guard
  declared first, so it is dropped after the HALs): `mod.rs` scatter x2, `metal_prover_runs_on_metal_hal`,
  `kernels_are_process_wide`, `warmup_builds_every_pso`, `metal_prover_reuse_under_budget`, `eval_check`,
  `metal_peak_memory`; `eval_check.rs` `matches_cpu` (→ `eval_check_matches_cpu`, `_po2_17`), `multi_chunk`,
  `shrinks_chunk_under_budget`, `stage_profile`; `witgen.rs` (K6's file, 3 one-line additions)
  `metal_witgen_matches_host`, `metal_witgen_rejects_inconsistent_scatter`, `metal_prover_uses_gpu_witgen`. The GPU
  tests now run one at a time under the default parallel harness; CPU-only tests (archive key, fit_chunk,
  run_buckets, vanishing quotients, …) still run in parallel. The budget command needs no `--test-threads=1`.
- `archive.rs` module doc corrected: adds to the archive are concurrent and unlocked (not "under a lock"), checked
  by the fail-on-miss reload with plain-PSO fallback.
- `archive.rs` build workers run each PSO build in `objc::rc::autoreleasepool` (the scoped threads had no pool, so
  autoreleased NSError/description objects leaked on a miss).
- `save_archive` also deletes `.<unit>-*.binarchive.tmp*` files older than 1 h (left by a process that died between
  serialize and rename; younger ones may be another process's write in progress).
- `k5_keccak_metal_e2e::keccak_e2e_po2_range` asserts, under `--features metal`, that
  `risc0_zkp::hal::metal::enabled("keccak")` holds, i.e. that `keccak_prover()` takes the Metal path; a disabled
  Metal backend now fails the test instead of passing on the CPU prover.
- Not changed: stale-archive cleanup still deletes the unit's other keys (see issues).

## Measurements (indicative; shared machine)
### Cold vs warm PSO creation, all 71 keccak PSOs (`archive_cold_warm_profile`, `scratchpad/K5/cachesize0_r2.log`, `profile1.log`)
How the OS cache was "cleared": deleting `$(getconf DARWIN_USER_CACHE_DIR)com.apple.metal` (1.5 GB, one cache shared
by every process of the user, i.e. every other agent) was not acceptable. `MTL_SHADER_CACHE_SIZE` (found among the
Metal framework's env strings in the dyld shared cache) set to `0` makes this process's PSO creation cold (no cache
read or write), which is what we need; this is undocumented Apple behaviour, observed only.
| Scenario | Time |
|---|---|
| OS cache warm, no archive (concurrent) | 0.05 s |
| OS cache **off** (`MTL_SHADER_CACHE_SIZE=0`), no archive, concurrent | 24.2 s (35.7 s in an earlier run); sequential (K4's loader) was 94-190 s per K3/K4 |
| OS cache off, fresh archive (miss → add → reload), concurrent | 24.3 s (adds 254 s summed over threads; serialize 0.14 s; 52 MB file) |
| first K5 design (plain PSO, then add) with OS cache off | 269.5 s (plain 58 s + sequential adds 212 s) → replaced by add-then-load |
| OS cache off, **archive hit, fresh process** | **0.05-0.07 s**, 71/71 hits |
| OS cache warm, archive hit, fresh process | 0.05-0.09 s |
So the archive makes a fresh process independent of the OS shader cache. The cold first build still costs ~25 s here
(more on 8-10-core base chips) and should happen at worker install/start via `metal_warmup` (M1).

### metal-tt offline archives (evaluation; manual, `scratchpad/K5/tt/`)
`metal-tt` is in the Metal toolchain (`$METAL_TC/usr/bin/metal-tt`). With a pipelines script
(`{"libraries":{"paths":[{"label":"keccak","path":"keccak.metallib"}]},"pipelines":{"compute_pipelines":[{"compute_function":"alias:keccak#<name>"},…]}}`)
`metal-tt -arch applegpu_g17s -macos-version-min 27.0 -o full.binarchive full.mtlp-json` builds an archive of all 71
kernels (without `-macos-version-min` it fails: "Architectures not supported for deployment target 'macOS 13.0'").
| arch | wall | CPU | size |
|---|---|---|---|
| applegpu_g17s (this M5 Max, `metal-arch`) | 55 s | 269 s | 34.1 MB |
| applegpu_g13g (M1 class) | 65 s | 275 s | 33.2 MB |
| applegpu_g16g (M4 class) | 50 s | 247 s | 34.3 MB |
`probe_archive_file` with the g17s file: **71/71 fail-on-miss hits** at runtime on this machine. Multi-arch in one
call failed for a mixed list (`-macos-version-min 14.0`: "image AIR version (2.9) is bigger than the one of the target (2.6)").
**Decision: not added to build.rs.** Every arch costs ~1 min wall / ~4.5 CPU-min per keccak-sys build and ~34 MB,
the arch list of consumer Macs (g13..g17 × base/Pro/Max variants) and the OS-version interplay are unknown, and the
runtime archive already gives a 0.05 s warm start after one ~25 s build. Possible later use (M1/M5 packaging): ship
offline archives for the common arches with the worker binary and load them as an extra read-only archive before the
runtime one (the code would just attach two archives); not verified on other machines or OS builds.

## Assumed / not verified / gaps
- `MTL_SHADER_CACHE_SIZE=0` as "cache cleared" is inferred from timing (0.05 s → 24-36 s), not documented.
- Concurrent `addComputePipelineFunctions` on one archive: worked every time here; guarded by the reload check.
- Not measured on a base-chip Mac (8-10 cores): cold build will be longer; the archive hit should stay sub-second.
- An archive from another OS build is never read (key); whether Apple's runtime would have accepted it is untested.
- Archive size 52 MB in the user's cache dir per (metallib, device, OS) — old keys of the unit are deleted on write.
- Two processes building the same archive at once both write it (rename is atomic; last wins; both valid).

## Issues for later items
- **M1 / zkvm owner (prover_impl.rs)**: call `risc0_circuit_keccak::prove::metal_warmup` from `start_metal_warmup`
  (it takes no GPU lock; safe to spawn beside rv32im's). The worker should run it at install/first start so the ~25 s
  (M5 Max; longer on base chips) cold build never lands inside a job; afterwards every process loads from the archive
  in ~0.05 s even if the OS shader cache misses. Still open from K6: narrow the host-witness cfg in `prover_impl.rs`.
- **C11 / R* / Z (zkp)**: `archive.rs` is unit-agnostic — move it into `zkp/src/hal/metal` and use it for
  `MetalKernels::new` (zkp, rv32im, recursion; C4/R4/R5 reported OS-cache misses of 47-95 s too).
- **K7**: the arm PSOs are now built eagerly with the stages (one load, concurrent): small-po2-only processes pay for
  them once (archive hit afterwards). metal-tt numbers above if offline archives are reconsidered.
- **Z6 / zkp**: budget overrun still panics (buffer.rs:49) rather than `Err` (po2 18 at 4 GiB).
- **Any later test author (keccak)**: a new test that creates a Metal HAL must take
  `hal::metal::tests::gpu_test_lock()` first, or the budget suite becomes scheduling-dependent again.
  `eval_check_shrinks_chunk_under_budget` (K4) could now assert chunk 4096 unconditionally; left as is.
- **Cache hygiene (open, not fixed)**: writing a new archive deletes the unit's other keys in the shared cache dir, so
  two binaries with different keccak metallibs on one machine (risc0 versions, worktrees) evict each other and pay
  the cold build on every switch. Fine for one production worker; an LRU/age-based cleanup would fix it.
- `warmup()`'s `catch_unwind` has no effect under `panic = "abort"` (only logging is lost; `keccak_kernels` would
  panic anyway).
