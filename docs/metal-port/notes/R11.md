## Summary
- **R11's gate as written ("all three GPU phases active") is NOT met.** The GPU witgen kernel (R5/R8, generated by `witgen_tu_gen.py`) produces wrong witnesses on large real segments. With `RISC0_METAL_RV32IM_GPU_PHASES=witgen` (the only all-GPU configuration), fix round 1 measured:
  - rv32im-torture po2 20, 3 segments × 5 reps: **15 of 15 proofs failed** (kernel fault 0x2);
  - sha256-chain po2 20, 2 segments × 4 reps: **8 of 8 failed** (kernel fault 0x2); bigint-mul po2 20/19: 8 of 8 passed;
  - R8's reproducer (`witgen_segment_file`, torture po2 20, 20 × par,single): **29 of 40 calls wrong**.

  So the opt-in all-GPU configuration fails most po2 20 segments of common guests. It is not "passing with an occasional flake": the all-GPU passes of `prove::`, `seal_matches_cpu`, the composite and the sweep only cover po2 13-17 test programs, simple_loop and M3's guest, which happen not to trigger it. The failures seen so far are clean errors (fault word or failed verification), never a verifying wrong seal, but R8 also saw silent wrong cells, so that is not guaranteed.
- **The fix is outside R8/R9/R10 code.** The defect is inside the generated kernel's execution (R8 note, "Kernel nondeterminism"; this note, "GPU witgen nondeterminism"). R11 owns R8's host glue (`hal/metal/witgen.rs`), not `witgen_tu_gen.py`, `cuda2metal.py`, `fp.h` or `rv32im-sys/build.rs`. Two rounds (R8 fix 1, R11) did not find a fix there. **Re-scope request to the plan owner (needs a PLAN section 8 erratum, which R11 cannot write):** R11 gates the default configuration (CPU witgen + GPU accum + GPU eval_check); the all-GPU gate (`witgen_segment_file` at 0 bad calls in ≥ 40 on ≥ 2 TU builds, plus the po2 20 torture and sha256-chain segments) moves to a named follow-up item that owns the witgen kernel generator and `fp.h` (R15 sub-track "single-buffer witgen bit-exact" or Z8).
- **The default configuration passes every gate:**
  - `prove::` (basic, multi_read, 46 riscv cases, fwd_rev_ab, the hal::metal tests);
  - CPU verification of every seal;
  - word-for-word seal equality with the CPU prover for a fixed `rand_z`, also under `--features witgen_debug` (14 segments in-crate; the reviewer's harness added 96 proofs at po2 14-16 over 16 zk-miner guest specs, and po2 20/21 torture and sha256-chain; fix round 1 re-ran po2 20 sha256-chain and torture: 8 of 8 equal to CPU);
  - the zkvm multi-segment composite → succinct round trip at po2 18 and 20;
  - a po2 14..21 sweep.
- The fwd_rev_ab "metal arm" compares Metal fwd with Metal rev witgen. In the default configuration both run the CPU witgen kernel, so it adds no GPU-witgen coverage; the CPU-vs-Metal check is `seal_matches_cpu`.
- No diffs were found in the R8/R9/R10 code paths that are on by default. R11's code changes are integration plumbing, a debug hook and tests (see "Changes").

## GPU witgen nondeterminism (R8's open issue): what R11 found
Reproducer:
- Segment: `/private/tmp/claude-501/-Users-user-zkminer/a30bccea-eec8-43d4-ac51-c5ccb6e4b957/scratchpad/R8/fix1/segs_torture20/seg0.postcard`.
- Script: `/private/tmp/claude-501/-Users-user-zkminer/a30bccea-eec8-43d4-ac51-c5ccb6e4b957/scratchpad/R11/repro.sh <variant|-> <reps> [modes]`.
- Variants are built with `/private/tmp/claude-501/-Users-user-zkminer/a30bccea-eec8-43d4-ac51-c5ccb6e4b957/scratchpad/R11/libs/build.sh` and loaded through `RISC0_METAL_RV32IM_METALLIB`.

1. **The wrong rows execute the wrong mux arm.**
   - I mapped the failing columns with a `LAYOUT_TOP` visitor. In the first bad row of a call (Mul0 minor 1 = SLLI, for example), the Metal values are the union layout of a different arm. For example, `s1.out` sits at col 34 (arm 2, MUL) instead of col 36 (arm 1). Cols 140/141 are arm 2's carries instead of arm 1's `shift_mul.low/high`.
   - This happens in a single-thread `fwd_stepExec` run too (R8's `seg_t20_fwd.log`). So a thread executes code of a branch its own data does not select. That is not a race between threads.
   - The affected majors are Mul0 (3) and Div0 (4). Both call `MultiplyAccumulate` inside a 4-7-way minor mux.
   - Across 150 failing calls, the first bad row was Mul0 minor 1 (83), Div0 minor 3 (33), minor 2 (23), and a few others.
2. **The failure rate depends on the exact instruction order, so a source change can hide it without fixing it.**
   - A witgen TU whose `Fp::mul` used a 32-bit 16×16-split Montgomery product failed 0 of 160 calls. The original 64-bit product failed 17 of 20 and 9 of 10, and `metal::mulhi` failed 78 of 80.
   - However, the same split product in different statement order failed 16 of 20. Its LLVM IR differs from the 0-of-160 build only in instruction order (`*.ll` in `libs/`). Built in-tree for every TU, it failed 21-26 of 40.
   - **So the "fix" was luck of scheduling, and I reverted it.** A guess about multiply-high hardware errata is not supported.
3. **Ruled out as the cause:**
   - Using the atomic `fetch_add` results of the lookup tables (15 of 40 still failed).
   - `MTLComputePipelineDescriptor.maxCallStackDepth`. The default is 1. Values 2, 4 and 8 still fail. 16 and above are rejected with "Compute pipeline exceeds available stack space" at 256 threads. With `[[max_total_threads_per_threadgroup(32)]]`, depths up to 24 are accepted and still fail.
   - Threadgroup size 32.
   - Everything in R8's list.
4. **Metallib detail found on the way.** `metal-nm` shows linkonce_odr helpers (`load(ExecContext&, BoundLayout<Reg>, size_t)`, `inv_chain`, `operator*(FpExt, FpExt)`, …) defined in both `witgen_tu.air` and `accum_tu.air` (and `eval_check.air`). The metallib link keeps one copy. The sources are identical, so this is not a semantic bug. However, it means a change in one TU changes the code of another, which matters for any experiment like (2).
5. **Conclusion:** a lane runs instructions of an arm it did not take. This is load- and schedule-dependent and happens even in a single thread, which points at the Apple GPU backend compiler, or a hardware or driver effect, for this deep, divergent call graph. It could not be fixed in R8/R9/R10 code. accum and eval_check, which are translated kernels too, showed no mismatch in any run: seal equality on 14 segments × 6 runs, R9's 10-rep accum test, and R10's po2 16 eval test.

### Blocking findings
1. **"All three GPU phases" gate not met.** Confirmed, not fixed (see Summary for the re-scope request and the measured failure rates). `CPU_WITGEN` stays the default.
2. **The review's lead (uninitialized mux results in the generated code) is not the cause.** Checked:
   - In `witgen_tu.metal` the "uninitialized" locals (`ValU32Struct x6;`, `Val x8;`, about 80 of them) are *default-initialized class objects*, not uninitialized scalars. `Fp` has `constexpr Fp() : val(0) {}` (`risc0/build_kernel/kernels/metal/fp.h:92`), `FpExt()` default-initializes its `Fp elems[4]` (fpext.h:47), and every `*Struct` in `rv32im-sys/kernels/metal/types.metal.inc` has only `Val`, `ExtVal`, `ValNArray` (`r0::array` of Val) or other `*Struct` members (checked with an awk pass over every `struct *Struct` body). So C++/MSL default-initialization runs `Fp()` on every leaf: the mux result is 0 on the assert-only fall-through, never an indeterminate value, and no read is undefined behaviour.
   - R8 fix 1 also compiled the TU with `-ftrivial-auto-var-init=zero`: still 7 of 10 calls bad (R8 note, "What was ruled out").
   - Value-initializing the results in the translator would therefore change nothing semantically; I did not spend a GPU run on it.
3. **Report wording.** The note (Summary) and the report now state the all-GPU failure rates on real po2 20 guests plainly.
