# P31-05: rv32im accum and witgen Metal paths on 3.1 (2026-11-16)

Branch `metal/P31-05` (worktree `deps/risc0-3.1-wt-P31-05`), based on `metal/P31-03` `5e9603212`.
Plan: `scratch/r31/PORT_PLAN.md` 1.1 rows 6-7, section 5 row P31-05, risk 1. Scratch and logs:
`scratch/w8/P31-05/`. Chain: P31-02 -> P31-04 -> P31-03 -> **P31-05** -> P31-06.

**Result.** The 3.1 regenerated accum and witgen call graphs are CPU-exact on Metal. The audit
found no divergence in any hand-written Metal counterpart, so no kernel, generator or Metal header
changed. The one code change is in a test: `witgen_segment_file` gets a `hal` mode. Without it, the
`RISC0_METAL_RV32IM_CPU_PHASES=witgen` gate tested nothing (see "Change").

## Change: `witgen_segment_file` mode `hal` (test only)

`witgen_segment_file` calls `metal_witgen` directly, so `RISC0_METAL_RV32IM_CPU_PHASES=witgen`
(read only in `MetalCircuitHal::generate_witness`) never affected it. A first run with the env
set gave the same per-call times as the default (sha seg0 `par` 95-210 ms against 93-202 ms):
that run tested only the GPU kernel. The new mode `hal` (`hal_witgen`) runs
`WitnessGenerator::new` with the circuit HAL itself, so the production dispatch picks the GPU
kernel or the CPU fallback. It then compares data and global after WitnessGenerator's zeroize
with the CPU reference. It does not observe `data_in`/`pf_out`. A failed witgen or missing
buffers count as a failure instead of panicking in the length assert. The other modes are
unchanged. File: `rv32im/src/prove/hal/metal/witgen_tests.rs`.

## Open issues

- **`r17_accum_segment_stress` vs W7-R2's early data drop** (accum/tests.rs, owned by P31-06/R1).
  The test calls `WitnessGenerator::accum` repeatedly on one generator. Since W7-R2,
  `accum()` sets `self.data = None` on unified-memory HALs, so the second call panics with
  `witgen.data missing` (witgen/mod.rs:504). The same code is on the frozen 3.0 tree. This is a
  test-harness break, not a kernel problem: the run with `RISC0_METAL_DROP_DATA_EARLY=0` is clean.
  Fix options: the test sets the env per process or re-creates the generator per rep, or
  `run_stress.sh` exports the knob. Until then, P31-16 must pass `RISC0_METAL_DROP_DATA_EARLY=0`
  with `rv32im_accum`.
- **GPU witgen does not reject a bad `totalCycles`.** `eqz` is a no-op in the Metal (and CUDA)
  witgen. A wrong `totalCycles` global would therefore surface in eval_check/verification, not in
  witgen, unlike the CPU kernel that 3.1's `total_cycles_mismatch_fails` exercises (that test uses
  the CPU HAL explicitly and passes under `--features metal`). The global is built on the host
  from `segment.po2`, so the honest prover cannot produce it. P31-06's seal-equality and verify
  runs cover the honest path; a Metal-side tamper test is optional.
- `run_stress.sh` has no rv32im witgen family. The witgen R17 gate is the `witgen_segment_file`
  reproducer above (as in W7-merge-rv32im).
- Not run here: seal equality and verify on 3.1 segments (P31-06), the full P31-16 battery
  (`-O0/-Oz/-Os` stress amplifier runs; this item scanned the IR only at those levels).
