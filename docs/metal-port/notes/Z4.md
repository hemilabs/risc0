## What was ported (from `risc0/sys/kernels/zkp/cuda/`)
| Metal | CUDA source | Notes |
|---|---|---|
| `batch_evaluate_any` | kernels.cu:46-78 | 1:1. Each threadgroup is one eval point; the 256 threads are CUDA's `getCachedSimpleConfig` block (maxThreads/4). Threadgroup memory is 256×16 B = 4 KB of dynamic memory. FpExt has no `+= Fp`, so `tot += FpExt(c)` is used instead (same value). |
| `eu2_pows` / `eu2_main` / `eu2_reduce` | kernels.cu:187-387, **non-HIP branch** (pairwise `eu_redc_pair`) | `__launch_bounds__(256)` becomes `[[max_total_threads_per_threadgroup(256)]]` (eu2_reduce: 32). `__ldg(uint4*)` becomes a `const device uint4*` load; 16-B alignment is guaranteed by the gate. `__shfl_down_sync` becomes `simd_shuffle_down`. SIMD width is 32, the same as a warp, so the reductions map 1:1; per D0, out-of-range lanes return their own value as in CUDA, and only lane 0 is used. `__shared__ FpExt red[8]` becomes raw `threadgroup uint32_t[32]`. The 64-bit REDC formulation is kept verbatim. |
| ffi.cu `risc0_zkp_cuda_batch_evaluate_any` (ffi.cu:293-358) | `eval.rs::eval_plan` / `batch_evaluate_any` | The gate is the same: Horner if `nEvals == 0 \|\| deg < 4096 \|\| deg % 4096 != 0 \|\| coeffs & 15`. The coeffs address is `BufferImpl::as_device_ptr()`, so slice offsets count. S selection uses CUDA's `targetBlocks = 1024`, not HIP's 512. The launch shapes are unchanged: pows `nEvals×256`, main `(S, nEvals)×256`, reduce `nEvals×32`. CUDA's stream-ordered scratch becomes three pooled `alloc_buffer`s; F0's pool returns them only after the batch completes. Everything is encode-only, with no sync. |
| `mix_poly_coeffs_v2` | kernels.cu:389-455 | 1:1, except threadgroup data is read and written as raw words. |
| `mix_poly_coeffs_v2_dcids` | the same v2 code with `TG_CIDS=false` | Combo ids are read from device memory, so the table is 16 B per input. This answers open question 4 (see below). |
| `mix_poly_coeffs_v1` | kernels.cu:158-185 | 1:1: thread 0 fills the power table. |
| ffi.cu `risc0_zkp_cuda_mix_poly_coeffs` (ffi.cu:245-275) | `eval.rs::mix_plan` / `mix_poly_coeffs` | CUDA uses v2 for `inputSize ≤ 2048` and v1 above that (with 40 KB shared). Metal: v2 for `≤ 1638` (20 B × 1638 = 32760 B); **v2_dcids** for 1639..2048 (≤ 32768 B); table-less `mix_poly_coeffs` above 2048. The grid is `ceil(count/256)` groups × 256 (uniform groups; the kernel returns after the barrier when `idx ≥ count`). Threadgroup bytes are asserted on the host against `min(32768, device.max_threadgroup_memory_length())` before dispatch, and F0's runtime asserts them again. ROCm v6 is not ported (plan). |

All kernels are exact field arithmetic with canonical outputs, so every path is bit-identical to the CPU HAL. The tests verify this.

## Open question 4 (decision: Z4)
At count 2^18, using 20 dispatches per batch averaged with wall time / 20, measured twice on a shared machine (load average ≈ 7–8; the numbers are indicative), times in ms:

| inputSize | NoTable | V1Table | V2DeviceCids | V2 |
|---|---|---|---|---|
| 100 | 1.46 | 0.51 | 0.45 | 0.45 |
| 1000 | 14.17 | 4.76 | 3.16 | 3.29 |
| 1638 | 23.2 | 9.60 | 5.85 | 6.84 |
| 2000 | 28.3 | 14.2–14.3 | 8.5–9.4 | — |
| 2048 | 29.1 | 14.3–14.4 | 8.8 | — |
| 2500 | 35.5–35.8 | — | — | — |

Decision: for 1638 < inputSize ≤ 2048, use v2 with combo ids read from device (`MIX_MID_KERNEL = V2DeviceCids`). It is about 1.6× faster than v1-with-table, which the plan row had named. v1 remains compiled and tested (forced) as the alternative.

Observation for Z9, not acted on: V2DeviceCids also matched or beat V2 at ≤ 1638. At 1638 it was 5.85 vs 6.84 ms, probably because the smaller table allows more resident threadgroups. I kept the plan's v2 gate at ≤ 1638. Above 2048, a partial-table v2 could replace the table-less kernel, which is about 2× slower.

## Assumed / gaps
- **Untrusted indices are not checked.** No fault flag is set for out-of-range `which[e]` or `combos[i]`. These come from the prover, not from untrusted input; the CPU HAL would panic, while Metal would read or write out of bounds.
- The Horner path assumes 256-thread groups, CUDA's `maxThreads/4` on 1024-thread devices. The kernel itself uses `threads_per_threadgroup`, but the 4 KB threadgroup size is computed for 256.
- 64-bit multiplies in `eu_redc_pair`/`mx_redc_pair` are kept verbatim. Per D0 they are ~4–5× slower than 32-bit. A `mulhi`-based REDC is a Z9 item; any exact formulation stays bit-identical.
- The timings are wall-clock over a batch on a loaded machine, not GPU timestamps.
- `multi_poly_eval` (legacy) is no longer called, but its name is still in `KERNEL_NAMES`; Z7 retires it. The legacy table-less `mix_poly_coeffs` changed signature (params struct): nothing outside `eval.rs` calls it.
