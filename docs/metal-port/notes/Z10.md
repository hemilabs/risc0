## 1. Profile before (CPU identity_p254)

- `z10_profile_cpu_p254` (WIP session, `profile_cpu.log`): a po2 18 p254 recursion proof takes 14.2-14.9 s on the CPU prover. 11.8 s of that is Poseidon254 Merkle hashing (data group 128 cols x 2^20 rows: 5.8 s rows + 0.8 s tree; code/accum/check: 0.7-1.4 s each). The same proof with Metal poseidon2 takes 0.21-0.43 s. So the hash is the entire cost, and everything else in the Metal recursion HAL (C6-C8) already runs on the GPU.
- In the wrap (my run, 7 cold processes, `abwrap/`): CPU identity_p254 has a median of **16.5 s** [15.7, 29.1].

## 2. Kernels

- Inputs and outputs match the CPU suite exactly:
  - fold: canonical Fr digests (8 LE u32).
  - rows: column-major BabyBear Montgomery words. Each value is decoded to canonical form and packed 8 per Fr as sum v_k p^k (Horner), absorbed 2 cells per permutation into cells 1 and 2 (cells 1 and 2 reset, cell 0 carries). A short last block is zero-padded, which equals the CPU's zero cells. Zero columns give the zero digest.
- Arithmetic variants (`RISC0_METAL_P254_KERNELS`):
  - `w64` (default): CIOS with 64-bit multiply-accumulate in the redundant range [0, 2r), fused 3-term dot products with the constants (one reduction per word), and straight-line SOS squaring.
  - `w64c`: the same, but squaring is done by CIOS multiplication.
  - `ref`: bn254.h `Fr` (fully reduced, 32-bit carry chains). This is the CUDA kernel's arithmetic and the revert path.
- Bound check (reviewed):
  - mul with a, b < 2r gives < 4r^2/R + r < 1.76r. RR*x gives < 2r. from_mont gives <= r, then one subtraction.
  - dot3k gives < 6r^2/R + r < 2.13r, then csub 2r. add stays < 4r < 2^256, then csub 2r.
  - The SOS top word is 0 because a^2 < 2^510.
- Measured A/B (kernel level, WIP session, `bench_sos.log`, 7 reps interleaved, whole po2 18 hash set):

  | variant | median | min | max |
  |---|---|---|---|
  | w64 | 965 ms | 962 | 1108 |
  | w64c | 1041 ms | 1029 | 1205 |
  | ref | 2112 ms | 2041 | 2443 |

  - A product-scanning port of the Intel kernel ("Opt") measured 4858-5171 ms and was removed.
  - Threadgroup size (`bench_tg.log`, 32..1024): 128-512 are equal within noise. 32/64 are worse. The default is `Grid::Threads`, which takes the PSO's `maxTotalThreadsPerThreadgroup` (1024 for all six) capped at 256. Nothing depends on core count.
- **Whole-proof A/B, mine** (`ab_kernels_proof.log`, 7 interleaved pairs, 3 proofs each, po2 18, GPU shared; load 41 -> 5):
  - w64: median of pair medians **2.81 s** [0.97, 3.33].
  - ref: **4.49 s** [1.96, 4.95].
  - w64 won all 7 pairs. In the one quiet pair it was 0.98 s vs 1.96 s.
- CPU crossovers (`RISC0_METAL_P254_CPU_TAIL`, `RISC0_METAL_P254_CPU_ROWS`): rejected as defaults, kept as knobs.
  - Alone they are faster for the tree tops (2^8 tree 6.9 -> 0.9 ms).
  - A whole-proof A/B (WIP session, `ab_tail_prover*.log`, 7 pairs, twice) gave 0.896-0.904 s either way, which is "no change".
- R17: every function is `always_inline` (pragma, including bn254.h). The state is 3 scalars, and no aggregate is passed by value out of line.
  - `ir_scan.py` on poseidon254.metal at -O0/-O1/-O2/-Os (`-std=metal3.2`) found **6 fns, A = B = C = S = 0**.

## 5. Wrap peak: release before identity_p254

- Measured problem: with p254 on Metal, `metal_wrap_after_stark` at 8 GiB peaked at **6800.8 MiB**, against 5653.5 MiB with the CPU p254. The cause is the identity_p254 HAL (1.44 GB) allocating beside the STARK pools held on the thread (5395 MiB). Those pools were only released later, by `shrink_wrap_with`'s callback.
- Fix: on Metal, `succinct_to_groth16` calls `prover_impl::release_cached_provers()` before identity_p254. The memory is released anyway a few seconds later, and the next session rebuilds the provers either way. The zk-miner worker does not prewarm p254, so nothing is lost.
- Knob: `RISC0_METAL_WRAP_EARLY_RELEASE=0` keeps the old order.
- Result at 8 GiB: peak **5653.5 MiB** (= the pre-Z10 wrap peak; the 5.7 GB key dominates). With the knob at 0 it was 6800.8 MiB.
- Budgets:
  - The p254 prover alone peaks at 1,443,741,696 B at no budget, 8 GiB and 4 GiB. Seal tests pass at 4 GiB.
  - At 4 GiB the wrap fails in both modes, at the Groth16 key load (5.93 GB > budget). This was known before (G8 / G9 / G10), and identity_p254 itself got through.
- Peak memory is not raised by Z10 at either budget.

## 6. Wrap A/B

### Cold processes

`metal_wrap_after_stark`, no budget, 7 interleaved pairs, one process per run, load 5.8 -> 29.7, `r2/abwrap/summary.txt`:

| | CPU p254 (A) | Metal p254 (B) |
|---|---|---|
| identity_p254 | 16.54 s [15.70, 29.06] | **2.61 s** [1.30, 4.29] |
| shrink_wrap | 6.66 s [3.58, 26.27] | 10.50 s [7.06, 12.22] |
| total wrap | 24.70 s [19.27, 45.35] | **13.11 s** [8.42, 16.50] |
| peak | 5653.5 MiB | 5653.5 MiB |

shrink_wrap got slower in B, and the verbose breakdown shows why. In a fresh process, Groth16's `prestart` builds the witness graph on a background thread (`fast::preload`, ~4 s, cached for the life of the process). The CPU identity_p254 used to hide it. Now it is on the path: `witness=` is a median of 4.0 s in B vs 1.6 s in A. The GPU part is the same (2.6-3.2 s). A long-lived worker pays this once per process, so its steady-state wrap should be about identity (1.3-2.6 s) + shrink_wrap (~3.6 s).

### Worker-style

Several jobs in one process, scratch bench `scratchpad/w5/Z10/wrapbench`, po2 20, 2^21 cycles. See `r2/worker_ab.log`.

Two processes per arm, interleaved cpu, metal, cpu, metal, 3 jobs each, so 6 jobs per arm. That is **fewer than the 7 pairs the protocol asks for**. The GPU was saturated by other agents throughout (load 24-54; STARKs of the same job took 8-503 s).
