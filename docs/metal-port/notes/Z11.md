## Profile before
I applied temporary timers to `fri_prove` (`fri_prof.patch`, not committed) and ran `prove_po2_sweep`
(`R11_PO2S=20 R11_CPU=0 R11_REPS=4 RISC0_VERBOSE=1 Z11_PROF=1`; `prof_A.log`). The phases are:
- rounds+final: the FRI fold rounds, their commits and the final polynomial (GPU work);
- inner: the openings of the code, data, accum and check trees at 50 queries;
- roundq: the openings of the FRI-round trees;
- write: the IOP writes.

| po2 20, reps 1-3 | rounds+final | inner | roundq | write | `fri=` (verbose) |
|---|---|---|---|---|---|
| A (unmodified) | 6.5-6.8 ms | **11.7-14.2 ms** | 0.3-0.8 ms | 0.03 ms | 18.6-21.9 ms |

On unified memory, `batch_prove_many` fell back to a serial per-tree `batch_prove`. It read
`matrix[row + i * row_size]` one element at a time on one thread: 50 x (211 + 103 + 16 + 1) ≈ 16.5K
strided reads, plus ~3.4K sibling digests through the default per-index `get_at`. The GPU is idle the whole
time.

**Why it is slow: first-touch page faults, not the loop.** I added a diagnostic that ran the same
`gather_multi` twice. The second pass took **0.07-0.38 ms**, against 3.4-4.4 ms for the first, parallel
pass. Each strided column read lands on its own 16 KB page of a buffer the GPU wrote, and the CPU mapping
of those pages is gone by the next segment, even for pooled buffers. That is also why the LEADS
microbenchmark, which used pre-faulted malloc memory, predicted 0.35 ms where the real floor is ~3.5 ms.
Inside the parallel gather, the digests took 0.1-0.6 ms and the columns ~3.5 ms (`z11gm` lines, quiet
reps).

## Change
- `zkp/src/hal/metal/query.rs` (new) overrides two `Hal` methods for Metal.
  - `gather_multi` syncs each tree's matrix and node buffers once, through `view`, on the calling
    thread. It then splits the work into one task per (tree, query) column plus one task per run of 32
    sibling digests, across all trees, and runs them in one rayon `for_each`. Each task writes a
    disjoint slice of the output. The values and their order are those of `gather_samples` /
    `batch_get_digest_at`, so the assembly in `merkle.rs` and the IOP order are unchanged.
  - `batch_get_digest_at`: one sync, then the reads; above 64 indices the reads run in parallel. This
    covers the single-query `MerkleTreeProver::prove`.
- `zkp/src/hal/metal.rs`: `mod query;` and the two overrides, 26 lines.
- `zkp/src/prove/merkle.rs`:
  - `batch_prove_many` now always offers the jobs to `Hal::gather_multi` first, through the new
    `try_gather_multi`. Before, a unified-memory HAL never reached it.
  - `batch_prove` on unified memory also tries `gather_multi` with its one tree. This covers the
    po2 >= 22 low-memory path in prover.rs.
  - Other HALs are unchanged:
    - CUDA/ROCm (not unified) take exactly the old path.
    - The CPU HAL's `gather_multi` returns `None`, so it falls back to the old per-tree path. The only
      extra cost is computing the sibling indices once more (microseconds).
- **Revert knob:** `RISC0_METAL_QUERY_PAR=0`, read per call. With it set, `gather_multi` returns `None`
  (back to the serial per-tree path) and `batch_get_digest_at` does one `get_at` per index, as before.
- Rayon workers only read host memory. They never call the HAL, so the `exclusive()` rule in metal.rs
  holds.
- No kernel was changed, so R17's IR scan and stress runs do not apply. GPU memory is unchanged: the
  outputs are host `Vec`s, the same as before.

### Tried and rejected: gather on the GPU (`gather_sample` per query)
The variant (`Z11_GPU`, prototype only, not committed) launched one `gather_sample` per (tree, query)
into one pooled buffer and synced once; the digests stayed on the host. Its encode time was 0.03-0.06 ms
and it avoids the page faults, but the wait-and-read took 1.5-14 ms on the shared GPU. In `ab1.log` it
measured query **-6.24 [-104.4, +28.0], 8/9**, against **-11.71, 9/9** for the host path. The FRI-round
trees came out worse than on the host (1.5-4.5 ms against 0.3 ms). It was rejected because it depends on
GPU queueing, which a host-side phase does not. It might be re-checked on a quiet GPU, but the host path
is already within ~3 ms of zero.

## Not done

  own:
  - enabling `EVAL_U_EARLY` beyond ROCm;
  - moving the fault-word syncs and the accum permutation build.

## Open issues
- The ~3.5 ms that remains is first-touch page faults on GPU-written pages. Two ways to remove it:
  - a GPU gather when the GPU is quiet (above);
  - keeping CPU mappings warm across segments, which nothing in the Metal API offers directly.
- The worker A/B needs a quiet machine (expected about -0.1 s on memory-merkle and ~-2 s on the full
  benchmark).
