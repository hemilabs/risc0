### Sequence (GPU scans, the default)
1. If a perm is built: `try_sync`, then `build_perm` on the CPU (unchanged from R9).
2. All in one batch, with no wait between them:
   - blit-fill the fault word;
   - `stepAccumA`;
   - `fpScanReduce`: groups (blocks, 4);
   - `fpScanBlockSums`: groups (1, 4);
   - `fpScanApply`: groups (blocks, 4);
   - `finalizeZeroizeAccum`.
3. One `try_sync`, then read the fault word. Any bit is an `Err` that names the bits.

R9 waited 3 times (perm, after stepAccumA, end). Now there are 2 (perm, end), and none when there is no perm. The CPU round trip in the middle of the phase is gone.

### Kernels
- **Algorithm:** reduce-then-scan. Pass 1 sums each block, pass 2 does an exclusive scan of the block sums per column, pass 3 does a threadgroup scan of each block from its carry-in, in place. That is 3 passes over the data: read, read, write.
  - I chose this over scan-then-apply, which needs 4 passes.
  - I did not use decoupled look-back. It depends on forward-progress guarantees between threadgroups that Metal does not document.
- **Block size:** 4 rows per thread × the threadgroup size. The threadgroup is 256 by default, capped by every scan PSO's maximum and rounded down to the SIMD width (`fp_scan_tg`).
- **No hard-coded core count or SIMD width:** the width comes from `[[threads_per_simdgroup]]` and from the PSO's `thread_execution_width`. The host checks that the simdgroups per threadgroup are ≤ min(width, 32).
- **Large inputs:** pass 2 loops in chunks with a running carry, so any number of blocks works. 2^20+7 rows gives 1025 blocks at tg 256, which is more than one chunk; the tests cover it.
- **Extra memory:** the block-sum buffer only, 4 × blocks words. That is 16 KB at po2 20, taken from the pooled allocator.
- **Why it is bit-exact:** canonical Fp words (< P) under `Fp::add` form the group Z/P, so every grouping gives the same canonical words as the host's sequential scan.
- **Non-canonical input:** an INVALID word, for example, has no such guarantee. On the CPU the result would depend on the order of additions, and cub's does on CUDA. So pass 1 ORs fault bit 0x100 instead of giving a silently different result. No real segment produced it: `accum_matches_cpu` and the R17 stress on 4 real po2 19-21 segments, including bigint/ecdsa.

### Knobs
- `RISC0_METAL_ACCUM_SCAN=cpu` restores R9's path: wait, check the fault, scan on the host, then finalize. The default is `gpu`, and unknown values fall back to `gpu` with an error log.
- The tests can pass a threadgroup size to `encode_fp_scan(..., Some(tg))`.
- `RISC0_METAL_RV32IM_CPU_PHASES=accum` still selects the whole-CPU fallback.

### Tried / rejected
- **Scan threadgroup size**, isolated, 2^20 × 4 (`ab2.log`): tg 32 0.37 ms, 64 0.27, 128 0.26, 256 0.26, 512 0.27 ms. tg 1024 had a median of 16 ms in one noisy session but 0.8 ms at po2 18, so it is unstable. 64-512 are equal within the noise, and 256 stays the default.
- **Hardware dependence:** the scan is bandwidth-trivial (48 MB of traffic at po2 20), so 8-10-core and 16-20-core parts should see the same ~0.3-0.5 ms. Nothing depends on the core count. Not measured on those parts.
- **Rows per thread** (4 vs 8): not tried. The scan is ~0.3 ms of a ~10 ms step, so no measurable effect is possible.

## R17 (Apple GPU stale private-memory defect)
- **New code:**
  - only scalar `uint32_t`, with no private aggregates;
  - every helper is `always_inline`;
  - the only loops are the simd-shuffle loop (it calls only `air.*` intrinsics), `#pragma unroll` loads and stores, and pass 2's chunk loop, which has no calls after inlining.
- **`ir_scan.py` on `misc.metal`** (`ir/base` vs `ir/new`):

  | -O level | before | after |
  |---|---|---|
  | -O2 | A = B = C = S = 0 | A = B = C = S = 0 |
  | -O1, -Os, -Oz | — | A = S = 0 |
  | -O0 | **A = 1** (`finalizeZeroizeAccum`'s `Fp prev[4]`: constructor loop, then filled in a loop) | A = S = 0 |

  - The -O0 fix: `prev[4]` became four scalars (`prev0..prev3`) and an always-inline `finalizeCell`. It is bit-exact (`accum_matches_cpu`, stress).
  - Tier C at -O0 went from 19 to 38. These are loop-counter allocas around calls in the -O0 code, which tier C counts and which are not the defect shape. -O2 has none.
- **Stress:** see Correctness. The defect control fails 10/10 in the same session, and accum shows 0 nondeterminism.

## Open issues / for later items
- **R1/R17 owner (cuda_compat.h):** move `RV32IM_FAULT_ACCUM_SCAN` (0x100) into `cuda_compat.h`'s fault list. It sits in misc.metal for now, with a static_assert that it is distinct from every bit there.
- **Merge:** `mod.rs` has a one-row change to `EXPECTED_KERNELS` (the Accum row). `rv32im-sys/src/lib.rs` `METAL_KERNEL_NAMES` does not list the scan kernels, because that file is not owned; nothing checks it exhaustively. The R15/merge owner may add them.
- **R14/R15:** the remaining host wait before `build_perm` exists only because the scratch perm may still be in flight. A double-buffered perm, or a GPU `majorKeys` sort, would make the phase wait-free up to its end. The end-of-phase wait could become a `flush`, but the fault word must then be checked later (for example, at the next sync).
- **R15:** stepAccumA is 5-9 ms of the ~10 ms step at po2 20, so it is the next accum target. Finalize is ~2.5 ms including its wait.
- **Known flake (R8/R17 open issue, not R13):** `witgen_snapshot_over_budget_is_an_error` failed once in the parallel harness, with "kernel fault 0x4" instead of a budget error. It is already listed in R17.md.
- **Unmeasured:** 8-10-core and 16-20-core GPUs. A quiet-machine re-run belongs in the final baseline.
