### Roofline check (LEADS #39 asks for it first)

`mb/rates.metal` + `tests_z10::bench_scratch_lib`, 2^20 threads x 8192 ops (`mb/rates2.log`):

| op (with one dependent add) | rate |
|---|---|
| 32-bit `x * y + c` | 3.05 T/s |
| `mulhi(x, y) + x` | 1.56 T/s |
| `ulong(x) * y + x` (32x32 -> 64) | 1.53 T/s |
| the same by the constant 0xf0000001 | 1.54 T/s (the compiler does not strength-reduce) |
| a shift/subtract form of it | 1.54 T/s (no cheaper) |
| `(x + y) ^ c` | 2.75 T/s |

- A 32x32 -> 64 product costs about two 32-bit multiply-adds. 64-bit limbs would need emulated 64x64 -> 128 products, so they are worse. 16-bit limbs would quadruple the product count at a rate at most 2x higher, so they are not better.
- Per permutation, `p254_rows_w64` needs ~50K 64-bit MACs. At 1.53 T/s, 10.7M permutations take 0.35 s of pure MAC. The kernel took ~0.55 s, about 62 % of the MAC-only rate, which is close to the instruction-throughput bound once the carry adds are counted. "Near the int-MAC roofline", as LEADS said. Only fewer instructions could help (a3), or something other than arithmetic (a1).
- Per-thread latency (`mb/lat.metal`, 1 SIMD group): one dependent chain of `ulong(x) * y + x` costs ~15 ns per step. Three independent chains in one thread cost 1.4x one chain, and eight cost 2.3x. A lone thread is latency-bound, and independent work in it is nearly free. That is why the 4-lane kernel (a2) helps the small layers.

### 2.2 (a3) K3 no-carry CIOS: NO-GO

- Implemented as `mulk_nc`, the gnark no-carry CIOS for the partial rounds' constant products. Its bound argument holds for x < 2r because 3r < 2^256.
- Also implemented a "K0" variant: each reduction's first limb as a carry only, `mulhi(m, r0) + (t0 != 0)`, in every reduction.
- Both were bit-exact (z10 tests). Diff kept in `nc_k0_lanes_v1.diff`.
- Measured on the unrolled kernels (`bench_nc1.log`, `bench_k3.log`, 9-21 interleaved reps):

  | variant | code rows | check / accum rows | change |
  |---|---|---|---|
  | `w64` (A) | 105.6 ms | 53.42 / 52.98 ms | |
  | `w64` again (A-vs-A) | | 54.13 / 54.43 ms | spread 0.7-1.5 ms |
  | `w64n` (no-carry) | 104.6 ms | 53.23 / 52.74 ms | -0.4 to -1 % |
  | `w64k` (K0) | 106.4 ms | | +0.8 to +2 % |

- The mulhi + compare of K0 costs more than the full 64-bit product it replaces, consistent with the rate table. No-carry saves only the t8/t9 bookkeeping of 84 of the ~350 reductions per permutation.
- Below the A-vs-A spread, so both were removed. LEADS' "W 1.2 %" was optimistic: the rows kernel's waste was code fetch, not arithmetic.
- Poseidon structure, the other ideas the brief lists:
  - The kernel already uses the sparse ("optimized Poseidon") partial-round matrices: 5 products per partial round, the minimum for t = 3.
  - It already reduces lazily: fused 3-term dot products with one reduction per word, the redundant range [0, 2r), csub only where a bound needs it.
  - Nothing structural is left.

### 2.3 (a2) 4 lanes per hash for latency-bound layers

- Layout:
  - Lane k (k < 3; lane 3 repeats lane 2) holds cell k.
  - Full round: each lane runs its own S-box. The lanes exchange the results with `simd_shuffle` (8 words per cell), and each lane takes one row of the matrix (`dot3k`).
  - Partial round: every lane runs the S-box. Lockstep makes it free, and only lane 0's result is used. Each lane then runs one uniform `dot3k` over (p0, s1, s2): lane 0 with (M00, sp0, sp1), lane 1 with (sp2, 1, 0), lane 2 with (sp3, 0, 1), where "1" is R mod r. The cells stay congruent mod r, so the canonical digest is bit-identical.
- The lanes kernels do ~2.7x the arithmetic, so they lose once 4n threads fill the GPU.
- Threshold sweep with the compact kernels (`bench_compact1.log`) and with the unrolled kernels (`bench_lanes3.log`):
  - 4096 and 8192 tie;
  - 16384 is worse;
  - 2048 is slightly worse on fri0 and accum.
- PLAN 9.1 forbids hard-coding the threshold for this GPU, so it is `LANES_PER_CORE` (128) x the GPU's core count. The core count is IOKit `AGXAccelerator` `gpu-core-count`, read once with a direct FFI call (microseconds).
  - This machine reports 32 cores, as System Information does. BASELINES calls it a 40-core GPU: `GPUConfigurationVariable.num_cores` = 40, but its core masks enable 32.
  - Without a core count the threshold is 1024 (that of an 8-core GPU).
  - Only the 32-core GPU was measured.
- `RISC0_METAL_P254_LANES` overrides it. `0` restores one thread per hash.
- Whole-proof lanes-only A/B (`ab_lanes_default_1.log` 9/11 faster, `ab_q_lanes.log` 8/11): not resolvable under the load, as expected for ~10 ms.

## 3. (b) Prewarm of identity_p254's ctrl group

- `prewarm_p254_ctrl(po2) -> Result<P254Prewarm>` is in `recursion/src/prove/ctrl_persist.rs` and re-exported from `risc0_circuit_recursion::prove`. zk-miner depends on that crate directly, so M9 can call it.
- What it does:
  1. Loads `identity.zkr` (memoized `get_zkr`, the same `Arc` the wrap uses).
  2. Takes the process-wide GPU lock.
  3. Builds a temporary `recursion_prover("poseidon_254")` and calls its `prewarm` (commit + C13 snapshot).
  4. Drops the prover, so no HAL stays alive.
- It returns `Kept { ms, bytes }`, `AlreadyKept` or `Skipped(reason)`.
- Gates (budget and policy). It is skipped when:
  - `RISC0_METAL_REC_CTRL_PERSIST` does not keep p254 groups;
  - the expected bytes (coefficients + 2 x domain digests + code) do not fit C13's cap (`would_keep`, a 32nd of the working set);
  - `allocated + 512 MiB > working-set limit` (measured need: +217 MB). This protects a small budget, e.g. while a segment prover holds its pool;
  - the build is not Metal, or `RISC0_METAL_REC_P254_PREWARM=0`.
- Measured (`c16_first_job`: fresh process per run, worker-style `metal_warmup` first, a poseidon2 lift, then identity_p254 on a fresh prover; 8 interleaved process pairs, `prewarm/summary.txt`, load 7-20):

  | | no prewarm | prewarm |
  |---|---|---|
  | identity_p254 ctrl | 151.6-173.2 ms (Committed) | 5.6-6.4 ms (Restored) |
  | first identity_p254 | 963-1164 ms | 828-1006 ms |
  | prewarm call | - | 221-263 ms |
  | prewarm device peak | - | +217 MB, released |
  | host memory | | +103,169,564 B (C13's copy, which a first wrap would make anyway) |

  Prewarm was faster in 7 of 8 pairs, by a median of ~-110 ms (whole proof, so noisy). The ctrl column is the robust figure: -150 to -167 ms.
- When to call it: on an idle GPU (worker start, or while the first job executes on the CPU). It serializes with proving through the GPU lock.
- Tests:
  - `c16_prewarm_p254_kept_then_restored`: `Kept`, then `AlreadyKept`. The kept group equals a fresh commit word for word (`same_as`), and a new p254 prover restores it (restores +1, no new snapshot).
  - `c16_prewarm_p254_skipped_when_persist_off`.
  - With `RISC0_METAL_REC_SEAL_CHECK=1 C16_PREWARM=1` (`gates/first_sealcheck.log`), the identity_p254 proof on the prewarmed group equals the CPU seal.

## 4. (c) Why the forced release made identity_p254 ~45 ms faster

Instrumented (temporary prints, removed). `metal_wrap_after_stark`, po2 20, 2^22 cycles, 3 jobs per
process, quiet minute (`relc/t3/`):

| arm | release inside `succinct_to_groth16` | release before recursion | identity_p254 (warm jobs) |
|---|---|---|---|
| auto (`0` behaviour at the default budget) | 50.2-65.9 ms (segment + recursion provers) | - | 967-980 ms |
| `=1` (worker) | 4.3-5.1 ms (recursion provers only) | 19.1-32.1 ms | 935-943 ms |
| `RISC0_METAL_WRAP_EARLY_RELEASE=0` | - | - | 910-915 ms, but shrink_wrap +190 ms: not a candidate |

- Under GPU contention the same drop took 0.3-0.8 s. Dropping the pool appears to wait for the GPU.
- So the ~45 ms is the synchronous drop of the segment prover's pool. It is counted in identity_p254 because `succinct_to_groth16` times from before its early release.
- Recursion is also ~20 ms faster with the release (BASELINES 5c.3).

Fix (`zkvm/src/host/server/prove/prover_impl.rs`):
- `release_segment_prover_before_recursion(wrap_follows)`. In auto mode it also releases when `self.opts.receipt_kind == Groth16`, from `composite_to_succinct` and from the PoVW path.
- Safe: in that call the wrap drops the segment prover anyway, so nothing that outlives the call changes, and memory only goes down.
- The worker's staged `compress` path is unaffected. M8 already forces `=1` there, so the benchmark does not change.
- If a caller makes a prover with Groth16 options but compresses only to succinct, the segment prover is rebuilt by the next session. That costs time only.
- `budget` restores the pre-C16 auto mode.
- `c16_groth16_release_ab` (zkvm, ignored) alternates `budget` / unset on `prove(.., groth16)`.
  - Run at the default budget (`relc/ab_def.log`): 16/16 Groth16 receipts verified, and the B arm released every time.
  - The timings were swamped by contention: shrink_wrap 1-30 s in both arms. They are not used.
  - The time effect is that of BASELINES 5c.3's `RELEASE_SEG_BEFORE_REC` row: identity_p254 -44.7 ms (8/8), recursion -20 ms (8/8), footprint -1.98 GB.
