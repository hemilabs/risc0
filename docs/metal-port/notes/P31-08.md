## Problem

The 3.1 recursion circuit (BIT_AND_ELEM canonical decomposition, `84a449919`) adds two constraints
(`top_a`/`top_b`) to the macro-op constraint sum of the regenerated `eval_check.cu`: +12 ops, +2
poly_mix terms, and zirgen renumbered every variable after them by +12. The fork's
`eval_check_split.py` was already re-pinned by hemilabs (12087 ops, `ec_lazyredc` (1062, 401)). Ours
were not, so the recursion metallib build stopped at:

- `cuda2metal_eval.py` PINNED (monolith `tally.fp_mul` 4679 -> 4681, `tally.poly_mix_read`
  1228 -> 1230, and, once those pass, every split form; the port plan listed only the monolith);
- `ec_regroup_metal.py` (C15 `--split-rg`): `FORCE_SPLIT = ('x1101', 'x12357')`, and x12357 is
  x12369 on 3.1. With the old name only one node split, there were 103 leaves, and the generator
  failed with "GROUPS must cover leaves 0..102 exactly once".

## Changes (commit `recursion-sys: re-pin the Metal eval translators on 3.1; derive C15's FORCE_SPLIT`)

### 1. FORCE_SPLIT is derived, not named (`ec_regroup_metal.py`)

The two forced nodes are the **first and the last top-level term of poly_fp's gated sum**
(`FORCE_SPLIT_POS = (0, -1)`; `x1101 * x285 * poly_mix[0]` and `x12369 * x1103 * poly_mix[157]`).
A sixth pinned text hook (`C15_FORCE_SPLIT = C15_FORCE(terms_of(ret), defs)`, applied exactly once
like the other five) computes them from the generator's own tree just before `build()`. The rule
reproduces C15's hand-picked pair on both circuits:

| circuit | derived | C15's names |
|---|---|---|
| 3.0 (frozen `deps/risc0`, `eval_check.cu` of `zkminer/metal`) | x1101, x12357 | x1101, x12357 |
| 3.1 | x1101, x12369 | (x12357 stale) |

`force_split_nodes` raises a clear `RegroupError` if either term has an Fp base (not a gated FpExt
sum). A base that does not split into several terms changes the leaf count, so the GROUPS coverage
check fails (that message now also says how many indices GROUPS covered and points at `--leaves`).
The generator prints the derived names (`ec_regroup_metal: 14 parts, FORCE_SPLIT x1101 x12369, ...`).
The shape pins (EXPECT, PART_OPS) still catch any change to what the nodes cover.

### 2. Re-pins, with the reason for each delta

Leaf tables (`--leaves`) for 3.0 and 3.1 have the same 115 leaves in the same order with the same
depths and factors. **Only leaf 41 changed**: `x1377 -> x1389`, the macro-op constraint sum gated
by `x320 * poly_mix[5]`, 302 -> 316 ops (14 more ops in its slice, of which 12 are new in the
whole poly_fp). So GROUPS is unchanged. Leaf 41 is in regrouped part 2.

| pin | 3.0 | 3.1 | why |
|---|---|---|---|
| `ec_regroup_metal.EXPECT` total ops | 12075 | 12087 | +12 ops (BIT_AND_ELEM) |
| `EXPECT` lazy REDC chain terms / folds | 1074 / 406 | 1076 / 407 | +2 poly_mix terms in the macro-op chain, one more fold |
| `PART_OPS[2]` | 1282 | 1294 | leaf 41 is in part 2 (other 13 parts identical) |
| monolith `tally.fp_mul` / `tally.poly_mix_read` | 4679 / 1228 | 4681 / 1230 | 2 more `poly_mix[k] * x` terms |
| split `lz_add_call` / `tally.fp_mul` | 1060 / 4855 | 1062 / 4857 | 2 more RecLz accumulations, 2 more Fp products |
| split `select.dropped_lines` | 14164 | 14188 | the HIP-only bodies of `eval_check_split.cu` grew by 24 lines (file 28006 -> 28042 lines: +12 CUDA, +24 HIP) |
| split-lz `lz.lz2_prod` / `lz.lz2_fin` | 4855 / 2557 | 4857 / 2561 | +2 lazy products; +4 REDCs: a structural diff of the 3.0 vs 3.1 output shows 2 new `rlf_fin(rlf_mul(..))` and 2 new `rlf_fin(rlf_fold1(xN_l))`; the two long chains feeding the decomposition are re-associated but still one REDC each |

The 3.0 values are kept as comments next to the pins. `cuda2metal_eval.py --check --split
--split-lz --split-rg` passes: pins, residual scan and the byte-for-byte round trip of all forms.
`--compile` builds all 5 TUs with 0 warnings. The hooked generator with no override still
reproduces `eval_check_split.cu` byte for byte. No `eval_check.rs` or `c15_tests.rs` change was
needed: no circuit constant lives there (`POLY_MIX_POWERS` count is unchanged, 158).

R17 rules: no kernel source was edited by hand. The generated forms keep C12/C15's straight-line,
always-inline shape, with no private aggregates written element-wise after calls and no out-of-line
functions taking aggregates by value. The IR scan confirms it.

**How the recursion crate was compiled for these gates.** On this base (`metal/P31-07`),
`risc0-circuit-recursion --features metal` does not compile: there are 16 errors, `&Program` vs
`&Arc<Program>`, from 3.1's `get_zkr` returning `Program`. They are in `ctrl_persist.rs:500` (lib)
and in `hal/metal/{c11,c13,c16,tests,z10}_tests.rs`, `witgen/c6_tests.rs`. Those files are P31-10's
(port plan section 5), not this item's. To run the gates, I applied a minimal local shim that wraps
those `get_zkr(..)` results in `Arc::new` (10 lines) and did **not commit** it:
`scratch/w8/P31-08/p31_10_compile_shim.patch`. With this commit, the recursion-sys Metal build goes
through. The recursion crate's Metal build also needs P31-10's fix (or that shim).

## Budgets and memory

No buffer, dispatch or allocation changes. The kernel set and bindings are the same, so peak memory
is the same as 3.0 by construction. Full suite process peak footprint: 3.83 GB, both runs. The
c8 po2 18 eval peak is +700 MB over the inputs, as on 3.0. The captures A/B ran at 4 GiB and 8 GiB
simulated budgets (`RISC0_METAL_MAX_WORKING_SET_BYTES`) with the same +3.3-3.6 ms per proof
delta. There was no fallback or budget path difference.

`RISC0_METAL_REC_KERNELS=rg|lz|lz32|split|monolith`, `RISC0_METAL_REC_EC_REGROUP=0` (-> lz),
`RISC0_METAL_REC_LZ_UINT4=0` (-> lz32).

## Open issues

- **P31-10:** the recursion crate's 3.1 `get_zkr` compile errors (above; shim patch in scratch).
  Until it lands, `cargo build -p risc0-circuit-recursion --features metal` fails on this branch.
- **P31-11:** the three Poseidon254 seal tests fail until the x^7 S-box lands (verified above).
- **P31-09 / P31-10 (perf, +3.4 ms per recursion proof, ~3 %):** 3.1's independent ZK noise is
  drawn serially on the CPU in `witgen.rs` (`ZK_CYCLES * data_size` and `ZK_CYCLES * accum_size`
  `BabyBearElem::random` calls per proof, in `pre_accum`). At about 180 recursion proofs per
  wave-7 benchmark, that is ~0.6 s. Options to measure there: draw from several CSPRNG streams in
  parallel (rayon, each seeded from the OS RNG), or move the generation off the critical path (the
  data commit could start while noise is drawn for the tail rows only). It must stay a CSPRNG with
  independent values per cell, and `with_noise_seed` must still reproduce CPU seals.
- The lift/join timing uses 3.0 captures (3.0 programs). Re-run `ab_caps.sh` on the P31-15
  captures. The per-proof delta should match unless the 3.1 zkrs change row counts.
- GROUPS is still hand-derived. The derived FORCE_SPLIT removes the renumbering failure. A structural
  change to poly_fp's tree (new leaves) still fails the pins loudly, as intended.
- Not run: the zk-miner worker `--benchmark` (merge/baseline agent, P31-17).
