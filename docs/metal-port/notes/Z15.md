## 2. Changes

### 2.1 Lazy-reduction eval_u: `eu2_main_lz` (eval.metal, eval.rs)
Go/no-go for LEADS #18 first (`z15_eval_u_bench`, `eu_bench1.log`): the rv32im data group (211 polys of
2^20, 670 points, taps per register 104 x 1, 11 x 2, 32 x 5, 64 x 6) took 7.47 ms; the same 670 points all
on poly 0 (every read after the first hits the cache: what perfect read sharing could reach) 7.20 ms; 211
points (one per register: the read floor) 3.03 ms. Read sharing is worth ~0.3 ms: the kernel is ALU-bound
in its per-pair REDCs. **#18 as specified: NO-GO.**

So the ALU was cut instead. `eu2_main` does, per point per 16 coefficients, 32 pairwise REDCs for the inner
product plus a full FpExt x FpExt (19 Montgomery multiplies) for `acc * step`. `eu2_main_lz` sums exactly:
four products of values < p fit in 64 bits; each group of four is split into 32-bit halves that are summed
in `lo` / `hi` (< 5 * 2^32 each); `acc * step` is four more products per component (x^4 = -11, so the
wrapped terms use `-11 * step`, precomputed); then **one** reduction per component per step,
`(lo + hi * 2^32) * 2^-32 mod p = REDC(lo) + hi mod p`, canonical. Exact field arithmetic, so the same
canonical values as `eu2_main` and the CPU HAL. Same bindings, grid and S selection; `eu2_pows` /
`eu2_reduce` unchanged.

| rv32im data shape, po2 20, 15 rotating rounds | pairwise `eu2_main` | lazy | lazy - pairwise per round |
|---|---|---|---|
| inner product only lazy (first step, `eu_bench2.log`) | 6.318 [6.248-] ms | 5.348 [5.288-] | -0.97 [-16.7, -0.82], 15/15 |
| **inner + step fused (kept, `eu_bench3.log`)** | **6.300 [6.203-]** | **3.936 [3.874-]** | **-2.34**, mins -2.33 |
| 670 points on poly 0 | 6.060 | 3.203 | -2.86 [-3.01, -2.71], 15/15 |
| 211 points | 2.553 | 2.388 | -0.19 |

After the change a multi-point kernel could still save at most the poly-0 gap, 3.94 -> 3.20 ms (~0.7 ms),
and only by sharing L2/SLC reads that already mostly hit (each poly is streamed from DRAM once today);
with K points it would need K x 64 registers of power tables or threadgroup-memory tables. Not attempted.
S (split factor): S = 1 / 4 / 8 were not better than eval_plan's S = 2 (mins 4.10 / 3.62 / 4.27 vs 3.62 ms,
`eu_s_bench.log`, load 31).

### 2.2 Fused write-once mix: `mix_poly_coeffs_fused` (mix.metal, mix.rs, Hal hook, prover.rs)
Before: `alloc_extelem_zeroed(combos)` (80 MB fill at po2 20) and one `mix_poly_coeffs_v2` per group (accum
103, code 1, data 211, check 16 inputs), each a read-modify-write of `combos` per combo-id run, 4-byte loads.
Now one dispatch: the host sorts all 331 inputs by combo id (counting sort) into (source buffer << 28 |
poly, power index) entries and uploads the mix powers `mix^j`; each thread owns 4 rows, reads every input
once with one 16-byte load, accumulates with one REDC per two products (v2's arithmetic) and stores each of
the 5 combo slots once. No zero fill, no RMW. The sum order differs; field addition is exact, so the result
is bit-identical.

- Hal API (additive, default no-op): `has_mix_poly_coeffs_fused()` (false) and `mix_poly_coeffs_fused(out,
  mix, &[(coeffs, combo_ids)], count)`. Metal implements it; shapes it does not take (more than 4 groups,
  rows not a multiple of 4, unaligned buffers, > 4096 inputs, ids out of range) fall back inside to the
  pre-Z15 zero fill + per-group mix. prover.rs uses it when the HAL has it and no ROCm early zero fill
  was queued; otherwise the old code runs unchanged.
- `z15_mix_bench` (`mix_bench1.log`, `mix_bench2.log`, po2 20, rv32im shape, 15 rotating rounds): old
  4.62-4.65 ms [4.42-], **fused 3.93 ms [3.74-]: -0.70 / -0.72 ms, 15/15**. 1.33 GB in 3.75 ms = ~355 GB/s,
  the copy bandwidth measured on the shared GPU (eltwise_copy of 1 GB ~310 GB/s): bandwidth-bound.
- Tried and rejected (all within +-0.1 ms of the kept kernel, `mix_bench2.log`): 4 rows / thread with 4 or
  8 entries in flight (3.99 / 4.06 ms), 8 rows / thread (32-byte loads) with 2 or 4 entries (4.04 / 4.03).
  The R18 32-byte-load miscompile class therefore never had to be risked: 16-byte loads only.
- Further floor: the coefficients must be read once after the mix challenge (Fiat-Shamir), so ~1.3 GB per
  segment stays.

### 2.3 Sync trim (prover.rs, rv32im metal mod.rs / witgen.rs / accum.rs)
- **eval_u + check eval, one wait** (prover.rs): the check group's 16 evaluations at z^4 are queued before
  the host reads eval_u (they do not depend on it), so one wait returns both. ROCm's `EVAL_U_EARLY` is
  unchanged (cfg rocm); this is cfg metal + the knob. Values identical.
- **Preflight copy** (`upload_preflight`): it did `try_sync()` (waiting ~3 ms for the segment's data-buffer
  fills) and then copied ~124 MB through `view_mut` (which syncs too) with the GPU idle (~1.5 ms). Now the
  scratch has a `pf_busy` flag, set by the upload and cleared by witgen after its phase-end wait; the upload
  syncs only if it is set, and copies through the raw pointer. The copy now overlaps the queued GPU fills.
- **Accum permutation**: the same with `perm_busy` (cleared after the accum phase-end wait): the host
  counting sort overlaps the accum buffer fill / scatter instead of following a full wait.
- Error paths leave the flag set, so the next call syncs as before. Waits per segment: **17 -> 14**
  (`synctrace_B1.log`), every seal verifies.

Not done (each ~0.1-0.2 ms, small risk): deferring the mdiv remainder read (only logged) to the first FRI
root wait; deferring the witgen / accum fault-word waits to the next commit-root wait (changes error
attribution); the eval_check pre-launch wait (R22/R23 code).

## 3. Rejected / measured only

- **#31 sync latency** (`z15_sync_latency_raw`, `sync_latency1.log`, `sync_latency_raw.log`). The trace
  shows 40-120 us from `GPUEndTime` to the host's return per wait (~1.2 ms per segment). A first version
  polled `status()` for up to N us before blocking (`RISC0_METAL_SYNC_SPIN_US`): tiny dispatch + sync
  165.2 us blocking vs 167.0 (200 us poll) / 185.1 (2 ms poll); ~0.3 ms work 549 vs 575 / 545 us; 2 ms
  work 3467 vs 3439 / 3467 us: **no gain** (the status flips when the completion handler runs, not when the
  GPU ends). Polling a shared event signalled at the end of the command buffer: medians inconclusive under
  load (tiny 172 vs 188 us, then 150-261 vs 213-234 us, then all ~1.2 ms), mins 38 vs 64-70 us in one run.
  Using it would also need completion bookkeeping without the command buffer's status. Removed; the raw
  probe test stays for a quiet-GPU re-check.
- **#33 PSO flag** (`z15_pso_flag_bench`, `pso_flag1.log`, load 18): only kernels dispatched with whole
  threadgroups were tested (the `dispatchThreads` edge threadgroup would break the flag's contract). eu2_main_lz
  off 3.714 / on 3.750 ms (mins), on - off median -0.33 [-7.3, +5.5] 12/21; fused mix 6.134 / 6.553 ms,
  +0.63, 6/21. No gain; not kept (and kernels.rs is Z16's).
- **#32 direct preflight write**: with the copy overlapped (2.3) its remaining value is CPU time
  (~1.5 ms of one core) and 124 MB of host memory traffic, not segment time. Not attempted.
- Not in this item's files but in the tail, for a later item: `mdiv_apply_e16` ~4 ms GPU per segment (15
  root passes over the combos; a multi-root pass or the lazy FpExt multiply of 2.1 could apply);
  `eltwise_sum_fpext` + `bit_rev` could be one pass (~0.2-0.5 ms); the query gather's ~3.5 ms of
  first-touch page faults (Z11 open issue).
