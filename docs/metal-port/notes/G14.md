## What the fuzz is for (determination)

The task asked for a precise determination before the fuzz could be dropped. Evidence:

1. **The fuzz is a public constant, the same for every proof and every machine.**
   - `kernels/cuda/util.cuh` `generate_random_scalars` uses ChaCha8 with `static const uint8_t key[32] = {0}`
     and `nonce[12] = {0}`. Metal's `fuzz_state()` is the same: `chacha_state(&[0; 32], &[0; 12])`.
   - The correction `-MSM(P, f)` for A, B1, B2 and C ships in the public rzup component as
     `fuzzed_msm_results.bin`. `groth16_prover.cuh` precomputes it under `SRS_READ_COEFFS` and adds it back after
     every MSM (`results.a.add(fuzzed_results.a)`, ...).
   - Anyone can compute f. It therefore hides nothing about the witness from anyone, including an observer of
     the prover.
2. **Its stated role is load balancing.** The CUDA bit-split (`kernels/cuda/msm_bit_split.cuh`, header comment)
   keeps the fuzz on the non-bit scalars because "random scalars avoid bucket pile-ups in sppark's accumulate:
   the unfuzzed non-bit scalars repeat values like p-1 thousands of times, 3x slower".
   - Upstream's introduction of the fuzz (`31ec8b4b5`, "New optimized groth16 implementation") carries no comment
     that claims any other purpose.
   - sppark's accumulate has no bucket cut. Metal's MSM cuts every bucket into pieces of at most `piece` points
     (G6). As the module doc says, "a bucket holding a large share of the scalars ... costs no more than the same
     number of points spread over many buckets".
3. **Neither prover is data-oblivious, so the fuzz is not a side-channel measure either.**
   - CUDA's `split_bit_sum` branches on the witness bit (`if (a.x == 1) acc.add(p)`).
   - Both provers' sorts skip zero digits, and H (never fuzzed) is a data-dependent MSM.
   - With f public, a fuzzed timing trace is a function of w as much as an unfuzzed one.
4. **Zero knowledge comes from r and s, which are unchanged.** `MetalProver::prove` draws r and s from the OS
   (`random_fr`). A' = MSM(A, w + f) - MSM(A, f) = MSM(A, w) holds exactly in the group, and the pre-blinding
   values are bit-equal, so the proof has the same distribution.
   - In zk-miner the witness is derived from the STARK seal, which is not secret either.

**Conclusion.** The fuzz is a numerical load-balancing device that cancels exactly. It has no privacy or
side-channel role. Variant A (no fuzz for A, B1, B2 and C) is therefore allowed, and it is what this item
implements.

## Change kept: `nofuzz` (Tuning switch, default on)

`MetalProver::prove_from` with `opts.tune.nofuzz`:
- skips the G10 late-fuzz stage (ChaCha regeneration into a, b, then `fr_add`), or the `fr_add` of the persistent
  fuzz buffer in the G9 layout;
- sorts and MSMs the witness itself;
- does not add the `fuzzed_msm_results` correction (`remove_fuzz`).

Unchanged:
- `fuzz_check` (still `MSM(P, f) + fuzzed = O`) and the fuzz buffers and layouts.
- MSM H.
- Memory: 0 bytes either way.

The verbose dump says `(no fuzz)` instead of `(fuzz removed)`.

Worst-case inputs:
- **A random full-width witness.** `nofuzz` is neutral: GPU 1175.6 vs 1186.0 ms in `g14_nofuzz_bit_exact`, and
  1148.2 vs 1148.5 ms in the G9 layout.
- **Pile-ups** (all ones, all r - 1, a few values repeated): the piece cut handles them. See `msm_edges` and
  `g14_witness_like_scalars`.

Revert knobs:
- `RISC0_G16_METAL_FUZZ=1` or `RISC0_G16_METAL_G14=0` (also `RISC0_G16_METAL_G9_OFF=nofuzz`, and
  `RISC0_G16_METAL_G9=0` as part of the G7/G8 baseline). The A/B shows that these restore A's timing.
- `RISC0_G16_METAL_FUZZ=0` forces the switch on.

## Tried / considered and rejected

- **Variant B (CUDA's bit-split): not implemented, and not needed.** Without the fuzz, each bit scalar w_i = 1
  already costs exactly one bucket addition (window 0, bucket 1, summed in 172-point pieces), and w_i = 0 costs
  none.
  - A plain sum of the bit points does the same ~1.69M additions.
  - The split would save only those entries' share of `sort_w`, which is now 8.1 ms for all scalars.
  - It would add the gather kernels, a ~25 MB permutation, the cached partial correction, and a witness check
    with a fallback.
  - CUDA needs the split because sppark has no bucket cut and wants the fuzz on the remaining scalars. Metal needs
    neither, since every bucket is pieced.
  - The expected gain over A is below 10 ms, so it was not built. This is an estimate, not a measurement.
- **Keeping the fuzz on the non-bit scalars only** (CUDA's arrangement, with the bit scalars unfuzzed). The fuzz
  gives every scalar 15 nonzero digits. The 21 % full-width values already have 15, so for them it changes
  nothing. Every other non-bit value (small values, r - 1 and other repeated values, which have 1-15 digits today)
  would go to 15. That is more additions by construction, with no balance benefit on Metal, so it was not built.

## Hardware dependence (PLAN 9.1)

Nothing depends on core count or RAM. The gain is a smaller number of additions, so it holds on every GPU. The
size of the gain depends on the witness's digit distribution, which is a property of the circuit
(stark_verify), not of the machine.

## Open issues

- **Segment reduce is slower** by +8.6 ms in B2 and +2.5 ms in each G1 MSM (about +16 ms in all), with the
  same piece count and no bucket gaps. It is not explained yet. Candidates:
  - divergence at runs of same-bucket pieces (window 0's 9.8K bucket-1 pieces);
  - data-dependent paths in `Xyzz::add` for pieces of a single point.

  It is small next to the -540 ms, but it is now 8 % of the MSM GPU time.
- **The MSMs are now a smaller share.** After G14, B2 is ~150 ms (buckets 111, segment 37) of a ~640 ms
  shrink_wrap GPU sum. MSM H (168 ms buckets, never fuzzed) and witness_poly + NTT (~140 ms) are now the larger
  shrink_wrap stages. identity_p254 (1.13 s) is now ~2/3 of the wrap.
- **Quiet baseline.** The machine was never quiet during this item. The next baseline should re-take the wrap
  quiet and add `RISC0_G16_METAL_FUZZ=1` as a knob arm.
- **CUDA could do the same.** On sppark the fuzz is what avoids the pile-ups, so dropping it there needs a bucket
  cut first. That is not in this item's files.
