## 2. #9: is the WOM sort permutation static? (go/no-go) — NO

Instrumented (a measurement-only probe in the witgen, since removed; the code is kept in
`perm_probe.rs.txt`): per (cycles, woms, iops) it kept the previous proof's per-cycle counts and its
permutation (sorted position -> exec slot) and checked whether that permutation sorts the next proof's
rows (`probe_caps.log`, 11 C11 captures x 2 rounds):

- The **per-cycle counts are identical** for every proof of a program (every lift, every join).
- The **order is not**: 28,514-33,516 of 844K-942K rows (lifts) and 76,100-80,664 of 1.76M rows (joins)
  land elsewhere, with 25,000-71,000 inversions. Only a replay of the *same* input (identity_p254 in
  round 2) hits.
- Every WOM address occurs in one run of identical rows (`distinct_addr == num_woms`), so the order is a
  pure function of the addresses, but which slot writes which address depends on the data (~3.5-4.6 %
  of the rows).

So a cached permutation would fall back on every proof. Per the lead ("the ROCm GPU radix sort is the
alternative if the permutation turns out not to be static") the sort moved to the GPU instead. The worker
run was not needed for the go/no-go once the captures failed it; the worker runs below count the GPU sort's
fallbacks instead (0 of 14 per memory-merkle run).

## 3. #9 kept: GPU WOM counting sort (`rec_sort.metal`)

A counting sort on the canonical address, encoded right after parStepExec into the same batch:

```
recSortHist (atomic histogram over the exec slots, flags addr >= numWoms / count > 9)
  -> recScanBlocks / recScanSums / recScanAdd: exclusive scan of the per-cycle counts (-> scan, nv)
     and of the histogram (-> cursors), 1024-element blocks, simd_prefix_exclusive_sum
  -> recSortScatter (atomic cursor per address; slots [nv, 9 * cycles) := invalid)
  -> recSortCheck (flags any address whose rows are not bit-identical)
-> wait (the existing exec wait) -> flags == 0 ? inject/verify bind (sorted, scan)
                                             : host sort_wom_rows on the untouched exec output
```

- **Self-validating**: rows with one canonical address land in arbitrary (atomic) order, so the check
  flags any bucket whose rows differ; without a flag the output is the unique `std::sort` order the
  host sort produces (rows with equal keys are bit-identical), and the scanned counts are the host's
  exclusive scan. With a flag (an inconsistent WOM, an address out of range, a count above 9) the host
  sort runs exactly as before on `wom_rows` / `wom_index`, which the GPU sort never writes; it then also
  reports the same errors as before.
- No extra host wait: the flags word is read after the exec wait that already existed. Merging
  inject/verify into the same batch (one wait less, ~0.1-0.3 ms) was not done: on a fallback the verify
  kernels would have run on the wrong order, and whether a re-run of `parStepVerifyWom` over its own
  output is idempotent was not established.
- Scratch: `rec_wom_sorted` (9 x 5 words per cycle, ~47 MB at 260K cycles + 25 % headroom), the scan
  (1 MB), the histogram (2.3 MB), the block sums. The recursion **Metal peak is unchanged** at 4 GiB
  (1910 MiB both arms) and 8 GiB (3096-3099 MiB both arms) — the HAL's pool covers it.
- `scan_ok`: the scans dispatch exactly 256 threads per group; a PSO whose max is below that falls back to
  the host sort (never seen; `c4_metallib_smoke` asserts the declared 256).

Witgen after (worker captures, debug timings, `RUST_LOG`): sort+scan 0, inject+verify 0.4-0.65 ms, exec
(now including the sort's ~0.3 ms) 2.3-3.1 / 4.6-4.8 ms; witgen total 15-29 -> 5-9.5 ms per proof.

## 4. #12 kept: staging in `prepare()` (`staging.rs`)

The Metal counterpart of CUDA's `pinned.rs`:

- `Prover::prepare()` copies the trace (wom, cycles, iops) and the host chains (heads, cycles, rows,
  wom_idx, wom_rows) into one `StorageModeShared` buffer on the prepare thread (`stage_metal`), held by
  the `Preflight` like CUDA's `PinnedTrace` (the shared `pinned` field and `pinned_ptr` now also cover
  `metal`; the raw trace pointers point into the buffer).
- The Metal witgen finds the buffer from those pointers (`staging::lookup`) and **binds wom and iops in
  place**; the cycles are copied to the scratch by a GPU kernel (`recCopyWords`; the kernels advance
  `iopIdx`, and the prewitgen / host-chain / witgen checks re-run the witgen on the same trace); the
  chains are applied by C1's existing `markHostChains` / `scatterHostChains` kernels (unused until now).
  Result: **no host copy and no sync before parStepExec** (fill 0.02 ms, host 0).
- Anything not staged (no `prepare()`, the e2e path, chains computed later, a lookup miss, the knob off)
  takes the old host path unchanged. Chain sizes are validated before anything is encoded; the per-element
  range checks fault in the kernels (an error from the witgen, as before, with a different message).
- Buffers return to a pool of 3 when the preflight drops (a fresh buffer costs its page faults again).
  Every witgen validates before encoding and waits before returning, so a pooled buffer is not reused
  while the GPU reads it. **They are not in the HAL's working-set accounting**: ~29 MB per lift, ~45 MB per
  join with headroom.

A/B (`ab_stage_w.log`, worker captures, A = `RISC0_METAL_REC_STAGE=0` B = staging on, GPU sort on in both, 8
pairs, load 8-16): round median 1862 -> 1585 ms, B faster 6/8; per-proof minima lifts 114.0-114.6 ->
112.8-113.9 ms, joins 120.5-121.3 -> 118.7-119.7 ms (-1 to -1.5 ms). The capture bench stages off the
timed path (as `prepare()` does), so this does not include the prepare-thread cost: 7 ms per join at load
23 (fresh buffers; pooled it is a parallel memcpy of 13-20 MB). In the worker, prepare runs ahead of the GPU
thread except where a join's input arrives late; the worker-level A/B that would settle this could not be
resolved on this machine (section 5).

**Deferred fault-word syncs (the other half of #12): not done.** The witgen's two waits are needed (the sort
flags gate inject/verify; `global` is read right after the witgen). The accum's one wait could move to the
accum commit's root read, but `CircuitHal::eval_check` returns no `Result`, so a deferred accum fault
would need a new trait hook in the shared prover; the gap it removes is one wake-up plus the commit's
encode (~0.2-0.4 ms, ~0.3 % of a proof), below what this machine can resolve.

**Default: off (fix round 1).** Under the protocol a change whose gain is not shown beyond the A-vs-A spread
must not be a default. The staging-only A/B had no A-vs-A of its own; the per-proof minima of identical arms
in `ab_aa_w2.log` differ by 1-3 ms on most proofs (0001 118.6 vs 121.1, 0003 128.7 vs 131.5 ms), more than
the -1 to -1.5 ms claimed; staging-off already reached 112.7-113.4 ms lift minima in `ab_sort_w.log` (the
same as staging-on in `ab_stage_w.log`); and the -15 % round median came from load swings (1.5-6.3 s
rounds). It also adds ~29/45 MB per lift/join outside the HAL working-set budget and moves work onto the
prepare thread, neither measured at the worker level. The code stays behind `RISC0_METAL_REC_STAGE=1`
(tested below, including fault injection and `RISC0_METAL_DEBUG`). To turn it on by default, a quiet
interleaved A/B with its own A-vs-A must show a staging-only gain above the per-proof A-vs-A spread,
including the worker `--benchmark` recursion time and the 4/8 GiB budgets.

## 4b. `RISC0_METAL_DEBUG` and fault injection on the staged path (fix round 1)

The staged inputs are caller-owned shared `metal::Buffer`s bound as `KernelArg::Buffer` (`In::Raw`) and
reused from a process-wide pool after their preflight drops, so the hazard LEADS #12 names (the host
rewriting a buffer an in-flight batch still reads) is real here. What covers it:

- The HAL's in-flight tracking **does** record raw `KernelArg::Buffer` bindings (`runtime.rs`, the
  encoder inserts every bound buffer into the batch's `used` set), but no HAL host accessor ever sees
  these buffers. A tiny additive hook, `MetalHal::debug_check_host_access` (`zkp/src/hal/metal.rs`, 8 lines,
  forwards to the existing `Runtime::check_host_access`), lets the witgen ask. With `RISC0_METAL_DEBUG=1`
  the witgen now checks, when it returns on every path (a drop guard, `StagedReleaseCheck`), that no
  unsynced batch still uses any staged buffer, i.e. that the preflight may drop it and the pool may hand it
  to the next `prepare()` to rewrite. Without debug mode it is a no-op.
- `debug_check_covers_staged_buffers` (new): a `recCopyWords` dispatch reading a staged buffer, then the
  check **panics** before `sync()` (message contains `RISC0_METAL_DEBUG`) and passes after it; then a full
  staged witgen in debug mode passes its release check and equals the CPU witgen.
- `staged_chain_faults` (new, fault injection on the default-when-enabled path, debug mode on): a staged
  trace with staged host chains, the `Staged` call counter asserting the staged path was taken, and one
  corrupted element per case. Each returns `Err`, never a witness: head `u32::MAX`, head == numCycles,
  chain cycle `u32::MAX`, chain cycle == numCycles -> `kernel fault 0x00000001 (inconsistent trace or
  out-of-range index)` (from `markHostChains` / `scatterHostChains`); `wom_idx` = 10 -> the GPU sort flags
  it and the host-sort fallback rejects it (`... wrote 10 WOM rows (max 9)`). After the faults the same
  HAL proves a good staged trace == CPU (`fault.log`).
- Suite and replay runs with `RISC0_METAL_DEBUG=1 MTL_DEBUG_LAYER=1 RISC0_METAL_REC_STAGE=1`: section 7.
  The C11 captures hold no trace (`Capture::preflight()` is `None`), so their replay exercises the GPU sort
  under debug but not the staged inputs; the staged path under debug is covered by the unit tests above
  and the po2 16/18 staged-witgen tests in the debug suite run.
