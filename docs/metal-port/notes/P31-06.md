# P31-06: rv32im Metal integration on 3.1 (seal equality, canonical LogUp, totalCycles) (2026-11-16)

Branch `metal/P31-06` (worktree `deps/risc0-3.1-wt-P31-06`), based on `metal/P31-05` `ced7b57c2`.
Plan: `scratch/r31/PORT_PLAN.md` 1.1 rows 3 and 8, section 5 row P31-06. Chain: P31-02 -> P31-04
-> P31-03 -> P31-05 -> **P31-06** (last rv32im link). Logs: `scratch/w8/P31-06/logs/`.

**Result.** The rv32im Metal prover on 3.1 makes seals equal to the 3.1 CPU prover's, word for
word, on the 6 po2 20 fixture segments. Every seal verifies with the crate's 3.1 verifier
(seal version 3, protocol `RV32IM:v2rev3___`, 91 outputs, `totalCycles == 2^po2`). Metal's accum
finalize is canonical when `prev[k] == 0`: the regression test now forces that case. A tampered
`totalCycles` through the Metal prover never yields an accepted proof. **Test-only change**: no
kernel, generator, prover or host code changed, so production speed and memory are unchanged.
There is no new knob, and nothing is blocking for the kernel owners.

## Changes (test-only; owned files)

### 1. `accum/tests.rs`: `finalize_canonical_with_zero_prev` (new; canonical LogUp, dfc7d5728)

Upstream 3.1 changed phase 3 of the CPU and CUDA accum from `cur + prev[k]` to `cur.zeroize();
cur + prev[k]`. When a machine cell is left INVALID and `prev[k] == 0`, the old form gives
`0xffffffff - P = 0x87fffffe`, which is not canonical. Metal's `misc.metal` `finalizeCell`
already counted INVALID as 0 (P31-05 audit), but no test had exercised the `prev[k] == 0` case.
The new test:

1. **Real segments** (basic po2 13, riscv `divu` po2 13, simple_loop po2 16). The Metal accum runs
   production-shaped: CPU witness, the bigint scatter of `WitnessGenerator::accum`, perm window 14,
   `stepAccumA`, then the GPU scans. A copy of the accum buffer is taken just before
   `finalizeZeroizeAccum`, which is then dispatched exactly as in `step_accum_metal` step 4. Checks:
   - the result equals the CPU circuit HAL's (3.1 C++ phase 3 plus zeroize) word for word, and
     every word is `< P`;
   - a Rust model of 3.1's phase 3 (`finalize_model`) applied to the copied buffer reproduces the
     CPU result, which ties the model to the real C++;
   - the copied buffers hold **1,703,932 INVALID finalized cells**, so INVALID handling with a
     nonzero `prev` is covered against the C++.

   Row 0 always has `prev == [0, 0, 0, 0]`, because the LogUp total of the last row is 0. These
   segments, though, have no INVALID finalized cell on row 0: 0 real INVALID + 0 cells. So the
   real traces do not reach the fixed case, and part 2 forces it.
2. **Forced.** Starting from the same copied buffer:
   - `prev[k]` is set to 0 on 4 rows in 7: all four k on one row, k=1 alone, k={0,2}, k=3 alone.
     This is done by zeroing the scanned columns of their back1 rows;
   - about 25 % of the finalized cells become INVALID, and others become 0 or `P - 1`;
   - this runs with `lastCycle == rows` and with `lastCycle = 3/4 rows`, which covers the
     wrap-around back1 and the zeroize-only tail rows.

   Checks:
   - `finalizeZeroizeAccum` equals the 3.1 model for every cell, and every word is canonical;
   - every INVALID + 0 cell becomes 0;
   - the pre-fix model leaves exactly that many cells at 0x87fffffe, which shows the comparison
     can tell the fixed form from the old one.

   Forced cells per case: 50,815-906,608.

### 2. `integration_tests.rs`: 3.1 constants, seal-v3 assertions, totalCycles against Metal

- `rv32im_3_1_constants` (new) checks:
  - `RV32IM_SEAL_VERSION == 3`;
  - `CIRCUIT_INFO == RV32IM:v2rev3___`;
  - `OUTPUT_SIZE == 91` and `REGCOUNT_GLOBAL == 91`;
  - the `totalCycles` offset is inside the outputs.
- `assert_seal_v3` / `seal_v3_error` (new): a seal's version word is 3 and the `totalCycles`
  global read from the seal's outputs is 2^po2. It is applied to:
  - every Metal seal in `seal_matches_cpu`;
  - the CPU and every Metal seal in `seal_matches_cpu_large` (it is part of the verdict, and the
    log line reads "seals equal, verify (seal v3, totalCycles == 2^po2)");
  - every Metal and CPU seal in `prove_po2_sweep`.
- `total_cycles_tamper_rejected_metal` (new, basic segment po2 13, default harness):
  - the honest Metal seal verifies and is v3;
  - with the 3.0 version word (2), `verify` returns `ReceiptFormatError`. 3.0-made seals are
    rejected;
  - with the outputs' `totalCycles` word changed to 2^12 or 2^14, `verify` rejects;
  - `TamperTotalCycles` (a test circuit HAL that wraps `MetalCircuitHalPoseidon2`) writes the
    claimed value into the device global buffer right before the Metal witgen. That is what
    uploading a tampered `PreflightResults::global` would do; the field is private to
    `prove::witgen`, which this item does not own. Driven through `SegmentProverImpl` at 2^12 and
    2^14, the Metal prover **returns a seal**, because the GPU witgen does not evaluate
    constraints (P31-05). That seal fails `verify` (`InvalidProof`), and it **also fails
    `risc0_zkp::verify` with no totalCycles check** (`InvalidProof`). So the circuit's constraint
    rejects it, not only 3.1's verifier check;
  - with the honest value, the wrapper gives the honest seal, and the plain Metal prover still
    gives the same seal after the tampered runs.
- 3.1's own `prove::witgen::tests::total_cycles_mismatch_fails` is not HAL-generic. Its honest
  case uses `segment_prover()`, which is the Metal prover in a `metal` build. Its tampered cases
  use the CPU HAL with `SeqForward`/`SeqReverse`, because the parallel mode does not unwind
  cleanly. It passes under `--features metal`. The Metal counterpart is the test above.

### 3. `accum/tests.rs`: `r17_accum_segment_stress` fixed for W7-R2's early data drop

This was P31-05's open issue. Since W7-R2, `WitnessGenerator::accum` drops `data` on
unified-memory HALs, so the stress test's second `accum()` on the same generator panicked with
`witgen.data missing` unless `RISC0_METAL_DROP_DATA_EARLY=0` was set. Each rep now gets a fresh
generator holding the CPU witness, so the accum input is the same every rep. Its ms/rep now
includes `WitnessGenerator::new`. Without the knob, sha seg0 and torture20 seg0 at po2 20 gave
0/5 reps differing from rep 0 and 0/5 from the CPU, for all 3 variants (`r17_accum_stress.log`).
P31-16 no longer needs the knob.

## Open issues

- **Real traces never reach INVALID + `prev == 0`** in the segments tested. `prev` is 0 only on
  row 0, and that row has no unwritten finalized cell. So the fixed case is covered only by the
  forced buffers, compared with the 3.1 model, and the model is checked against the C++ on real
  buffers that have INVALID cells with nonzero `prev`. The real C++ phase 3 cannot be driven on a
  forced buffer: its phase 1 rewrites the buffer from the preflight.
- **GPU witgen accepts a tampered `totalCycles`** (`eqz` is a no-op). The constraint rejects the
  proof at verification instead of at witgen, unlike the CPU kernel. An honest prover cannot hit
  this: the host builds the global from `segment.po2`. It costs a wasted proof only for a
  malicious caller.
- Not run here, belonging to other items:
  - the stock crates.io `risc0-zkvm = "=3.1.0"` verifier on composite or succinct receipts
    (P31-14);
  - `seal_matches_cpu_large` under `RISC0_METAL_RV32IM_CPU_PHASES=witgen`;
  - `total_cycles_tamper_rejected_metal` under `RISC0_METAL_RV32IM_CPU_PHASES=witgen`, where the
    CPU witgen kernel's parallel mode does not unwind cleanly on a constraint failure (3.1's test
    comment).
- The phase table was measured at load average 14-17. P31-17 owns the quiet-machine 3.1 baseline.
