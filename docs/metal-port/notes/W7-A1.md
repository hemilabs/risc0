## Changes (each with its revert knob)

1. **Process-wide pool cap with LRU eviction across pools** (`RISC0_METAL_POOL_GLOBAL=0` restores the old
   per-runtime limit/2 cap and disables 1b-1c). The pooled bytes of every live runtime are summed per
   accounting group (group 0 = production; tests use private groups) and kept under half of the process limit
   (`RISC0_METAL_MAX_WORKING_SET_BYTES` capped at `recommendedMaxWorkingSetSize`, else the latter). A release
   past the cap evicts the least recently returned idle buffers across pools (one pool lock at a time, never
   the registry lock while holding a pool lock). A per-HAL explicit budget still caps its own pool (LRU within
   the pool instead of freeing the returned buffer). Small buffers (< 64 KiB) are never evicted.
   - 1b. **po2/phase change**: commits (`commit_coeffs_lde*`, `batch_interpolate_ntt_zk_shift_from`) report
     their row count; a new value starts a new po2 epoch. A pool miss (>= 64 KiB) that would lift the
     runtime's live + pooled bytes above its own high-water mark evicts LRU idle buffers **of sizes last
     requested before the epoch** (the previous po2's), so a new po2 reuses the old sizes' memory instead of
     adding to it. Sizes of the current po2 are never evicted on a miss, so a steady workload never churns.
   - 1c. **Stale sizes**: a size not requested within `RISC0_METAL_POOL_STALE_BATCHES` (default 1024, 0 = off)
     batches of its own runtime is evicted (~36 po2 20 segments of that HAL's own work; an idle HAL does not
     age).
   - Tried and rejected (in this item, before keeping 1b): evicting on every miss against the runtime's
     **live** high-water mark, then against the live + pooled mark without the epoch. Both churned in steady
     state: po2 20 x4 reps had 12 misses per rep after rep 0 (old policy: 0) because a miss in rep 0 evicted
     a buffer needed later, which missed in the next rep and evicted another. With the epoch rule, reps 1-3
     have 0 misses (3 extra misses in rep 0 only; `prof/po220_*.log`).
2. **Memory-pressure drain** (`RISC0_METAL_PRESSURE_DRAIN=0`): a libdispatch
   `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` source (WARN | CRITICAL) installed once per process on a utility
   global queue. Its handler runs `drain_idle_pools()`: ready buffers and pending ones whose batch completed,
   never in-flight pending buffers, Z14 set-aside buffers or live buffers; it takes pool locks only, never
   `exclusive()`. Public API: `drain_idle_pools() -> u64`, `register_idle_releaser(f) -> IdleReleaserHandle`
   (dropping the handle unregisters; `.leak()` keeps it), `PRESSURE_{NORMAL,WARN,CRITICAL}`, `pool_counters()`.
   Test seam: `runtime::on_memory_pressure(level)`. **`memory_pressure -S -l warn` does not work without
   sudo** ("sysctl: kern.memorypressure_manual_trigger failed: Operation not permitted"; probe
   `tests_a1::probe_simulated_pressure_event`), so only the seam is tested.
3. **System-wide GPU memory check** (`RISC0_METAL_SYSTEM_CHECK=0`): without an explicit budget, an allocation
   of >= 256 MiB (shared or private) reads the IOAccelerator `PerformanceStatistics` (IOKit, no sudo, ~18-45
   us, cached <= 1 per 50 ms). If the reading + the allocation exceeds `recommendedMaxWorkingSetSize`, every
   pool of the process is drained (purged, see 4), the counter re-read, and then the allocation fails with
   "Metal working-set budget exceeded: ... system-wide ..." (the budget error class) instead of wiring the
   machine. At HAL creation it warns when other processes already hold more than half of the working set.
   Probe (`tests_a1::probe_system_counter`): **"In use system memory" moves only when a buffer is first used
   by the GPU** (a new or CPU-written 1 GiB shared buffer: +0; after a blit: +1 GiB), "Alloc system memory"
   moves at allocation; both drop at release, neither at `setPurgeableState(Empty)`. The check therefore uses
   `system_gpu_committed()` = max(In use, Alloc), not "In use" alone. It never tripped on this machine's
   background use: a traced full `--benchmark` (all six programs, `logs/full_B.log`) ends with `refused 0`, and
   all 15 B worker runs at the default budget (7 A/B, 2 purge-all, 4 knob probes, 1 traced trial, 1 full suite)
   proved and verified.
4. **Purge on free** (`RISC0_METAL_PURGE_ON_FREE`): unset (default) = `setPurgeableState(Empty)` only on idle
   buffers released by the pressure drain and the system check's drain; `1` = on every idle buffer the pool
   frees (evictions, drains, dropped runtimes, bypass frees with no batch in flight); `0` = never. Pending
   (in-flight) buffers are never purged. **Purging every free was rejected**: worker A/B (default budget, 2
   rounds, `ab/wdef_purgeall/`): recursion +0.095 s [+0.085, +0.105], identity_p254 +27.7 ms, shrink_wrap
   +20.8 ms, STARK +0.125 s, 2/2 slower; one run each with the knobs off confirmed purge was the cause (Metal
   reuses the pages of recently freed buffers for later allocations; purged pages fault in again). And it
   does not shorten the footprint decay (5).
5. **Z14 single-thread check**: `prefill_unfilled` records the marking thread per set-aside buffer;
   `prefill_take` of a filled buffer on another thread trips a `debug_assert` (and logs one error in release
   builds). Unit test `prefill_cross_thread_take_is_caught`.
6. **zkp test suite**: `heavy_test_lock()` (separate from `gpu_test_lock`, taken first when both) for every
   test measured above ~2 GiB alone (`prof/pertest.txt`, each of the 234 tests run alone with `time -l`):
   the six `tests_z2::*_lg_1_20` NTT tests (5.3-6.8 GB), `commit_coeffs_lde` (2.2), `combos_divide_explicit_e`
   (5.7), `combos_divide{,_nonzero}_po2_22` (3.4 / 2.3), `z6_combos_divide_po2_22` (3.2),
   `z6_poly_group_no_coeffs_spill` (3.9). `ntt_interpolate_zk_shift_from_lg_1_20` stops 211 columns at lg 16
   (10.8 GB -> 0.84 GB alone), full range kept as the ignored `..._full`. Every ignored test in the owned test
   files calls `require_gpu_run()` first (panics "run under bin/gpu-run" without `GPU_RUN_MODE`). Pool-state
   tests (`pool_reuse_across_batches`, `alloc_failure_drains_pool_and_retries`,
   `z6_working_set_budget_errors_early`, the three z8b drain/scope tests) put their HAL in a private pool
   group so another test's release can never evict their buffers. rustfmt drift fixed in `hip.rs`, `metal.rs`,
   `tests_z15.rs`.
7. Measurement tool: `RISC0_METAL_POOL_TRACE=<ms>` prints `pool_report()` (per pool: live, peaks, pooled
   sizes; counters; system reading) every `<ms>` and at runtime drop.

## Fix round 1 (review findings)

- **rustfmt** (blocking): the item's own new code in `runtime.rs` (`purge_mode`) and `tests_a1.rs`
  (`relief_frees_are_purged`) was not fmt-clean. Formatted; `cargo fmt -p risc0-zkp --check` now lists no
  owned file (only the pre-existing `prove/poly_group.rs` and `prove/prover.rs` hunks, not owned).
- **Prefill messages**: the `tracing::error!` / `debug_assert!` strings in `prefill_take` carried ~20
  embedded spaces (lost `\` continuation); fixed.
- **Test isolation of the OS pressure source**: the libdispatch source is installed in test processes too,
  and a real OS WARN could drain the pools of a test that holds `gpu_test_lock` between two assertions.
  The handler now calls `os_pressure_event`, which in test builds takes `gpu_test_lock` first (the
  convention the Z8b budget-failure drains already rely on); production builds are unchanged (drain at once,
  never the GPU lock). New test `os_pressure_event_waits_for_test_lock` reproduces the finding: with the
  lock line removed it fails ("the OS event must wait for the test lock"; the event drained the held
  test's pool), with it it passes.
- **Revert knob in tests**: under `RISC0_METAL_POOL_GLOBAL=0` five `tests_a1` tests (global cap, LRU, miss
  eviction, stale eviction, relief purge) asserted policy that the knob turns off and failed. They now skip
  when the knob is `0`; `tests_a1` passes 11/11 with and without it.
- Gates re-run after the fix: `hal::metal` suite 191 passed / 0 failed / 44 ignored twice under the default
  harness at `--no-budget` (footprint 9.03 / 10.09 GB, 70.9 s, load ~6.5-9.8); `tests_a1` 11/11 three times;
  CPU `--features prove --lib` 30 passed; `seal_matches_cpu_large` over the six R11 fix2 po2 20 segments,
  3 release processes of 2: 6/6 seals equal to the CPU and verify (19.86 GB footprint per process);
  clippy clean in owned files. No production code path changed (strings and a test-build-only lock), so
  the speed and memory A/Bs above stand and were not re-run.
- Not changed (non-blocking, noted): `Pool::last_req` keeps one entry per distinct requested size ever seen
  (sizes below 64 KiB or never pooled are not pruned): small, but unbounded if request sizes vary per job.
  The alternating-po2 churn the reviewer simulated (2-3 misses per segment at po2 16/15) is real for a
  workload whose last segment is shorter; it was not A/B'd here (open issue below).
  The prefill thread check can miss a take after a thread exits and its TLS address is reused; it cannot
  raise a false alarm except for a deliberate cross-thread handoff of a HAL, which no caller does today
  (zkvm `CACHED_SEGMENT_PROVER` is thread-local) - W7-R2 should keep that in mind.

## Budgets and knobs

| knob | default | effect when set |
|---|---|---|
| `RISC0_METAL_POOL_GLOBAL=0` | on | old per-runtime limit/2 cap; no cross-pool LRU, no epoch or stale eviction |
| `RISC0_METAL_POOL_STALE_BATCHES=<n>` | 1024 | staleness horizon in the runtime's own batches; 0 = off |
| `RISC0_METAL_PRESSURE_DRAIN=0` | on | no memory-pressure source |
| `RISC0_METAL_SYSTEM_CHECK=0` | on | no IOAccelerator check |
| `RISC0_METAL_PURGE_ON_FREE` | relief only | `1` every idle free, `0` never |
| `RISC0_METAL_POOL_TRACE=<ms>` | off | print `pool_report()` periodically and at runtime drop |

Nothing hard-codes core counts or RAM fractions; the cap follows the process working-set limit (PLAN 9.1).
Peak memory was measured at both simulated budgets and does not rise (footprint -0.3 / -0.5 GB; process Metal
maximum unchanged; recursion-phase peak +355 / +1225 MiB as described).

## Open issues

- **Releasers to register** (other items; this item only adds the registry): recursion C13 kept ctrl host
  copies / device ctrl caches (C1/V2 owners), the Groth16 witness graph `fast::PROGRAM` and the proving key
  (G1 owner; M9 issue 1: ~1.4-2 GB), keccak eval scratch (K owner). Call
  `risc0_zkp::hal::metal::register_idle_releaser(|| bytes_freed).leak()` from their cache constructors; the hook
  must not take `exclusive()` or wait for the GPU.
- M9 issue 2 (freed pages lingering ~1.5 s after a wrap) is **not** in the zkp pools and is not fixed by
  purging; the Groth16 / driver side is the remaining candidate (G owner).
- The po2 epoch starts at the first commit of a new po2, so the preflight/witgen allocations of the first
  segment at a new po2 still miss beside the old po2's pool (~1.2 GiB above a lone po2 20 run in the sweep).
- The system check reads IOAccelerator, which counts every process's GPU memory but not CPU-side memory; it
  cannot help when host RAM, not GPU memory, is what runs out (e.g. `seal_matches_cpu_large`'s CPU prover).
- The rv32im lib suite (16 GB) and the zkvm `host::recursion::tests` suite (20.9 GiB wired, merge-zkp note)
  still need their own heavy-test locks (rv32im / zkvm owners).
- `memory_pressure -S` needs sudo, so the pressure path is only tested through the seam.
- Short-last-segment workloads (po2 alternation) pay 2-3 pool misses per po2 change under the miss rule;
  the miss-time allocation cost at po2 20 has not been A/B'd (reviewer simulation, fix round 1).
- W7-R2 (chained) edits the prefill cap in `metal.rs`; the prefill thread check here is in `runtime.rs`.
