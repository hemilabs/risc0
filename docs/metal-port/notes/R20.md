## Summary
- **Change (default on):** a fourth evalfast TU, `eval_check_ef_fc.metal` (the generated TU compiled with
  `-DEF_FC_FORM`), has the split kernel `ef_eval_split_fc` with the evaluation domain as function constant 0
  (`ef_fc_domain`). The chain functions' row stride `rk_s` and the kernel's `domain` uses become that
  constant, so the trace offsets `k * rk_s` and the row mask are immediates. Constant folding only, so the
  results are bit-exact by construction (and tested).
- The host (`eval_check.rs`) builds one PSO of it per job domain with `MTLFunctionConstantValues` on a
  background thread, through a binary archive of its own (new zkp API `archive::specialized_pipeline`; the
  key includes the constant value; one archive unit per domain, `rv32im_fc<domain>`). eval_check uses the
  specialized PSO once it is ready and the unchanged plain `ef_eval_split` until then, so a cold 20-28 s
  compile never blocks a segment. At library load a background prewarm loads the specializations that a
  previous process archived (hits only, ~0.02-0.05 s each, most recently used first), so a warm worker runs
  specialized from its first segment.
- **Win (quiet-GPU windows, interleaved):**
  - kernel, po2 20: **-41.5 ms per round (-6.3 %)**, faster in 49/55 rounds; A-vs-A -1.1 ms;
  - kernel, po2 18: -11.1 ms (-6.8 %), 15/15; A-vs-A -0.3 ms;
  - phase, po2 20, 7 process pairs: **eval_check 670 -> 622 ms**, segment 1100 -> 1050 ms (medians);
  - 4 GiB (po2 18) and 8 GiB (po2 19): same direction, 5/6 pairs each, noisier.
  
  That is the review's measurement (-6.7 to -8 % in a Swift harness): the cargo-built metallib is in the same
  R18 regime. Computed, not measured: ~41.5 ms x 147 po2-20-equivalent segments = ~6.1 s, **~3.1 % of the
  benchmark STARK** (the review's estimate).
- **Revert knob:** `RISC0_METAL_RV32IM_EVAL_FC=0` (plain PSO only, no prewarm, no background builds).
  `RISC0_METAL_RV32IM_EVAL_FC=wait` builds the needed PSO before the dispatch (benchmarks, tests).
- **The plain kernel is unchanged:** the LLVM IR of `eval_check_ef.metal` (the plain `ef_eval_split`) is
  identical to the baseline's, apart from metadata (section 3). The fallback is therefore the R18 kernel.
- **Memory:** Metal peak +16 MiB (9287 -> 9303 MiB at po2 20, 2339 -> 2355 at 4 GiB, 4655 -> 4671 at
  8 GiB), from the 7 cached specializations the prewarm loaded (~2.3 MiB each). No buffer changes.
- **Cold start:** the startup PSO set is unchanged (13 PSOs, the archive as before). The metallib grows
  23.08 -> 27.76 MB (+4.67 MB, one more ~10-15 s parallel front-end compile in the build). Each new po2
  costs one background compile (20-28 s measured under load) the first time on a machine.
- **Correctness:** all hold for the specialized PSO:
  - CPU == specialized == plain == r15e == r12 == baseline, bit for bit, at po2 4, 10, 12 (extreme), 16;
  - `evalfast_seeds_match_baseline` 8/8 seeds at po2 18;
  - six of six R11 po2 20 seals equal the CPU and verify;
  - run_stress rv32im_eval 0/30 differ at po2 20, defect control 9/10 failing;
  - ir_scan tier A = B = C = S = 0 for all four evalfast TUs;
  - suites pass twice in parallel and at 4 / 8 GiB.
- **Not measurable this session:** the worker memory-merkle A/B. Another agent kept the GPU at 95-100 %
  (STARK 13-44 s against 9.5 s quiet); 10 pairs were run and are recorded as inconclusive (section 4).

## 1. Profile before
The baseline is BASELINES.md wave 5b / R19 (po2 20 segment ~1.07 s; eval_check 652 ms, of which the split
kernel is 653 ms; `ef_combine` 0.75 ms). This session's quiet-window A arms agree:
- `ef_variant_bench` po2 20, plain split: 659 ms median [647, 1147];
- `prove_po2_sweep` po2 20, arm A: eval_check 670 ms [654, ...], segment 1100 ms [1077, ...].

The split kernel is the whole eval_check phase, so a gain in the kernel carries through. R18 / R19 left
the main chain ALU-bound (links and Fp arithmetic). The trace loads are `EF_LD(argN, k * rk_s + ((rk_c - j)
& rk_m))`, with `rk_s` the runtime domain, in all 22 chain functions. Specializing `rk_s` removes a
multiply-add per load address and a register per function.

## 2. Implementation
- `rv32im-sys/kernels/cuda/evalfast/to_metal.py`:
  - `EF_FC_STEPS(s)` replaces the 22 `const uint32_t rk_s = (uint32_t)steps` sites (pinned, new COUNTS
    key `fc_steps`); the split kernel's bound check, chain calls and stores use `dom = EF_FC_STEPS(domain)`;
  - by default `EF_FC_STEPS(s)` is `(uint32_t)(s)`. Under `-DEF_FC_FORM` it is the function constant
    `ef_fc_domain [[function_constant(0)]]`, the kernel is named `ef_eval_split_fc` and there is no
    `ef_combine`;
  - `EF_FC_FORM` with the R12 / R15e forms is an `#error`;
  - `TO_METAL_EXPECT` (regen.py) is unchanged; `regen.py --check` and `--metal <OUT_DIR> --check` are up
    to date.
- `rv32im-sys/build.rs`: `R20_EF_FC_TU` (`#define EF_FC_FORM 1` + `#include "eval_check_ef.metal"`) as
  `$OUT_DIR/metal/eval_check_ef_fc.metal`, as R18 did for r15e.
- `zkp/src/hal/metal/archive.rs` (additive):
  - `specialized_pipeline(dir, device, library, bytes, unit, name, constants)`: one PSO built with
    `newFunctionWithName:constantValues:`, through an archive keyed by metallib, device, OS build and
    `specialized_name` (`name[fc0=<value>]`). It has the same fallbacks as `ArchivedKernels`;
  - `specialized_archive_base`, `archive_used` (newest archive file's mtime) and `specialized_name`;
  - `build_all`'s per-kernel body moved into `build_function`, shared by both. Behaviour is unchanged
    (the R14 rv32im archive tests and keccak's 11 archive tests pass).
- `rv32im/src/prove/hal/metal/mod.rs`: `Rv32imKernels::source` (`KernelSource`: the metallib bytes, the
  archive unit and dir, set for the process-wide instance only), `MetalRv32imCtx::kernels()`, and the
  prewarm call after the library loads.
- `rv32im/src/prove/hal/metal/eval_check.rs`:
  - `FcMode` / `EVAL_FC_ENV`;
  - `fc_pipeline`: a process-wide `domain -> Building | Ready | Failed` map with a condvar; the first call
    for a domain spawns the build thread; Background returns None until the PSO is ready, Wait blocks;
  - `fc_prewarm` and `fc_domain_in_range`. Only the domains of po2 `MIN_CYCLES_PO2..=MAX_CYCLES_PO2` (13-24)
    are specialized, which bounds the archives at one per segment po2 and keeps unit tests at po2 4-12 from
    compiling into the user's cache;
  - `eval_check_evalfast` uses the specialized PSO when `fc_pipeline` returns one.
- Tests:
  - `Which::EvalfastFc` (`fc_test_pso`: the specialization without an archive) in every
    `evalfast_matches_*` test and in `evalfast_seeds_match_baseline`;
  - `fc_archive_roundtrip`: a miss, then a save, then a hit; the key includes the value; CPU-exact;
  - `eval_fc_parsing`; `non_default_eval_psos_are_lazy` also covers `ef_eval_split_fc`;
  - `ef_variant_bench`: a 4th spec field `fc` (e.g. `fc=builtin:128:ef_eval_split_fc:fc`) and
    `R15E_ROUNDS=1`, which prints every round for paired statistics.

## 3. Tried and rejected
- **An optional function constant in `ef_eval_split` itself** (the review's design: `is_function_constant_defined`,
  with the runtime domain as fallback). Metal refuses it: `validateWithDevice: function ef_eval_split cannot be
  used to build a pipeline state. Use newFunctionWithName:constantValues:...`. This is an assertion even
  without the debug layer. Every loader would have to create every function with constant values (zkp
  `build_all`, `MetalKernels`, `try_load_library`), and the plain kernel's AIR would change, which risks the
  R18 regime. The separate TU leaves all loaders and the plain kernel alone.
- **Reading `domain` at the top of the kernel** (first version). It reordered the plain kernel's prologue in
  the IR (the `domain` load before the `cycle` arithmetic). The read now follows `cycle`. The plain TU's -O2
  IR, minus metadata, is now identical to the baseline's (`diff` of `ir/main_eval_check_ef.ll` and
  `ir/eval_check_ef.ll`: 0 lines).
- Not tried (left for follow-ons, as the review suggested):
  - specializing `ef_combine` (0.75 ms);
  - the same specialization for recursion `ec_lz_part` and the keccak stages;
  - a zk-miner call that prewarms the job's po2 at job start (the prewarm covers archived po2s; a new
    po2's first job runs plain).

## 6. Budgets, hardware, knobs
- Nothing depends on core counts or RAM fractions. The specialization is per domain, the archive is per
  machine, and the threadgroup size is still 128.
- Peak GPU memory is +16 MiB: the loaded specialized PSOs, measured at the default, 4 GiB and 8 GiB.
- Untested on base and Pro GPUs (8-10 and 16-20 cores). There the cold compile takes longer, but in the
  background.
- Knob: `RISC0_METAL_RV32IM_EVAL_FC=0|1|wait` (default `1`: background build, plus the prewarm).
  `RISC0_METAL_ARCHIVE=0` or `RISC0_METAL_RV32IM_ARCHIVE=0` still specializes, without an archive: every
  process then compiles each po2 once in the background.

## 7. Open issues
1. **A quiet-machine worker A/B and BASELINES.** The worker memory-merkle A/B could not be resolved under
   GPU contention. The next baseline agent should measure the full `--benchmark` (expected about -3 % STARK)
   and memory-merkle at 4 GiB.
2. **Short-lived processes.** A background compile still running at process exit is lost, and the next
   process starts over. The long-lived worker is not affected. The zk-miner worker could call a prewarm for
   its configured segment po2 at startup (a follow-on: zk-miner is not in this item).
3. **Cold OS shader cache.** Archive "hits" can take seconds (8.6 s seen with `MTL_SHADER_CACHE_SIZE=0`).
   The prewarm hides this, but a job's first segments can run plain then.
4. **Disk.** About 11.5 MB per (po2, metallib) archive. Consider a lower keep count for the `rv32im_fc*`
   units if the cache size matters on small Macs.
5. **Follow-ons (review):** the same function-constant specialization for recursion `ec_lz_part` and the
   keccak eval stages (same addressing shape), and `ef_combine`.
6. Per R18, any later evalfast generator change must re-measure both the plain and the specialized kernel:
   the regime can flip.
