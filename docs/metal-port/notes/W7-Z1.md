## Fixes

### (b) The explicit-directory seam no longer reads `RISC0_METAL_AOT_DIR`

`ArchivedKernels::new_in` / `new_in_threads` now use the offline archive only for a **process-wide load**,
defined as a load whose runtime archive directory is the process's `archive_dir()` (compared as absolute
paths; `archive::process_aot_dir`, `is_process_dir`). Every process-wide loader passes `archive_dir()`
(rv32im `Rv32imKernels::get`, zkp `MetalKernels::new_zkp`, recursion `Pipelines::new_in_unit`, groth16
`prover::kernels`, keccak through `ArchivedKernels::new`); the tests pass their own directories and never see
the environment. `new_in_aot` (explicit offline dir) stays the test seam. Proof: the rv32im lib suite with
`RISC0_METAL_AOT_DIR` set passes, twice, including `archive_roundtrip_relative_dir` and
`archive_roundtrip_small_set` (which failed at tests.rs:430 before); `w7z1_aot_name_and_scope`.

Why not literally "new_in passes None": the process-wide loaders themselves call `new_in` /
`new_in_threads`, and three of them are in files this item does not own (recursion `hal/metal/mod.rs` is
W7-C1's; rv32im `hal/metal/mod.rs`, zkp `kernels.rs`, groth16 `prover.rs`). The directory rule gives the same
result without touching them.

### (c) Offline names are independent of `RISC0_METAL_ARCHIVE_HASH`

`aot_stem` and the offline checksum (`aot_checksum`, `aot_file_name`) always use `parallel_digest`, what
`build_archive.py` writes; `RISC0_METAL_ARCHIVE_HASH=sha256` only switches the runtime archive's key and
checksum. Test: `w7z1_aot_name_and_scope` (stem and checksum equal the parallel digest).

### (a) OS key in the offline name

`<unit>-<parallel_digest(metallib)[..24]>-<arch>-<os key>-<checksum16>.binarchive`, OS key:

- `os<ProductBuildVersion>` (e.g. `os26B131`): made for exactly this OS build (`build_archive.py --os-key build`);
- `macos<major>` (e.g. `macos27`): made with `metal-tt -macos-version-min <major>.0`, used by every build of
  that major version (`--os-key major`, the default and the packaging form).

The runtime tries its exact build, then its major version (`aot_os_keys`); a file with any other key (another
build, another major, or a Z16 name without a key) is never opened: a clean miss, no error, PSOs built as
without it. The key cannot name "the compiler the OS would use": offline binaries come from the downloaded
toolchain (`metal-tt` 32023.922), not from the OS compiler. If Metal finds an offline binary unusable it
reports a miss (Z16's control) and the PSO is compiled, never wrong. Tests: `w7z1_aot_os_key` (other build,
other major and the old name: clean misses; major key alone: hit; exact build preferred over major),
`w7z1_aot_os_keys_for`. `os_build()` / `os_version()` are read once per process now.

### (d) A fully offline-served load seeds the runtime archive

When the offline archive served every PSO of a load and no runtime archive was loaded, a background thread
clones the offline file into the runtime archive under the runtime key (`seed_runtime_archive`; temp file +
rename like `save_archive`, mtime set to now, then the unit's keep-N prune). On APFS `fs::copy` clones, so it
costs **< 1 ms** (`zkp: offline archive copied ... in 0.000 s`, rv32im 53 MB likewise) and no space. The
runtime checksum is taken from the offline name (same digest) unless the hash knob is `sha256`. Measured: AOT
first install, then a cold start (`MTL_SHADER_CACHE_SIZE=0`) without `RISC0_METAL_AOT_DIR`: rv32im+zkp warmup
0.091 s, all 85 PSOs hits from the seeded runtime archive (instead of ~65-90 s). Specialized PSOs seed the same
way. Knob `RISC0_METAL_AOT_SEED=0`. Test: `w7z1_aot_seeds_runtime_archive`. Not seeded: a partial offline
hit (some kernels compiled); the runtime archive then holds only the compiled ones.

### (e) groth16-sys and keccak hooks

`risc0-groth16-sys` `pipelines::build_archived` now goes through the two-archive path explicitly
(`build_archived_in(device, dir, aot, bytes)`; the process-wide call passes `process_aot_dir(archive_dir)`);
keccak (`ArchivedKernels::new`, process-wide) gets it from the shared code. Tests `aot_archive_hook` in both
crates (a runtime archive placed as the offline file serves every PSO). Measured cold (`MTL_SHADER_CACHE_SIZE=0`,

~60 s -> 0.12-0.15 s (probes `g11_kernels_cold`, `c5_tests::z16_probe_warmup`, `ef_tests::z16_probe_warmup`).

## (f) Function-constant specializations from offline archives: GO

Go/no-go:

1. `metal-tt` pipeline scripts accept `libraries.specialized_functions` (`{label, function: "alias:lib#f",
   constant_values: [{id_type: FunctionConstantIndex, id: {data: i}, value_type: ConstantUInt, value: {data:
   v}}]}`; the schema strings are in `air-nt`). A 1-kernel test library: the plain pipeline fails ("cannot lower
   module with unresolved function constants"), the specialized one builds; the runtime
   (`w7z1_probe_fc_archive`, `MTL_SHADER_CACHE_SIZE=0`) gets a **HIT** for the same constant (results correct,
   `io*7+i`) and a clean MISS for another value.
2. On the rv32im metallib `metal-tt` fails: "applegpu-nt: error: cannot find private metadata at offset '128'".
   Reproduced with a two-kernel library: specializing works only for the function whose metadata is first
   (offset 0). A toolchain defect.
3. Workaround `tools/metal_aot/metallib_extract.py`: writes a library with only the requested functions
   (their metadata and bitcode byte for byte; on the test library the result is byte-identical to the
   single-`.air` metallib). An archive built from it is a HIT for a PSO of the full library's function (tested
   on the 2-kernel library, then on rv32im).
4. rv32im `ef_eval_split_fc` for domain 2^20 from the extracted library: 22.5 s, 11.6 MB; probe with the full
   embedded metallib and a cold OS cache: **HIT, specialize 5.66 s, PSO 0.001 s**.

Implementation: `build_archive.py --fc 0=<domain>` (extracts the function, keeps the full library's digest in
the name); the rv32im dump lists `rv32im_fc<domain>` for domains 2^18..2^22 (segment po2 16..20) of the default
(hoisted flat) chain form; `archive::specialized_pipeline` tries the unit's offline archive first for a
process-wide call (`RISC0_METAL_AOT_FC=0` disables it), and eval_check's regime guard reads the offline file
when the PSO came from it. Test `w7z1_fc_aot_archive` (offline hit, CPU-equal results; the same file under
another domain's unit: opened, clean miss). Effect: (ii-b) above, 18.5 -> 5.5 s on a first install. With the
runtime archives present it changes nothing (ii-a): `newFunctionWithName:constantValues:` specializes in the
compiler service before any archive lookup (Z16; LEADS2 refuted that part). Only baked entry points (rank 54)
can remove the ~6.5 s.

## 5. Archive GC

Round-0 design below; **fix round 1 replaced the per-unit rule** (keep the process's own keys, see "Fix round
1" further down). `archive::gc_archives(dir, metallib_dir, now, keep, dry, live)`; at most once per 24 h per
directory (`.gc-stamp`), on background threads:

- runtime archives (`<unit>-<key24>-<sum16>.binarchive`): per unit keep the `keep` (default 2:
  `RISC0_METAL_ARCHIVE_GC_KEEP`) most recently used keys (a key's time = its newest file's mtime; loads set the
  mtime); delete the older keys' files, **except any file used or written in the last hour** (a live process
  may have it open or be about to load it); temp files of dead saves older than 1 h;
- the `risc0-build-kernel` metallib cache beside the default archive dir (`<stem>-<key32>.metallib`,
  `<sha256>.metallib`): per stem keep 2 newest, delete older ones unused for 24 h (build-kernel's own rule: a
  build may be about to copy one; a cache hit touches its mtime);
- offline names, other files and other directories are never touched. `RISC0_METAL_ARCHIVE_GC=0` off,
  `=dry` logs only.

Not "keep what the installed workers reference": a runtime key hashes the metallib digest with the device, the
OS build and each unit's kernel set (and each specialization's constants), which the installed binaries do not
expose, so their keys cannot be computed; the keep-two rule keeps the current worker's archives and the previous
one's (e.g. `.w5c-bak`). Unit test `w7z1_gc_fake_dir` (keep/evict/recent/temp/metallib/dry/idempotent/keep=1).

### Fix round 1: the GC never deletes the running binary's archives

Review reproduction (`scratch/w7/W7-Z1-rev/logs/gcrepro.log`): the running binary's rv32im and zkp
archives, last used 4 h ago, plus two newer decoy keys per unit: the round-0 GC deleted the live archives
and kept the decoys, and the process then compiled rv32im for 57.8 s. Now:

- every load registers its runtime base (`<unit>-<key24>`) in a process-wide set before it opens the file
  (`register_live`; ArchivedKernels and specialized PSOs, so every unit and fc domain);
- the GC starts only after the first process-wide load has opened (and touched) its archive, and each
  later process-wide load of the same process runs the pass for its own unit (`gc_archives_of`);
- per unit: a unit with a live key keeps it and its `keep - 1` most recently used other keys (keep 2 =
  "current plus the newest previous"); a unit this process has not loaded loses only keys unused for 30
  days (`GC_UNUSED_MAX_AGE`, the save-time `ARCHIVE_MAX_AGE`), which also clears retired units
  (`rv32im_r15e`, old `rv32im_fc<small>` domains) that the round-0 rule kept forever; the 1 h rule still
  spares any recently used file;
- bare `<sha256>.metallib` build-cache files are left alone (they had all been grouped under one stem);
- an explicit `RISC0_METAL_ARCHIVE_KEEP` raises the GC's keep (`max`), so a user keeping several binaries
  warm is not overridden.

Tests: `w7z1_gc_fake_dir` (live key the oldest of five: kept, the next-newest old key deleted; a 40-day
unused unit deleted; an unloaded unit's keys kept; the single-unit pass; no live keys and nothing recent:
nothing but a stale temp file goes), `w7z1_gc_keeps_live_archive` (a real zkp archive loaded through a test
dir, backdated 4 h, decoys at 3 h and 2 h: the older decoy goes, the live archive and the newer decoy stay,
a reload is all hits from the same file). The review's reproduction rerun on the fix-1 binary
(`fix1/gcrepro.log`, same layout, real rv32im/zkp archives of this branch): GC deleted only the older
decoy of zkp, then (rv32im's own pass after its load) the older decoy of rv32im; zkp 72/72 and rv32im 13/13
hits from the live files, test passed in 0.88-1.07 s (round 0: rv32im 57.83 s, 0 hits).

## 6. Warm start (+7 ms)

Profile (`w7z1_probe_warm_costs`, warm OS cache, 4 reps): per archived unit the archive path costs the
metallib digest (rv32im 46 MB 7.1-8.2 ms, recursion 6 MB 2.2-3.2 ms), the archive checksum (rv32im 53 MB
4.6 ms, recursion 2.1-3.0 ms), Metal's archive open (4.8-5.3 / 0.9-1.5 ms) and the lookups (0.3-1.4 ms); the
recursion process digests the same metallib for two units. Tried: a process-wide digest memo for metallibs in
a loaded image (`dladdr`-checked `include_bytes!` data, knob `RISC0_METAL_ARCHIVE_MEMO`): recursion+zkp warmup
0.034 s (0.032-0.039) off vs 0.034 s (0.033-0.039) on, rv32im+zkp 0.084 vs 0.079 s with overlapping spreads,
8 pairs: **no change, removed** (the two units build on parallel threads, so the second digest overlaps).
Caching the checksum verification by (path, size, mtime) was not done: every load rewrites the mtime, and the
checksum is what keeps a damaged archive (which can abort the process inside Metal, K8) from being loaded; ~3-5
ms per unit is not worth that. Kept: `os_build`/`os_version` read once per process. Net (iii): pipelines -4 ms
median, 7/7 pairs lower, within the A-A spread (no claim).

### Fix round 1: warm start with `RISC0_METAL_AOT_DIR` set

wave-6 worker warm, B = W7-Z1 worker first install with offline archives, 2 runs each: Metal peaks (segments /
recursion / wrap) A 344 / 1477 / 3942 MiB (4 GiB, po2 18) and 344 / 1477 / 5377 (8 GiB, po2 19); B 328 / 1461 /

MiB at start; the peak is not higher), and 1158-1304 MiB for a first install that compiles. Offline archive

## Knobs

- `RISC0_METAL_AOT_DIR=<dir>`: offline archives (unset = none, as before).
- `RISC0_METAL_AOT_FC=0`: no specialized PSOs from offline archives.
- `RISC0_METAL_AOT_SEED=0`: no clone of a fully used offline archive into the runtime archive.
- `RISC0_METAL_ARCHIVE_GC=0` (off) / `dry` (logs only; writes no stamp, so it scans at every start);
  `RISC0_METAL_ARCHIVE_GC_KEEP=<n>` (default 2: the current key plus one; raised to
  `RISC0_METAL_ARCHIVE_KEEP` when that is set explicitly).
- Unchanged: `RISC0_METAL_ARCHIVE=0`, `RISC0_METAL_ARCHIVE_DIR`, `RISC0_METAL_ARCHIVE_HASH`, `RISC0_METAL_ARCHIVE_KEEP`.
