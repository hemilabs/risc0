## (a) Constant-inverse memo + overlapped digest (LEADS #44 K5) — kept

`fast.rs`: one inverse per distinct constant (2,134 inverses instead of 3.55M), the node copy and translation
in parallel (rayon), and the SHA-256 check on a scoped thread beside the parse. The program is the same values
(`witness_bit_equal_to_reference`: all 5,635,930 elements equal to circom-witnesscalc's for the fixture and a
perturbed seal, with and without the knob). After it the build is read 21 + digest-and-parse 430-680 (the SHA,
~500 ms in the `sha2` crate, now overlaps the ~270 ms parse and is the longest leg) + program 40-70 ms.
Knob: `RISC0_G16_GRAPH_MEMO=0` (pre-G13 build: serial digest, per-node inverse).

Tried/considered: a faster SHA (`openssl` hashes the file in 0.1 s; `sha2`'s `asm` feature) — not done: a
feature switch in the workspace affects every crate (feature unification). It is the next 0.3-0.4 s of graph
readiness (open issue).

## (b) Compiled evaluators on Metal, witness in place (LEADS #24) — kept

`metal_witness.rs` compiles the graph for CUDA's evaluators instead of `fast.rs`' generic one:
- `par` (`witness_par`, dataflow over components; threads = `available_parallelism`, knob
  `RISC0_G16_WITNESS_THREADS`): 30-50 ms per witness here (25-38 ms in quieter rounds; 126 ms at load 70);
  keeps an 18.1M x 32 B (580 MB) value array resident. **Default only when the working-set limit (explicit
  budget, else `recommendedMaxWorkingSetSize`) is >= 20 GiB** (`PAR_MIN_LIMIT_BYTES`: 32 GB Macs and up; a 16 or
  24 GB Mac and every 4/8 GiB budget run get `fast`).
- `fast` (`witness_fast`, ~30K recycled slots): ~160-170 ms, no per-wrap 580 MB calloc. Default below the limit.
- `ref`: `fast.rs` (memoized), also the fallback if the graph does not qualify.
Knob: `RISC0_G16_METAL_WITNESS=par|fast|ref`. `witness_evaluators_bit_equal`: `fast`, `par` x1/x4/x18 equal the
reference generator element by element on two seals.

With `par` and the key already cached (or loading early), the witness is written straight into the prover's
shared witness buffer under the GPU and cache locks (`metal_prove_in_place`; `g13_in_place_witness_bit_exact`:
same proofs with fixed blinding as the copying path, two random witnesses). Otherwise the witness is computed
into a host vector beside the key load, as before. Knob: `RISC0_G16_METAL_DIRECT=0`.

The direct write is **no change in speed** (the copy was 3-12 ms) and is kept for memory: it avoids a 180 MB
host vector (+0.18 GB peak footprint per round without it; 0.19 GB in session 3). Session 2 (swap-bound) showed
why it must not be taken without a cached key: then the key load (0.6-2.3 s under swap) and the witness ran in
series; the final build only writes in place when `metal_is_loaded()` (which also waits for an early load in
progress) — otherwise the parallel path.

Small Macs: `fast` lowers the process peak at 4/8 GiB budgets by ~1 GB (fibonacci 5.55 -> 4.51 / 4.53 GB;
memory-merkle 9.08 -> 8.09 GB at 4 GiB, 9.67 -> 8.51 GB at 8 GiB; one run each, `budget/`), because neither
the ref program (~1.45 GB) nor the per-wrap 580 MB array exists any more.

## (c) Early key load during identity_p254 (LEADS #36) — kept

`prestart` (the zkvm calls it just before identity_p254, then releases the STARK provers, Z10) starts a loader
that polls `currentAllocatedSize` every 2 ms and loads the key when
`allocated <= 2 GiB && allocated + planned_key + 2 GiB <= limit` (`early_key_fits`; `planned_key` from
`metal_planned_bytes`, 3928 MiB, not a constant; the 2 GiB is identity_p254's reserve, measured peak
1.4-1.7 GiB). The first condition keeps G8's rule: the key never sits beside the STARK pools. The loader gives
up when the wrap starts (`stop_early_key_wait`, also from `release_srs`) or after 10 s; the wrap then loads the
key after `pre_gpu`, as before. Knob: `RISC0_G16_METAL_EARLY_KEY=0`.

- Effect (`Bnoearly` vs B): `cpu_path` +165 ms [+135, +276] fibonacci session 1, +629 ms [+428, +1624] session 3;
  memory-merkle +266 ms. identity_p254 itself: no slowdown visible (B - Bnoearly -96 ms median, noise-level).
- Session 1 used a 300 ms wait: memory-merkle loaded early in only 17 of 32 runs (the zkvm's release of
  5-11 GiB of pools took longer); the final build waits until the wrap starts.
- **Memory**: at 28 GiB and at 8 GiB the wrap's Metal peak rises from max(identity_p254, key) to their sum:
  fibonacci 3926 -> 5331 MiB; memory-merkle at 8 GiB 4165 -> 5331 MiB (< 8192; proved and verified). At 4 GiB
  it never loads early (peak 3928 MiB, as before). Tests: `early_key_load_follows_the_budget` (none / 8 GiB
  load early, 4 GiB does not, all verify), `wrap_after_stark_*` (modelled pools never stacked with the key:
  peak 4394 MiB), `early_key_gate`.

## Knobs

| knob | effect |
|---|---|
| `RISC0_G16_GRAPH_MEMO=0` | pre-G13 graph build (serial digest, one inverse per Div node) |
| `RISC0_G16_METAL_WITNESS=par\|fast\|ref` | evaluator (default `par` at a working-set limit >= 20 GiB, else `fast`) |
| `RISC0_G16_WITNESS_THREADS=n` | `par` threads (default `available_parallelism`) |
| `RISC0_G16_METAL_DIRECT=0` | `par` writes into a host vector, then copies |

| all of `WITNESS=ref GRAPH_MEMO=0 EARLY_KEY=0` | restores A: first wrap +0.08 s [-0.96, +1.30] vs A, 3/8 lower (no change) |

## Open issues

- The warm-wrap total (-200 ms expected, ~7.5 %) is not resolved by this session's whole-wrap timings (GPU
  contention swamped them; the second session was swap-bound and aborted). The CPU-path delta is solid; a quiet
  baseline run should confirm the wall-clock number.
- zk-miner `metal_host::GROTH16_RESIDENT_BYTES` (5,930,236,936) is stale: the prover allocates 3899.6 MiB and
  plans 3928 MiB with the G10 defaults. It only feeds `keep_groth16_cache` (zk-miner, not owned here);
  `metal_planned_bytes` is now available to replace the constant.
- Graph readiness is now bounded by the `sha2` SHA-256 (~0.5 s) and, for `par`, its ~0.4-0.5 s compile; caching
  the compiled schedule or a hardware SHA would bring `par` to ~0.5 s.
- `par`'s 580 MB array is resident for the process; under heavy swap it was paged out (in-place witness 126-823 ms
  in the swap-bound runs). The 20 GiB gate keeps it off small Macs; a recycle/idle release could drop it.
- The `ref` evaluator's process peak sometimes read 6.36 GB (vs 5.52) in session 1 (rounds 5-7); not the
  default, not investigated.
