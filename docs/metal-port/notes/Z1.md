### Input validation (plan 2.9)
Indices from callers are checked on the host before upload, panicking where the CPU HAL would panic on an out-of-range index: scatter (for each cycle range `[index[c], index[c+1])` with start < end: the range lies inside offsets/values and every offset in it is < `into.size()`; offsets outside every range are never read and are not checked, matching the CPU HAL and CUDA), scatter_bits (`(base+31)*cycles+row < into.size()` per triple, computed in u64, with `into.size()` asserted to fit in u32 so the kernel's u32 index math cannot wrap; no `row < cycles` requirement, since the CPU HAL and CUDA accept any in-bounds triple), copy_elem_slice (source and target region ends), combos_prepare (largest offset < `combos.size()`), and everything that becomes a `u32` kernel argument. So the kernels need no fault flag. The scan is O(n) host work (cheap next to the upload memcpy).

`eltwise_copy_elem_slice` uploads only `from[from_offset..last+1]` (CUDA uploads all of `from`; same values copied).

### Prover spills (zkp/src/prove/prover.rs)
- `commit_group`'s po2 ≥ 22 `release_evaluated_to_host` is skipped when `unified_memory_gpu(hal)` = `has_unified_memory() && gpu_total_memory() != usize::MAX`, i.e. only for the Metal HAL. CPU (`has_unified_memory` true, `gpu_total_memory` = `usize::MAX`), CUDA/HIP/Intel (`has_unified_memory` false) and `DualHal` (default `gpu_total_memory` = `usize::MAX`) keep their behaviour. `restore_evaluated_from_host` before eval_check was already conditional on `evaluated_host.is_some()`, so it is a no-op too, and `restore_coeffs` is a no-op whenever nothing was spilled.
- Not changed: the `low_mem` `release_evaluated` in `finalize_complete` and the FRI per-group `restore_evaluated`/`release_evaluated`. They are not host spills: they drop the LDE and recompute it. On Metal a dropped multi-GB buffer goes to the pool (up to half the working set) unless trimmed, so the saving there is uncertain; deciding it needs a po2 22 measurement (plan 7, open question on po2 22 feasibility).
- Gap: the coeffs host spill at size ≥ 2^22 happens in `prove/poly_group.rs::new_impl`, which Z1 does not own. On Metal it still runs (a `to_vec` copy within the same physical memory, no saving). Recommended follow-up for the file's owner: gate that spill with the same `unified_memory_gpu` test.

## Assumed / not verified / gaps
- Duplicate offsets in `scatter` (or overlapping scatter_bits cells) are last-writer-wins in an unspecified order on the GPU, as on CUDA. The CPU HAL is sequential. The tests use unique offsets. The reviewer audited the rv32im injector (witgen/mod.rs `build_injector_serial`, `Injector::set`): every offset a row writes is `col*cycles+row`, so different cycle threads never write the same cell and same-row duplicates stay sequential within one thread. Real callers have no race.
- `eltwise_copy_elem_slice` with overlapping target rows (`into_stride < from_cols`) races on the GPU, while the CPU HAL applies rows in order (last row wins). CUDA has the same race (eltwise.cu:41). The only callers (recursion witgen.rs:527/585) use `into_stride = total_cycles >= from_cols`, so they cannot hit it.
- Plan 2.4 asks for a device fault flag where a kernel can detect bad input. Z1 validates on the host instead, panicking exactly where the CPU HAL would (after fix round 1, never stricter), so these kernels have no fault buffer.
- `combos_prepare` bit-exactness relies on field addition being exact: summing deltas and then subtracting once equals sequential subtraction. This holds mathematically and the tests confirm it, including merged offsets.
- `unified_memory_gpu` is a heuristic built from two existing trait methods. A future unified-memory HAL that reports a finite `gpu_total_memory` would also skip the spill, which is the intended behaviour.
- The poly_group.rs coeffs spill and the `low_mem` recompute path on Metal: see above.
- `cargo check -p risc0-zkvm --features metal` was not run. Z1 changes no public API: new methods are `pub(crate)`, and the Hal overrides keep their trait signatures.
- These ops were not exercised end-to-end in a real proof. That happens when the circuit HALs (rv32im/recursion/keccak) run on Metal.
