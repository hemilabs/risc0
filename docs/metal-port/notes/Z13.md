## 1. nttq port: NO-GO

### What was built

The prototype is in `nttq_proto/` (`ntt_q.metal`, `q.rs`, `tests.rs`, `nttq_r11_proto.patch`).

**Kernels.** `ntt_q.metal` ports `nttq::pass_k` for modes 0, 1 and 2:
- inverse column pass, row pass with `n^-1 * g^k`, and the forward coset column pass over 4 cosets;
- line lengths 2^8..2^10;
- the TB x L tile is exactly 32 KB: (10, 8), (9, 16) and (8, 32);
- twiddle tables are read from device memory (no room left to stage them in threadgroup memory);
- uint register arrays, every helper always_inline, every loop unrolled.

**Swizzle.** A tile cannot be padded at 32 KB, so bank conflicts are avoided with an XOR swizzle of the
low five word-address bits per line: `phys = c*L + (w ^ F(c, w>>5))`, with F GF(2)-linear.
- Layout A covers the stage-1 writes and stage-2 reads; layout B the stage-2 writes and stage-3 reads.
- The masks come from a search under a 32-bank model (`proto/swz.py`, `swz2.py`). They are
  conflict-free for every access of every mode and every tile shape.

**Host.** `q.rs` ports CUDA's per-size schedule (IR/FR for lg 16..20) and its tables (`k_line_tabs`,
`k_pow_table`).
- T1 lives in E of the chunk's columns, as in CUDA.
- T2 is a scratch of `chf` columns (32 MB at lg 20 with chf 2).
- Routing is behind `RISC0_METAL_NTTQ`.

**Correctness.** Bit-exact against the ntt_x commit and the CPU:
- lg 16..20 x 1 / 3 / 17 columns, both layouts;
- every valid (ir, fr) schedule at 2 columns;
- the Hal routing test.

### Why

Per pass (`passes2.txt`, GPU time, lg 20 x 211):

| | median ms | min ms |
|---|---|---|
| plain copy of the same size | 4.69 | 4.43 |
| column pass, plain | 12.84 | 12.60 |
| column pass, swizzled | 14.28 | |
| row pass, plain | 10.62 | 10.58 |
| row pass, swizzled | 12.37 | |

A standalone Swift harness (`proto/qbench.swift`, `proto/q_exp.metal`, min GPU ms) separates the memory
pattern from the arithmetic:

- **Without the arithmetic** (same loads, threadgroup traffic and stores):
  - column pass 11.7 ms and row pass 9.6 ms at TB = 8: lines of 1024 give 32-byte segments for the
    strided reads and the transposed writes;
  - the same column pattern at TB = 16 (64 B) takes 6.2 ms;
  - at TB = 32 (128 B) it takes 4.5 ms, which is copy speed.
- **With the arithmetic**, TB = 16 and TB = 32 take 10.3 and 10.7 ms. That is ~6 ms of ALU per pass
  that does not overlap the memory phase. A 32 KB tile allows one threadgroup per core, and the
  load / compute / store phases are separated by barriers.
- **lg 20 needs lines of 2^10** for two passes, and 32 KB holds only 8 such lines. So Metal gets
  32-byte segments (CUDA's TB = 8 has the same shape, but 32 B is a native sector there).
- **The threshold is out of reach even in the ideal case.** Two passes at exactly copy speed are 8.9 ms,
  0.565x of gs_x. Reaching 0.6x needs both passes within 7 % of a plain copy while doing ~6 Montgomery
  products per element.
- **The swizzle is slower than the plain layout**: its address arithmetic costs more than the bank
  conflicts it removes.
- **Z9's premise holds**, for a different reason than Z9 gave. The 32 KB limit does not raise the pass
  count; it forces narrow tiles, hence 32 B segments, plus one serialized threadgroup per core.

### R17-family defect found in the prototype (not in the tree)

**Symptom.** In the mode-2 (coset) column pass, the first version applied the coset twist in
`if (MODE == 2 && bz != 0) { for m: v[m] = mul(v[m], t); t = mul(t, st); }`. Here `v` is a
`uint v[16]` register array, every function is always_inline and the loop is unrolled. With that
version:
- whole threadgroups with `bz == 0` (8192 outputs each, the threadgroups that skip the branch) came
  out wrong;
- the corruption was nondeterministic: 7/20 to 19/20 repetitions, with both layouts, at lg 17 (tile
  (8, 32)).

**Fix.** Applying the twist unconditionally (t = 1 when bz = 0) gave 0/120.

This is a new shape: a conditional element-wise update of a private array, with no out-of-line call
anywhere. It does not ship. R17 owners may want to add the shape to `ir_scan.py` or the stress corpus.
Repro: apply `nttq_proto/nttq_r11_proto.patch` and restore the `bz != 0` condition. The original kernel
is `proto/ntt_q.v1.metal`, and `z13_debug_stress` in the prototype tests shows the failure.

## 2. Two-pass CT with radix-11 passes: NO-GO

**What was tried.**
- `ct_x`/`gs_x` take a max-threads template parameter.
- New 1024-thread instantiations `*_r11` (Z = 8, 2^10 threads, 32 KB) cover passes of 11 iterations.

**Bug found and fixed in the prototype.** `apply_intermediate_twiddles` indexes the 10-bit plus-one table
with `thread_ntt_idx` up to 2^iterations - 2. A radix-11 pass that is not the first (CT) or last (GS) one
read past the 1024-entry row:

| split | wrong outputs |
|---|---|
| [11, 11] CT lg 22 | 3.67M of 4.19M |
| [10, 11] CT lg 21 | 1.84M of 2.10M |

The fix computes the per-z steps `root^bitrev(idx, nbits)` and `root^bitrev(idx+1, nbits)` from the
partial twiddles. After it, CT and GS are exact against the CPU at lg 21 ([11, 10], [10, 11]) and lg 22
([11, 11]), 1 and 3 columns (`ntt_r11_splits_match_cpu`).

**Timing** (`split_sweep2.txt`, GPU time, CT lg 22 x 211, 9 pairs, load ~30), min ms:

| split | min ms |
|---|---|
| sppark [7, 7, 8] | 76.0 |
| A-A | 76.4 |
| [11, 11] | 65.4 |
| [11, 6, 5] | 62.4 |
| [11, 5, 6] | 72.6 |
| **[10, 8, 4] (no radix 11)** | **54.9** |
| [10, 7, 5] | 56.6 |

The radix-11 coalesced pass (1024 threads, one 32 KB threadgroup per core, 5 threadgroup exchange
levels) is slower than the 3-pass split that carries 8 more units of traffic. The radix-11 kernels were
dropped.

- The split pays off only when the transform is DRAM-bound: sppark's full-width commit drops from 98.7

  commit NTT is bound by on-chip per-pass work, not by DRAM, which is also why nttq could not win.

## Open issues
- **LEADS / COMMIT ceiling.**
  - Set #3 (crossport-nttq-commit + commit-ntt-2pass) to ~0 for Metal.
  - The commit NTT is on-chip-bound per pass in the cache-resident chunked regime. The remaining lever
    is fewer passes over data that is already on chip, i.e. fusing into the hash (#2), not fewer DRAM
    passes.
  - If #2 processes wide column sets, it will be DRAM-bound like the full-width runs here. Then the
    measured splits ([10, 8, 4] at lg 22, [10, 7, 4] at lg 21, [9, 7, 4] at lg 20) are worth -13..-26 %
    of the CT time.
- **R17.** The conditional element-wise private-array update (section 1) is a new failing shape without
  calls. It is worth adding to the stress corpus.
- **ntt_x pass constraints.**
  - Radix 11 needs the plus-one fix (section 2). Today's 1..=10 limit is safe.
  - The `set_split` hook accepts invalid splits (first CT pass < 6; GS pass > the levels left).
    Measurement code must check exactness; `z13_measured_ct_splits_are_exact` covers the measured ones.
- **Profiler.** With hundreds of small dispatches (the chunked commit), `RISC0_METAL_PROFILE` GPU sums
  overstate the work by ~40 %. Use wall time there.
