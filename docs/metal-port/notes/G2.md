# G2: BN254 arithmetic header for the Metal Groth16 prover

Branch `metal/G2`, based on `metal/G1` (`7088048e0`). Scope: PLAN.md 4.5 row G2 (kernels table
`bn254.h` row).

## What was ported

- `risc0/groth16-sys/kernels/metal/bn254.h` (namespace `bn254`) is a port of the Intel SYCL
  prover's `kernels/intel/bn254.hpp` (whole file), same algorithms and the same memory layout:
  - `addc`/`subb` (Intel lines 34-49), field constants `FpParams`/`FrParams` (51-102, now
    program-scope `constant` arrays behind static accessor functions, since MSL has no
    `static constexpr` array members), `Mont<Params>` (104-247): zero/one/from_limbs,
    `is_zero`, `==`, `reduce_once`, `+`, `-`, `neg`, `dbl`, CIOS Montgomery `*` with 32-bit
    `mul`/`metal::mulhi` only (Intel `mulhi32` -> `metal::mulhi`), `sqr`, `to_mont`,
    `from_mont`, `pow`, `inv` (Fermat).
  - `Fp2` (252-283, Karatsuba mul, 2M squaring, norm-based inverse), `Affine`, `Jacobian`,
    `Xyzz` (287-440: `from_affine`, `from_jacobian`, `dbl` dbl-2008-s-1, `dbl_affine`
    mdbl-2008-s-1, `add_affine` madd-2008-s 8M+2S, `add` add-2008-s, `neg`, `mul_small`,
    `to_affine`), the G1/G2 aliases.
  - Additions beyond Intel: `Mont::is_canonical()` (value < P), `Mont::rr()`,
    `from_limbs` overloads for `device`/`constant` pointers, `Affine::neg`, `Jacobian::is_inf/inf`,
    `Xyzz::to_jacobian()` (X ZZ^2, Y ZZZ^2, ZZZ: no inversion), `Fp2::is_canonical`.
    `to_affine` uses one inversion (t = 1/(ZZ ZZZ)) instead of Intel's two.
    `mul_small` iterates all 32 bits (no data-dependent `top` search loop).
  - Address spaces: all arithmetic is by value on `thread` objects; compound assignment
    returns `thread Mont&`. `R0G16_OUTLINE` (noinline) became `BN254_OUTLINE`, empty by
    default (overridable before the include).
- Documented contract for values >= p (header comment): arithmetic requires canonical inputs
  (not detected); `is_canonical()` is the rejection check for untrusted loads; `to_mont()` and
  `from_mont()` accept any 256-bit integer and reduce (CIOS bound a*b < P*R).
- `risc0/groth16-sys/kernels/metal/bn254_test.metal`: elementwise test kernels
  `bn254_test_fp_op`, `bn254_test_fr_op` (one template, `[[host_name]]` instantiations),
  `bn254_test_fp2_op`, `bn254_test_g1_op`, `bn254_test_g2_op` (template + `[[host_name]]`), and
  benchmarks `bn254_bench_fp_mul`, `bn254_bench_g1_add_affine`. Buffer indices documented at
  the top of the file. G1's build.rs picks them up automatically (names generated).
- `risc0/groth16-sys/src/metal/tests.rs` (+ `#[cfg(test)] #[path = "tests.rs"] mod bn254_tests;`
  in `src/metal/mod.rs`; `mod tests` was already taken by G1's inline test module).

## Reference used

No ark-bn254/ark-ec/num-bigint is reachable from groth16-sys (dev-deps are only test-log and
tracing), so the test has a self-contained reference: 4 x u64-limb integers; Montgomery
multiplication with u128 products (different limb size and code than the GPU); every Montgomery
constant (R mod p, R^2 mod p, -p^-1 mod 2^64) derived at run time from the decimal moduli, not
copied from the header; reference Montgomery mul cross-checked against double-and-add modular
multiplication (2000 cases per field); curve reference in affine coordinates with
chord-and-tangent formulas and batch inversion, so the XYZZ formulas under test are not reused.
Reference self-checks: G1 and G2 (EIP-197) generators on their curves (G2 b' = 3/(9+u)),
(k1+k2)G = k1G + k2G, r*G1 = O, Fp2 a*a^-1 = 1.

## Measured (indicative; other agents were using the GPU)

M-series GPU of this machine, `throughput` test, best of 3, command-buffer GPU time:
- **Fp mul: 5.6 Gop/s** (2^20 threads x 512 dependent muls, 96 ms; 2 runs: 5.607, 5.579).
- **G1 mixed add (XYZZ += affine, 8M+2S): 455-460 Mop/s** (2^18 threads x 255 adds over 4096
  points, 146 ms), i.e. ~10 muls/add consistent with the Fp mul rate.
- Per-op test dispatches over 100016 cases (single run): G1 add_affine 1.0 ms, G2 add_affine
  5.5 ms, G2 mul_small 90 ms, to_affine (one Fermat inversion each) ~16-17 ms.
Bench kernel outputs are verified against the reference (64 / 16 threads).

## Assumed / not verified

- Bit-compatibility with sppark/ark Montgomery limbs is by construction (same constants as
  Intel, R = 2^256, verified against the run-time-derived reference constants); no ark
  comparison was run (no ark dependency; G3's VK test settles ark compatibility).
- No dedicated squaring or 32x32->64 (`mul32_wide`) accumulation variant was tried; the CIOS is
  Intel's 32-bit mulhi formulation. Optimization belongs to G9.
- The front-end time of large kernels that inline many point ops (MSM) is not measured here.

## Known gaps / open issues

- No ark-bn254/ark-ec/num-bigint dev-dependency in groth16-sys (Cargo.toml not owned): the
  test uses its own reference. Adding ark as a dev-dependency (G1's open issue already asks for
  optional ark deps) would allow an extra cross-check against ark-ec.
- `Xyzz::to_jacobian` returns (0, 0, 0) for infinity (Z = 0 is the only infinity marker).
