## Result

- **The remaining W7-G1 defect is fixed and was reproduced first on 3.1.** A prestart whose wrap never came
  (identity_p254 failed, or a wrap that failed before `gpu_prove`) left a reservation counted. Each later
  prestart renewed the one shared timestamp, so in a miner that starts a job at least every 30 s the count
  never reached 0 again, and the after-wrap release stayed off for the life of the process.
  - Before (the long-run test on `cdbe92ded`, 8 GiB, `MallocLargeCache=0`, `logs/long8G_off_old.log`): after
    the first missed wrap (job 4), the graph stayed cached at every later proof start and after every
    wrap. The process footprint between jobs went from **14.8 MiB to 1023.3-1023.5 MiB** for the remaining
    19 jobs.
  - After (`logs/long8G_off.log`): **14.8-15.0 MiB between jobs, 24 jobs.** The missed wrap's graph is held
    only until the next proof start (1023 MiB measured right after the missed job, 14.9 MiB at the next start).
- **Host footprint with the release on (worker, `MallocLargeCache=0`, arm R against unmodified A): -1.32 GiB
  at 8 GiB, -1.43 GiB at 4 GiB** (8/8 and 6/6 rounds below A). At the default budget only the allocator
  setting acts (-0.52 GiB, the same as A with the variable).
- **Shipped default (no `MallocLargeCache=0`, which is zk-miner-3.1's default: tier table `w7`): no change** in
  time or footprint at 4 GiB, 8 GiB or the default budget (B0 inside A-vs-A).
- **Wrap time:** default unchanged. With the release on:
  - 8 GiB: -113 ms (`par_transient` default, 0/8 > 0);
  - 4 GiB: **+20 ms** (+1.1 %, 6/6 > 0; identity_p254 +7 ms beside the graph build, shrink_wrap +9 ms).
    W7-G1 measured +23 ms there on 3.0.
- **Long-running miner:** 24 jobs (20 wraps, every 5th prestart without a wrap) in one process at 4 GiB and
  8 GiB, with and without `MallocLargeCache=0`. The Groth16 key is released between jobs, as the worker does
  it. There is no growth in footprint or device allocation, and every wrap verified.

## (1) The fix: owned, individually lapsing reservations

`metal_witness::Reservations` (a `Vec` of `{owner: ThreadId, at: Instant}`) replaces the `(count, latest
time)` pair.

- **Each reservation lapses on its own**, `RISC0_G16_GRAPH_RESERVE_MS` (default 30 s) after it was made. A later
  reservation no longer renews an earlier one.
- **Owned by the prestart's thread.** The zkvm calls `prestart_prover`, identity_p254 and the wrap on one
  thread, one job after the other (`succinct_to_groth16`, `prove_with_ctx`). So a thread with an untaken
  reservation that prestarts again (the next job) replaces it: its wrap never came.
- **A wrap takes its own thread's reservation, else the newest.** The fallback covers a caller that
  prestarts on one thread and wraps on another. Taking the newest leaves an older, leaked reservation to
  lapse on its own schedule; FIFO would carry it forward one job at a time, which was the same defect.
- **The wrap guard starts in `shrink_wrap_or_docker`**, before `tempdir()`, the capability check and the
  Docker fallback. Before, it started at the top of `gpu_prove`, so a wrap that failed before that never
  took its reservation. Guards nest per thread (`WRAP_DEPTH`): `gpu_prove`'s own guard counts as the same wrap.
- **Proof start** (`preload_graph_background`, which the zkvm's prover constructor calls on the job's
  thread): a reservation this thread still holds belongs to a missed wrap. It is dropped. With the release on,
  the graph is dropped too if no wrap is in progress and nothing else is reserved, on a helper thread. So a
  missed wrap does not carry ~0.9-1.0 GB into the next job's STARK.
- **Lapse helper** (`schedule_lapse_release`, at most one thread). It runs when a finished wrap could not
  release only because a reservation was live, and at each prestart.
  - It sleeps until the next lapse.
  - It then releases the graph if no wrap is in progress and no reservation is live.
  - If a wrap is in progress, it exits, and that wrap's own release takes over.

  This covers missed wraps whose thread never starts another proof.
- In tests, the helper and the lapse are driven by `TEST_TTL_MS` (set only under `gpu_test_lock()`). A helper
  left sleeping by one test therefore cannot drop the graph under a later test (PLAN 8.7).

Unchanged from W7-G1: the drain hook's rules, the after-witness release by the last wrap out, and
`RISC0_G16_GRAPH_RESERVE_MS=0` (no reservations).

## Knobs

| knob | effect |
|---|---|
| `RISC0_G16_GRAPH_RESERVE_MS` (default 30000; `0` = no reservations) | now per reservation; also bounds the lapse helper |
| `RISC0_G16_GRAPH_RELEASE=0` | no release at all: no proof-start drop, no lapse helper (W7-G1's revert) |
| W7-G1's knobs | unchanged (`RISC0_G16_METAL_WITNESS`, `RISC0_G16_PAR_GATE`, `RISC0_G16_GRAPH_REVERIFY`, `RISC0_G16_METAL_COEFF_CACHE_GC`) |

No separate knob for the ownership rules: they only change which reservation a wrap takes and when an
untaken one ends. `RISC0_G16_GRAPH_RESERVE_MS=0` or `RISC0_G16_GRAPH_RELEASE=0` removes them with the feature.

## Open issues

- The release (and this item's footprint saving) still depends on the worker being spawned with
  `MallocLargeCache=0`. zk-miner-3.1 does that only with tier table `r2`; its default is `w7`, so the beta
  ships with the release off. The beta's footprint is therefore BASELINES '3.1' (4 GiB 5.02 GB, 8 GiB
  7.33 GB per `BENCH_ONLY` process), not the R column. Turning it on is a zk-miner decision:
  - footprint -1.3 to -1.4 GiB;
  - wrap -113 ms at 8 GiB, +20 ms at 4 GiB.
- Ownership assumes a job's prestart, identity_p254 and wrap run on one thread. That is true for the zkvm,
  and zk-miner calls the zkvm synchronously. Another caller falls back to the newest reservation, and to the
  30 s lapse for one that leaks.
- The proof-start drop uses `preload_graph_background`, which the zkvm calls from `ProverImpl::new`. A caller
  that reuses one prover object across jobs gets only the lapse (30 s) for a missed wrap.
- 4 GiB: the Groth16 key load is refused in some worker runs (6/40 here, every arm but R; BASELINES 3.1.5,
  P31-14: ~57 MiB of headroom with the v0.2.0 key). Not this item's change; still open.
- At 4 GiB with the release on, the wrap waits 8-17 ms for the graph build beside identity_p254 (W7-G1 open
  issue; caching the compiled schedule would remove it).
- The A/Bs were run under other agents' load (up to 18). B0 is inside A-vs-A anyway, and every R footprint
  delta is 0/8 or 0/6 rounds above 0.
