## What was ported, and from where

Template: the Intel SYCL prover, `groth16-sys/kernels/intel/groth16_intel.hpp`:
- constants and digit extraction (lines 535-544: c = 16, 16 windows, 2^16 buckets, bucket 0 unused);
- `msm_sort` (583-644) -> `msm_clear` + `msm_hist_count` (step 1), `msm_window_scan` (step 2;
  Intel uses one work-item per window over 64K entries, here one threadgroup per window: chunk
  sums, a threadgroup scan, chunk rewrite), `msm_scatter` (step 3; one dispatch for all windows,
  each thread loops over the windows of its scalar). No grid syncs (the CUDA `sort`/`sort_y`
  kernels with cooperative syncs and PTX are not ported).
- `msm_sorted` (646-706) -> `msm_buckets` (step 4), `msm_segment_reduce` (step 5),
  `msm_window_reduce` (step 6's per-window sums, on the GPU) + `MsmCurve::combine_windows` (step
  6's sum_w 2^(c w) S_w, on the host in ark, as Intel does it on the host).
- The CUDA prover's `integrate_split`/`integrate_combine` (`kernels/cuda/msm_groth16/pippenger.cuh`
  298-405) are the same idea as `msm_window_reduce`: a parallel tree over sub-ranges of a window.

Deviations from the Intel scheme (deliberate):
- **Load-balanced buckets ("pieces").** `msm_window_scan` also scans `ceil(count / piece)` per
  bucket; one `msm_buckets` thread sums one piece (at most `piece` consecutive sorted entries of one
  bucket; it finds its bucket by binary search over the piece offsets). `piece = max(16,
  ceil(2n / 2^c))`, so pieces per window <= n/piece + min(n, 2^c - 1) (~1.5 x 2^c). Intel uses one
  thread per bucket, which for a witness (most scalars 0/1: digit 1 of window 0 holds a large share
  of all entries) puts millions of serial additions on one thread.
- **Segment reduction over pieces**, weighted by their bucket: descending running sums, where a gap
  of g buckets adds `g * running` (`msm_mul_var`, double-and-add from the top bit; g = 1 is one
  add), and the segment ends with `b_last * running`. Every segment has `seg` pieces, whatever the
  occupancy. (Intel: segments of 64 buckets and a fixed 32-bit `mul_small`.)
- **Window groups**: `pieces` (Xyzz per piece) is capped by `MsmConfig::max_piece_bytes` (default
  256 MiB); windows are processed in groups that fit (G2 at 2^20: 2 groups). A memory knob for the
  4-8 GB tier; no core count or RAM fraction is assumed anywhere.
- **Window combination on the host**: a GPU kernel doing the 256 serial doublings + 16 adds
  (`msm_window_combine`, in an earlier revision of this item) cost ~15 ms for G2 on one GPU thread;
  in ark it is well under a millisecond. `encode_msm` therefore writes `nwins` window sums into the
  caller's buffer, and `MsmCurve::combine_windows` finishes on the host (G7 does its Horner/blinding
  in ark anyway, plan 4.5 host glue).
- Points at infinity are not filtered in the sort (as Intel: the sort depends on the scalars only,
  so A/B1/B2/C share one sort); `add_affine` skips them.
- `first` (the C offset, Intel `msm_sorted(..., first)`): scalar i uses `points[i - first]`,
  scalars below `first` are skipped in `msm_buckets`.

API (encode-only, caller-owned compute encoder and command buffers, like G4's wrappers):
`MsmKernels::new(device, library)`, `MsmScratch::new(device, cap_n, cfg)` (StorageModePrivate),
`encode_sort(enc, &mut scratch, scalars, n)`, `encode_msm::<G1|G2>(enc, &scratch, points, first,
out)` with `out` = `scratch.windows()` Xyzz, then `G1::combine_windows(words, wbits)`.
`msm_stages`/`encode_msm_stage` expose the individual dispatches (per-stage profiling).
`MsmConfig::for_size(n)` picks c = max(4, floor(log2 n)) and seg = 16 below 2^16 terms (the default
c = 16 is slow for sparse windows, see measurements).

Scalars: canonical little-endian 8 x u32 (not Montgomery); any 256-bit integer is accepted and the
result is s * P for the integer s (tested with values >= r). Points: affine, Montgomery limbs
(ark's in-memory form), infinity = all-zero coordinates (G2's convention).

## Measurements (indicative: other agents were using the GPU; M5 Max 40-core)

n = 2^20, default config (c = 16, seg = 64, piece = 32), GPU time from command-buffer
GPUStart/EndTime, best of 3 (`msm_2_20 --nocapture`):

| | GPU time |
|---|---|
| sort (clear + count + scan + scatter), shared by all MSMs over the same scalars | **3.9 ms** |
| **MSM G1 2^20** | **66-69 ms** (stages: buckets 52 ms, segment_reduce 14 ms, window_reduce 0.8 ms) |
| **MSM G2 2^20** | **286-304 ms** (stages: buckets 143 + 87 ms in two window groups, segment_reduce 36 + 28 ms, window_reduce 2.6 ms) |
| host combine (ark) | < 1 ms (not separately timed) |
| ark reference, both curves, ~18 CPU threads | 1.7-2.4 s |

G1 bucket throughput: 16.7M affine adds in 52 ms = 320 M/s (G2's note measured 455 M/s peak for
the bare add loop). G2: 16.7M adds in 230 ms = 73 M/s.

**Peak GPU memory** (`device.current_allocated_size()`, single-threaded test run, after allocating
inputs and scratch, nothing else alive): **557-569 MiB at 2^20**, of which MSM scratch 328 MiB
(hist/offset/piece_off 3 x 4 MiB, sorted 64 MiB, pieces 256 MiB cap, piece_bucket 6 MiB, partial
6 MiB) and inputs 224 MiB (G1 points 64 MiB, G2 points 128 MiB, scalars 32 MiB). 2^16: scratch 280
MiB (the pieces buffer is already near its cap: ~1.5 x 2^16 pieces x 16 windows x 256 B), process
299 MiB. Small n: 12 MiB (the 3 x 4 MiB c = 16 tables). Projection for the real witness (~5.6M):
sorted 358 MiB + pieces 256 MiB + ~25 MiB = ~640 MiB scratch, inside the 4 GB tier together with the
key; `max_piece_bytes` can lower it further at the cost of more (serial) window groups.

Small-n latency with c = 16 (serial chains on few threads): n = 1000 G2 92-122 ms, n = 31 G2 38-49
ms; with `for_size` (c = 9 / 4): 9 ms / 5 ms. `max_piece_bytes = 1` (16 groups) at n = 1000: G2
1.6 s, i.e. window groups cost one serial segment chain each.

Pipeline creation: 0.04-0.06 s warm. Cold (first run after the metallib changed) the first test
runs took 1-3 minutes, attributed to cold PSO compilation of the G2 kernels (not isolated from the
other groth16 kernels in the same run).

## Assumed / not verified

- Not run under `RISC0_METAL_MAX_WORKING_SET_BYTES` budgets: the MSM does not use MetalHal (no
  `risc0-zkp` dependency in groth16-sys, like G2/G4), so that HAL knob does not apply; memory is
  reported above instead.
- Timings are on the 40-core M5 Max under shared GPU load; nothing was measured on 8-10 core parts.
  Grid sizes are derived from n and c only (no core counts).
- No fault buffer: indices are generated by the sort itself; `msm_buckets` still bounds-checks the
  point index against `npoints` (host-checked `n - first <= npoints`). Points are trusted canonical
  (G3's loader is where untrusted key data is validated).
- The order of entries inside a bucket depends on atomic scheduling; only the group element is
  deterministic (XYZZ representations differ between runs).
