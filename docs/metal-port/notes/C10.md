# C10: recursion Metal review (fault/clamp coverage, buffer growth, cfg gates, p254, locks, memory)

Branch `metal/C10` (worktree `/Users/user/zkminer/deps/risc0-wt-C10`), based on `zkminer/metal`
`9827b70c4`. Plan rows followed: 4.3 row C10, 2.6 (scratch, lazy sync), 2.9 (faults, clamps),
8.7 (test isolation, parallel harness), 9.1 (peak memory, 4 GB / 8 GB budget runs).

This item is a review followed by fixes. I read the recursion Metal host code (`prove/hal/metal/{mod,witgen,accum,eval_check}.rs`,
`prove/{mod,witgen}.rs` metal paths), the Metal kernels and headers (`recursion-sys/kernels/metal/{context.h,
extern.h,rec_kernels.metal}`, the wrapper templates in `cuda2metal_steps.py`, the generated indexing
pattern in `step_exec.cu`) against the CUDA sources they mirror (`kernels/cuda/ffi.cu` `injectWomBacks`,
`parStepExec`/`nextStepExec`, `extern.cuh`) and against the C10 checklist. I also read the zkp Metal runtime
parts the recursion HAL depends on (`runtime.rs` pool/budget, `buffer.rs`, `exclusive()`) and the zkvm
call sites (`prover_impl.rs`, `prove/mod.rs` `exclusive_gpu`, lift/join prepare threads).

## Findings

Severity: P0 = wrong result, crash or silent corruption. P1 = resource or robustness. P2 = hygiene.

| # | Sev | Finding | Status |
|---|---|---|---|
| 1 | **P1** | **A panic while the scratch guard is held poisons `MetalCircuitHal::scratch` for good.** In practice the panic is the zkp HAL's working-set budget panic inside `grow()` (`hal.alloc_buffer` panics, `buffer.rs:49`), raised while `self.scratch()` is borrowed. Every later `scratch()` then did `lock().unwrap()` and panicked with `PoisonError`. The prover is cached per thread (`PROVER_CACHE`), so every later recursion proof on that thread failed. This is M1's finding: "a panic leaves the recursion HAL's `scratch` mutex poisoned (every later proof failed with `PoisonError`)". | **fixed** (`hal/metal/mod.rs`); regression test `c10_tests::scratch_poison_recovers_after_budget_panic` |
| 2 | P2 | The witgen host-side shape checks were incomplete. The Parallel path only checked `data.size() % steps == 0` and that there are at least 5 columns, and the CPU (Seq) path checked nothing. `parStepExec`/`parStepVerifyWom` and the CPU witgen write every data column and read every ctrl column at `col * steps + (row & mask)`, so a short buffer would cause an out-of-bounds GPU write into whatever follows it (silent corruption). Internal callers always pass full-size buffers (`WitnessGenerator::new`), so this is a programming-error guard, PLAN 2.9. | **fixed** (`hal/metal/witgen.rs` `check_witgen_shapes`: power-of-two rows, cycles <= rows, ctrl/data/global sizes, all modes, before anything is encoded); regression test `c10_tests::witgen_rejects_short_buffers` |
| 3 | P2 | The process-wide `CTRL_CACHE` (host ctrl transposes) and the `RISC0_RECURSION_PREWITGEN_CHECK=once` set (`CHECKED`) in `prove/witgen.rs` used `lock().unwrap()`. A panic on any thread holding them would fail every later recursion proof in the process. Entries are inserted whole, so ignoring the poison is safe. | **fixed** (`ctrl_cache()` / `CHECKED` use `PoisonError::into_inner`); regression test `c10_tests::host_ctrl_cache_survives_poison` |
| 4 | P2 | `RecursionKernels::get` and `eval()` cache a PSO-load error in a `OnceLock` forever, so a failed load needs a process restart. PSO creation failures are deterministic in practice (missing name, compiler rejection), and the zk-miner worker restarts on failure, so I left it. | documented, not changed |
| 5 | P2 | Buffer growth. `ScratchBuffers` only grows (25 % headroom) while the prover lives, and the zkp HAL pool is capped at half the working-set limit per `MetalHal`. Recursion always runs at po2 18, so scratch stays about 52 MB (wom_rows 47 MB, cycles 2 MB, wom_index 1 MB, accum_tmp 4 MB) and never grows beyond that. Both are released by `release_cached_provers()` (zkvm `release_hal_buffers`). One caveat: `PROVER_CACHE` is thread-local, so every proving thread owns a `MetalHal` with its own pool. The budget check (`check_budget`) compares the device-wide `currentAllocatedSize` and drains only the allocating HAL's pool. With several proving threads in one process, idle pools of other threads can therefore cause a spurious budget error. The zk-miner worker proves on one thread per process (M1), so the worker is not affected. | documented (owner: Z8 for the runtime, M4 for the worker) |
| 6 | P2 | Test infrastructure: under `RISC0_METAL_MAX_WORKING_SET_BYTES=4294967296` the zkvm e2e tests `test_recursion_lift_join_identity_p254_e2e` and `test_recursion_lift_resolve_e2e` **fail when run in parallel in one process**: "allocating 67108864 bytes for nodes with 4234608640 bytes already allocated would exceed the limit". The budget is device-wide, so two concurrent tests add up. Each one passes alone. Budget runs of the zkvm suites must therefore run one test per process (or under a shared budget lock). | documented; addressed to the zkvm tests owner (M3/M4) |
| 7 | info | Pre-existing upstream behaviour, not Metal: the ZK noise fill of the data and accum tails is `vec![BabyBearElem::random(&mut rng); n]`. That repeats **one** random element over all `ZK_CYCLES x cols` cells (upstream `b9bfc8ad3`, "ZKVM-1344: Migrate recursion witgen to GPU"). The CPU and every GPU HAL share it, so seals stay comparable. Changing it changes the protocol's randomness for every backend, which is out of scope for a Metal review. | reported only (project owner / upstream) |

No P0 was found.

### Checklist items reviewed with no defect

- **Fault and clamp coverage (kernels).** `extern.h` range-checks every trace-derived index (`iopIdx` in readIOPBody, `addr` in womRead, `womIndex` slots in plonkWrite/plonkRead_wom, `cycle` in the accum externs). An out-of-range index sets `ctx->bad` and reads zero or skips the write. The C2 wrappers fault when `numCycles > totalCycles` (exec) or `workCycles > totalCycles` (accum), and bound `gid`. Step-function trace indexing is `col * steps + ((cycle - back) & mask)` (generated), with `steps` checked to be a power of two on the host (witgen, now on every path; accum `check_accum_shapes`). `injectWomBacks` is CUDA's `ffi.cu:728` plus a fault on `idx > numWomRows`. `markHostChains`/`scatterHostChains` (unused, kept optional) bound their cycles. `fillOneExt`/prefix trio bound `i < n`. eval_check has no asserts, only `& mask` reads, and the host asserts its shapes (`check_shapes`).
- **Fault and clamp coverage (host).** `sort_wom_rows` runs only after the exec fault check passed. It bails on a per-cycle count > 9, and the counting sort indexes `cnt` by canonical addresses `<= max_addr < nv`. `apply_host_chains` (C6's request) validates everything (row block, sizes, `data_cols`, every head and cycle `< num_cycles`) **before** writing. Its rayon tasks write disjoint columns through a raw pointer, after a sync, while the proving thread holds the GPU lock and nothing else encodes on this HAL. Every index is bounded by those checks. The canonical-value sort key (`BabyBearElem::new_raw(raw).as_u32()`) is what CUDA `Fp::asUInt32()` and the CPU `operator<` compare. Equivalence is covered by `RISC0_RECURSION_FAST_SORT_CHECK` and by C6/C9's bit-exact witgen and seal checks.
- **Sliced group buffers (C7's request).** `BufferImpl::as_arg()` binds the view's byte offset (`buffer.rs:141`), so the kernels index from the view start, and checking the view's `size()` is the right check. No change needed.
- **`check` read before a sync (C8's request).** `eval_check` ends with `hal.flush()` (no wait). `check` is next touched by GPU work encoded after it (the zkp prover's NTT/FRI, serial encoder) or by a `BufferImpl` host accessor, which syncs (F0 lazy model). Nothing reads its raw `contents()` before that. The `RISC0_METAL_DEBUG=1` validation-layer run (below) passed with F0's unsynced-host-read assertion on.
- **`with_noise_seed` (C9's request).** It is a thread-local `Cell<Option<u64>>`, restored by a `Drop` guard (so also on panic). Only the tests and `RISC0_METAL_REC_SEAL_CHECK` set it. Otherwise `noise_rng` returns `rand::rng()` exactly as before. The `cpu.rs` cycles copy (8 B per cycle) makes the CPU witgen a pure function of its inputs. Both are fine.
- **Gating host-chain computation on HALs that use chains (C9's suggestion).** Not done. `prepare()` and `WitnessGenerator::new` would both need to know whether the circuit HAL consumes chains. That takes a trait method in `prove/hal/mod.rs`, which is not a C10 file. The cost is a few ms of host time per identity_p254, and Z10 makes p254 a Metal prover that uses the chains. Deferred to C11/Z10 (below).
- **p254 CPU-fallback path.** `recursion_prover("poseidon_254")` returns `hal::cpu::recursion_prover` in both the factory and the `RISC0_METAL_REC_SEAL_CHECK` wrapper (not wrapped). `enabled("recursion") == false` routes every hashfn to the CPU prover and makes `host_chains_backend()` false. `p254_cpu_fallback_with_host_chains_check` and the zkvm `test_recursion_lift_join_identity_p254_e2e` pass.
- **cfg gates.** Every Metal item is behind `feature = "metal"` (`hal/mod.rs`, `prove/mod.rs` `metal_warmup`/`start_metal_warmup`/`host_chains_backend` arm/`recursion_prover` arm/`exclusive()`). recursion-sys has the macOS-only and backend-exclusivity `compile_error!`s and builds the metallib only with `CARGO_FEATURE_METAL`. `cargo check -p risc0-circuit-recursion` (default features and `--features prove`) and the non-metal clippy run are clean. In non-metal builds `host_chains_backend()` is `false` (cuda/rocm `true`), as before C5.
- **Lock interaction with zk-miner worker threads (C5's request, M1).**
  - `exclusive()` is a parking_lot `ReentrantMutex`. It has no poisoning and is released on unwind, so a panic never wedges the GPU lock.
  - `Prover::run`/`prewarm` hold it for the whole proof. Inside, accum re-enters it on the same thread. zkvm's `prove_session_impl` holds it for the session, and recursion proofs nest on that thread (reentrant).
  - The zkvm lift/join `prepare()` threads (`prover_impl.rs:1862/1934/1999`, `rec_pipe`) are joined while the session lock is held. `prepare()` is host-only (preflight, `try_host_chains_range`, `host_ctrl_for`): no HAL and no lock, so it cannot deadlock.
  - The recursion warmup thread takes the lock only inside `MetalHalPoseidon2::new()`, and nobody joins it.
  - The remaining hazard is generic, the same as F0 and CUDA. Rayon is used under the lock (`apply_host_chains`, `par_sort_unstable_by_key`, the CPU p254 prover). If `Prover::run` were called from a rayon worker while all other workers block on `exclusive()`, the holder's `par_iter` could starve. The worker calls the prover from a dedicated thread, so this is not reachable there.
  - The scratch poisoning is fixed (finding 1). M1's exit-70-after-panic policy is still justified by the zkvm segment prover's pool (M1's own note), not by the recursion prover any more.
- **Memory vs budgets.** Peaks are unchanged from C5/C9 (table below). No recursion shape comes near 4 GB.

Regression tests. Each one **failed before its fix**: I reverted the fix in place, ran the test, then restored the fix.

- `scratch_poison_recovers_after_budget_panic`: on a fresh HAL, `set_working_set_limit(Some(1))` and then `fault_word()` panics with "working-set budget exceeded" inside `grow()` under the scratch guard (asserted). The mutex is poisoned (asserted). After the limit is restored, a full po2-16 `test_recursion_circuit.zkr` proof runs through **the same circuit HAL** (`RecursionProverImpl::new(hal, circuit_hal)`, as the cached prover would). It must succeed, match the CPU prover's output and globals, and leave the mutex unpoisoned. Before the fix: `called Result::unwrap() on an Err value: PoisonError { .. }` at `mod.rs:316`. That is M1's failure, reproduced (`c10_mutation_scratch.log`).
- `witgen_rejects_short_buffers`: an empty trace with full-size buffers is accepted. Short data (5 columns), short ctrl or short global gives `Err` naming the buffer, in Parallel and SeqForward. A non-power-of-two row count gives `Err`. Before the fix, Parallel with 5 data columns returned `Ok` (`c10_tests.rs:122` expect_err) (`c10_mutation.log`).
- `host_ctrl_cache_survives_poison`: a thread panics holding `ctrl_cache()`, and `host_ctrl_for` still returns the same ctrl. Before the fix it panicked with `PoisonError` at `witgen.rs:57` (`c10_mutation.log`). In that mutation run the poisoned global cache also failed the concurrently running scratch test. That shows why the process-wide cache must be poison-tolerant, and why the scratch mutation was re-run separately with only the scratch fix reverted.

None of the three takes `global_state_test_lock`. They use their own HAL (the working-set limit is per HAL runtime) and assert only on their own objects. `SCRATCH_POISON_RECOVERIES` is compared with `>` and only this test poisons a scratch mutex. The ctrl-cache test poisons a process-wide lock, but that is harmless after the fix by construction.

## Issues addressed to later items

- **Z8 (zkp Metal runtime)**: the budget check drains only the allocating HAL's pool, while the budget is device-wide (finding 5). (Checked and fine: `Runtime::release` drops an over-cap buffer immediately, `runtime.rs:882-886`, which is safe because batches use `new_command_buffer`, which retains bound resources, `runtime.rs:154,459`.)
- **M4 (zk-miner worker)**: the recursion prover now survives a panic on the same thread. The exit-70 policy is still needed for the zkvm segment prover's undroppable pool (M1). If zkvm exposes a public `release_hal_buffers()`, the worker could keep running after a recursion-only panic. Keep one proving thread per worker process (finding 5).
- **M3/M4 (zkvm tests)**: budget runs of the zkvm suites must run one test per process (finding 6). Alternatively, add a shared budget lock to the zkvm GPU tests.
- **C11/Z10**: skip host-chain computation for HALs that ignore chains (`CircuitWitnessGenerator::uses_host_chains()` in `prove/hal/mod.rs`), until p254 runs on Metal.
- **C11**: `RecursionKernels` caches a PSO-load error for the life of the process (finding 4). If warmup becomes fallible in the field (e.g. archive loading, K5-style), make the cache retry.
- **Project owner / upstream**: the ZK noise fill repeats a single random element per tail (finding 7). It predates the Metal port and is shared by every backend.
