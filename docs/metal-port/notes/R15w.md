**Convention:** `parse_variant` applies a variant over `DEFAULT_TUNE`. The round-1 `prof2-6` logs ran

### 1. Major-sorted first launch (kept, default window 14)
HIP's par_stepExec runs its first launch (cycles before the table split) grouped by major within
2^win-row windows (`RISC0_HIP_WITGEN_SORT`, `wmsSort`), so a SIMD group mostly runs one arm of step_Top's
mux. Metal now does the same: `witgen_sort_perm` builds the permutation on the host from the pristine
preflight cycles (accum's per-window counting sort, `build_perm_by`; the same order as `wmsSort`'s stable
(window, key) ranking) before anything is encoded, and binds it as the kernel's `perm` (`usePerm = 1`,
the path R17's `LaunchOrder::Sorted` test hook already used). Same witness: each cycle still runs once and
writes only its own row; table counts are commutative atomic adds.

### 2. Single-buffer witgen (kept, default on)
- **Why we believe it is bit-exact (empirical, not a proof).** With `pre_data == data`, a back load
  (back > 0) of row r−k may run before or after row r−k's own thread writes it. Snapshot mode reads the
  injected value v0 (or 0), and the sequential CPU witgen reads the final value v1. The two give identical
  witnesses on every segment tested (R8-R17 and here). That shows the output is the same for all-v0 and
  all-v1 reads on those segments. It does **not** cover a cycle whose back loads see v0 for some cells of
  row r−k and v1 for others, and it does not prove f(v0) = f(v1) in general. No column-by-column argument
  (which columns par_stepExecW reads at back > 0, and whether each is injected or written once with the
  injected value) was done. CUDA's own generator says the opposite for the fully inlined build
  (`kernels/cuda/witgen_tu_gen.py:28`, `ffi.cu:1545`: "the fully inlined build reorders the back-row
  loads of rows written by neighbouring threads (latent race) and is not bit-exact"). So correctness
  rests on (a) the noinline step graph, which Metal's witgen TU keeps (R17), (b) CUDA's single-buffer
  default with that same graph, and (c) the R17-method gate below. Anyone who inlines the step graph or
  changes the generator must re-run the gate.
- **Gate** (R17 methodology, one session 22:22-22:36 MST, load 4-26; `gate/summary.txt`):

  | test | baseline (`libs/base_O2`: `--map-lowering loop` + shared fp/fpext, the R17 defect shape) | this branch (embedded metallib) |
  |---|---|---|
  | single-buffer, sorted amplifier (`RISC0_METAL_WITGEN_PERM=sorted`), 40 calls each: torture20 seg0, sha seg0, merkle seg0, torture seg7, ecdsa seg170 (po2 18) | 5/5 bad (torture20, 640 rows) | **0/200** |
  | single-buffer, production order (`RISC0_METAL_WITGEN_SORT=14`), 40 each, same 5 segments | 5/5 bad (sha, 4384 rows) | **0/200** |
  | single-buffer, cycle order, 40 each, same 5 segments | — | **0/200** |
  | snapshot + sort 14, 20 each: torture20 seg0, sha seg0 | — | **0/40** |
  | `witgen_sorted_amplifier` (in the suite, default tune) | — | passes |
  | `witgen_tune_matches_cpu` (8 combinations incl. single+sort, snapshot+sort, single+cycle order, tg 32/64) | — | passes |

- **Speed: no change claimed.** Round 1 measured the call at −7.6 ms median per pair (single alone) and

### 6. wmsSort and the accum perm
- `wmsSort` (HIP ffi.cu) builds both permutations in one LDS kernel. A Metal port needs a kernel in
  `misc.metal` and `build.rs`/`METAL_KERNEL_NAMES` changes, which R15w does not own. Its witgen half is
  done on the host instead (section 1). Round 1 ran it on the critical path; fix round 1 overlaps it with
  the GPU setup (section 7).
- The accum half (reuse the witgen-time permutation in accum, HIP `wmsAccum`) would save accum's
  `build_perm` (0.35-0.51 ms, R13) and the wait before it. In the prover the queue is already idle at that
  point (the data commit ends with a sync), so the saving is the 0.5 ms of host sort: far below the noise.
  Not done; open issue for whoever owns misc.metal if a GPU sort is ever wanted.

### 7. Fix round 1: the sort off the critical path (kept, default on)
**Finding.** The reviewer's interleaved A/Bs (A = `sort=0,single=0`) reproduced the sort's kernel gain
(−5 to −13 ms) but not the call-level claims. With the sort on, the non-kernel time was 18-33 ms whenever
the load was ≥ 40, against 2.4-3.0 ms without it. The rayon counting sort ran on the calling thread
between inject and the encode, and under CPU oversubscription its joins waited on descheduled workers.

**Change.** `metal_witgen` now starts the sort before anything else: before the preflight upload, the
lookup tables, the fault word and `injectCycleCols`. It runs as a sequential counting sort
(`build_perm_by_seq`, no rayon) on a scoped `witgen_sort` thread and is joined just before the kernels
are encoded. The permutation is identical (`witgen_sort_seq_matches_par`), so the GPU work is unchanged.
`RISC0_METAL_WITGEN_SORT_OVERLAP=0` restores round 1's inline rayon sort.

three po2 20 segments: sha seg0, merkle seg0, torture seg7. Every call was compared with the CPU witgen,
and all 873 timed calls matched (the untimed warm-up calls are checked too, and the test asserts 0 bad). A = `r13` (`sort=0,single=0`, the R13 path); the second `r13` is A′. "host"
is call − kernels. The figures below are per-pair medians of B − A, with the number of pairs where B
was faster. The loads are the 1-minute load average at the start → end of each session. Scripts and logs

- Pooled over all six sessions (210 pairs): the defaults vs R13 give kernels **−5.9 ms** (163/210) and
  call **−13.0 ms** (183/210). A′ gives −0.03 ms (108/210) and +4.9 ms (70/210). Host time is 4.9 ms
  for the defaults against 14.2 ms for R13; R13's host time includes the snapshot copy.
- Overlapped vs inline sort, same pair (177 pairs, 5 sessions): call −11.1 ms (125/177), host −7.6 ms
  (133/177). At load ≈ 20 the two are equal (4 GB session: host 3.4 vs 3.4 ms, as the reviewer saw
  at load 20). At load ≥ 40 the inline sort's host time is 11-27 ms and the overlapped one's 3.6-5.9 ms.
- The A′ call median is positive in every session (+0.2 to +13.9 ms): a slot effect for the last
  slot. In ab3 `base` ran in slot 0, before A, and was still −16.7 ms (42/45).
- **Rule check.** The claimed call gain (−11 to −17 ms per session) is larger than every A′−A
  per-session median (−0.0 … +13.9 ms; the largest, +13.9 ms, is the 8 GB session's last-slot effect,
  where base was −13.1 ms). The per-pair extremes (A′−A ranges of ±100-400 ms, from GPU contention
  spikes) are larger than any effect here, so by the strict per-pair range rule everything in this item
  is "no change". The medians, sign counts and q1 values are the evidence; the quiet-machine baseline
  should settle the size (open issue 2).
- Restated claims (also in the `DEFAULT_TUNE` and module docs): the sort is a kernel-time gain. At call
  level it pays only because it is overlapped, and its host cost depends on CPU load. Single-buffer is
  a memory win with "no change" claimed for call time. The two together, against R13, are the call-level
  gain above.
- Not tried: writing the permutation straight into a shared Metal buffer from the sort thread, which
  would save the 4 MB `copy_from_u32` (~0.3-1 ms). That would need an unsafe cross-thread write into a
  pool buffer, and the copy is within the noise.

## Budgets (PLAN 9.1)
`prove_po2_sweep` (`R11_PO2S=18,19,20 R11_CPU=0`), default vs `RISC0_METAL_WITGEN_SINGLE_BUFFER=0`:
- 4 GB: largest po2 18 in both (po2 19/20 fail at eval_check's `evaluated` allocation); witgen-phase peak
  at po2 18: 259 vs 470 MiB.
- 8 GB: largest po2 19 in both (po2 20 fails at `evaluated`); witgen-phase peak at po2 19: 2817 vs 3239 MiB.
- Whole po2 20 prove (`prove_segment_measure`, no budget, 2 × 2 processes): GPU peak 9343 MB in both.
So single-buffer lowers the witgen phase's peak and never raises any peak, but it does not move the
largest po2 that fits a budget: the data commit and eval_check set that. **Correction to R8's note:**
R8 expected that "po2 22 fits 4 GB" once the snapshot was gone. That is not borne out: without the
snapshot the largest po2 at 4 GB is still 18. (The fix-round reviewer reproduced the memory figures:
po2 20 +991 vs +1876 MB, po2 18 248.7 vs 470.0 MB, the same at 4 and 8 GB.) The `GPU peak` column of
`r15w_witgen_ab` is the process-wide peak, the same for every variant, and cannot show this win;
`witgen_matches_cpu_large` measures it.
Fix round 1 adds no allocation: the overlapped sort's `Vec<u32>` is host memory (4 MB at po2 20), the
same as round 1's. The fix-round A/B ran at both budgets (section 7) with every call equal to the CPU.
