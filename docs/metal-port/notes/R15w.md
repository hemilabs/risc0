## Profile before (measured first)
`r15w_witgen_ab` times one `metal_witgen` call (the production path) with an idle queue before it:
"kernels" = encode of the two par_stepExecW launches -> wait done (with timing on, the snapshot copy is
waited for before), "call" = the whole `metal_witgen` (preflight upload, table/fault fills, inject, snapshot,
kernels, wait). po2 20, M5 Max 40-core, shared GPU (other agents), base = the unmodified behaviour
(cycle order, snapshot; the same code path as R13's binary):

| segment | kernels median (q1, min) | call median (q1, min) |
|---|---|---|
| rv32im-torture seg0 (R8) | 15-32 ms (q1 15-24, min 10.0-14.5) | 22-106 ms (min 16-36) |
| sha256-chain seg0 (R11) | 19-44 ms (q1 20-25, min 15-18) | 27-112 ms (min 21-54) |
| memory-merkle seg0 (R11) | 16-35 ms (min 14-16) | 48-72 ms (min 22-31) |
| ecdsa-verify seg0 (R12-adv) | 14-37 ms (q1 12-14, min 10.4-13.9) | 23-113 ms (min 17-29) |

- The witgen kernels are 10-35 ms, not the 60-100 ms the brief quotes for "witgen" (that includes the host
  side of `WitnessGenerator::new`: scatter, allocation, zeroize).
- The snapshot (an 885 MB `eltwise_copy_elem` plus its allocation) is most of the gap between call and kernels.
- stepAccumA + scans + finalize (`r15w_accum_ab`, step from an idle queue): 10.5-11.5 ms on a quiet GPU
  (sha seg0 and torture seg0, min 10.3-10.8), 13-18 ms medians when contended; R13 had stepAccumA at 5-9 ms of it.
- Noise: the GPU was shared throughout (CPU load 3-80; GPU contention is not visible in the load). Per-pair
  A'−A differences span p10/p90 −29/+35 ms for the witgen kernels, so single pairs mean little; the claims
  below rest on the median of per-pair differences over 100-230 pairs, the sign count, and the q1/min
  (uncontended) values, all of which agree.

## Changes and A/B
All interleaved within one process (`R15W_VARIANTS="base;...;base"`, the second `base` is A'), except the
inline and atomics A/Bs, which alternate processes (A B A B ...) because they need another metallib.

### 1. Major-sorted first launch (kept, default window 14)
HIP's par_stepExec runs its first launch (cycles before the table split) grouped by major within
2^win-row windows (`RISC0_HIP_WITGEN_SORT`, `wmsSort`), so a SIMD group mostly runs one arm of step_Top's
mux. Metal now does the same: `witgen_sort_perm` builds the permutation on the host from the pristine
preflight cycles (accum's per-window counting sort, `build_perm_by`; the same order as `wmsSort`'s stable
(window, key) ranking) before anything is encoded, and binds it as the kernel's `perm` (`usePerm = 1`,
the path R17's `LaunchOrder::Sorted` test hook already used). Same witness: each cycle still runs once and
writes only its own row; table counts are commutative atomic adds.

Per-pair kernel differences vs base, all po2 20 sessions pooled (prof2-prof6, 4 segments):

| variant | faster in | kernels B−A median | call B−A median |
|---|---|---|---|
| A' (base again) | 119 / 229 | −0.15 ms | +1.24 ms |
| sort=14 | **165 / 229** | **−5.47 ms** | −4.61 ms |
| sort=12 | 133 / 196 | −5.87 ms | −3.04 ms |
| sort=11 | 102 / 140 | −5.85 ms | −2.11 ms |
| sort=16 | 27 / 33 | −4.67 ms | −2.29 ms |
| sort=14, minor key | 83 / 122 | −5.62 ms | −4.06 ms |
| sort=14, tg 128 | 88 / 133 | −5.91 ms | −4.59 ms |

- Per segment (prof6, 21 pairs, q1 / min): torture 22.6/12.9 -> 15.1/9.3 ms; sha 21.0/15.4 -> 16.0/10.5;
  ecdsa 12.1/10.6 -> 9.1/7.6. memory-merkle gains least (prof4/prof5: within noise; its mix is dominated
  by a few majors already).
- Windows 11-16 are equal within the noise; 14 is HIP's gfx11 default and the accum window, so it stays.
  The minor key (HIP `RISC0_HIP_WITGEN_MINOR`) adds nothing here.
- Cost: the host sort of ~1M cycles (rayon counting sort, included in "call") and a 4 MB perm buffer from
  the pool per call.
- By the per-pair range rule (A'−A spans ±30 ms) this is within the spread; by the median shift (−5.5 vs
  −0.15 ms), the sign count (binomial z ≈ 6.6) and every q1/min it is a real ~25-35 % kernel reduction. The
  quiet-machine final baseline should confirm the size.
- **R17 note:** the sorted order is the R17 amplifier: the `--map-lowering loop` baseline fails 5/5 calls
  (4384 rows) with `RISC0_METAL_WITGEN_SORT=14` alone. With the guards in place (IR scans, loop scan,
  linked-metallib check) that is a sensitivity, not a defect; it also means production now runs the
  order in which a future regression of the defect shape would show up fastest.

### 2. Single-buffer witgen (kept, default on)
- **Why it is bit-exact.** With `pre_data == data`, a back load (back > 0) of row r−k may run before or after
  row r−k's own thread writes it. Snapshot mode reads the injected value v0 (or 0), the sequential CPU
  witgen reads the final value v1, and the two give identical witnesses on every segment tested (R8-R17
  and here), so the output is the same function of v0 and of v1; single-buffer reads one of the two. This
  holds as long as a thread writes each data cell at most once (no intermediate value), which the generated
  step functions do (NondetReg/STORE write once). HIP's ffi.cu makes the same argument for its sorted
  launch; CUDA's default is single-buffer.
- **Gate** (R17 methodology, one session 22:22-22:36 MST, load 4-26; `gate/summary.txt`):

  | test | baseline (`libs/base_O2`: `--map-lowering loop` + shared fp/fpext, the R17 defect shape) | this branch (embedded metallib) |
  |---|---|---|
  | single-buffer, sorted amplifier (`RISC0_METAL_WITGEN_PERM=sorted`), 40 calls each: torture20 seg0, sha seg0, merkle seg0, torture seg7, ecdsa seg170 (po2 18) | 5/5 bad (torture20, 640 rows) | **0/200** |
  | single-buffer, production order (`RISC0_METAL_WITGEN_SORT=14`), 40 each, same 5 segments | 5/5 bad (sha, 4384 rows) | **0/200** |
  | single-buffer, cycle order, 40 each, same 5 segments | — | **0/200** |
  | snapshot + sort 14, 20 each: torture20 seg0, sha seg0 | — | **0/40** |
  | `witgen_sorted_amplifier` (in the suite, default tune) | — | passes |
  | `witgen_tune_matches_cpu` (8 combinations incl. single+sort, snapshot+sort, single+cycle order, tg 32/64) | — | passes |

- **Speed.** The snapshot copy is gone: call time −7.6 ms median per pair (single alone), −15.0 ms with sort
  (89 pairs; e.g. torture q1 call 43 -> 20 ms, sha 50 -> 20 ms in prof4). The kernels alone are slightly
  slower in single-buffer mode (+4.5 ms median, 34/89 faster) — back loads now read the rows being
  written instead of a cold copy — but the call is faster in every segment.
- **Memory** (`witgen_matches_cpu_large`, `+` = growth of the HAL's allocation during `WitnessGenerator::new`):

  | po2 | snapshot | single | saved |
  |---|---|---|---|

  | 21 | +3748 MB | +1978 MB | 1770 MB |

  Same at the 4 GB and 8 GB budgets (at 4 GB, po2 21 with the snapshot only fit after the pool drained).

### 4. accum always_inline vs noinline (always stays)
Variant metallibs from `accum_tu_gen.py --inline always|noinline` (scratch `mk_accum.sh`; `acc_always`'s
`accum_tu.metal` is byte-identical to the build's, md5 a61fec95...), alternating processes, 7 pairs × 5 runs,
sha seg0 po2 20, quiet GPU (load 6-9):
- always: per-process step medians 11.21-12.02 ms (one 18.39), mins 10.88-11.31;
- noinline: 12.26-12.76 ms (two contended 17.0/24.0), mins 12.20-12.54;
- noinline slower in 6/7 pairs, by ~1.2 ms (~10 %). Cold PSO of the noinline library: 105 s. Kept as is.

### 5. tableU16 atomic cost (no change)
Scratch variant `libs/noatomic` (tables.h's `atomic_fetch_add` replaced by a racy plain increment: wrong
counts, measurement only), alternating processes with `acc_always`, 6 pairs × 5 runs, sha seg0 and ecdsa
seg0, base and sort=14 (`logs/atomic.txt`): mins and medians overlap completely (sha base mins 15.2-34.6 vs
15.5-36.7 ms). The 65536-counter atomics are not a measurable cost, also with the sorted order (where
neighbouring threads hit the same counters more). Privatizing them is not worth it.

### 6. wmsSort and the accum perm
- `wmsSort` (HIP ffi.cu) builds both permutations in one LDS kernel. A Metal port needs a kernel in
  `misc.metal` and `build.rs`/`METAL_KERNEL_NAMES` changes, which R15w does not own. Its witgen half is
  done on the host instead (section 1), at ~0.5 ms of CPU per segment, overlapping nothing on the GPU.
- The accum half (reuse the witgen-time permutation in accum, HIP `wmsAccum`) would save accum's
  `build_perm` (0.35-0.51 ms, R13) and the wait before it. In the prover the queue is already idle at that
  point (the data commit ends with a sync), so the saving is the 0.5 ms of host sort: far below the noise.
  Not done; open issue for whoever owns misc.metal if a GPU sort is ever wanted.

## Budgets (PLAN 9.1)
`prove_po2_sweep` (`R11_PO2S=18,19,20 R11_CPU=0`), default vs `RISC0_METAL_WITGEN_SINGLE_BUFFER=0`:
- 4 GB: largest po2 18 in both (po2 19/20 fail at eval_check's `evaluated` allocation); witgen-phase peak
  at po2 18: 259 vs 470 MiB.
- 8 GB: largest po2 19 in both (po2 20 fails at `evaluated`); witgen-phase peak at po2 19: 2817 vs 3239 MiB.
- Whole po2 20 prove (`prove_segment_measure`, no budget, 2 × 2 processes): GPU peak 9343 MB in both.
So single-buffer lowers the witgen phase's peak and never raises any peak, but it does not move the
largest po2 that fits a budget: the data commit and eval_check set that.

## Knobs (all read once per process)
- `RISC0_METAL_WITGEN_SORT=<win>` (default 14; 0 = cycle order), `RISC0_METAL_WITGEN_SORT_MINOR=1`.
- `RISC0_METAL_WITGEN_SINGLE_BUFFER=0|1` (default 1; 0 = R8's snapshot).
- `RISC0_METAL_WITGEN_TG=<n>`, `RISC0_METAL_ACCUM_TG=<n>` (default 0 = runtime's min(256, PSO max)).
- `RISC0_METAL_WITGEN_SORT=0 RISC0_METAL_WITGEN_SINGLE_BUFFER=0` is exactly the R13/R17 behaviour.
- Measurement tests: `r15w_witgen_ab` (`R15W_SEGMENTS`, `R15W_VARIANTS`, `R15W_PAIRS`), `r15w_accum_ab`
