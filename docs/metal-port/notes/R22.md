## Summary
- **(a) Regime guard (insurance, default on, no speed change).** The evalfast split kernel's speed has two
  compiler regimes (R18/R21: ~2.4x apart) that show in the native per-thread stack size. Three checks now
  read that field:
  - build time: `rv32im-sys/build.rs` (R22 block) translates `ef_eval_split` (and `ef_eval_split_fc` for
    po2 20 when the build compiled its `.air`) with `metal-tt` through `tools/metal_audit/agx_size.py` and
    warns loudly when the stack exceeds 24 KB (`RISC0_METAL_EF_STACK_GUARD=warn|fail|0`);
  - run time: at library load a background thread reads the stack of the OS driver's compile of
    `ef_eval_split` from the binary archive the process already wrote (~5 ms), logs it, and if it is slow
    warns and tries fallbacks (the nested chain, then R15e's form) through archives of their own, using the
    first one in the fast regime; each domain-specialized PSO is checked when built and refused while the
    plain kernel is fast (`RISC0_METAL_RV32IM_EVAL_GUARD=1|warn|0|force`);
  - test time: `eval_regime_guard_kernels` fails when the plain / po2-20 specialized kernels (flat and
    nested) leave the fast regime, and checks that R15e's form still reads slow (calibration).
- **(b) Stack probe: the stack size is a symptom, not the cause; the call-nest depth is a lever.**
  - Padding the kernel frame with a cold private array (+1 to +16 KB, stack 19.0 -> 35.3 KB, same code)
    costs nothing measurable (< 1 % at po2 20; section 3.1). A slow-cluster-sized stack does not make the
    kernel slow, so "reduce the stack" is not a lever in itself.
  - Flattening the generated chain's 21-deep call nest (each chain function called by its root in turn
    instead of by its predecessor; arguments through a private array) cuts the stack to ~4 KB **and** the
    split kernel time by ~7 % (section 3.3). `[[clang::musttail]]` is ignored by the AGX back end (same
    native code), so the flattening is done in the generator.
  - **Change (default on): the flat chain** (`to_metal.py`, `EF_NEST_FORM` keeps the old text). Bit-exact
    (same arithmetic in the same order). Revert knob `RISC0_METAL_RV32IM_EVAL_FLAT=0` (the nested
    `ef_eval_split_nest` / `ef_eval_split_fc_nest`, native-identical to the pre-R22 kernels).
- Correctness: CPU == flat == flat specialized == nested == nested specialized == r15e == r12 == baseline
  at po2 4/10/12-extreme/16; 6/6 real po2 20 seals equal the CPU and verify; 0/30 repeat differences at po2
  20 (specialized and plain); defect control 10/10 failing; ir_scan A = B = C = S = 0 for all six evalfast
  TUs; suites 2x + 4/8 GiB pass.

## 2. Sub-track (a): the regime guard
### 2.1 Reading the field from runtime archives
The binary archives zkp `archive` writes (`~/Library/Caches/com.risczero.RISC-Zero.risc0/metal-archives/`) are
fat images with magic `0xCBFEBABE` (big-endian header as `0xCAFEBABE`): slice `0x01000017` is the AIR
metallib, slice `0x01000013` the native applegpu image. Its `__TEXT,__compute` section holds one nested
Mach-O object per pipeline; each object's `__GPU_LD_MD` section has the function name as a length-prefixed
string, and its first `__compute` section is the FlatBuffers metadata R21 decoded (root -> field 0 ->
field 14 = stack; an absent field is 0, e.g. `ef_combine`). The runtime numbers equal metal-tt's for every
kernel checked (table above), so the guard sees what the OS driver really compiled, for free: the archive
is written anyway.

### 2.2 What was built
| Piece | Behaviour | Knobs |
|---|---|---|

### 2.4 Cost
Runtime: one 23 MB file read on a background thread at load (4.8 ms), one 11 MB read per specialized PSO
build. Build: +18-28 s per metallib change (cached per digest; `=0` skips). A phase A/B of the guard alone
(A = baseline, B = guard, A2; 7 rounds, `ab/logs/g1_*`) was contended (A-vs-A spread +-400 ms) and shows
no change, as expected for a background read.

### 2.5 Caveat (from 3.1)
The stack field is a *correlate* of the slow regime, not its cause: a compile with a large but cold stack
would be a false positive. In all 84 R18/R19 variants and every kernel here, large stack and slow time
coincide; only the artificial padding probe separates them. A false positive costs at most the fallback
build in the background and (for a specialized PSO) R20's 4 %; `warn` mode removes even that.

## 3. Sub-track (b): stack probe
Go/no-go (R21 P2): measure time against stack near 19 KB. Variants built from the generated TU
(`stk/ef_stk.metal`) with `build_eval_variant.sh` (same flags as the build), timed in
`ef_variant_bench` (interleaved, odd rounds reversed, bit-exact asserted every run).

### 3.1 Cold stack padding (NO effect)
`EF_STKPAD=N`: a private `uint32_t[N]` in the kernel, written once before the chain and read once after at
run-time indices (the back end must keep it). Code size unchanged (+170 B), stack +4N:

| N | 0 | 256 | 512 | 1024 | 1536 | 2048 | 3072 | 4096 |
|---|---|---|---|---|---|---|---|---|
| stack (B) | 18,928 | 19,952 | 20,976 | 23,024 | 25,072 | 27,120 | 31,216 | 35,312 |
| po2 18 min ms (`stk18_1`, 9 rounds, load 20) | 162.6 | 164.5 | 163.3 | 163.5 | 163.6 | 164.9 | 163.5 | 165.0 |
| po2 20 min ms (`stk20_1`, 7 rounds, contended) | 677.6 | | | 685.9 | | 682.5 | | 679.5 |

A = builtin 161.8 / 682.3, A2 163.1 / 683.0. +16.4 KB of stack costs < 1 % (mins within A-vs-A).
**Verdict: stack size alone is not the regime's cause or a lever.** Only cold stack was added here; the
next test asks whether the *touched* stack spread (the nested frames) matters.

### 3.2 Tail calls (not available)
`[[clang::musttail]]` needs identical signatures, so a variant passed the chain's Fp arguments through a
private array (`targs`) with every link `(cycle, steps, ctx)`. With and without `musttail` the AGX native code
is byte-identical (2,406,978 B, stack 19,120): the back end does no tail-call elimination.

### 3.3 Flat chain (WIN)
`mkflat.py`: the links return instead of calling the next; `poly_fp` (v2_19 ... v2_3) and `rk_accblk`
(v2_2 ... v2_0) call them in turn, arguments through `targs`. Stack 4,016 B.

Gated sessions at po2 20 (`flat20_2`, `flat20_4`; rounds where A-vs-A2 < 1.5 %):

| | A (nested plain) | targs (nested, array ABI) | flat plain | R20 fc (nested) | flat fc | A2 |
|---|---|---|---|---|---|---|
| `flat20_2` clean rounds 0/2/4 | 646-654 | 675-691 (+4 %) | 599-633 (-7 %) | | | 652-655 |
| `flat20_4` clean rounds 0/1/2/6 | 658-662 | | 606-617 | 613-628 | **568-579 (-7 % vs fc)** | 652-660 |

The argument array costs ~+4 % on its own (targs), and removing the nest gains ~-11 % on top: the hot,
spread-out stack of 21 live frames (the touched working set per thread, not the allocation) is what costs.
